# V19.3：上下文与提示词

本文给出[V19.3](V19.3.md)的生成与反思接口。生成利用全局经验改进算法；反思在评价后从演化轨迹提炼经验。两个角色共用任务说明与函数接口。

## 1. 反思借鉴与轨迹适配

ReEvo通过明确的代码优劣对比提炼简短建议，再结合新认识整合长期经验；RefineEvo将经验表示为改进摘要、具体建议与适用条件。V19.3沿用比较式反思与情境化经验，将反思输入组织为多步形成轨迹及相关旁支。

反思以本次新评价为依据，结合历史分析三个问题：各次父子变化对应了怎样的适应度与执行结果；连续修改怎样共同发展算法策略；后续结果怎样限定已有建议并形成更新的认识。形成的经验在所有候选算法之间共享。

## 2. 上下文组织

### 2.1 全局经验

正负经验在同一任务的一次搜索中全局共享，使用同一结构：`summary`、`recommendations`、`applicable_when`。系统关联实际来源轨迹。经验以三项内容建立BM25索引，查询取当前及近期版本的`design`，分别从两个池取至多三条相关经验。零匹配不展示，同分随机；索引兼容英文和中文词项。

内容完全相同的经验合并来源，提示内去重展示。全局检索允许算法读取自身分支及其他分支形成的经验。生成时实际提供的经验随尝试保留，评价后直接作为反思背景；有关既往迁移的记录提供当时建议的内容。

经验效用沿用RefineEvo源码的计分规则：新条目初始分数0，以本尝试最后一个实际已评价版本判定，有效且改善所选父代时给实际提供过的条目加1，否则减1；分数小于0的条目移出检索池。只有实际获得算法评价时更新此分数，一次尝试仅更新一次。经过打包而未展示的经验不评分。效用与正负类别分别维护，各反思范围对照共用这项规则。

经验在提示中呈现为：

~~~text
[Positive Design Experience]
Summary: ...
Advice: ...
Applies when: ...

[Negative Design Experience]
Summary: ...
Advice: ...
Applies when: ...
~~~

### 2.2 演化轨迹

主链默认最近三次演化尝试；反思时包含刚完成的尝试。每次尝试分别保留生成、评价与修复阶段，同一父代最近两次其他已完成尝试作为旁支。

记录按真实父子关系呈现，给出版本代码或完整差分。每次尝试先列所选父代的有效适应度，再按生成、修复顺序列出各版本的执行状态、有效适应度与增益。适应度增益为`parent_fitness - child_fitness`，同时标明改进、持平或退步；运行失败与超时版本的适应度为`unavailable`。修复差分以失败代码为起点，修复后的适应度明确相对于本次所选的有效父代。

当前完整代码给出全文，历史中的同一版本在提示内共享。代码使用python围栏，差分使用diff围栏。超时历史仅标`timed out`，实际时限按[实验约定](../../experiments/PROTOCOL.md)用于超时修复。

历史与经验默认共用8192 tokens，当前完整代码另行保留。打包优先保留本次评价结果、相关经验和最近主链修改，再补充旁支。比较完整diff与尚需提供的版本所占token，选择较短表示。放不下的修改保留结果摘要，并标明`Evaluation only; code change unavailable`。计数使用生成模型对应的tokenizer。

完整输入另检查模型窗口，并预留角色输出、schema与协议空间。当前完整代码放不下时记录上下文失败。初始化顺序进行，实际展示的初始设计及结果编号随调用保存。反思对照只改变可见范围：`local`为本次尝试，`siblings`增加同父代旁支，`trajectory`再加入近期主链。

### 2.3 两个角色的输入

| 角色 | 输入 | 输出及用途 |
| --- | --- | --- |
| Generator | 任务、函数接口、当前算法、近期演化记录、全局正负经验 | 完整候选及其设计说明，进入评价 |
| Reflector | 任务、函数接口、已评价的多步轨迹、相关旁支、生成时提供的经验 | 新的正负经验，加入全局池 |

生成中的当前代码放在经验之后、生成指令之前。反思中的最新已评价代码与其结果明确对应。来源算法编号与轨迹编号用于关联资料，经验正文以可被其他算法理解的策略和条件表达。

### Generator output

~~~text
Return only one JSON object with three string fields, in this order:
- "code": The complete Python implementation of the required function, including
  imports and helper functions.
- "analysis": {analysis_requirement}
- "design": A brief, self-contained description of the resulting algorithm's
  representation and decision rule (2-3 sentences).
~~~

各入口使用对应的analysis要求：

| 入口 | analysis_requirement |
| --- | --- |
| Generator | The actual differences between your code and the code under Current Algorithm, and their rationale (2-3 sentences). |
| Initialization | The chosen solution strategy and why it suits the task (2-3 sentences). |
| Format repair | A brief explanation of the algorithm implemented in the recovered code (2-3 sentences). |
| Program repair | The implemented correction relative to the failed version (2-3 sentences). |

### Reflector output

~~~text
Return only one JSON object with two arrays:
- "positive": Lessons supported by observed gains in solution quality or computational
  feasibility. Identify feasibility-only gains explicitly.
- "negative": Lessons supported by observed regressions, failures or ineffective
  computations.
Each lesson has three fields:
- "summary": The new or revised finding supported by the latest evaluated attempt
  and its algorithmic context.
- "recommendations": Concrete algorithm-design advice motivated by that finding.
- "applicable_when": The algorithmic setting and conditions for using the advice.
Prioritize lessons about how successive changes interact. Give each distinct lesson
once, and return up to three lessons in total. Write recommendations as a list of
short sentences. Either array may be empty.
Express reusable strategies and conditions. Omit source identifiers and incidental
tuned constants from the lessons.
~~~

~~~text
{task_description}

[Required Function]
{function_template}
~~~

~~~text
{provided_experience_block}

{evaluated_trajectory_block}

{alternative_variants_block}

{output_contract}
~~~


### Error instruction

~~~text
Correct the computation or data handling responsible for the reported failure,
preserving the intended algorithm.
~~~

### Timeout instruction

~~~text
Make the algorithm meet the reported time limit while preserving its core decision
strategy. Remove redundant work, reuse intermediate results, or simplify expensive
search and evaluation.
~~~

## 5. 调用时序与经验保存

一次演化尝试先检索经验并生成候选，完成评价与至多一次共享修复，再对已观察的轨迹反思。生成默认输出上限16384 tokens，反思默认2048 tokens；实际请求、用量与评价分别计数。

反思返回的有效条目按类别加入全局池，并关联实际呈现的轨迹。初始算法提供演化起点；具有实际代码与评价反馈的演化尝试提供经验学习材料。经验提取失败时，已有算法及结果继续保留。

有效经验按回复中的顺序最多保留三条，原始条数、超量与无效条目均保存。实现中的输出要求为版本内常量，分别绑定角色schema与输出上限。

## 6. 轨迹经验示例

以下为构造示例。假设全候选前瞻超时，筛选候选后可以运行但适应度仍差于初始算法，随后让前瞻估计参与最终选择才获得改进。轨迹反思可同时形成：

~~~json
{
  "positive": [
    {
      "summary": "Screening made lookahead feasible; fitness improved after its estimate informed the final choice.",
      "recommendations": ["Bound the cost of lookahead and align its estimate with the selection criterion."],
      "applicable_when": "A constructive heuristic introduces lookahead whose cost or decision role is not yet well controlled."
    }
  ],
  "negative": [
    {
      "summary": "Computing lookahead without using its estimate did not improve the selection rule.",
      "recommendations": ["Ensure an added estimate supplies useful information to the decision rule."],
      "applicable_when": "An expensive auxiliary estimate is calculated alongside an unchanged selection criterion."
    }
  ]
}
~~~

其他算法可以从同一全局池检索这些经验。已有前瞻估计的算法可据此调整估计的决策作用；尚无前瞻的算法可借鉴可承受的实现方式。新的评价结果再进入轨迹反思，形成更多具有适用背景的经验。
