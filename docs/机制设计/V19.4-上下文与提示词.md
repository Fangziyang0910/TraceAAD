# V19.4：演化上下文、两级反思与提示

本文给出[V19.4设计](V19.4.md)中四个模型角色的输入、指令与输出。起点选择并排读取候选的局部轨迹，决定从哪里开发；生成模型以轨迹与经验为参考，判断改进方向并提出更好的算法思想；短期反思解释最新尝试在局部演化中的意义；长期反思把一批短期反思及其结果合并为全局正负经验。

## 1. 输入与比较关系

所有角色使用同一份任务说明和函数接口。起点选择、开发与两级反思均提供`Fitness to minimize: {score_definition}`。实例数量、数据规模、划分、种子和评价器内部设置按[实验条件](../../experiments/PROTOCOL.md)处理。普通演化记录只呈现超时状态，实际时限仅用于超时修复反馈。

### 1.0 起点选择视图

每次开发前，从有效且源码不同的节点中按\(1/(\text{rank}+1)\)不放回抽取四个候选，顺序随机。每个候选依次包含：

| 内容 | 范围与用途 |
| --- | --- |
| Program / fitness / Design | 候选编号、有效适应度与算法描述 |
| How it was formed | 沿候选的实际形成路径回溯最近三次尝试，与生成视图的Recent Evolution格式相同，含各尝试的短期反思；初始根写作“An initial design.” |
| Attempts made from it so far | 此前从候选出发的已评价尝试数，以及最近两次尝试，格式同上 |

不呈现代码，也不单独给出全局最好适应度。只有一个有效节点时不进行选择调用。

### 1.1 生成视图

当前节点为\(p\)。输入依次包含：

| 内容 | 范围与用途 |
| --- | --- |
| Task / Required Function | 任务、接口和成绩含义 |
| Recent Evolution | 沿\(p\)的实际形成路径回溯最近三次尝试，按演化顺序呈现各版本的算法描述、修改说明与结果 |
| Previous Attempts from the Current Algorithm | 此前从\(p\)出发的最近两次已评价尝试，按发生顺序以同样形式呈现 |
| Positive / Negative Design Experience | 从全局双池检索的相关提示，每条一行 |
| Current Algorithm | \(p\)的完整代码、独立算法描述及有效适应度 |

只有当前算法提供代码。形成路径以首次有效源码的生成关系为准。修复中间版本留在所属尝试内部，不另外占一个主链步骤。根节点没有形成尝试时，省略该块。

### 1.2 短期反思视图

最新尝试从有效父代\(p\)产生候选\(c\)。输入依次包含：

| 内容 | 范围与用途 |
| --- | --- |
| Task / Required Function | 与生成相同的任务、接口和成绩含义 |
| Recent Evolution | \(p\)此前两次形成尝试的算法描述、生成分析与结果；与单独呈现的最新尝试共同构成至多三步主链 |
| Other Attempts from the Same Parent | 最新尝试以外，从\(p\)出发的最近两次其他已评价尝试，形式同上 |
| Latest Evaluated Attempt | 所选父代的算法描述，以及本次所有已评价版本的描述、分析与结果 |

短期反思不读取代码和全局经验。它发生在本次评价与可用修复结束之后：至少一个版本运行失败，或产生了新的有效源码时触发，包括与父代同分的新源码。重复源码、未产生实际评价的尝试和初始化不触发。

### 1.3 长期反思视图

新的短期反思累积到十条时，长期反思在当前尝试结束前进行。输入依次包含：

| 内容 | 范围与用途 |
| --- | --- |
| Task / Required Function | 与生成相同的任务、接口和成绩含义 |
| Recent Reflections | 最近三十条短期反思（`long_term_window`），各附所依据尝试的结果 |

长期反思不读取上一版经验池和当前最好算法，理由见[设计](V19.4.md)§4.3。每条反思的格式为：

```text
Attempt {attempt_id}: selected parent fitness={parent_fitness}; result fitness={fitness}|timed out|program error; best fitness before this attempt={best_before}.
Design: {design}
Reflection: {reflection}
```

结果取该尝试最后一个已评价版本。

### 1.4 版本与反馈格式

每个尝试显示以下关系与结果：

```text
Attempt {attempt_id}. Selected parent: P{parent_id}; fitness={parent_fitness}.
| Version | Phase | Edited from | Execution | Fitness | Gain vs selected parent |
| ...     | ...   | ...         | ...       | ...     | ...                     |
P{version_id} analysis: {analysis}
P{version_id} design: {design}
```

已有短期反思的尝试，在末尾另加一行`Attempt {attempt_id} reflection: {reflection}`；生成与短期反思中的轨迹都这样呈现。短期反思的最新尝试前另加一行`Selected parent P{parent_id} design: {design}`。`Gain`由系统计算为\(f(p)-f(c)\)。运行失败与超时的`Fitness`和`Gain`均为`unavailable`；运行错误另显示`P{version_id} failure type: {exception}`。

## 2. 起点选择

```text
{task_description}

[Required Function]
{function_template}

Fitness to minimize: {score_definition}

[Candidate Programs]
{candidate_programs}

[Instruction]
Choose the program whose further development is most promising for this task.
Judge each program by its local trajectory: its current state, the trend of
its recent changes, and the potential it still leaves. The first
implementations of a new idea often perform worse than an algorithm that has
been refined over many attempts.

Return only one JSON object with two fields, in this order:
- "assessment": A short comparison of the candidates.
- "choice": The number of the chosen program, for example 12 for P12.
```

模型先写简短比较，再给出编号。编号必须是候选之一；调用失败、无法解析或编号不在候选中时，使用提出候选时预先均匀抽定的节点。

## 3. 算法生成

模板为：

```text
{task_description}

[Required Function]
{function_template}

Fitness to minimize: {score_definition}

[Recent Evolution]
{formation_trajectory}

[Previous Attempts from the Current Algorithm]
{previous_attempts}

[Positive Design Experience]
{positive_experience}

[Negative Design Experience]
{negative_experience}

[Current Algorithm]
{current_algorithm}

[Instruction]
Use the evolution history and design experience as reference. The design
experience records tentative impressions from earlier attempts, not
established facts. Analyze possible directions for improving the current
algorithm, such as further refining its idea or combining it with other
algorithmic ideas. Then propose a better algorithm idea and implement it.

Return only one JSON object with three string fields, in this order:
- "code": The complete Python implementation of the required function,
  including imports and helper functions, without comments or docstrings.
- "analysis": State the chosen improvement direction and the resulting algorithm idea in 2-3 sentences.
- "design": Describe the resulting algorithm's representation and decision
  rule in 2-3 self-contained sentences.
```

空材料块连同标题省略。轨迹与经验是设计参考：指令要求模型先分析改进方向，例如继续精炼当前思想或融合其他算法思想，再提出更好的算法思想并实现。`analysis`写所选方向与新的算法思想；`design`独立描述新算法，供后续检索和理解使用。历史版本以这两项和评价结果呈现。

## 4. 两级反思

### 4.1 短期反思

短期反思读取真实跨代演化和同起点替代的文字记录，问最新尝试试了什么思想、怎样实现、以后怎样能实现得更好，输出一两句暂定的提示。提示保存在该尝试上，来源与版本关系由程序侧关联。

```text
{task_description}

[Required Function]
{function_template}

Fitness to minimize: {score_definition}

[Recent Evolution]
{preceding_evolution}

[Other Attempts from the Same Parent]
{other_attempts}

[Latest Evaluated Attempt]
{latest_attempt}

[Instruction]
Reflect on the algorithmic idea that the latest attempt tried and on how it
was realized, in the context of the preceding evolution and the other attempts
from the same parent. A worse result may come from an immature implementation
rather than a poor idea. Give a short, tentative hint about how this idea, or
a related idea, could be realized better in later designs, at the level of
algorithmic ideas rather than code details.

Return only one JSON object with one string field:
- "reflection": The hint in one or two short sentences.
```

### 4.2 长期反思

长期反思沿用正负双池与适用条件的组织方式。它从近期短期反思及其实际结果重新形成完整的经验池。正经验是看起来有希望的思想，负经验是实现思想时遇到的陷阱。

```text
{task_description}

[Required Function]
{function_template}

Fitness to minimize: {score_definition}

[Recent Reflections]
{recent_reflections}

[Instruction]
Form the global design experience for this task from the recent reflections
and their outcomes. The experience is a tentative, meta-level understanding
that gives hints for later designs; it is not established knowledge. Each
experience is a brief, high-level hint about an algorithmic idea, at the level
of representation, decision rule, or search strategy rather than code details
or tuned constants.

The first implementations of a new idea often perform worse than an algorithm
that has been refined over many attempts. A few poor results therefore do not
show that an idea is unpromising; they show how those attempts went wrong.

Return only one JSON object with two arrays:
- "positive": Ideas that appear promising, including ideas that are not yet
  well realized.
- "negative": Pitfalls seen when realizing an idea: what went wrong, and
  how a later design might avoid it while still pursuing the idea. A kind of
  change that showed no effect is also a pitfall.

Each experience has two fields:
- "summary": The hint in one short sentence.
- "applicable_when": The algorithmic conditions under which the hint is
  relevant, stated briefly.

Keep each array concise.
```

提示停留在表示、决策规则与搜索策略层面，例如“在昂贵的前瞻之前缩小候选集看起来有希望”。策略本身的名称正常保留，例如2-opt；局部调参值和公式不写入。

## 5. 全局经验的检索与呈现

经验查询按以下步骤构造：

1. 当前算法的`design`在前。
2. 最近三次形成尝试按演化顺序加入各代码版本的`design`。
3. 对规范化空白后的相同描述去重，以换行连接；缺失描述跳过。

BM25文档拼接`summary`与`applicable_when`。英文标识符与数字按小写词项分词，中文按汉字及相邻双字词分词；沿用V19.3的`knowledge.tokens`。两池使用合并语料的IDF与平均文档长度，\(k_1=1.5,b=0.75\)，再分别取得分大于0的前至多三条。同分优先较新经验。空查询或无匹配时返回空集。

生成中，每条经验一行：

```text
- {summary} Applies when: {applicable_when}
```

检索发生在父代选中之后，只检索当前版本的经验池。最终加入生成提示的条目原文与编号一并保留。

长期反思的回复中，字段恰为`summary`、`applicable_when`且均为非空字符串的条目进入新版本；其他条目单独保存，不入池。读取顺序固定为`positive`再`negative`，各数组保持原顺序；同一回复中按“极性加两个内容字段”的规范化JSON键去重。新版本中的条目都获得新编号，旧版本条目和使用记录保留供分析。用于同分排序的“较新”按编号定义。

## 6. 上下文长度

历史与经验均为文本，代码只来自生成的当前算法或修复对象。方法不设材料上限、装入顺序或窗口检查。所有角色的输出上限为16384 tokens；输入长度由模型服务约束，约24K tokens。实际呈现的尝试、经验与代码版本随请求保存。

## 7. 初始化与修复

### 7.1 初始化

输入为任务、接口、成绩含义，以及已完成初始设计的描述和实际结果。调用方提供任务模板示例时，也将该示例标为未评价的初始化上下文；主实验沿用与V19.3相同的任务模板。指令为：

```text
Design an effective algorithm for the task.
```

使用生成输出契约，其中`analysis`改为：

```text
Explain the chosen solution strategy and why it suits the task in 2-3 sentences.
```

初始化计五次基础尝试，修复属于该次尝试；没有有效节点时继续初始化。初始化不产生相对父代的改进标签。

### 7.2 格式修复

输入为任务、接口、原始回复和解析反馈。指令为：

```text
Recover a complete implementation consistent with the original algorithm,
and correct the JSON syntax and string escaping.
```

输出契约中`analysis`改为：

```text
Briefly explain the algorithm implemented in the recovered code in 2-3 sentences.
```

### 7.3 程序修复

输入为任务、接口、失败算法描述、实际失败代码及反馈。运行错误指令为：

```text
Correct the computation or data handling responsible for the reported failure,
preserving the intended algorithm.
```

超时反馈可以提供该次实际时限与耗时，指令为：

```text
Make the algorithm meet the reported time limit while preserving its core
decision strategy. Remove redundant work, reuse intermediate results, or
simplify expensive search and evaluation.
```

输出契约中`analysis`改为：

```text
Describe the implemented correction relative to the failed version in 2-3 sentences.
```

每次尝试共享至多一次修复机会。格式修复使用后不再安排程序修复；已评价失败后的修复需要剩余评价预算。修复描述针对失败版本。

## 8. 输出接口与模型调用

生成、初始化和两类修复均使用严格JSON对象，必需字段恰为`code`、`analysis`、`design`，值为非空字符串。起点选择必需字段恰为`assessment`（字符串）和`choice`（整数，候选编号）。短期反思必需字段恰为`reflection`，值为非空字符串。长期反思必需字段恰为`positive`、`negative`，值为数组；每项必需字段恰为`summary`、`applicable_when`，值为非空字符串；禁止额外字段。

请求使用后端支持的严格JSON schema，同时验证返回内容。反思格式不合格时保留原始回复与状态，不发起修复或虚构经验。短期反思失败时该尝试没有提示；长期反思失败时经验池不变，下一次短期反思后重新触发长期反思。空数组是有效的长期反思结果。

一次起点选择请求确定父代，一次开发请求产生候选，实际评价立即形成响应记录。完成该尝试后，至多一次短期反思请求和一次长期反思请求。各角色的输入及输出分别保存。调用恢复依据已完成阶段进行，已获得的评价与反思不重复执行。
