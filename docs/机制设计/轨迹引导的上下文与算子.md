# 轨迹引导的上下文与算子

日期：2026-11-03，北京时间。本文给出 EvoTrace 生成侧的多视角修订规格；与[轨迹反思与经验学习](轨迹反思与经验学习.md)配套。本轮已按[提示词全面检查](../记录/2026-11-03-上下文与算子提示词全面检查.md)更新英文提示与卡片；经验直接取融合排名前3条。规则已在[V20](V20.md)中实现，指令与卡片以[context.py](../../traceaad_v20/context.py)为准。

## 机制概述

EvoTrace 将父代的局部演化轨迹与累积经验加入生成上下文。LLM 沿祖先路径分析已有设计的演化，比较同一父代上不同修改的效果，再借鉴相关经验提出下一步方案。祖先路径保留连续改进的联系，直接子代呈现不同修改方向的反馈；两者使生成同时考虑当前设计的形成过程与已有尝试。已选算子规定本次修改的方向，模型输出简短分析、算法设计与完整代码。

轨迹的作用是提示尚可发展的方向。成功实现可以继续改进，失败实现可以调整，已有经验也可以重新解释。我们希望模型利用历史形成新方案，同时保留改变已有结构和重新实现某种思想的空间。

## 0. 沿用 Base 的公共模板

任务说明、函数模板与生成输出协议直接沿用 [Base 的 COMMON_TEMPLATE](../../traceaad_base/prompts.py:8)。`task_description`、`function_template`、成绩含义、接口与任务约束保持原样；上下文放入 `[Context]`，算子与历史使用要求放入 `[Instruction]`。没有重写任务说明，也不增加原任务未提供的评价设置。

生成仍返回严格 JSON 对象，且只有 `analysis`、`design`、`code` 三个必填字符串。沿用 Base 对分析、完整设计、完整实现和代码无注释／docstring 的要求，以及 JSON Schema 与格式修复流程。不再采用上一稿的 Markdown 三段与代码块输出协议。新的轨迹与经验使用要求写入 Instruction，输出字段与解析合同不变。

Init与Repair保留Base流程和三字段JSON。初始化不读取经验，修复不额外加入轨迹与经验。所有提示中的失败反馈均去敏，不展示内部时限、实例或评价设置。

| 项目 | 当前规则 |
| --- | --- |
| 任务与接口 | 原样复用 Base task_description、function_template 与成绩说明 |
| 历史视图 | 最多8祖先、3有效子代、2失败；近期连续性与不同修改方向共同选取 |
| 经验 | 状态、修改需求、实现三路召回；完整融合排名前3条直接展示，不足3条全部展示 |
| 融合参考 | 质量筛选后综合结构、语义与可用的成绩互补，短名单内均匀抽取一个，生成时分析计算接入 |
| 生成输出 | Base 的 analysis／design／code 三字符串 JSON |
| 成本 | 反思与嵌入成本单列；无生成前材料判别请求 |

## 1. 设计选择

### 1.1 当前代码与历史记录采用不同表示

当前父代提供完整代码、算法设计说明与成绩。模型需要据此理解实际计算，并实现本次修改。融合时，参考算法也提供设计与完整代码，以便理解可借鉴的计算机制。

历史默认以算法设计、修改说明、算子与评价结果呈现。完整档案保留全部直接子代；本轮模型视图从中选取有界记录，按产生顺序排列。相同字段使用固定名称，明确哪个程序相对哪个程序发生了什么变化。

这一取舍减少多份历史源码对生成的牵引，也节省上下文。代价是文字可能遗漏实现差异。因此，历史说明应描述实际修改，避免把生成器原先打算做什么直接写成已经做了什么。记录无法准确区分某项修改时，先保留这一未知，不据此归纳具体机制的成败。历史不附整份源码。每条记录可附最多两个完整变更语句块，补足文字不能交代的计算；片段选取与长度规则见第2.2节。

当前代码还用于辨认算法实际采用的状态表示和主要决策规则。已有 JSSP 案例中，模型看到了工序级父代完整代码，仍生成整项作业排列；另有被称作关键路径的计算并未控制邻域。因此，analysis说明本次改变的计算及理由；精炼时据此交代延续的机制，探索时说明决策差异，融合时说明接入点。design描述最终完整方法。这些计算交接在本次生成中完成，不增加独立材料判别请求。[代码与调用核对](../记录/2026-11-03-轨迹双机制调研-本地案例.md#s3完整当前代码仍不能保证接续开发保住有效表示)

### 1.2 保留好坏反馈，描述本次实现的结果

记录区分可运行且改善、可运行但持平、可运行但退步、执行失败与重复实现。改善与退步相对所选父代计算，不把“改进了父代”写成“超过了当前最好”。数值由评价器填写，模型给出的原因解释另列为文字。

一次开发尝试使用一个 `attempt_id`，其中生成版、修复版和各次评价分别编号。直接尝试按开发尝试列出，修复过程附在同一记录中；末个实际已评价版本确定最终父子比较，较早的报错与修复内容仍保留。执行失败不填数值增益。同分新源码仍是不同实现，相同源码从不同父代生成也仍是不同修改关系。事件编号同时绑定任务与独立运行，具体口径两侧共用。

生成的设计和修改说明原样保存为设计意图。评价后的联合反思另写短字符串 `review`，概括实际代码改变了什么、与设计说明有何差异；系统将它绑定已评价版本，存入旁表，不改变 Base 的 Program 字段。下一轮历史以 Reviewed change 将这段代码分析与原始评价一起展示；没有代码分析的记录以 Proposed change 标为生成器自述。review 是可复查的模型判断，原始代码仍留存，系统不把它升级为已自动验证的事实。即使不新增全局经验，本次局部说明也可写回。

低分子代仍留在轨迹中。它可能提示某种组合不合适、实现不充分，或需要继续精炼。单次执行失败也仍是实现反馈。提示使用“本次实现未改善”“执行失败”等措辞，保留模型重新构思的余地。

### 1.3 经验按相关性提供，不要求逐条执行

每条可见经验包含设计启发、适用条件、正面或负面观察，以及来源事件编号。生成器结合父代结构和算子目标选择性借鉴，可以不采用不相关经验。检索与修订规则见反思设计。

历史事件被经验引用后，仍是一份原始观察。重复出现的文字、多个摘要和经验修订次数均不增加成功次数。经验不使用“已证明最优”“必须保留”等措辞。

### 1.4 语义、结构与反馈分别表示什么

系统按源码版本建立多视角旁表，不改 Base 的 Program 和评价标量合同。

| 表示 | 确定内容 | 用途 |
| --- | --- | --- |
| 源码身份 | 不带位置属性的 AST dump；保留名称与常量，忽略排版与注释；解析失败仅规范化首尾空白 | 合并完全相同的实现，不宣称行为等价 |
| 结构特征 | AST 父子类型二元组、祖孙类型三元组及运算符类型的计数；计数取 log(1+n) 后 L2 归一化；名称、常量取值不入该特征 | 历史变化点、实现相似性召回；另存常量掩码后的 AST 以标记 constants-only |
| 语义向量 | design、review 与代码分开编码；代码以必需函数及顶层 helper 的完整函数为单元，保留标识符 | 找相近设计、修改方向与可借用计算，避免把生成自述等同于代码 |
| 静态线索 | 作用域内赋值、名称读取、直接调用、return 的源码位置；纯局部表达式的 def-use 边 | 在反思中定位计算；遇别名、容器修改、动态调用标 unknown，不判为无效计算 |
| 评价明细 | 原始标量、执行状态；若评价适配器提供可比逐实例成绩，则另存完整对齐数组 | 描述结果；可选地估计参考对父代的成绩互补 |

源码身份与结构相似分开。AST 形状相同、只改一个比较符或常量，也可能改变算法行为。静态线索只报告可定位事实：名称没有被读取，不等于赋值语句没有副作用；没有静态依赖路径，也不等于计算对结果没有影响。局部 def-use 遇控制流合并保留可能定义，涉及未知动态行为的函数不输出“未影响结果”的结论。

现有 server3 的 Qwen3 服务用于文字与代码嵌入，编码和缓存见反思第5节。代码函数超出编码窗口时整函数跳过并标缺失，不把任意截断的前缀当作完整实现。结构解析仍可使用。不同表示只回答各自的问题，既不硬凑一个“思想距离”，也不把高复杂度当改进目标。

## 2. 完整轨迹与本轮模型视图

演化轨迹的定义包含全部直接子代；保存范围不等于每次提示的展示范围。程序、尝试、修复和评价完整留档，预算模块读取原有完整记录；生成与反思读取有界视图。早期没有历史时，正常退化为任务、当前父代和已存在的经验，不补造历史，也不跨父代凑数。

### 2.1 有界窗口内保留连续性与覆盖

8／3／2继续作为展示上限，延续 Base 的输入量级；它们是候选配置，不是实验得到的最优数量。选取内容改为利用修改差异，不再直接继承“最好＋最近2”。所有选择只读本轮之前的档案。

**祖先，最多8条。** 沿真实 parent_id 路径回溯，排除当前父代与0号样例；缺失或成环时停止并记录。保留最近3条。其余位置从较远祖先中选变化点：对每个祖先相对它自己父代的结构距离、绝对成绩变化分别排序，以 RRF 合并后取前5条。同分优先较近者。某一路分数全部相同则不参加排序；两路都没有信息时取较近祖先。最终按路径顺序展示，并标出省略的中间节点数量；两个展示节点不能因此被误称为直接父子。

**有效直接子代，最多3条。** 先按相同父代、源码身份、评价条件与反馈分组，取最新记录代表；同分不同源码仍分别保留。第一个名额给成绩最好者，同分取最新。Refine 的第二个名额给其余最近者，第三个名额给最能补充已有修改方向者；Explore／Crossover 的后两个名额都用于补充方向。

补充方向使用最远优先（farthest-first）：对每个未选子代，分别计算它与已选集合的最小 review 向量距离、最小 AST 结构距离；两路各自从大到小排序，以 RRF 选一个，更新已选集合后再选下一个。缺 review 时用 design，缺向量时只用结构；两路均不可用或全同则选最近者。这里只增加窗口的信息覆盖，不排除相似实现，不判定它们属于同一思想。

**最终失败尝试，最多2条。** 同父代、源码、状态及去敏错误摘要完全相同的尝试合并展示。先按 error／timeout 与异常类型划类，各类取最近者，再取最近两个不同类；只有一类时补该类另一条最近记录。修复后成功者归有效子代，前序报错留在同一尝试内。

所有子代选完按生成顺序呈现，不按成绩排列。结构或向量在候选之间缺失时，缺失通道本次不参加该集合选择，使用其余有效通道，不能把缺失填成零距离。完整来源、次数与首次／最近编号留档，预算机制继续读全量真实投入。空段省略，不跨父代补数。经验按第2.5节直接取最多3条；融合参考按第2.4节抽取一个。

本文件的 RRF（倒数排名融合，reciprocal rank fusion）统一为 `sum(1 / (60 + rank_j))`，名次从1开始；只有可用且有区分信息的排名参与，同分先用相同竞赛名次，最终按编号决胜。该常数沿用检索文献的起点，不声称无参数或最优。RRF 避免直接相加不同尺度的距离与成绩，但仍假设各路排名有用，须分别消融。

### 2.2 记录与段落布局

Context 沿用 Base 顺序：`Ancestor History → Evaluated Offspring → Failed Offspring → Relevant Experience → Reference Algorithm（仅融合）→ Current Algorithm`。公共任务和函数模板在 Context 前，Instruction 和 Output 在后。

历史卡使用固定的 Algorithm、Parent、Operator、Reference（若有）、Result、Design 与修改说明。先显示关系和客观 Result，再显示方法与解释。Result 的比较对象始终是该事件自己的父代，不能被理解成当前全局最好。没有可比父代的初始化记录省略数值变化。

修改说明只展示一份：已有 review 时用 `Reviewed change`，否则用原始 analysis 并标 `Proposed change`。前者是评价后的模型代码解释，不叫 Verified change；后者是生成意图。原始 analysis、design、review 全部留档，精简仅作用于提示视图。当前父代的原始 analysis 如展示，标为 `Origin proposal`，以免被误认为本轮已经确定的修改。可选变更单元另列。

Result 按原始有限 fitness 严格比较，较小为改善，不以显示时的四舍五入判为持平。若另显示增益，使用 `父代fitness－子代fitness`，正值为改善。报错或超时没有有效成绩，不计算数值增益。

```text
[Evaluated Offspring]
Direct attempts from Algorithm 8: 20 valid; showing 3.

Algorithm 15
Parent: Algorithm 8
Operator: Refine
Result relative to Algorithm 8: {parent_fitness} -> {child_fitness}; {improved / tied / regressed}
Design: {self-contained algorithm description}
Reviewed change: {review, when available}
Proposed change: {original analysis, only when review is unavailable}
Changed computation: {at most two complete changed statement units}

Algorithm 17
...

[Failed Offspring]
Failed direct attempts from Algorithm 8: 4; showing 2.

Algorithm 19
...
```


上例数字仅说明格式，不作为实验结果。每段只出现一次标题，段内各卡依次排列。子代段与失败段在标题下标明总数与可见数，避免模型把未展示解释为从未尝试。祖先卡在末行标出省略的中间节点数和真实parent_id。失败记录显示 `error（含非法结果）/ timeout` 与必要的异常类别和候选代码位置，不填性能增益；超时历史不显示具体时限。完整栈、实例规模、内部预算和其他协议禁止字段仅留后台，修复提示也只使用去敏反馈。

可选 `Changed computation` 提供局部代码：比较父子 AST，在新增、删除或改变的语句中，按源码顺序取最多两个包含完整控制块的变更单元。系统同时列出变化单元总数与已展示数。这些片段帮助辨认实际计算，不代替父代完整代码；反思仍读取完整差异。

Reviewed change 与 Proposed change 两行互斥，示例的占位说明不发送给模型。失败卡先显示执行状态和去敏错误，再显示设计与一份修改说明，不填性能增益。空段连同配套指令一起省略，不制造代码核对结论。初始节点没有子代或经验时，生成仍能正常进行，信息会随实际尝试逐步增加。

### 2.3 输入长度

输入不做长度检查，也不裁剪。材料超出模型窗口时，请求失败直接记在调用中，按未评价尝试处理。长度问题由此暴露，不被裁剪掩盖。

### 2.4 融合参考：筛选质量，再判断成对关系

参考与父代必须来自同一可比评价组。先按源码身份分组，每组取最小 `(fitness,id)` 代表。在全部代表上计算成绩中位数，再排除父代同源码组；不劣于中位数者构成质量优先池 A；A为空时以全部不同源码代表为优先池，记录 relaxed。没有不同源码代表时，则保持父代，实际执行 Explore，记录请求算子、实际算子与 `no_distinct_reference`；不能转为 Refine，因为父代按拓展价值选出。

在合格池内建立三类成对信息：

1. **设计差异**：父代与参考 design 的余弦距离；寻找不同的设计资源，而非直接奖励越远越好。
2. **结构差异**：父代与参考 AST 特征的余弦距离；补充文字未描述的实现差异。
3. **成绩互补（可选）**：仅对完整、同顺序、同条件的训练实例成绩计算 `H(r|p)=mean_i max(0, f_p[i]-f_r[i])`，以越小越好的成绩为准。它表示逐实例择优相对父代的余量，既不是融合收益预测，也不保证参考擅长的是父代绝对最弱的实例。

设计与结构两条排名先用 RRF 合为“差异”一票，再与参考整体质量、可用的成绩互补排名做外层 RRF。全同排名不参加；缺明细时不把 H 填成0，也不只惩罚缺失程序。仅当全部不同源码参考都有对齐明细时才启用 H。

短名单最多4个。质量优先池的每个有效外层通道先保留第一名，去重后按外层 RRF 补齐。若质量池外还有参考，则为它们保留一个名额，质量池只占最多3个：该名额优先取 H 最大者；H不可用或全同则取差异 RRF 最高者，再按质量与编号决胜。没有池外候选时，4个名额都在质量池内选。这个出口针对“整体成绩较差，但含有值得迁移的局部计算”，不让中位数门把它们全部遮蔽；它只是候选，不因差异大就强制融合。

按编号排列短名单后，使用本路随机状态均匀抽取一个参考；只有一个则直接采用。先确定该参考，再按第2.5节检索经验，生成时提供参考完整设计与代码。各通道首项保留避免只让共同偏好的一个方向占满短名单。两路差异都不可用时只按质量与可用的 H 排名；全部无区分时按编号取短名单，记录退化。

逐实例成绩不是当前 Base 的现成字段：[当前 Base](../../traceaad_base/evaluation.py:43)要求任务返回标量。本机制在没有 H 的情况下完整运行。启用 H 需要评价适配器在同一次原有评价中额外保留明细，验证聚合值、随机数、执行顺序和计时不变；不额外评价，不读取独立测试，不向生成提示泄露实例数量、规模或设置。

结构／语义差异用于扩大可借鉴的资源，不作为互补判据。真正的接入关系由模型指出“借哪项计算、接到哪个决策点”。所选参考给生成器完整代码。若模型最终无法合理采用，允许在 analysis 中说明参考未使用，不换参考重试，也不据子代改善声称融合成功。

### 2.5 排名直接决定生成材料

先完成融合参考抽取，再召回经验。State、Need、Implementation各自对全库可比活动条目形成完整排名，通道内先合并相关子路，再做外层RRF。取前3条直接进入生成上下文。库中不足3条时全部提供，空库时省略。不设相似度阈值，也不为另一次生成前判断准备候选子集。

Crossover的Need只针对实际抽中的一个参考构造：融合要求＋最近尝试反馈＋参考design。只有不存在不同源码参考时，才保留父代执行Explore，随后按实际算子召回经验。其他情况都发送Crossover提示。

三条经验均展示完整系统观察视图，包含已登记的改善与未改善来源。经验是可借鉴材料，生成模型结合当前和参考完整代码决定是否采用、如何适配，不要求逐条执行。参考不附暂定接入说明；借用什么计算、接到哪个决策点，由融合指令交给生成模型判断。

所有实际排名、参考短名单、抽样结果和来源视图随尝试记录落盘。恢复只读回已完成的尝试。材料选取不增加生成前LLM请求。

## 3. 三种算子的生成要求

三种算子共用上述上下文与输出格式，只替换本次操作要求。区分的是修改目标，不为三个算子建立三套历史或经验池。

### 精炼

```text
Refine the current decision mechanism. Identify a specific limitation or opportunity and change the computation that addresses it, keeping the main mechanism as the basis of the new method. Make coordinated changes where the improvement requires them, and implement the complete function.
```

精炼延续当前设计，但不要求保留每个已有组件。轨迹可以启发恢复被误删的计算，也可以启发继续简化；本次评价仍针对生成出的完整程序。

参数调整本来就是精炼的一种形式，不能为减少无效调参而一概禁止。提示要求说明具体问题和修改依据，不用代码改动量或是否改常数判定修改价值。

### 探索

```text
Develop an alternative decision mechanism for the required function. Introduce or reorganize a computation that changes how the method uses the available information to make its decisions, and explain that difference from the current method. The alternative need not retain the current representation or computation pattern. Implement the complete function.
```

当前完整代码就在眼前，探索容易退化为精炼；倒数第二句针对这一失败。轨迹的使用由第4.2节随材料出现的指引说明，算子文本不依赖历史是否存在。探索不以源码差异大或参数变化多为目标。新思想需要进入实际决策，暂时较差的历史实现仍可启发另一种实现或组合。

新增评分项若引入新的决策信息，也可能实现一个新思想；提示不按修改的语法形式排除它。区分的是实际决策机制是否改变。

### 融合

```text
Adapt a useful computation from the reference to work with the current method. Identify the decision it will change and how the two sources contribute to the resulting procedure, adjusting their representations or order of computation where needed. Implement the complete function with that interaction in its actual decision process. If the full reference code does not offer a coherent adaptation, briefly say that the reference was not used and implement your proposed candidate without claiming a fusion.
```

融合允许选择性借鉴和调整接口，不要求把两份程序中的组件全部保留。解释应指出借鉴的具体机制及其与父代的配合方式。

## 4. 最终提示与输出协议

一次生成调用返回 Base 的严格 JSON 三字段。`analysis` 简短说明修改依据及预期作用，`design` 用独立完整的一段描述状态表示、主要求解原理与返回结果的形成，`code` 给出完整实现。分析与设计用short或brief提示，不设字数检查或长度拒收。设计先说明要实现的完整算法，代码实现该方案；这与输出先文字后代码并不矛盾，无需因此改动 Base 公共模板。

### 4.1 公共模板，沿用Base输出字段

````text
{task_description}

Implement the following Python function:
```python
{function_template}
```

[Context]
{context}

[Instruction]
{instruction}

[Output]
Return exactly one valid JSON object with three string fields, in this order:
- "analysis": Briefly explain the algorithmic rationale of the proposed change, the evidence that motivates it, and its expected effect on solving the task.
- "design": Describe the final algorithm implemented in "code" in one short self-contained paragraph. State the solution representation, the main solving principle, and how the procedure determines the returned result.
- "code": Provide the complete implementation of the required function, including necessary imports and helper definitions. Do not include comments or docstrings.
First determine a complete executable algorithm; then make "analysis" and "design" accurately describe the final "code".
Preserve the required function signature and satisfy the task constraints and input/output requirements.
Return only the JSON object, without Markdown fences or additional text.
````

客户端使用 Base 的 `CANDIDATE_RESPONSE_FORMAT`，不接受额外字段、空字符串或 Markdown 包裹。模板变量由已有任务和本节定义的上下文、指令填充；占位符本身不发送给模型。

### 4.2 指令组合

`instruction` 按以下顺序拼接：公共要求 → 第3节唯一一个实际算子 → 与实际展示材料对应的上下文指引 → 输出职责。下列大写标签是组装控制流名，不作为正文发送；空段连同指引省略。无不同源码参考而转 Explore 后，使用 Explore 文本，不发送 Crossover 指令。

公共要求始终发送：

```text
Develop a candidate to improve solution quality for the stated task. Read the current code as the implementation being modified. Historical designs, reviews, and experience notes are interpretations or proposals; evaluated results report outcomes, not the cause of those outcomes.
```

函数角色、接口与输出合同已由任务文本和公共Output说明，公共要求不再重复。

以下指引只在有对应记录时出现。父子关系与省略区间已写在祖先卡上，指引不再重复：

```text
ANCESTORS:
Use the formation path to understand earlier changes to the current computation.

OFFSPRING:
Compare the modifications already tried from this parent and their outcomes. A useful next proposal may extend an improvement, revise an unsuccessful implementation, or test a different combination.

FAILURES:
Use execution feedback to address the reported implementation issue; it does not establish that every realization of the idea is unsuitable.

EXPERIENCE:
Use a note when its conditions hold or when your proposed change can establish them. Adapt the idea to the current computation; leave it unused when it adds no useful guidance. A note can also inform further development of a computation already present.
```

下列职责说明最后发送，之后由公共模板接上原样的 `[Output]`：

```text
In analysis, briefly identify the computation you will change and why the change is worth trying. Cite an Algorithm or Experience id only when a specific observation informed that choice; a proposal may also follow from the task and current code without a historical precedent. Describe expected benefits as expectations, not measured improvements.
```

design与code的职责由公共Output说明，这里只补analysis：Output要求写出动机证据，这句把它收回到一次具体修改，避免逐条引用历史。实现见context.py。

analysis 聚焦一次修改及其理由，不逐条解释所有祖先、尝试或经验；design 承担完整方法说明，code 实现它。无历史时，依据可以来自任务结构和当前代码，不补造经历或来源编号。JSON与代码格式要求以公共Output为准，输出长度不作硬性检查，不加第四个字段，不要求长篇逐步推理。

### 4.3 调用与修复

生成、已有格式／运行修复沿用 Base 流程；评价后反思单独请求和记账，不混入生成输出 schema。反思新增的 `review` 写回历史，经验在后续 Context 中提供。反思失败不要求生成器补填，也不重发生成调用。输出内容与实际实现的一致性仍需结合代码和评价检查，结构化格式本身不证明算法有效。

## 5. 设计收益、代价与来源

| 取舍 | 预期收益 | 可能代价 |
| --- | --- | --- |
| 当前代码完整，历史以文字为主 | 接续已有思想，减少历史代码复制 | 修改说明可能遗漏真实计算 |
| 连续路径与同起点反馈同时呈现 | 同时考虑机制形成和不同修改的效果 | 复合修改与评价噪声仍可能被误解释 |
| 正负经验带适用条件 | 借鉴经验，保留重新实现的空间 | 条件过宽会误用，过窄会妨碍迁移 |
| 短分析、设计、代码一次输出 | 将修改依据与实现联系起来，便于复查 | 分析可能只是事后合理化，也会增加输出成本 |

以下文献提供设计借鉴。论文中的效果不直接等同于本机制的收益。

- **EoH：思想描述与代码共同演化。** 其方法先描述算法思想再实现代码，并以不同提示区分探索与修改。借鉴这种表示与算子分工，不据此宣称显式分析或轨迹不可缺少。[本地方法原文](/home/fang/code/LLM4AD/papers/Evolution_of_Heuristics_Towards_Efficient_Automatic_Algorithm_Design_Using_Large_Languag/3-method.tex:6)
- **ReEvo：比较性能后生成反思并指导演化。** 借鉴修改反馈与生成之间的直接联系。[本地方法原文](/home/fang/code/LLM4AD/papers/ReEvo/sections/04_evolution.tex:38)
- **RefineEvo：带适用条件的正负经验。** 论文比较了有无经验、正负经验及情境筛选。借鉴相关经验进入生成的机制；其消融没有检验本机制的多步轨迹或三段输出。[论文实验](/home/fang/code/LLM4AD/papers/RefineEvo_Planning-Guided_Heuristic_Evolution_with_Bidirectional_Experience/04_experiment.tex:271)
- **Contrastive CoT：正负对照示例。** 它在推理任务中比较有明确正误标签的解释。我们据此保留对照关系，但低分算法不使用“错误思想”标签。[原论文](https://arxiv.org/html/2311.09277v1)
- **Lost in the Middle：信息位置与长度影响使用。** 借鉴固定分区和关注输入负担；其问答、检索实验没有证明本布局最优。[原论文](https://arxiv.org/html/2307.03172v3)
- **Self-planning Code Generation：简短计划与代码生成。** 其变体比较不支持无限增加解释层级。我们保留一次调用中的短分析与设计，算法计划与代码仍在一次生成内输出；经验直接按排序提供，不增加生成前规划或判别调用；当前模型是否需要分析仍待检验。[原论文 §4.3](https://arxiv.org/html/2303.06689v3)

相关依据与替代方案保存在[外部上下文调研](../记录/2026-11-03-轨迹双机制调研-上下文借鉴.md)、[AAD生成调研](../记录/2026-11-03-轨迹双机制调研-AAD生成.md)和本地案例核对。

本轮进一步结合 Opus、哈基米 Gemini 与 Muse 的专项意见收敛规则。最新元评审与分歧裁决见[元评审综合](../记录/2026-11-03-轨迹机制元评审-综合裁决.md)，它替代旧裁决中单路经验检索、随机参考和最好加最近窗口的定案。采纳与未采纳项、六个用户问题对应的规格位置见[完善裁决](../记录/2026-11-03-轨迹机制完善-综合裁决.md)。辅助报告保留原文，当前执行口径以本文件和反思规格为准。

## 6. 实现检查与完整比较

先核对程序身份、真实parent_id关系、空历史生成、缺通道不填零、经验来源好坏结果保留、短名单均匀抽样、实际算子记账，以及恢复后抽样与不中断时一致。生成提示只含任务、接口、分数与算法材料，不含实例、划分、随机数、预算、时限或评价器设置。

V20集成全部机制后检验完整搜索的训练赢家与独立测试，另报生成、修复、反思和嵌入成本。过程记录实际计算接续、参考采用与经验使用，不用模型自述代替代码和评价证据。当前实现验证使用离线或替身模型，不执行真实模型冒烟和正式对比。
