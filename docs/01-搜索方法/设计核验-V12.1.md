# 设计核验：把每个 Explore 版本读成设计在起点算法中的一次检验（V12.1）

在 [V12.0 复提接续](复提接续-V12.0.md) 上实现，取代 V10.17 的随机续写。代码位于 `traceaad/v12_1/`，运行入口见[实验入口](../../experiments/traceaad_v12_1/README.md)。

**摘要。** LLM 算法设计搜索对设计作决定：继续哪个设计、放弃哪个设计、下一次实现参考哪份程序。评价器只给程序打分。一次 Explore 在起点算法中写入一个新设计，起点就是天然的对照：版本与起点的分差，就是这个设计在这个算法中的作用。这个读法要求版本是一次有效检验：它实现了设计，并且保留了起点中设计没有替换的计算。本项目的记录显示，两个条件经常不成立：Design 写节约法，代码是最近邻回路；首版重写了起点，丢掉调好的常数与局部搜索。现有搜索把两种情况都读成“设计变差”。V12.1 在搜索状态中补上这一关系。每个 Explore 版本由两次独立请求阅读：是否实现了 Design，是否保留了起点的其余计算。版本不是有效检验、且不优于起点时，搜索补全检验：缺设计就在原版本上补上设计，丢了起点就把设计放回起点；至多两步。没有实现设计的程序不再作为该设计的已有实现被继承。后续提示如实记录阅读与补全的结果。父代选择、算子份额与 V12.0 的提出、匹配、实现步骤都不变。

## 1. 研究问题

一次 Explore 提出一个新计算，在起点算法中写成程序，评价器给程序一个分数。搜索随后根据这个分数决定这个计算的去留。

这个分数什么时候是关于设计的证据？版本与起点只差这个设计时。这时起点是对照，版本是处理，分差归因于设计。这要求两件事同时成立：

- **实现**：版本执行了 Design 描述的主计算。
- **保留**：版本保留了起点中 Design 没有替换的计算。

两件事分别不成立，产生两种不同的错误：

| 版本 | 分数差时说明什么 | 正确的下一步 |
| --- | --- | --- |
| 实现且保留：有效检验 | 这个设计在这个算法中没有作用 | 放弃，记下结论 |
| 没有实现设计 | 设计没有被检验 | 把设计实现出来 |
| 实现了设计，丢了起点的部分 | 分差混入了丢失部件的损失 | 把设计放回起点再检验 |

三种情况需要三种决定。只读分数的规则把它们当成同一种情况。

本文研究的问题是：**怎样让一个设计的去留取决于它在起点算法中的一次有效检验，而不是取决于一次没有检验它的程序？**

## 2. 现象

**同一设计的不同实现，结果经常不同。** V9.21 在相同搜索状态与相同设计说明下，独立生成两份实现并分别评价。5,495 组两份都有有效成绩的配对中，1,653 组（30.1%）结果类别不同，504 组（9.17%）一份严格改善、另一份没有改善；各任务与重复中为 23.5%–42.0%（Git `bbf4b61d`：`docs/analysis/机制分析/TraceAAD-V9.21机制首跑分析.md`）。一次实现的分数含有大量实现的偶然成分。

**评价的程序没有实现提出的计算。** CVRP 第 3 路 Explore 33 的 Design 是节约法，代码构造忽略容量的最近邻回路，得 9.998。随机抽中的续写补上容量可行的 Clarke-Wright 路线，达到 9.285，这个结构随后发展到最终的 8.408。较弱的三路也提出过节约法：首版或用最近邻代替，或把合并循环写成 `pass`，得 10.3–10.5，只试了一次（[首版门槛](../03-现象与检验/2026-10-04-短程改写诊断与首版门槛.md)）。V10.21 图着色中，一次回复声称实现模拟退火，代码没有温度、概率接受或退火循环；这条 Design 原样进入后续三次请求（[提示材料检查](../03-现象与检验/2026-10-08-提示目标与历史材料检查.md)）。

**首版丢掉起点的成熟部件。** V10.17 的短程改写中，557 次得到改写的探索里，382 次最好结果的代码更接近提出前的旧程序；改写第一步有 27.7% 的 Design 明确写着恢复旧程序。首版与起点的相似度中位数为 0.62；相似度低于 0.5 的首版超过起点的不到 1%（[改动检验诊断](../03-现象与检验/2026-10-06-新设计开发诊断与改动检验.md)）。V10.19 在提示中要求“保留不替换的部分”，TSP 与 VRPTW 的首版仍是重写，落后起点的中位数为 9.9% 与 10.9%（[改动检验结果](../02-实验结果/2026-10-06-改动检验-held-out阶段结果.md)）。写进提示的要求没有被核对，也就没有生效。

**落后的首版得不到第二次机会。** V10.16/17 中，节约法加局部搜索被引入 127 次，其中 92 次首版落后当时最好 1% 以上；TSP 补全路径加 2-opt 引入 137 次，104 次落后。进入最终程序的结构变化，几乎都来自首版直接胜出的那一次。父代选择的质量项 \(\exp[-\beta(q-q_{\min})]\) 使落后的首版几乎得不到下一次尝试。

**按分数开发，预算落在已被否定的设计上，成功多是回到起点。** V10.18 开发预算约 60% 落在首版落后 10% 以上的设计上，3 步内超过起点的只有 4.6%（[新设计的开发过程](新设计的开发过程.md)）。V10.19 开发后超过起点的版本中，首版新增代码留下的比例中位数为 0.00–0.19，首版删掉的起点代码被恢复的比例为 0.50–0.85；抽查的成功版本丢掉了全部新计算，只改起点的一两个常数。“超过起点”不能区分设计成立与精炼起点。

## 3. 现有方法的不足

| 做法 | 代表方法 | 对上述问题的局限 |
| --- | --- | --- |
| 按分数选择父代或灵感程序 | EoH、FunSearch、ReEvo、AlphaEvolve | 设计以一次实现的分数参与选择；程序没有检验设计时，设计与程序一起被淘汰 |
| 让描述对齐代码 | MCTS-AHD 思想对齐 | 按代码重新描述算法，记录变真实，但提出的设计被丢掉，从未得到检验 |
| 对计划重新采样实现 | PAEvo R1 | 只对最优的计划重新独立实现；落后的计划得不到重采样，每次实现也不知道上一次缺了什么 |
| 在提示中要求保留、以超过起点为开发目标 | TraceAAD V10.18–V10.24 | 要求没有被核对；开发由分数触发，成功多为精炼起点 |
| 按设计继承已有实现 | TraceAAD V12.0 | 以 Design 文本判断“同一计算的已有实现”；没有实现该计算的程序也被当作它的实现状态继承 |

这些做法有一个共同根源：**搜索状态中没有“这个版本是否检验了它的设计”这一关系。** 每种做法都把 Design 文本当成程序真实的计算，把版本与起点的分差当成设计的作用：选择用程序分数代表设计，记录用 Design 代表程序做过什么，继承用 Design 找同一计算的实现，开发用“超过起点”代表设计成立。这个关系缺失时，没有一条分配规则能区分未被检验的设计和已被否定的设计。V10.18–V10.24 调整的是分配规则，没有补上这个关系。

## 4. 方法：设计核验

### 4.1 核心思想

搜索要对设计作决定，需要三项关系：

| 关系 | 回答 | 由什么提供 |
| --- | --- | --- |
| 同一 | 这个提案与哪些已有程序是同一个计算？ | V12.0 匹配 |
| 检验 | 这个版本是这个设计在起点中的一次有效检验吗？ | **V12.1 两项阅读** |
| 价值 | 这个设计在这个算法中值多少？ | 版本与起点的分差，**仅当检验有效时** |

V12.1 补上中间一项。由此有五个步骤，每一步回应一个具体缺口：

1. **两项阅读。** 每个 Explore 版本评价后，模型先对照 Design 阅读代码，判断是否实现了主计算；实现了，再对照起点阅读，判断是否保留了 Design 没有替换的计算。不成立时说出缺了什么、丢了什么。两项分两次请求：一次请求同时回答两个问题时，模型把两者混在一起（见 4.5 冒烟检查）。没有这一步，后面四步都没有依据。
2. **补全。** 版本不是有效检验、且不优于起点时，补全检验，按阅读结果分两种：
   - **缺设计：在原版本上补上设计。** 版本保留了起点，只差设计的一部分。在它上面补，起点的成熟部件仍在。
   - **丢了起点：把设计放回起点。** 版本已经写出设计，但丢了起点的部分。从起点出发，展示这个版本作为设计的示范，说出丢了什么。结果重新以起点为对照。

   只阅读不补全，设计仍会被质量项淘汰：阅读改变了对它的认识，没有改变它的去留。
3. **停止。** 版本成为有效检验、优于起点、补全返回了已有程序，或补全满两步，探索结束。有效检验无论结果好坏都停止：分数差的有效检验是一次否定，再改就是开发。补全返回已有程序（重复或已知失败），说明模型没有更多可改的。
4. **继承。** 没有实现设计的程序不进入 V12.0 匹配的候选。V12.0 把同一计算最好的已有程序传给下一次提出；混入没有实现该计算的程序，继承就把错误传下去。丢了起点部分但实现了设计的程序仍是这个设计的实现，照常继承。
5. **如实记录。** 后续提示中，程序的 Design 后注明阅读结果；起点的尝试记录注明补全的结果。没有这一步，“声称模拟退火，没有改善”会作为经验继续传播。

补全由阅读触发，不由分数触发。实现且保留、分数差的版本不补全，它是一次有效的否定。这是它与 V10.18、V10.19 的区别。补全后的版本同样阅读：回到起点只调常数的版本优于起点，探索结束，但它被读为没有实现设计，记录与继承都如实反映。

### 4.2 Explore 的步骤

```text
提出 → 匹配 → 实现（V12.0，不变；匹配候选排除没有实现设计的程序）
  → 评价，得到首版
阅读：实现？（verify）→ 实现了才读：保留？（contain）
  ├ 有效检验，或优于起点 → 结束
  ├ 缺设计，不优于起点     → 在该版本上补全 → 评价 → 阅读 → ……
  └ 丢了起点，不优于起点   → 在起点上补全（展示该版本）→ 评价 → 阅读 → ……
  补全返回已有程序，或满 2 步 → 结束
```

**实现阅读（verify）。** 独立请求，温度 0，输出上限 8192 tokens，不产生候选。上限只防失控：Qwen 逐项写出的保留阅读常有两三千 tokens，截断的回复没有判断行，记为未判断。

````text
[Task]
{任务说明，与搜索提示的第一段相同}

[Design]
{提案的 Design}

[Program]
```python
{版本代码}
```

Does the program carry out the main computation the Design describes? Judge by what the code computes and returns, not by its names.
First state in a few sentences what the program computes. Then end your reply with one line: "Carried out: yes", or "Missing:" followed by one sentence naming the part of the Design's main computation that the code does not carry out.
````

只给任务、Design 与代码，不给分数：判断的是代码做了什么，分数会把判断拉向“结果差所以没实现”。先描述程序计算了什么，再给判断，使判断落在代码上，而不是落在名字上。“主计算”与 V12.0 匹配用的是同一个词，两处判断针对同一个对象。

**保留阅读（contain）。** 只在实现阅读不为“缺设计”时进行，条件相同。

````text
[Task]
{任务说明}

[Start Algorithm]
```python
{起点代码}
```

[Design]
{提案的 Design}

[Program]
```python
{版本代码}
```

The program was written to carry out the Design in the start algorithm. Does it keep the computations of the start algorithm that the Design does not replace? Judge by what the code computes, not by its names. A changed constant is not a dropped computation, and neither is a computation whose result the start algorithm uses only for what the Design replaces, or does not use.
First list the computations of the start algorithm in a few words each, and for each say whether the Design replaces it and whether the program keeps it. Then end your reply with one line: "Dropped: none", or "Dropped:" followed by one sentence naming the computations that the Design does not replace and the program does not keep.
````

问题限定为“丢掉的计算”，不问“其他改动”：常数与细节的变化是实现的一部分，不影响归因。只为被替换的计算服务、或起点本身没有使用的计算，随替换一起消失，不算丢失；离线重放中，没有这一句时模型把这类计算读成丢失。逐项列出起点的计算，再对每项分别判断“是否被 Design 替换”与“是否保留”，避免模型写出“删掉了 X，因为 Design 要求”却仍判为丢失。

**解析。** 各取最后一个判断行。`Carried out: yes` 与 `Missing: none` 为实现；`Missing: {一句}` 为缺设计；`Dropped: none`（或 `no`、`nothing`）为保留；`Dropped: {一句}` 为丢了起点。缺失与丢失的句子保存下来，提示中原样引用。没有判断行时记为未判断，按有效处理，不触发补全。

**补全。** 产生一个候选。缺设计时从该版本出发：

````text
{任务、分数与目标函数}

[Current Algorithm]
Score: {该版本成绩}
```python
{该版本代码}
```

[Proposal]
The current algorithm was written for this proposal.
{提案：Analysis 与 Design}

[An Earlier Program for the Same Computation]
{V12.0 展示过的接续程序，若有}

[Reading of the Code]
Read against the Design: {缺失}

[Your Task: Complete]
Change the current algorithm so that it carries out the Design, and keep the rest of what it computes.

[Output Format]
Reply in this order:
Analysis: <a few sentences: what the current algorithm computes, and what it must compute to carry out the Design. It will not be shown again>
Code:
```python
<the complete program>
```
Write no comments or docstrings in the code, and nothing after the code block.
````

丢了起点时从起点出发，`[Current Algorithm]` 是起点，其后为：

````text
[Proposal]
This proposal was made for the current algorithm.
{提案}

[An Earlier Program for This Proposal]
Written from the current algorithm for this proposal.
Score: {该版本成绩}
```python
{该版本代码}
```

[Reading of the Earlier Program]
Read against the Design and against the current algorithm, from which it was written:
{缺失，若有}
{丢失}
````

每一段都有用途。提案给出原意：Analysis 说明起点缺什么、新计算要捕捉什么。MCTS-AHD 对齐描述时丢掉的正是这一段。接续程序与该版本是同一计算已写出的示范；本项目的记录显示，示范对生成的作用大于分析问题和目标句。阅读说出的句子指出要补的部分。目标只说这一步为这个设计做什么，不要求更好的分数：补全的目的是让设计被检验，不是再做一次改进。回复不写 Design，补全版本的 Design 固定为提案的 Design。

提示超过输入上限时去掉接续程序；仍超限则不补全，结束这次探索。补全失败时照常 Repair，最近有效版本不变。第二次补全从最近有效版本按同一规则进行。

**如实记录。** 程序在形成路径、最好成绩刷新与参考程序中显示为：

```text
Design: {Design} (read against this Design: {缺失}) (besides this Design: {丢失})
```

起点的尝试记录中，这次 Explore 的结果后接：

```text
→ score 8.86 (worse); read against its Design: {缺失}; completed: score 8.03 (improved), still not carrying out the Design
```

丢了起点写作 `besides its Design: {丢失}`；第二次补全写作 `completed again`；补全版本仍丢失起点时加 `still dropping part of the start algorithm`。补全尝试不计入父代选择的尝试经验：它是对一次检验的修正，不是从一个程序出发的算子尝试。

### 4.3 决定权

每项判断都可能出错。判断越不确定，给它的决定权越小。

| 判断 | 为什么不确定 | 得到的决定权 | 判断错时的代价 |
| --- | --- | --- | --- |
| 读为缺设计 | 模型可能误读代码，或对 Design 理解过严 | 至多两个补全候选；该版本退出匹配候选；提示中注明 | 至多两个候选；一份真实实现不被继承，但它仍可作为父代与参考程序 |
| 读为丢了起点 | 模型可能把实现方式的变化读成丢失 | 至多两个补全候选；提示中注明 | 至多两个候选；照常继承 |
| 读为有效检验，或未判断 | 模型可能漏看 | 没有额外动作 | 与 V12.0 相同 |
| 只补全不优于起点的版本 | 优于起点的版本背后也可能有更好的设计 | 不补全，只注明 | 程序已凭分数留在竞争中，Refine 会看到注明 |
| 至多两步，返回已有程序即停 | 有的设计需要更多步 | 硬上限 | 第三步之后是开发，交给父代选择 |

阅读不进入父代选择。没有检验设计的程序仍是真实的程序，它的分数是真实的分数；选择它作为父代，开始的是对这份代码的改进，不受 Design 是否属实影响。阅读只改变三件事：这个设计是否得到补全，这份程序是否代表这个设计被继承，后续提示怎样描述它。

### 4.4 保持不变的部分

- 父代选择：质量 × 尝试经验，\(w_i=\exp[-\beta(f_i-f_{\min})]\frac{k_i+3r}{n_i+3}\)。
- 算子份额：Refine 45%、Explore 30%、Crossover 25%；Refine、Crossover、Repair 的提示与生成不变。
- V12.0 的提出、匹配、实现三步与全部提示；匹配候选只排除读为缺设计的程序。
- 初始化、去重、失败修复、档案与预算计数；评价协议与 V12.0 相同。

去掉的部分：V10.17 的随机续写（新 Explore 程序以 1/8 概率获得至多 3 次 Refine）。补全占用它的位置。

只阅读 Explore 版本。Explore 引入新计算，它的去留取决于第一份程序，首版门槛作用在这里。Refine 与 Crossover 保留当前算法的核心计算，它们的 Design 描述已有计算上的改动。

### 4.5 预算与成本

预算按候选计数。阅读不产生候选，作为模型请求记录，token 计入总消耗；每个有效 Explore 版本一到两次。补全每步一个候选。随机续写每次探索期望至多 \(\frac18\times3\approx0.38\) 个候选；补全每次探索期望至多 \(2p\)，\(p\) 为首版不是有效检验且不优于起点的比例。离线检查中 Qwen3.8 的 \(p\approx0.39\)（220/558），补全每次探索至多约 0.79 个候选。

2026-10-14 用真实 DeepSeek 做了五次冒烟检查（TSP 四次、JSSP 一次，预算 12–16，只用 Explore），用来定提示，不代表效果。第一次只有实现阅读，6/9 读为缺设计，抽查两例判断正确。第二次把两个问题放在一次请求里，缺设计 0/10，“其他改动” 8/10，多为把常数和细节读成改动：两个问题混在一起，于是拆成两次请求，并把保留阅读限定为丢掉的计算。第三次出现“删掉了 X，因为 Design 要求”却判为丢失的矛盾，于是改为逐项判断；两次从起点补全返回了已有程序，于是加入返回即停。第四次（预算 16，62 次请求）13 次实现阅读中 5 次缺设计，句子具体（如 “does not perform greedy nearest-neighbor chaining”）；平均每次实现阅读 760 入／140 出，保留阅读 1,180 入／640 出；两次保留阅读达到当时 1,024 的输出上限，上限因此提到 2,048。本路最好的 6.26 来自一次补全：首版读为缺设计、得 25.78，补全后得 6.26。第五次在 JSSP 上，10 个首版全部读为有效检验，没有补全；保留阅读最长 1,313 tokens，没有截断。一例阅读偏宽：Design 要求在关键弧上移动，阅读写出代码只是交换排列中的工件，仍判为实现。JSSP 程序较长，实现阅读平均 3,900 入、保留阅读 6,570 入；只用 Explore 时，阅读占输入 token 的 44%、输出的 12%。完整搜索中 Explore 约占三成候选，比例相应降低。

## 5. 与已有认识的关系

V12.1 不是对历史机制的叠加。历史上几项有价值的认识，各自对应它的一个部分：

| 来源 | 当时的认识 | 在 V12.1 中的位置 |
| --- | --- | --- |
| V9.21 同一设计两份实现 | 一次实现的失败，可能是设计不合适，也可能是代码没有兑现 | 问题本身；V12.1 用阅读直接区分两者，独立重采样作为对照组（C3） |
| V9.22 稳定脚手架与当前实现 | 设计的价值要在一份稳定的程序上读 | 起点是对照；丢了起点的版本把设计放回起点 |
| V10.17 随机续写 | 部分弱首版经续写成为最终结构（CVRP 8.408） | 随机抽签换成按阅读触发 |
| V10.18–V10.24 开发调度 | 按分数开发弱首版，预算落在已否定的设计上 | 补全的触发条件不读分数的落后程度 |
| V10.19 改动检验 | 改动要在原算法上检验；“超过原程序”不能区分改动成立与精炼原程序 | 保留阅读核对“改动之外不变”；补全后的版本仍要读为有效检验，才算设计成立 |
| V10.25 失败与修复分开展示 | Repair 可能删掉新计算 | 修复后的版本同样阅读 |
| V12.0 复提接续 | 同一计算的实现进展跨提案积累 | 接续对象限定为实现了该计算的程序 |
| “可执行改动实验”构想（2026-10-14 讨论） | 改动要能归因；不要生成重复代码；对照组与独立实现谁更有用 | 归因由起点对照加保留阅读完成；返回已有程序即停；独立实现作为重采样组 |

该构想的其余部分没有采用：由 LLM 控制器选择下一步动作，与“展示的尝试会被模仿”的观察冲突，且没有对照证据；为每个改动额外生成分解的两臂程序，预算翻倍，而起点已经是对照；在提示中写预算与工作清单，违反最小提示原则。

## 6. 检验

五个主张分别对应以下实验。条件按[实验规范](../08-实验规范与共识/README.md)：DeepSeek `deepseek-v4.1-flash`，六任务各三路，1000 候选。阅读使用与搜索相同的模型。

**主张一：不是有效检验的首版常见，且可以识别（C1，离线重放）。** 在 V12.0 基础组与接续组档案上，对每个 Explore 首版离线运行两项阅读，统计：

- 有效检验、缺设计、丢了起点三类的比例，分首版优于起点与不优于起点两组；
- 不优于起点的首版中，有效检验与非有效检验两组此后各有多少被选为父代；
- 每路按三类各抽 10 例，对照代码检查阅读是否正确。

这一步给出第 2 节缺少的分母：首版落后中，可修的检验问题占多少。比例很低，或抽查显示阅读不可靠，V12.1 没有作用对象，不再运行后续实验。重放可在运行前缀上开始，不需要等待整场完成。

**主张二：补全使设计得到检验，并改变它的去留（C2，随机补全组）。** `DrawConfig` 中，需要补全的探索按固定抽签以 0.5 概率补全。比较补全与未补全两组：最终版本为有效检验的比例、有效检验优于起点的比例、探索最好版本优于起点的比例、此后被选为父代的比例；补全组再按缺设计与丢了起点分开。抽签与设计、分数无关，两组差别是补全的因果作用。

**主张三：补全的作用来自阅读，而不是多一次采样（C3，重采样组）。** `ResampleConfig` 的触发条件与候选数与主实验相同，补全请求换成原样再发一次第一次实现请求，即从起点独立重新实现。比较两组补全的同一组指标。阅读组更好，说明说出缺什么、丢什么是作用来源；两组相当，说明作用来自第二次机会本身，阅读只需决定给谁第二次机会。

**主张四：继承只沿实现了设计的程序进行（C4）。** 在 V12.1 运行上用接续报告读新实现超过同计算已有最好实现的比例，与 V12.0 接续组比较。

**主张五：整场搜索受益（C5）。** V12.1 与 V12.0 接续组、基础组及外部基线各六任务三路，报告各任务三路测试成绩的均值与 token 消耗。V12.1 与 V12.0 接续组只差阅读、补全与继承过滤，补全的预算来自原随机续写。

**离线行为检查（2026-10-14）。** 补全上线前，用 V12.0 接续组的 Qwen3.8 档案（`20261013_qwen_co6`，六任务各三路）检查阅读与补全的行为。V12.0 以固定 1/8 抽签开发探索，与设计和分数无关，被开发的 602 次探索是随机样本。每个首版按 V12.1 读两次。对不优于起点且不是有效检验的首版，从同一状态做三组下一步：`develop` 是该路自己的第一步 Refine（档案已有），`resample` 原样重发第一次实现请求，`complete` 是 V12.1 补全。新程序按该路条件评价，不修复，再用同样的两项阅读读。

558 个已判断的首版中，有效检验 54%，缺设计 37%，丢了起点 9%。首版优于起点时，不是有效检验的比例相近（缺设计 42%，丢了起点 12%）。不优于起点且不是有效检验的 220 个首版：

| 组 | 有效 | 优于起点 | 读为有效检验 | 有效检验且优于起点 | 超时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `develop` | 92.3% | 13.2% | 8.2% | 0 | 10 |
| `resample` | 85.5% | 16.8% | 35.9% | 5.0% | 15 |
| `complete` | 80.5% | 8.6% | 43.2% | 6.4% | 29 |

- 开发的成功几乎都不检验设计。`develop` 优于起点的 29 个程序中，28 个仍缺设计。V12.0 把它们记为设计的进展，实际改进的是另一个计算。
- 补全把多数版本变成检验，但相对重采样的增量小。配对比较中，只有补全成为检验 54 次，只有重采样成为检验 38 次。从起点重新实现本身就让多数版本成为检验。
- 按一步分数，重采样更常优于起点（配对 30 对 12），但它的 37 次胜出中 22 次缺设计。成为检验的版本中，两组优于起点的比例相同：补全 14/95，重采样 11/79。补全多出的超时集中在 FSSP（38 次中 19 次）：缺失的计算放回后，程序超出时限。

一步的“优于起点”奖励偏离设计的程序，不衡量设计是否得到正确的去留。这里只确认补全按设计工作：它产生检验，它的胜出多为检验。补全是否使搜索受益，由 C3 与 C5 的整场搜索判断。脚本为 `experiments/traceaad_v12_1/completion_pairs.py`。

## 7. 实现与记录

**代码。** `traceaad/v12_1/`：`verification.py` 为两项阅读的提示与解析，搜索与离线重放共用；`prompts.py` 为补全提示与注明；`traceaad.py` 为搜索。共用代码增加两处钩子：`PromptBuilder.design`（Design 的显示）与 `PromptBuilder.followup`（尝试结果的后续），默认与 V12.0 相同。

**配置。** `Config`：`completion_steps=2`、`completion_probability=1.0`、`completion="read"`、`verify_output_tokens=8192`，随机续写参数为 0。`DrawConfig`：`completion_probability=0.5`。`ResampleConfig`：`completion="resample"`。每次探索一个固定抽签 `random.Random(f"v12.1:{seed}:complete:{exploration_id}")`，断点恢复后不变。

**记录。** 每个被阅读的程序在事件中写入 `verdict`：

| 字段 | 内容 |
| --- | --- |
| `program_id`、`start_id` | 被阅读的程序与它的起点 |
| `design` | 阅读依据的 Design |
| `implemented`、`missing` | 实现阅读：`true`、`false` 或未判断 `null`；缺设计时说出的缺失 |
| `kept`、`dropped` | 保留阅读：`true`、`false` 或未判断 `null`；丢了起点时说出的丢失 |
| `error` | 提示超过输入上限时的原因 |
| `call_ids` | 阅读请求 |

阅读结果按程序保存，恢复时直接读取，不重复请求。探索记录增加 `versions`（各有效版本的 `implemented`、`kept` 与是否有效检验 `tests`）、`test_id`（第一个有效检验的版本）、`test_improved`（它是否优于起点）与 `completion_draw`；`developed` 表示是否进行了补全。补全尝试的 `action` 为 `Complete`，带 `design`、`completion` 与 `exploration` 编号。`calls.jsonl` 中三类请求的 `stage` 为 `verify`、`contain` 与 `complete`。
