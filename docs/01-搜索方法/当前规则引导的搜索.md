# 当前规则引导的搜索

2026-10-06。实现标识为 V10.20，以 V10.17 的整理版（`research-simple-v2-20261006`）为基础；代码位于 `traceaad/v10_20/`，入口为 `experiments/traceaad_v10_20/`。诊断见 [V10.17 之后改什么](../03-现象与检验/2026-10-06-版本差异与计算使用.md)；第一版设计的检验见 [重放与 ACO 评价噪声](../03-现象与检验/2026-10-06-V10.20重放与ACO评价噪声.md)。训练集、测试集和评价种子不变。

## 0. 要解决的问题

**改进一个算法，不只是改它的决策规则，也可以让它用这条规则做更多搜索。现有的生成步骤都只在规则上改。**

## 1. 设计思想

### 1.1 改进的两个方向

启发式算法可以沿两个方向改进：

| 方向 | 做什么 | 对应的步骤 |
| --- | --- | --- |
| 规则 | 调整打分与参数、换一种决策方式、借用其他程序的部件 | Refine、Explore、Crossover |
| 规则之上的搜索 | 保留规则，在决定时用它引导更多搜索：前瞻、rollout、多起点构造、对完整解做局部搜索、更长的内部迭代 | Deepen |

第二个方向是启发式设计的基本维度：从贪心到 rollout、beam search、多起点与局部搜索，规则不变，搜索加深。评价时限就是这一维的资源。我们最强的程序都走过这一步：TSP 对每个候选补全剩余路径并做局部搜索，CVRP 在函数内构造并改进完整解，再写进先验。在其他任务上，程序始终是打分公式，只用时限的 1%–11%。对固定程序只加一层由它引导的搜索，OP50 提升 2.2%，CVRP 提升 1.6%。

这一维不针对某个任务：任何决策规则都可以用来引导搜索。对某个任务是否有用，由模型根据任务判断，也由搜索中的实际结果决定。

### 1.2 一个步骤由目标和材料共同决定

第一版只给 Deepen 一句目标，材料沿用 Refine 的：当前算法、形成路径和尝试记录。固定父代重放显示，模型照着材料做事：

| 条件 | 子代函数耗时 / 父代（OP、CVRP 中位数） |
| --- | ---: |
| Refine | 0.9 |
| Deepen，Refine 的材料 | 1.2–1.3 |
| Deepen，去掉形成路径与尝试记录 | 12–13 |
| Deepen，Refine 的材料，目标后写明做法 | 15–17 |

形成路径里是几十步对同一公式的小修改。在这样的材料中，“用规则引导搜索”被理解为把某一项估计得更精细。这不只是 Deepen 的问题：过去几版的目标句改动常常不改变行为（V10.19 的“保留不替换的部分”、耗时剖析），原因也在这里。

所以，**每个步骤的材料要服务于这个步骤的决定**：

- Refine 延续当前算法的形成过程，需要形成路径和尝试记录。
- Explore 改变决策方式，需要当前算法、从它出发的尝试和本次搜索的进展（V10.17 不变）。
- Deepen 保留规则、加深搜索，需要规则本身（当前算法全文）、它的实测代价（耗时占时限、调用次数）以及从它出发的 Deepen 尝试。它不需要规则是怎样一步步调出来的。

材料里不列举具体做法。写明做法确实也能让模型增加计算，但会把例子变成待办事项，而且例子是按任务写的。

### 1.3 引入新计算的步骤需要开发机会

加深后的程序是一种新结构。搜索的预算、规则在搜索中的用法、结果怎样写回输出，都需要调整。重放中，一步生成的耗时程序与父代接近，没有直接变好。CVRP V10.19 rep1 从“构造解 → 写进先验”到 7.95，用了几百步开发。

V10.17 已经让 Explore 的新程序有短暂的开发机会：随机 1/8 接着做 3 次 Refine，每步从已达到的最好版本开始。Deepen 同样引入新计算，所以用同一条规则。**Explore 与 Deepen 的提出都开启一次探索。** 这样不必为 Deepen 另设开发机制，也不因为一步的成绩就放弃一个方向。

### 1.4 关于计算的事实必须真实、可见

模型决定用多少计算，依据的是任务文字和测量。OP、CVRP 的文字原来说函数“会被调用很多次”，实际每个实例只调用一次；VRPTW 没有说明服务时长会计入时间；测量行没有说明耗时占时限多少；测试规模和测试时限也没有说明。程序变重之后，最后一项决定它在 200 节点的测试上会不会超时。

### 1.5 这一版不做什么

- 不按任务定规则，不因为某个任务一步的结果增删步骤。一个步骤的价值，要看它在各任务的完整搜索中做了什么、带来了什么。
- 不改变训练集、测试集和评价种子。
- 不调整开发步数，不拆分预算。

## 2. 规则

除下列各项外，V10.20 与 V10.17 相同：父代按训练质量乘尝试经验选择；形成路径、尝试记录、修复、最终选择不变。

### 2.1 任务事实

更正放在 V10.20 的提示层中，不修改 `benchmarks/` 下的任务文件，以免影响外部方法的提示。

| 任务 | 原文 | V10.20 |
| --- | --- | --- |
| OP、CVRP | Use efficient NumPy operations because the function is evaluated many times. | The function is called once per instance, before the ant colony starts. |
| VRPTW | 没有说明服务时长 | At a customer, the vehicle waits until the time window opens if it arrives early, then spends the customer's service duration before moving on. The current time passed to the function already includes the waiting and service durations of the customers served so far; the service durations themselves are not passed to the function.（任务文字的最后一段） |

方法测试直接用评价器核对这两处：ACO 每个实例只调用一次函数；VRPTW 传入的时间等于到达时间取窗口开启后的较大值，再加服务时长。

### 2.2 测量行写出时限占用

```
Score: 8.74006 · Evaluation time: about 2.8 s of the 120 s limit · 10 calls to the function, under 0.1 s inside it
```

### 2.3 评价段落写出训练与测试

```
[Evaluation]
Each program is evaluated on 10 training instances with 50 customers.
Score: the average total length of the best routes found by the ant colony. Lower is better.
The whole evaluation must finish within 120 seconds.
After the search, the final program is tested on 64 instances each with 20, 50, 100 and 200 customers; each test set must finish within 3600 seconds.
```

| 任务 | 训练 | 测试 | 每组测试时限 |
| --- | --- | --- | ---: |
| TSP | 16 个，50 节点 | 各 16 个，50/100/200 节点 | 3000 s |
| CVRP | 10 个，50 客户 | 各 64 个，20/50/100/200 客户 | 3600 s |
| OP | 5 个，50 节点 | 各 64 个，50/100/200 节点 | 3600 s |
| VRPTW | 16 个，50 客户 | 各 16 个，50/100/200 客户 | 1000 s |
| OBP | 1,000 与 5,000 件物品，容量 100 与 500，共 4 个 | 1,000/5,000/10,000 件物品，容量 100/500，各 5 个 | 1000 s |

数字都从 `benchmarks/` 读取。

### 2.4 Deepen

目标：

> **[Your Task: Deepen]** Keep the current algorithm's decision rule and use it to guide a search that spends more of the time limit on finding better decisions, so that the program scores better than the current algorithm. Every version and attempt shown above has already been evaluated.

Analysis 提示：

> which decisions of the current algorithm a search guided by it could improve, and how much computation that search can use within the time limit on the training and on the larger test instances

材料，依次为：任务、评价、目标函数；`[Current Algorithm]`（实测与全文）；`[Earlier Deepen Attempts From the Current Algorithm]`，即从当前算法出发的 Deepen 尝试及其成绩与耗时，最多 8 个，超长时先删最早的。没有形成路径，也不列出其他步骤的尝试。

父代选择与经验计数和其他步骤相同：Deepen 的尝试计入父代的 `n/k`，也出现在 Refine、Explore、Crossover 看到的尝试列表中。

份额：

| 步骤 | V10.17 | V10.20 |
| --- | ---: | ---: |
| Refine | 0.45 | 0.40 |
| Explore | 0.30 | 0.25 |
| Crossover | 0.25 | 0.20 |
| Deepen | — | 0.15 |

### 2.5 Explore 与 Deepen 的提出都开启探索

提出得到新的有效程序时，按探索编号固定抽签（沿用 V10.17 的抽签），1/8 接着做 3 次 Refine，每步从本次探索已达到的最好版本开始。开发的 Refine 使用完整的 Refine 材料，形成路径中最新的一步就是这次加深。预期约 `0.40 × 1/8 × 3 ≈ 15%` 的普通生成用于开发（V10.17 约 11%）。

## 3. 检验

本机运行，5 个任务各 3 路，种子 0–2，预算 1,000，held-out 用 `traceaad` 条件。基线是同一主机的 V10.18 与 V10.19（每任务 6 路），server3 上的 V10.17 只作参考。

| 检查 | 量 | 预期 |
| --- | --- | --- |
| Deepen 是否在加深搜索 | Deepen 子代函数耗时相对父代的倍数（`computation.time_ratio_to_start_median`） | 明显高于 Refine，多数任务在数倍以上 |
| 新结构是否进入前列 | 前五名中由 Deepen 及其开发产生的程序；最好程序占时限的比例 | 多数任务中计算型程序进入前列，占时限明显高于基线（1%–11%） |
| 开发是否发生 | `explorations.by_proposal_action` 中 Deepen 的开发数与改善数 | Deepen 与 Explore 的开发改善率相当 |
| 失败 | 训练超时率；held-out 超时 | 训练超时率不明显高于 V10.17；held-out 无超时 |
| 读取时钟的程序 | `computation.clock_programs` | 记录 |
| 最终成绩 | 各任务 held-out | 多数任务不差于基线，计算型程序进入前列的任务更好 |

解释 ACO 任务时注意：OP 同一程序换 ACO 种子，训练成绩的标准差约 1.1%（CVRP 约 0.5%），前沿程序在搜索种子下偏高。需要比较具体程序时，另用多个种子重新评价，这只用于分析；搜索本身的种子不变。

会改变方向的结果：

- **Deepen 子代的耗时仍与父代相近。** 材料仍在把模型引向小修改，要再检查 Deepen 的材料。
- **计算型程序占比上升，但开发后仍长期落后于公式。** 说明在这个模型和这些接口下，加深搜索的实现成本高于收益；再比较哪些任务、哪类规则能从中受益。
- **held-out 出现超时。** 在最终选择时加入最大测试规模下的耗时检查。

## 4. 设计过程中的认识

- 第一版只给 Deepen 一句目标、沿用 Refine 的材料，结果与 Refine 没有区别。去掉形成路径后，同一句目标使计算量升到 12–17 倍。认识是：步骤由材料和目标共同决定，材料的作用更大。
- “加一层搜索，首版就不会比父代差”只对构造任务的 rollout 成立。加深后的程序需要开发，不能按一步的成绩判断。
- 判断一个步骤，不能根据单个任务一步的局部表现。第一版检验中，我一度把 TSP 去掉历史后变差、VRPTW 子代大幅变差当作结论。这些都来自一个父代、一步生成，不足以支持增删机制。
- ACO 训练成绩带有种子噪声。“子代都不如父代”的一部分来自父代在搜索种子下的运气。

## 5. 实现要点

- `traceaad/v10_20/`：搜索类继承 V10.17，`EXPLORING = ("Explore", "Deepen")`。`config.py` 设定份额并拒绝未知步骤。`prompts.py` 改写任务文字、评价段落和耗时表述，`build("Deepen")` 组织 Deepen 自己的材料。
- 共用代码只加钩子：`PromptBuilder.ACTIONS` 声明版本写的步骤；`task_text`、`evaluation_text`、`evaluation_time` 可由版本覆盖；`Search.EXPLORING` 声明哪些提出开启探索（基类为 Explore）；`OPERATORS` 含 Deepen，使它进入经验与尝试列表。用 V10.16–V10.19 已完成运行的记录重建提示，修改前后逐字相同。
- V10.20 继承的 V10.17 运行路径已逐项核对。从 V10.16、V10.17、V10.19 原始日志中各抽 375 条 Refine、Explore、Crossover、Repair 提示，用当前代码在当时的记录上重建，逐字相同。整理时，V10.16/V10.17 对“没有改动的初始程序”的说法曾被统一成 V10.18 的写法，现已恢复为原文 “an initial design”。V10.17 的 3,584 次开发抽签与当前代码一致，1,666 次开发都从已达到的最好版本开始。本机实跑的 V10.17 在中途终止后可以续跑，候选编号连续、不重复。V10.20 实跑 36 步（OP），完成了 Deepen 开启探索、Explore 开发、选择、诊断和 held-out。
- `diagnostics.json`：所有方法增加 `computation`（最好与前五名占时限的比例、各步骤子代相对起点的耗时倍数、超时、读取时钟的程序数）；探索统计增加 `by_proposal_action`。
- 方法测试 `tests/method/test_traceaad_v1020.py`：份额；Deepen 的材料（无形成路径、只列 Deepen 尝试、超长裁剪）；V10.17 不接受 Deepen；Deepen 计入经验、开启探索并按最好版本开发；完整运行与诊断；五个任务的训练与测试文字；评价器行为与更正文字一致。
- 启动清单对全部方法目录计算哈希。固定父代重放与噪声审计的代码保留在 `experiments/diagnosis_v1020_replay/`、`experiments/diagnosis_aco_noise/`。
