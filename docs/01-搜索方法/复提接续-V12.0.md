# 复提接续：让同一计算的实现进展跨提案积累（V12.0）

沿用 V10.17 的基础搜索规则与当前评价协议，现已独立实现，不依赖旧版本代码。运行入口见[实验入口](../../experiments/traceaad_v12_0/README.md)。

**摘要。** LLM 算法设计搜索只能通过某一次实现评价一个想法。一个想法要继续改进，它的程序必须被选为父代。父代选择依据的分数同时包含想法价值与这一次实现的质量，所以首版写差的想法会失去改进机会，而以后对同一想法的提出都从零开始。在我已核对的改变选择、保护多样性或重新采样实现的方法中，实现进展沿谱系内传递。同一想法的实现进展在多次提出之间传递，是本设计的检验对象。V12.0 增加一条按计算继承的路径：模型提出一个计算后，搜索在档案中找到同一计算目前最好的已评价实现，模型在它的基础上实现新提案。父代选择、算子份额与预算分配都不变。我们用三组实验检验三个主张：问题在当前模型下存在，实现进展确实跨提案积累，整场搜索因此受益。

## 1. 研究问题

LLM 算法设计搜索中，模型提出一个计算，再写出实现它的程序，评价器给这份程序一个分数。这个分数同时反映两件事：计算本身的价值，以及这一次实现写得是否正确、计算是否真正进入了决策。

现有搜索中，一个计算要继续改进，只有一条路径：它的程序被选为父代或参考程序。选择依据的是上面的分数。因此：

1. 首版写差的计算得不到改进机会。计算和这份实现一起被淘汰。
2. 同一计算以后再被提出，是一次独立的新实现。前一次实现的进展不会传给它。
3. 搜索偏向一次就能写对的计算，而不一定偏向价值最高的计算。

本文研究的问题是：**不增加新的调度判断，也不改变预算去向，能否让同一计算的实现进展在多次提出之间积累，使一个计算的去留更少取决于它的某一次实现？**

## 2. 现象：同一计算反复从零实现

V10.16/17 中，结构从无到有的每一次引入如下（[首版门槛诊断](../03-现象与检验/2026-10-04-短程改写诊断与首版门槛.md)）：

| 结构 | 引入次数 | 首版落后当时最好 >1% |
| --- | ---: | ---: |
| CVRP：节约法 + 局部搜索 | 127 | 92 |
| TSP：补全路径 + 2-opt | 137 | 104 |
| OBP：跨调用记录物品尺寸 | 69 | 63 |
| VRPTW：模拟补全当前路线 | 38 | 37 |

进入最终程序的结构变化，几乎都来自首版直接胜出的那一次。OBP 第 3 路把记录物品尺寸的想法提出约 50 次，第 885 次的首版才达到 725.75。之前几十次实现各自独立，没有一次从前一次留下的代码出发。

首版落后多由实现造成：代码没有实现所说的计算，或者计算没有进入决策。这类错误可以在下一次实现中修正，但下一次实现看不到上一次的代码。V10.17 的 Explore 只展示当前程序的代码、直接尝试的 Design 与结果，以及全局最好刷新的 Design，从不展示同一计算更早的实现。

强程序的共同点，是函数承担的计算发生了改变：构造解、模拟后续、跨调用记录状态。这些计算恰好最需要细致的实现，也最容易被单次实现的质量过滤掉。

## 3. 现有方法的不足

| 做法 | 代表方法 | 对上述问题的局限 |
| --- | --- | --- |
| 按分数选择父代或灵感程序 | EoH、FunSearch、ReEvo、AlphaEvolve、MCTS-AHD | 每个计算只以某一次实现参与选择；首版差，计算就失去改进机会 |
| 保护多样性或新颖性 | ShinkaEvolve、CDEoH、PartEvo | 让不同计算留在档案中，但不改进它们的实现。ShinkaEvolve 用嵌入与 LLM 判断拒绝相似候选，同时拿走了同一计算的再次实现 |
| 对好的 plan 重新采样代码 | PAEvo R1 | 增加独立实现的次数，每次仍从零开始，实现进展不积累 |
| 用调度规则给新设计开发机会 | TraceAAD V10.18–V10.24 | 需要判断哪份弱程序值得投入，而判断依据仍是同一个单次实现的分数；开发占用预算，实验没有显示跨任务稳定收益（[新设计的开发过程](新设计的开发过程.md)、[改动检验](对原算法的改动检验.md)） |
| 检索搜索经验 | ReEvo 反思、HiFo-Prompt、DeltaEvolve、MEMOIR | 传递文字经验或修改记录，按质量或搜索状态检索，不传递该计算已经评价过的实现 |

这些做法有一个共同根源：计算本身没有跨提案保存的实现状态。它的进展只能附着在被选中的程序上，而生成前就选定的上下文无法针对模型即将提出的计算。

## 4. 方法：按计算继承

### 4.1 核心思想

每个计算有一个实现状态，即档案中实现它、分数最好的已评价程序。模型提出一个计算后，从这个状态出发实现新提案。新实现进入档案；如果它更好，该计算的实现状态向前推进。

这在父代选择之外增加了第二条继承路径。比较同一计算 X 的 k 次提出：

- 原有搜索：X 的最好实现是 k 次独立实现中的最好一个。X 的程序不被选为父代，X 就无法改进。
- 按计算继承：每次实现都从之前最好的实现出发，进展逐次积累。即使 X 的程序从未被选为父代，X 的实现也能改进。

继承由模型的再次提出触发。一个弱计算是否值得再投入，本身是不确定的判断；V10.18–V10.24 把它交给调度规则，没有成功。按计算继承不做这个判断。模型反复提出一个计算，已经表达了继续投入的意愿；机制只决定这次实现从哪里开始。

搜索的目标是：值得投入的，是在当前起点、剩余预算和生成能力下，更可能改善最终最好成绩的机会。按计算继承不判断哪个机会值得投入，也不纠正提出分布。Explore 何时发生、从哪个父代出发、提出什么计算，都与 V10.17 相同。它只改变已提出的计算用什么材料实现。

### 4.2 Explore 的三个步骤

按计算继承需要先知道这次要实现哪个计算，再找到同一计算的已有实现，最后在它上面实现。因此一次 Explore 分为三个模型请求，仍只产生一个候选：

```text
提出（V10.17 Explore 提示，停在代码前）
  → Analysis + Design
匹配（独立请求，不产生候选）
  → 档案中与该 Design 主计算相同的程序
实现（原材料 + 提案 + 最好的匹配程序）
  → 代码，即候选
```

**提出。** 提示与 V10.17 Explore 完全相同。请求带停止序列 `("```", "\nCode:")`，模型写完 Analysis 与 Design 即停止。回复在第一个停止序列处截断，得到提案，再从中取出 Design。

**匹配。** 这一步找出与提案主计算相同的已有程序。

- 候选列表：从档案中取有效程序，排除当前父代（它已作为当前算法完整展示）。Design 文本相同的程序只列一次，保留分数最好的一个。用 DashScope `text-embedding-v4` 计算余弦相似度，取最接近提案 Design 的 20 个。档案中没有其他有效程序时，跳过匹配。
- 请求：温度 0，输出上限 1024 tokens。

  ```text
  Each design below describes an algorithm for the same task.

  [Design A]
  {提案的 Design}

  [Earlier Designs in This Search]
  [{程序编号}] {Design}
  ...

  Which earlier designs are built on the same main computation as Design A?
  End your reply with one line: "Same:" followed by their numbers separated by commas, or "Same: none".
  ```

- 解析：取回复中最后一行 `Same:`，读出属于候选列表的编号。没有这一行，或写 `none`，视为没有匹配。
- 选择：匹配程序中训练分数最好的一个，即该计算的实现状态，作为接续程序；分数相同时取编号小的。

**实现。** 实现请求保留提出提示中 `[Output Format]` 之前的全部材料，然后依次加入：

````text
[Your Proposal]
{提案：Analysis 与 Design}

[An Earlier Program for the Same Computation]
An evaluated program from this search, built on the same main computation as your Design.
{该程序的评价结果}
Design: {该程序的 Design}
```python
{该程序的完整代码}
```

[Your Task: Implement]
Implement your Design in the current algorithm.

[Output Format]
Reply with one Python code block:
Code:
```python
<the complete program>
```
````

没有接续程序时，省去 `[An Earlier Program ...]` 一段，其余相同。提示只陈述事实：该程序已在本次搜索中评价，与提案主计算相同。提示不要求复用、超过或保留它，由模型判断怎样使用。

提示超过输入上限时，先去掉接续程序；仍然超限，再把提出阶段的材料缩为任务说明、当前程序与提案。最小材料仍然超限时，不发送实现请求，保存已完成请求与 token 成本，将该父代记为上下文不可用，搜索转向其他父代；没有其他可用父代时进入最终选择。此时没有生成候选，不消耗候选预算。匹配提示单独超过输入上限时，跳过匹配并记录原因，继续无接续实现。

Design 固定取自提出阶段，代码只从实现回复解析，之后按普通交付规则去重和评价。实现回复额外输出的 Design 不覆盖提案；交付失败或源码无效时也保留原提案。原始请求与回复仍完整保存在调用记录中。

### 4.3 设计选择

每项设计依赖一个不确定的判断。设计原则是：判断越不确定，给它的决定权越小。

| 设计 | 不确定的判断 | 得到的决定权 | 判断错时的代价 |
| --- | --- | --- | --- |
| 嵌入相似度取前 20 | 文字相近不等于计算相同 | 只缩小匹配范围 | 同计算程序排在 20 名外时被漏掉，该次提案按原方式实现 |
| 由模型判断“主计算相同” | 模型可能把相近当相同 | 只决定展示哪一份代码；不改变预算、父代与算子 | 展示无关代码，可能把实现拉向它 |
| 取匹配程序中分数最好的 | 整份程序的分数不完全代表该计算的实现质量 | 决定展示哪一份 | 展示的程序可能靠别的部分得分 |
| 完整代码，只陈述事实 | 模型会恰当取用 | 由模型决定继承多少 | 模型可能整份复制，产生重复候选，计入预算 |

两项实现细节有明确理由。匹配与实现分成独立请求：匹配只依据 Design，实现请求不含匹配推理，材料与原 Explore 一致。匹配回复以最后一行 `Same:` 作答：模型先逐条推理、最后才给编号，冒烟检查中只读第一行的解析漏掉了全部回答。

### 4.4 保持不变的部分

- 父代选择：质量 × 尝试经验，\(w_i=\exp[-\beta(f_i-f_{\min})]\frac{k_i+3r}{n_i+3}\)。
- 算子份额：Refine 45%、Explore 30%、Crossover 25%；Refine、Crossover、Repair 的提示与生成不变。
- 续写：新有效 Explore 程序以 1/8 概率获得至多 3 次 Refine。
- 初始化、去重、失败修复、档案与预算计数。
- 评价：当前协议（平均函数 CPU 预算、原始目标值，revision `research-protocol-v6-20261012-raw-objective`）；提示只交代问题、接口与分数。

### 4.5 预算与成本

预算按候选计数，每次 Explore 仍计一个候选。提出与匹配请求不产生候选，作为模型请求记录，token 计入总消耗。每次 Explore 的模型请求从 1 次变为 2–3 次。冒烟检查中，每次 Explore 平均为：提出 1305 入／145 出，匹配 307 入／182 出，实现 1725 入／746 出。

## 5. 作用范围与风险

按计算继承是一项局部干预：父代选择、算子份额与续写规则都不变。但它产生的新程序进入档案，会改变之后的父代选择、参考程序和全局刷新，效果会传到整场搜索。效果可能是改善，也可能是损害：多次提出被拉向同一份实现，会减少独立实现带来的变化；错误匹配会把实现拉偏。因此需要用完整搜索的成绩判断，而不只看 token 成本。

## 6. 检验

三个主张分别对应以下实验。三组共用同一实现，只差配置：基础组 `BaseConfig`（关闭接续，即 V10.17 Explore），接续组 `Config`（总是展示），诊断组 `DisplayConfig`（以 0.5 概率展示）。条件为 DeepSeek `deepseek-v4.1-flash`，六任务各三路，1000 候选。

**主张一：问题在当前模型下存在（E0）。** 先运行基础组，它同时是 E1 的对照。在其档案上离线重放匹配：对每次 Explore 提案，只用提案之前已评价的程序，统计三项：

- 可接续比例：有同计算已有实现的提案占多少；
- 已有实现是否走得更远：接续程序是否好于该提案自己的首版；
- 代码抽查：匹配程序是否真的实现了提案所说的计算。

如果可接续比例很低，或已有实现很少好于新首版，那么在当前模型下，重复从零实现不构成主要损失，不再运行 E1。E0 可以在运行前缀上开始。

**主张二：实现进展跨提案积累（E1 过程检查与随机展示诊断）。** 主要指标是：可接续的提案中，新实现超过同计算已有最好实现的比例。每次超过，该计算的实现状态就向前推进一步。

- 接续组的这一比例与基础组重放中的同一比例比较。后者是独立实现超过已有最好实现的比例。
- 诊断组在同一搜索中随机决定是否展示接续程序。展示与不展示两部分的差别，是展示已有实现对新实现的即时因果作用。接续组与基础组日志中的分组只是观察对照，不是因果对照。
- 同时报告整份复制接续程序的比例，包含 Repair 后复制的情况。重复有效程序按其已知训练成绩比较，不当成无效首版；复制接续程序是同分，不是已有实现更好。高复制率说明继承没有带来新的进展。

**主张三：整场搜索受益（E1）。** 接续组与基础组各六任务三路，报告各任务三路测试成绩的均值与 token 消耗。最终程序中出现了多少强计算类，不作为检查项。

**归因。** 只在 E1 显示收益时进行。用 `display_probability=0` 运行：保留三个步骤与匹配请求，但从不展示接续程序。它区分收益来自提出与实现分开，还是来自继承已有实现。

## 7. 实现与记录

**随机展示。** `display_probability` 控制找到接续程序后是否展示。每个候选编号有一个固定抽签 `random.Random(f"v12.0:{seed}:display:{attempt_id}")`，小于该概率才展示，断点恢复后抽签不变。不展示时，匹配结果照常记录。

**记录。** 每次 Explore 尝试增加 `link`：

| 字段 | 内容 |
| --- | --- |
| `design` | 用于匹配的 Design |
| `candidates`、`similarities` | 候选列表及余弦相似度 |
| `matched` | 模型判断主计算相同的程序 |
| `linked_id` | 接续程序 |
| `display_draw`、`shown` | 展示抽签与是否实际展示 |
| `trims` | 实现请求的裁剪 |
| `error` | 嵌入服务失败时的错误；该次提案不接续 |

`calls.jsonl` 中每次请求带 `stage`：`propose`、`match`、`implement`。尝试的 `call_ids` 包含这三次请求。恢复时核对配置、任务、评价协议与嵌入设置，不另设机制版本标签。
