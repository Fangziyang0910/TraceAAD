# 新设计的开发过程

2026-10-04。每个由 Explore 提出、首版落后的新设计，都先得到开发，直到它显示出能否成立，再与已有程序竞争。实现标识为 V10.18，代码位于 `traceaad/v10_18/`，入口为 `experiments/traceaad_v10_18/`。程序选择、尝试记录、形成路径和 Refine/Crossover/Explore 的目标句与 [V10.17](提出后的短程改写.md) 相同。

## 0. 要解决的问题

**一个新设计的价值，不能只由它的第一份实现判断。**

[V10.17 的诊断](../03-现象与检验/2026-10-04-短程改写诊断与首版门槛.md)显示：进入最终程序的结构变化，几乎都是首版直接胜过当时最好的那一次；首版落后 1% 以上的结构引入，平均得不到一次后续尝试。模型反复提出构造可行路线、模拟后续、记录物品分布等计算，搜索却只接受碰巧一次写好的那一份。各路成败因此依赖首版的偶然性。

## 1. 认识：两种工作，两种判断标准

算法专家改进算法时做两种工作，判断标准不同：

| 工作 | 要回答的问题 | 判断标准 |
| --- | --- | --- |
| 精炼已有算法 | 这一步能否让它更好 | 与它自己比较；投入随实际产出变化（V10.16 的经验项） |
| 开发新设计 | 这个计算能否成立 | 先让代码实现所说的计算，并让结果进入决策；看开发是否持续推进；成立后再与最好的算法比较 |

V10.15-6 让精炼有了连续的来源（形成路径），V10.16 让精炼的投入跟随产出，V10.17 承认首版低估设计价值。V10.18 把 V10.16 “投入随产出”的逻辑从程序扩展到设计：一次 Explore 提出开启一个开发过程，代码在开发中改变，开发记录随这个设计累积。

## 2. 规则

### 2.1 每个新设计开启一次探索

Explore 产生新的有效程序（包括修复后有效）时，开启一次探索。提出没有产生新程序（重复、修复失败）时，探索立即结束。

### 2.2 开发持续到设计显示出能否成立

每一步从本次探索已达到的最好版本出发，动作为 Develop，照常计入预算，失败照常修复。

| 条件 | 结果 | 理由 |
| --- | --- | --- |
| 最好版本进入全搜索训练分前 5 名 | 结束（competitive），普通选择接手 | 前 5 名就是最终选择的候选集，质量权重已足以让它得到持续精炼 |
| 已开发不足 2 步 | 继续 | 首版常缺约束或计算未生效，至少给一次修正和一次确认的机会（CVRP 33→34 一步修正） |
| 连续 2 步没有产生更好的版本 | 结束（stalled） | 开发已不再推进 |
| 已开发 8 步 | 结束（cap） | 初步开发负责让设计成立；成熟后的长期精炼由程序池承担 |
| 预算用完 / 上下文超限 | 结束（budget / context） | — |

首版已在前 5 名时不开发，直接参与普通竞争：这类首版本来就能得到持续精炼（V10.17 CVRP 第 1 路的 Explore 870）。

`(k + s·r)/(n + s)` 是采样权重，不会自然停止，所以开发长短用上面的显式条件决定，不用经验项代替。

### 2.3 开发与新提出共用 Explore 的份额

算子抽样为 Refine 0.35、Explore 0.40、Crossover 0.25。抽到 Explore 时：

- 有正在开发的探索：执行它的下一步 Develop；
- 没有：选择父代，提出新设计。

同一时刻只有一个探索在开发。开发未完成时不提出新设计，提出速度因此受开发能力约束，不会积压“等待开发”的设计。Refine 与 Crossover 不受影响，照常按 V10.16 的规则选择父代。

预期占用：若平均每个设计开发约 3 步，约 990 次搜索生成中，Explore 份额约 396 次，对应约 100 次提出与约 300 次开发；V10.17 约为 250 次提出与约 100 次改写。减少的是重复的冷启动提出：V10.16 第 3 路把同一个“记录物品尺寸”的想法从头提出了约 50 次。持续精炼（Refine + Develop）合计约占 65%，高于 V10.17 的约 55%。

### 2.4 Develop 的上下文与目标

上下文以这个设计为主体：

| 区块 | 内容 |
| --- | --- |
| Current Algorithm | 本次探索已达到的最好版本，附分数、耗时与调用量 |
| Where the Proposed Design Came From | 一句事实：Explore 从哪个分数的算法（附它的 Design）提出了这个设计；本搜索当前最好分数 |
| How the Proposed Design Has Been Developed | 从首版开始的形成路径（失败的首版折入修复步骤），每步给 Design、分数与 diff；不展示出发前程序的代码与 diff |
| Other Development Attempts on This Design | 本次探索中没有进入上述路径的开发尝试及结果，无论从哪个版本出发 |

目标句：

> Develop the proposed design further: make the computation it introduces work as intended and write a version that scores better than its current version. Every version and attempt shown above has already been evaluated.

Analysis 要求说明：代码是否计算了设计所说的内容，这个计算怎样进入决策，是什么让设计得分不够高，以及修正实现或修正估计对象的哪项改动能解决它。

这样设计的理由：

- **不展示出发前程序的 diff**：V10.17 中，开发第一步有 27.7% 明确写着恢复旧程序，69% 的探索最后更接近旧程序。上下文持续提供高分旧程序的代码时，恢复它就是最容易的改进。来源程序只作为一句事实保留，模型仍可借用旧部件支持新计算。
- **“让所提出的计算按意图工作”**：直接对应诊断中的三类首版缺陷——代码没实现所述计算、计算没进入决策、估计对象不合适。允许修正估计对象，使开发延续的是“这个设计要解决的计算问题”，而不是首版 Design 的每一句话。
- **列出本设计的全部开发尝试**：经验跟随设计累积。程序池中，每个新版本的尝试计数从零开始；而在开发中，下一步能看到这个设计上已经试过什么、结果怎样。

### 2.5 不改变的部分

- 程序选择：`exp(−β(q − q_min)) × (k + 3r)/(n + 3)`；Develop 尝试照常计入出发程序的经验。
- Refine、Crossover、Explore 的上下文与目标句同 V10.17；Refine 的尝试列表也会列出从该程序出发的 Develop 尝试。
- 不在提示中展示过去的想法列表，不加入任务专用信息。任务接口事实（ACO 按行归一化、VRPTW 隐藏的服务时间）会改变任务描述与比较条件，作为单独决定。
- 初始化、修复、最终选择与替补、评价协议与时限不变。

## 3. 检验

完整搜索，5 个任务 × 3 路，种子 0–2，两路 Qwen 服务交替。搜索与评价在本机运行，模型在 server3 上提供。本机评价比 server3 快 2.5–3.3 倍，同一墙钟时限下程序可用的计算更多，因此与 V10.15-6/16/17（server3）的比较带有主机差异，TSP 这类接近时限的任务受影响最大。

看过程，判断机制是否按设计工作（`diagnostics.json` 的 `explorations`）：

| 过程 | 看什么 |
| --- | --- |
| 落后的新设计是否得到开发 | `developed`、`development_steps_mean`、结束原因分布 |
| 开发是否让设计成立 | 首版到最好版本的增益；`competitive_after_development`；开发后最好版本与来源程序的代码相似度变化（应不再系统性回到来源） |
| 预算怎样分配 | `proposal_share_of_search_generations`、`development_share_of_search_generations` |
| 开发出的设计能否进入最终候选 | `top_programs_from_development`；沿代码检查决定性结构（构造可行路线、模拟后续、跨调用记录）是否更稳定地出现在最终程序中 |

再看结果：各任务逐路差距是否缩小，弱路次是否改善，held-out 是否保持。

**会改变方向的结果：**

- 开发很少让落后设计进入前 5 名，且常在 2 步后 stalled：模型仅凭代码与总分难以诊断首版缺陷，下一步补行为证据或接口事实。
- 开发后的设计多数仍回到来源程序：检查上下文中哪项材料仍在引导恢复。
- 提出太少导致结构覆盖下降（OP、VRPTW 等依赖广泛入口的任务变差）：调整 Explore 份额或开发上限。
