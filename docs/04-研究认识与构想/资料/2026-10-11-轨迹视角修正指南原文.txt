# TraceAAD：回到轨迹视角的问题清单与修正指南

核心判断：TraceAAD 应继续以 Search Trajectory（搜索轨迹）为研究中心，而不是把轨迹缩减成代码差异、实验反馈、错误证据或计算积累。

你最初的 idea 有一个值得保留的核心：

> 一次算法搜索不仅产生候选算法，还产生了关于如何设计和改进算法的过程经验。我们希望让 LLM 利用这些轨迹经验，改善后续搜索决策，从而更高效地发现优秀算法。

这里的“轨迹”既包含成功，也包含失败；既包含一条程序的形成路径，也包含整个搜索的探索过程。

它可能帮助模型决定下一步修改什么、选择什么起点、借鉴哪条路线、何时继续投入以及何时转向。不应该预先规定轨迹只能用于某一种决策，也不应该把某个版本的实现当作轨迹的最终定义。

## 一、最新仓库的情况

我重新读取了 GitHub `main` 分支。截至本次检查，最新提交为 `cfe0379`，提交时间是 2026 年 10 月 11 日 17:20（日本时间），提交说明为 `docs: restore trajectory-feedback research focus and correct historical claims`。

这很关键：最新仓库已经开始回归原始轨迹方向。

新的 `README.md`、`AGENTS.md` 和《研究主线与问题》已经撤下“必须通过真实代码 diff 和计算继承实现贡献”的预设，并把研究目标改回：

> 利用自动算法设计搜索中获得的轨迹与反馈经验，改善后续决策，提高有限预算下发现和改进优质算法的效率。

这是正确的调整。不过，恢复研究目标和真正恢复轨迹视角不是同一件事。现在还需要检查历史资料怎样组织、什么内容被反复强调、哪些局部结论容易重新限制我们的思考。

## 二、最大的剩余问题：轨迹被研究成了几种零散的“历史材料”

我重新读了当前版本的搜索实现，以及 V1–V10.25 的方法整理后，认为现在最需要纠正的是三个倾向。

第一，把轨迹缩小成当前程序的形成路径。第二，把利用轨迹缩小成在 Prompt 中展示历史。第三，把轨迹的价值缩小成某种局部代码改动是否成功。

这些事情都属于 TraceAAD，但都不能代表完整的轨迹思想。

从最初的研究视角看，轨迹至少有三个层次。

1\. 搜索时间线（Search History）

整场搜索按时间发生了什么：尝试、改进、失败、停滞、转向、预算投入与最好成绩变化。

2\. 算法演化路径（Evolution Path）

某个程序从哪里来，经历了哪些修改，哪些路线持续发展，以及不同程序之间有哪些来源或参考关系。

3\. 探索与竞争过程（Search Dynamics）

搜索把机会给了哪些程序或路线，为什么继续或停止，已经探索了哪些区域，还有哪些方向没有获得充分尝试。

这三个层次不是要求实现三个模块，而是重新认识“轨迹”这个研究对象。

例如，V10.17 的代码确实保存了程序、生成尝试、失败与修复、探索记录等事件。但它在生成时主要提供所选父代的短形成历史、直接尝试，以及部分全局最好进展。父代选择器主要使用质量和直接改善次数。

也就是说，搜索保存下来的轨迹，比实际用于决策的轨迹丰富得多。

这不是已经证明的性能问题，但它是最初轨迹 idea 下值得重新注意的设计空间。以前我们过于专注某一段历史怎样写进 Prompt，而没有持续区分“搜索经历了什么”和“系统实际上利用了什么”。

对应代码：[history.py](https://github.com/Fangziyang0910/TraceAAD/blob/main/traceaad/common/history.py)、[prompts.py](https://github.com/Fangziyang0910/TraceAAD/blob/main/traceaad/common/prompts.py)、[selection.py](https://github.com/Fangziyang0910/TraceAAD/blob/main/traceaad/common/selection.py)。

## 三、问题清单：从原始轨迹视角看，目前仍有哪些偏差？

以下是新的视角审查，不是重复上一轮已经修正的 26 项数值、归因和文档错误。

| 优先级 | 问题                   | 应怎样修正认识                                                         |
| --- | -------------------- | --------------------------------------------------------------- |
| P0  | 01. 轨迹被等同于父代形成链      | 形成链只是一个视图。整场搜索还包含其他分支、未被采用的尝试，以及路线之间的关系。                        |
| P0  | 02. 成功路线被用来代表搜索过程    | 最终最好程序的形成路径可以解释结果怎样产生，但不能单独说明搜索为什么有效。失败和停滞路线同样属于轨迹。             |
| P0  | 03. 搜索过程被压缩成静态历史材料   | 轨迹不仅包含发生过什么，还包含先后顺序、投入变化及后续响应。简单的记录列表不等于充分利用了过程关系。              |
| P0  | 04. 利用轨迹被缩小成指导代码生成   | 轨迹也可能影响搜索起点、算子、参考、续投、停止和转向。上下文生成是重要入口，不是全部用途。                   |
| P0  | 05. 轨迹价值被绑定到局部改善率    | 某次改写是否超过父代，不等于这段探索对整场搜索的价值。研究目标仍是有限预算下发现更好的算法。                  |
| P1  | 06. 算法谱系被当成思想谱系      | 同一个根可能产生多种计算方法，不同根也可能反复提出同类算法。程序来源不自动定义思想类别。                    |
| P1  | 07. 探索被等同于结构性重写      | 调参、修复、重用、组合和重新设计，都可能是合理的轨迹后续动作。不能事先规定哪种修改更有价值。                  |
| P1  | 08. 搜索经验被压缩为成功/失败计数  | 成功次数可以是实用的统计量，但它丢失了改动顺序、投入条件、变化幅度和路线之间的联系。                      |
| P1  | 09. 从几个历史展示实验推导轨迹价值  | 某种历史列表无效，只说明该种用法没有改善所测结果。不能代替对轨迹整体用途的判断。                        |
| P1  | 10. 模型行为诊断逐渐取代研究问题   | 模型回退、写错代码、忽视提示等，首先是具体运行现象。应把它们放回搜索轨迹中，理解其后果，而不是每次都把研究主线改成修复该现象。 |
| P1  | 11. 版本迭代被组织成单向认识进步   | V10.24 比 V10.17 更新，不意味着它对轨迹的理解更全面；复杂机制也不一定比简单机制更接近研究目标。         |
| P2  | 12. 相关工作与研究记录按技术模块分散 | 生成上下文、搜索路径、预算分配和经验记忆被分开讨论，容易看不见它们其实在回答同一个轨迹使用问题。                |

我认为最需要优先处理的是 01–05。它们影响你理解自己究竟在研究什么。其余问题主要影响后续解释和资料组织。

## 四、哪些历史内容应该从轨迹视角重新找回来？

这次有一个值得特别强调的发现：你并不是在后期才开始研究轨迹，反而是后期的诊断逐渐遮住了早期更完整的设想。

你的旧方法文档保留了下面这些方向。

| 阶段            | 当时关注的轨迹问题                    | 现在应该怎样看                       |
| ------------- | ---------------------------- | ----------------------------- |
| V1–V9.6       | 不同路线怎样竞争、如何回传后代结果、怎样安排多步开发   | 轨迹不仅用于生成，还能描述整场搜索的机会分配        |
| V9.7–V9.8     | 形成历史怎样影响局部生成，新探索如何获得初始机会     | 轨迹可以支持连续改进，但不必限于连续改进          |
| V9.9–V9.12    | 延迟收益、访问次数、近期失败与算子选择          | 轨迹可能提供搜索策略随时间调整的依据            |
| V9.14–V9.20   | 演化深度、阶段开发、行为距离、路径覆盖          | 轨迹中的路线发展和搜索覆盖是不同维度            |
| V9.21–V9.22   | Continue/Branch、稳定起点、不同动作的响应 | 轨迹可以用于决定沿已有路线走，还是产生新的路线       |
| V10.15–V10.25 | 真实形成历史、尝试反馈、有限续写、问题级开发       | 轨迹的表示与使用被实现得更具体，也出现了局部优化过度的问题 |

来源主要是 [《形成历史与生成上下文》](https://github.com/Fangziyang0910/TraceAAD/blob/main/docs/01-%E6%90%9C%E7%B4%A2%E6%96%B9%E6%B3%95/%E5%BD%A2%E6%88%90%E5%8E%86%E5%8F%B2%E4%B8%8E%E7%94%9F%E6%88%90%E4%B8%8A%E4%B8%8B%E6%96%87.md) 和 [《生成后的继续改写》](https://github.com/Fangziyang0910/TraceAAD/blob/main/docs/01-%E6%90%9C%E7%B4%A2%E6%96%B9%E6%B3%95/%E7%94%9F%E6%88%90%E5%90%8E%E7%9A%84%E7%BB%A7%E7%BB%AD%E6%94%B9%E5%86%99.md)。

这里不需要重新相信那些旧机制，也不需要回到复杂的路线调度。

需要恢复的是当时提出的问题：

搜索为什么不断沿某些路线发展？已经走过的路线能否帮助选择下一步？哪些探索经历值得影响其他路线？过去的尝试怎样改变整个搜索过程？

这几类问题与你最初的轨迹直觉更接近。

另一方面，我也不建议重新把“路线”“分支”“潜力”都做成专门的数据库对象。它们首先是分析轨迹的角度。等到某个问题需要明确的数据表示时，再决定如何建模。

在方法和实验文档中，我建议以后统一回答四个简单问题：

- 这是什么轨迹？ 形成路径、局部尝试、分支竞争，还是全局搜索时间线？
- 它被谁使用？ LLM 生成器、父代选择器，还是其他搜索决策组件？
- 它改变了什么决定？ 是修改内容、起点、参考、继续投入，还是停止？
- 最终产生了什么结果？ 观察范围内的收益、成本和失败是什么？

这些是记录与分类问题，不是要求所有实验都覆盖四种决策。

### 一个很重要的具体修正：区分“保存的轨迹”和“使用的轨迹”

我建议在研究索引里明确区分：

| 层次       | 当前实现中的例子                       | 作用            |
| -------- | ------------------------------ | ------------- |
| 搜索中发生的轨迹 | `events.jsonl` 中的程序、尝试、修复与探索事件 | 整场搜索的记录       |
| 选出来的轨迹视图 | 最多 8 步形成历史、当前程序的尝试、全局进展、参考程序历史 | 部分搜索过程被展示给模型  |
| 轨迹影响的决定  | LLM 修改代码；选择器根据质量与尝试经验调整父代概率    | 搜索实际使用这些信息的方式 |

这样以后就不会因为“我们保存了完整轨迹”，便误以为“我们利用了完整轨迹”；也不会因为“8 步形成历史没有提高成绩”，就否定轨迹的其他可能用途。

## 六、以后应该怎样叙述 TraceAAD？

这里建议使用一种轨迹中心、问题开放的叙述，而不是先为某套机制设计动机。

建议保留的研究叙述

传统的候选评价告诉搜索系统一个算法当前有多好，但一次搜索还包含丰富的探索过程。模型尝试过不同方法，部分得到改进，部分失败；有些路线持续发展，有些被放弃，有些计算在不同程序之间得到复用。

TraceAAD 研究如何利用这些搜索轨迹，使 LLM 的后续算法设计不只依赖当前候选，还能参考搜索已经走过的路线，从而更有效地决定下一步怎样探索和改进。

轨迹中哪些信息最有价值、应怎样组织、用于哪些决策，以及在什么条件下产生实际收益，是研究需要回答的问题。

这段话没有预设：

- 轨迹必须使用真实 diff。
- 轨迹必须转成文字反思。
- 轨迹必须构建知识种群。
- 轨迹必须预测未来潜力。
- 轨迹必须通过保留某一种计算结构发挥价值。

因此，它允许后续研究根据实际效果自然收敛，而不是现在就选定一种技术路线。

## 七、建议按什么顺序完成这轮整理？

1

先固定“轨迹”的研究含义

把搜索轨迹理解为多轮算法设计的过程，包括时间、程序来源、尝试、分支与搜索选择。明确区分搜索轨迹与 LLM 单次生成中的推理文本。暂不规定统一的数据结构。

2

重新整理历史版本，但不评选最终方法

对每个主要阶段记录：尝试使用什么轨迹、指导什么搜索决定、观察到了什么。将“机制表现较弱”和“这个轨迹方向没有价值”分开。

3

调整文档默认入口

让 `docs/README.md` 首先呈现轨迹的几个研究视角。旧诊断继续作为按需查询的材料，不再自动把对话引向具体代码问题、复杂调度或某个版本。

4

最后再重新审视机制与实验

等研究对象清楚后，再确定哪类轨迹最值得利用、哪种决定最值得改善。现阶段不新加机制，不通过另一个版本来寻找主线。

## 最终建议

上一轮文档清理解决了“历史判断不够客观”的问题。这一轮应该解决“研究视角被局部机制牵着走”的问题。

两者不同。即使每一项局部分析都准确，如果文档长期只强调代码差异、形成路径、修复和开发，它仍可能让我们误以为 TraceAAD 就是研究这些东西。

我认为目前最应恢复的认识是：

TraceAAD 最初关心的，是如何让算法搜索利用自己走过的路。

搜索轨迹不仅说明最终算法怎样产生，也记录了探索如何展开、机会如何分配、不同路线如何发展。轨迹可能帮助生成，也可能帮助决定在哪里继续搜索。

我们现在不需要证明上述每一种用途都有效，更不需要把它们全部做进系统。只需要先保留这个完整的研究空间，让未来的实验决定哪一部分真正值得深入。

此次我只进行了最新仓库的定向复核，没有修改仓库文件、运行实验或重新定义最终论文机制。
