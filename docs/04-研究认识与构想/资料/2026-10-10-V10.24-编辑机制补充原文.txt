**是的，我认为 edit 是值得优先推进的方向，而且我会据此调整前面 V10.24 的设计：对已有程序的改进，默认采用结构完整的 edit；把后续编辑接入连续开发过程；根据实际需要保留完整代码输出。**

我前面把完整代码输出保留下来，对这一层的重要性考虑得不够。**模型怎样表达和执行一次算法改进，本身就会影响搜索能提出什么、能正确实现什么，以及已经取得的进展能否积累下来。**

你提到的三个收益——成功率、推理能力、效率——都有成立的机制。不过，它们分别来自不同地方，需要一起设计：

- **edit 的直接价值**：明确表达变化，让系统精确保留其余代码，减少重复生成。
- **多轮编辑的价值**：让模型以已经落地的程序为工作状态，继续思考、修正和发展。
- **执行反馈的价值**：让下一轮利用上一轮尚不知道的信息，调整算法设计。
- **效率的关键**：把这些收益组织成尽量少的、有实质作用的模型调用。

下面展开说。

## 一、edit 改变了算法改进的表示方式，也改变了搜索倾向

目前 V10.23 的输出提示确实要求 Analysis、Design 和完整程序，与你的描述一致。[当前输出提示](https://github.com/Fangziyang0910/TraceAAD/blob/af15d5ac4ee7bdc27d49b41d7c433557c574dac3/traceaad/v10_23/prompts.py)

省略分析文字，仅看代码交付，两种方式可以写成：

**完整代码生成：**

\[
h' \sim p_\theta^{\mathrm{full}}(\,\cdot\mid h,C)
\]

**编辑生成：**

\[
\Delta \sim p_\theta^{\mathrm{edit}}(\,\cdot\mid h,C),
\qquad
h'=\operatorname{Apply}(h,\Delta)
\]

其中，\(h\) 是当前程序，\(C\) 是任务、历史和反馈，\(\Delta\) 是本次修改。

这里最有意义的变化是：

> **没有被指定修改的代码，由程序确定性地保留下来。模型承担的任务集中在“本次变化是什么、怎样实现”。**

这对 TraceAAD 有三项直接意义。

### 1. 已经形成的有效实现，更容易被继承

假设当前算法已经有一套不错的路线构造、可行性检查和局部搜索，本次只想改候选选择机制。

完整输出要求模型在生成新选择机制的同时，再次输出其余实现。即使提示说“保留其他部分”，那些部分仍然经过了一次模型生成。

采用 edit 后，范围之外的源码会原样保留。这减少了一类风险：**本轮有价值的改动实现了，但已经成熟的细节在其他位置被顺带改坏或简化了。**

这与你原先提出的“没有针对算法思想逐步精炼得到好的地方”直接相关。逐步精炼要求系统能够稳定积累有效变化。edit 为这种积累提供了更可靠的执行基础。

当然，保留源码不等于保留全部行为：改一个共享函数也会影响其他部分。模型主动决定删除一个机制时，edit 也会执行删除。因此，改进方向和上下文仍然需要设计好。

### 2. “本次改动”成为明确的对象

完整代码也可以事后计算 diff，但模型生成时承担的是交付整个结果。

edit 则让分析与实际修改更容易对应：

- 想改变哪种求解行为？
- 为实现它，需要修改哪些位置？
- 哪些联动修改必须一起完成？
- 实际提交的编辑是否落实了这些变化？

这也让 Trace 更有用。可以把**改进意图、实际修改、评价反馈**对应起来，后续模型更容易看清一次尝试究竟做了什么。

但这里仍应以实际应用后的代码和 diff 为准，Design 是模型对实现的说明。

### 3. 它会改变模型提出改动的分布

即使 edit 和完整输出最终都能表达同一份程序，模型生成它们时的难度、注意力分配和习惯也不同。于是，最终采样到的程序分布也可能不同。

这已经有直接的 AAD 观察。EvoTrace 在同一任务和同一模型的一组比较中发现：使用 diff 时，“改变数值后重新引入旧代码”的行占比为 20%，关闭 diff 时为 2%。这个指标描述的是修改构成，说明输出表示确实会影响搜索倾向。[arxiv.org](https://arxiv.org/html/2605.20086v1?utm_source=chatgpt.com)

因此，我赞成 edit，同时会明确规定：

> **编辑的单位应当是一项完整的算法改动，粒度由实现依赖决定。**

一项改动可以只涉及一行，也可以同时修改几个函数。不能把“改得少”当作目标，否则很容易进一步强化你担心的局部调参和短视开发。

例如，将采样权重从 \(w_i\) 改为 \(w_i^\alpha\)，可能只改一行，却改变整个采样分布；反过来，重写几十行循环，也可能只是保持原算法行为的向量化。

**代码改动范围与算法变化范围，是两个不同维度。** 搜索是否贪心，主要取决于怎样选方向、怎样接受结果、怎样继续开发，不能用输出了几行代码来判断。

## 二、你记得的那类论文确实存在，但最有价值的结论是“怎样 edit”

### 1. 最直接的格式研究：*To Diff or Not to Diff?*

这项工作分别用不同输出格式微调同一基础模型。Qwen2.5-Coder-7B 的多项评测平均 pass@1 如下：

| 输出方式 | 平均 pass@1 |
|---|---:|
| 完整代码 FullCode | 57.07% |
| 内容定位的 ContentDiff | 54.43% |
| 函数结构完整的 FuncDiff | 57.32% |
| AdaEdit＋FuncDiff | 57.95% |

在一个 80 例的较长代码子集中，AdaEdit＋FuncDiff 将平均输出从约 648 降到 482 tokens，pass@1 为 39.75%→40.69%。其主要正结果来自专门微调；效率指标主要按输出 token 衡量，不能直接换算为 TraceAAD 的总耗时收益。[arxiv.org](https://arxiv.org/html/2604.27296v1?utm_source=chatgpt.com)

对我们的启发是：**保留计算块或函数的结构完整性、提供可靠定位，有机会同时改善交付质量和输出效率。** 当前模型对具体格式的熟练程度，也要纳入选择。

### 2. 关于“输出过程能否改善能力”：LintSeq 更接近这个问题

ICLR 2025 的 *Training Language Models on Synthetic Edit Sequences Improves Code Synthesis*，把程序重构成有结构的编辑序列来训练模型。与完整代码训练相比，编辑序列训练在多项代码基准上保持或改善了生成质量，并改善了 pass@k 随测试计算量增长的表现。[proceedings.iclr.cc](https://proceedings.iclr.cc/paper_files/paper/2025/file/e43f900f571de6c96a70d5724a0fb565-Paper-Conference.pdf?utm_source=chatgpt.com)

它支持你更深一层的判断：**程序生成过程怎样分解，会影响模型能够实现的能力。**

还有一个很有意思的细节：该工作推理时生成连续的 edit 序列，再依次应用，并不在每个 edit 之间调用评价器获取反馈。这说明“编辑式生成”和“交互式 agent”可以分别产生作用。[proceedings.iclr.cc](https://proceedings.iclr.cc/paper_files/paper/2025/file/e43f900f571de6c96a70d5724a0fb565-Paper-Conference.pdf?utm_source=chatgpt.com)

### 3. 在自动算法设计系统中，edit 已经是实际采用的方式

AlphaEvolve 使用 SEARCH/REPLACE 块，同时允许短代码或适合整体重写的情况输出完整代码。ShinkaEvolve 也同时支持 diff、完整重写和交叉组合。它们提供了可用的设计参考，但没有给出足以单独证明“diff 总是优于 full”的格式对照。[arxiv.org](https://arxiv.org/html/2506.13131v1?utm_source=chatgpt.com)

我从这些工作中提取的原则是：**让交付表示适应这次算法变化，而不是把所有变化压进一种固定粒度。**

## 三、关于“多轮 edit 能否提高推理能力”，我认为可以从两个层面理解

### 第一层：单次 edit 改善推理的利用方式

在完整代码输出下，一次改进通常混合了两种工作：

1. 判断算法应怎样变化；
2. 重新交付整份实现。

edit 将更多生成工作集中到变化本身。对已经有明确基底的精炼、修复、部件移植，这种任务组织更自然。

不过，输出 token 省下来，并不会自动变成更多推理。如果模型配置、分析长度和调用次数都没变，不能直接说它“想得更多了”。

更准确的说法是：

> **相同模型有机会把计算更有效地用在算法变化上，减少重复交付对这次改进的干扰。**

### 第二层：多轮 edit 让程序成为可继续修改的外部工作状态

这层更接近你所说的“提高推理能力”。

模型先把一个设计落地，再面对真实的当前程序继续推理，可以：

- 发现上一轮遗漏的依赖；
- 重新组织已经写出的计算；
- 根据执行结果调整实现；
- 根据算法成绩判断下一步怎样发展。

即使没有运行反馈，重新审视落地代码，也可能发现一次生成时遗漏的问题。多轮确实提供了额外的思考和修正机会。完整代码重写也能完成这种过程，edit 则有机会降低每次修正的交付成本。

**但不同的多轮，价值差异很大。**

| 过程 | 后一轮主要获得什么 | 主要作用 |
|---|---|---|
| 一次输出多个关联 edit | 同一计划中的全部修改 | 完成一致的算法变化 |
| edit 后接匹配、语法、接口反馈 | 明确的交付错误 | 提高实现成功率 |
| edit 后重新检查当前程序 | 已落地的程序状态 | 发现遗漏、继续组织实现 |
| edit 后接算法评价反馈 | 实际运行表现 | 改变后续算法设计 |

你之前的 agent 前几轮就生成了不错结果，我会把它当作值得追踪的正信号。最值得看的是：**好结果是在第一次编辑后就出现，还是在看到错误、运行结果、成绩之后出现？**

这能帮助我们判断，主要收益究竟来自改进表示、持续思考，还是基于反馈的开发。

## 四、旧记录已经揭示了一个关键效率问题：短输出可能被多次往返抵消

我查到了一组相关历史：**V10.13-r2 曾实现 full/edit 与有限上下文读取**。它还没有与您回忆的那个可反复调用工具的 agent 完全对应上，但记录很有参考价值。

其中，188 个有效 edit 开发候选里，50 个超过父代，15 个超过当时前沿。由于当时 edit/full 是模型自行选择，这些数量不能直接用于判断两种格式孰优；它们确实说明项目已有通过 edit 继续改好算法的实际案例。[V10.13-r2 早期运行诊断](https://github.com/Fangziyang0910/TraceAAD/blob/036b055afb8c6ae67ba98ed69fa490f5c73b5e6e/docs/02-实验结果/2026-09-24-V10.13-r2早期运行诊断.md)

更值得重视的是成本。在各 20 路取前 50 次真实评价、合计 1,000 次评价的比较中：

| 成本 | r1 | r2 | 变化 |
|---|---:|---:|---:|
| LLM 调用次数 | 1,115 | 1,662 | **＋49.1%** |
| 输入 tokens | 231 万 | 313 万 | **＋35.3%** |
| 输出 tokens | 169 万 | 137 万 | **−19.3%** |
| 总 tokens | 400 万 | 449 万 | **＋12.2%** |

当时同时修改了协议与读取流程，不能把差值全部归因于 edit。诊断已经定位到具体损耗：读取空历史、合法内容因外围封装被拒收、额外修复调用等。这批运行的耗时没有同步上升，因此这里能直接确认的是调用和 token 开销。[同一份诊断中的成本与接口分析](https://github.com/Fangziyang0910/TraceAAD/blob/036b055afb8c6ae67ba98ed69fa490f5c73b5e6e/docs/02-实验结果/2026-09-24-V10.13-r2早期运行诊断.md)

**这个教训应当直接进入新设计：edit 的收益，可能被围绕它组织的交互过程消耗掉。**

对于一条串行开发链，总时间可以近似拆为：

\[
T_{\mathrm{total}}
\approx
\sum_{j=1}^{m}
\left(
T_{\mathrm{往返},j}
+
T_{\mathrm{输入处理},j}
+
T_{\mathrm{输出生成},j}
\right)
+
T_{\mathrm{应用与检查}}
+
\sum_{\ell=1}^{n}T_{\mathrm{算法评价},\ell}
\]

这里，\(m\) 是模型调用次数，\(n\) 是实际算法评价次数。

edit 主要压缩每轮的输出生成部分。多轮可能同时增加：

- 串行往返次数；
- 重复输入的代码和历史；
- 重复分析；
- 算法评价次数。

另外，SEARCH/REPLACE 的输出长度包括**原片段、新片段和标记**。代码本来就很短，或者要重写大半个函数时，它未必比直接输出完整代码短。

所以，效率目标应当是：

> **完成一次有价值、可以继续发展的算法改进，需要多少总计算和时间。**

“每次 edit 输出很短”只是其中一项因素。

## 五、我会怎样把它纳入 V10.24

我的建议是先形成一个简洁的默认过程：

> **一次分析，一批相互配合的编辑，生成完整程序并评价；让需要继续解决的问题带着实际反馈进入下一轮。**

### 1. 保留 Analysis 和 Design，把成熟程序上的 Code 默认改为 Edits

我不建议因为采用 edit，就把分析去掉。分析仍然承担理解算法、选择改进方向和组织依赖的作用。

输出可以保持熟悉的结构：

```text
Analysis:
说明本轮希望改变的求解行为、判断依据，
以及哪些代码位置需要一起修改。

Design:
简要描述更新后的算法核心。

Edits:
一组针对当前程序的 SEARCH/REPLACE 块。
```

对模型的核心提示，我会写成类似这样：

> 理解当前算法后，完成本轮确定的算法改进。根据实现需要，可以同时修改多个相关代码块。让每个替换块具有足够的上下文，并保持计算结构完整。保留与本次改进无关的实现细节。如果整体重写更清楚、代价更低，可以交付完整代码。

这段提示强调的是算法变化与实现的一致性，没有把“最少改几行”设为目标。

### 2. 一次提交所有已经明确的关联修改

例如，将一段局部搜索向量化，可能需要同时修改：

- 数组布局；
- 增益计算；
- 索引选择；
- 状态更新。

如果这些依赖已经清楚，应当在一次响应中提交一组编辑，整体应用。

**没有必要把一个已经想清楚的改动，拆成四次模型调用，也没有必要评价明显尚未完成的中间程序。**

SWE-agent 对接口的研究也强调：有意义的操作应尽量在少量动作内完成，编辑反馈应提供足够信息，避免额外的导航与往返。这个原则对我们减少多轮编辑成本很有参考价值。[arxiv.org](https://arxiv.org/html/2405.15793v3?utm_source=chatgpt.com)

### 3. 模型负责表达变化，宿主负责准确应用

基底由系统绑定到当前程序，模型直接提交编辑内容即可，不需要抄写 hash。

执行器负责：

- 检查原片段是否唯一匹配；
- 检查关联编辑是否冲突；
- 将整批编辑应用成一致的完整程序；
- 做语法和接口检查；
- 保存实际 diff 和完整结果。

评价器继续接收完整程序，档案也保存完整程序。这样，后续运行和分析不需要依赖一条越来越长的补丁链才能恢复状态。

**edit 是模型的交付方式，完整代码仍是系统中的程序事实。**

这里还应吸收旧版经验：允许的说明文字、代码围栏等封装问题，尽量由解析器确定性处理，避免让模型花一轮去修复本来有效的交付。

### 4. 上下文仍然要支持全局理解

采用局部编辑，不意味着只让模型看到局部代码。

我会让当前程序保持为清楚、自洽的主状态，并配上：

- 本轮正在发展的算法方向；
- 最近一次实际修改；
- 与本次决定相关的评价或失败信息；
- 确实需要借鉴的参考实现。

后续轮次需要知道**当前代码究竟是什么**。不能同时堆积多份旧全文、新全文和长工具日志，让模型自己辨认哪一份才是最新状态。

对于已知必须读取的材料，可以在调用前组织好。系统明知没有历史时，就直接表达这一事实，避免再花一次模型调用读取空结果。

### 5. 多轮续改接入现有开发过程，共享预算与历史

我赞成保留多轮能力。适合继续的情况包括：

- 刚得到明确错误，需要修复；
- 实际运行暴露了之前不知道的瓶颈；
- 算法成绩和实例表现提示下一步应怎样发展；
- 一项复杂改动还存在需要根据当前实现继续解决的依赖问题。

对于已得到完整算法成绩的编辑，它已经构成一次真实搜索尝试，应当进入统一预算和历史。不能让一个 agent 在内部评价了多个程序，外层却只记作“一个候选”。

反过来，一次 patch 匹配失败后的格式修正，不等于一次新的完整算法评价，但模型调用和时间仍应计入。

这样，多轮编辑就能服务于同一思想的持续开发，外层调度也能知道这条路线已经花了多少资源、获得了什么信息。

### 6. 完整输出继续用于适合它的改动

我会保留完整输出用于：

- 从零建立程序；
- 本身很短的实现；
- 大范围重组；
- edit 的定位与重复片段已经比重写更繁琐的情况。

也不宜机械规定“Refine 必须 edit，Explore 必须 full”。探索性的算法变化可能只改一个关键计算块；精炼也可能需要重构多个组件。**输出方式应服从实际修改范围和当前模型的交付能力。**

## 六、我对这个方向的最终判断

**我赞成你的核心判断：算法改进的输出模式，本身就是可以优化的计算机制。它有机会同时改善实现成功率、有效推理和搜索效率。**

对 TraceAAD，最值得期待的收益是：已有的有效计算更容易保留，新的想法更容易被有针对性地落实，同一算法方向能够以较低的交付成本持续发展。

我会把三个层面的改进这样安排：

| 层面 | 优先改什么 | 期待获得什么 |
|---|---|---|
| 改进表示 | 结构完整的块级 edit | 减少无关改写，准确落实变化 |
| 思考过程 | 以当前程序承接下一轮推理 | 修正遗漏，发展复杂改动 |
| 交互安排 | 合并已知关联修改，按需要继续 | 控制调用、上下文与评价成本 |

判断成效时，首先应看相同改进意图能否更可靠地落地；进一步看相同总预算下，是否更稳定地得到更好的算法，以及这些改进能否继续被精炼。

**因此，我现在对 V10.24 的建议会明确加入：成熟程序默认采用成组 edit，多轮续改围绕同一算法问题展开，所有调用与评价统一计量。** 这项调整直接关系到 TraceAAD 如何把一次有价值的发现积累成一个成熟算法，值得放在较高优先级。
