**有。我的判断是：V10.24 已经有一条值得保留的核心主线，但预算控制和上下文组织背负了过多附加规则。其中几处规则会相互抵消，使系统在局部允许连续开发，却在关键边界上中断它。下一步适合做一次围绕主线的减法重构。**

我审阅的是 GitHub 上的提交 [`b9a649c`](https://github.com/Fangziyang0910/TraceAAD/commit/b9a649c659150bef1830d31cbf3d86b2027c669a)，包括研究主线、V10.24 全局设计、成组编辑文档和对应实现。两份 V10.24 专属测试共 **43 项**已在本次临时 Python 3.12 环境通过；我另外用真实控制器和提示构造代码做了定向重放，检查预算、编辑状态和上下文边界。这些验证能够确认下面的执行路径；完整搜索效果仍需要真实模型实验，不能由离线检查推断。

我也需要修正此前建议中的一部分：**“完整证据、连续开发、事前计划、预算保护”分别都有道理，但把它们各自做成硬规则，再叠加到一起，并不会自然得到一个好的整体机制。** 当前版本已经暴露出这种叠加带来的问题。

## 一、从奥卡姆剃刀看，真正的核心主线是什么？

我认为可以压缩为一句话：

> **围绕一个具体的求解效果，从已有算法出发，利用真实开发证据，连续完成、修正或放弃一个改进问题，并在有限总预算内积累更好的算法。**

这里每个部分都有明确职责：

| 部分 | 它必须解决的问题 |
|---|---|
| 求解器事实与接口 | 生成的计算究竟能怎样影响最终解？ |
| 一个具体改进问题 | 当前这段开发在解决什么，为什么值得试？ |
| 当前工作版 | 下一步应当从哪份实际代码继续？ |
| 最好结果 | 怎样保住已经取得的成果，同时允许工作版暂时退步？ |
| 开发证据 | 下一次修改应该从哪些真实失败、差异和结果中学习？ |
| 全局预算 | 继续发展已有问题与提出其他问题，如何分配有限机会？ |

从第一性原理看：

- **算法设计的价值落在计算及其对求解过程的作用上。** 改一行可以改变采样分布，改很多行也可能没有有效作用；一个局部目标也可能要求多个位置共同修改。
- **LLM 的后续开发依赖它实际看到的代码和证据。** 系统保存了什么、展示了什么、把哪份代码定义为当前状态，会直接塑造下一次提案。
- **TraceAAD 的历史必须服务于下一次决策。** 记录丰富只是基础，真正要说明的是：哪些历史使模型识别了错误、保留了有用计算、改变了实现方式，最终形成了更好的算法。

这与仓库当前的[研究主线][mainline]是相符的。

### V10.24 已经做对的几件事，应当保留

**第一，TaskCard 开始明确描述输出如何被外层求解器消费。** 这使改进问题有了实际作用边界，而不只是笼统要求“设计更强的启发式”。

**第二，工作版与最好版分离。** 块内的新有效程序即使暂时较差，也可以成为下一次的工作起点。这是跨越短期退步所需要的基本状态机制。

**第三，成组 edit 的方向正确。** 所有已知的关联修改可以在同一批中完成，宿主原子应用，最终评价一个完整程序；未编辑部分由宿主保留。完整 Code 仍然适用于初始化和大范围重组。

**第四，原始提案、失败源码、修复差异和兄弟尝试得以保存。** 这能避免“修复删掉了新计算，后续却再也看不到原计算”的问题。[算子与上下文实现][prompts]、[成组编辑设计][editdoc]

这些构成了一个有意义的机制。**目前最需要审视的是：外围规则是否仍在帮助这个机制。**

## 二、最主要的过度设计：连续开发的资格被多种代理条件共同控制

### 1. 开发多长，过度依赖它最初叫什么算子

当前实现大致是：

| 开发来源 | 第一块 | 取得第二块的方式 |
|---|---:|---|
| `Refine / front_refine` | 4 次尝试 | 不进入普通续投通道 |
| `Crossover / front_transfer` | 4 次尝试 | 不进入普通续投通道 |
| `Explore / new_question` | 4 次尝试 | 首轮通过两块计划准入，或后续 champion 属于当前前沿 |

其中，事前两块计划只接受**第一次 Explore 尝试**中的 `Plan、Stage 1、Stage 2、Dependency、Location` 字段。实现检查结构和字段完整性，不验证依赖关系是否真实。没有事前承诺的新问题，续投又取决于 champion 是否仍属于当前八个质量组。[分配与续投实现][allocate]、[计划准入实现][admission]、[开发块关闭实现][close]

这里的底层问题是：

> **计算之间的依赖关系，并不按照 Refine、Crossover、Explore 的名称划分。**

一次跨程序迁移，很可能需要协调表示、尺度、过滤和输出映射；一次 Explore，也可能只是修改一个指数。把“是否值得获得更长的连续开发机会”强绑定到开题算子，需要一个很强的假设，而当前证据没有支持这个假设。

同时，真正需要多步开发的原因，也可能在第二、第三轮收到反馈后才显现。当前规则却让**首轮格式完整的计划**拥有特殊资源地位。

我做的一个重放确认了这个边界：

- 第一次 Explore 的 edit 不完整，没有产生程序。
- 下一次仍是 Explore，首次交出合法程序和完整两块计划。
- 此时剩余预算足够。
- 但由于已经过了“第一次尝试”，这份计划不再具有事前准入资格。

这使一次交付错误进一步改变了该问题未来的资源机会。**格式失败已经付出一次候选成本，没有必要再自动承担失去某类开发资格的额外后果。**

另一个重放中，Refine 的四次尝试产生了一个最好版，随后又连续产生了几个较弱的有效工作版。第四次结束后，单元关闭，下一单元从 champion 出发。较弱工作版仍在档案里，但标准续投入口不会恢复它继续解决原问题。

这不证明第五次一定有价值；它说明：**块内非贪心已经实现，跨块非贪心仍只有一个相当狭窄的通道。**

### 2. 四次或八次本身可以是边界，但不应被包装成算法规律

有限预算是必要的。你的“大 Mission”要求，也不意味着每个候选想法都应该无限开发。

问题在于，现在同时存在：

- 四类名义预算槽；
- 每块四次；
- 最多两块；
- 首轮计划准入；
- 至多一个未兑现承诺；
- 前沿资格续投；
- 预留预算；
- 尾部跨槽分摊；
- 未花预算回流；
- 没有可续投对象时的替代规则。

其中相当一部分复杂度，是为了维持前面几条人为规则之间的一致性。

**四次是否够用，是经验问题；用哪些条件决定谁只能有四次、谁可以有八次，则是机制问题。** 这两个问题需要分开。

我的建议是：先统一开发资格和状态，再依据完整搜索结果确定开发长度。计划可以帮助模型组织工作，但不宜承担特殊的资源许可证功能。

### 3. 当前设计确实承担了明显的开题机会成本

设计文档已经坦率记录：在没有回流的名义账期中，每 100 次候选约有 **6.25 次专门的 Explore 开题**；V10.23 的既有诊断中，这个数约为 **21.28 次**。这不是思想数量对比，也不能直接推出优劣，但它明确表明，当前机制用提案宽度换取了开发深度。[全局设计 §9.7][design]

因此，要回答的是：

> **连续开发带来的最终强算法产出，能否补偿减少的其他搜索机会？**

“每个开发问题更容易改善”“一个开发块内出现了好结果”，都不足以单独回答这个问题。

当前版本对开发寿命设置了很多细则，却还没有足够证据说明这套细则提供了合适的全局取舍。这是我认为控制器应当简化的主要原因。

## 三、第二个结构性问题：完整存档与完整提示被绑在一起，反过来破坏连续开发

这是我认为应优先修正的一处。

### 1. 当前要求会让一次开发越深入，越难继续

每次请求都要求提供若干代码角色的完整源码：

- anchor；
- worktip；
- champion；
- 原始 proposal；
- pending failure；
- 必要的 donor。

相同 ID 会去重，但不同 ID 的相近源码仍会分别出现。然后再加入**本单元全部尝试的实际 diff、失败结果，以及尚未应用的失败 edit 文本**。

上下文过长时，可以删关联历史，但这些本单元材料不能进一步调整，最后只能结束开发。[提示构造实现][context]

保留这些事实的动机是正确的。但：

> **事实必须完整保存，并不意味着每次决策都需要以相同形式读取全部事实。**

当前写法让“不要丢掉重要历史”变成了“多份完整源码与全部局部差异始终同时出现”。这既增加输入成本，也把连续开发长度与材料膨胀直接绑定。

此前我们讨论 edit 的效率时，强调了减少重复生成源码。现在还必须把另一半补上：**如果输出变短，但输入反复携带多份近似完整源码，整体效率未必改善。**

### 2. 更严重的是，局部上下文失败会扩大为全局起点排除

`_search()` 捕获 `ContextTooLong` 后，如果当前块还没有花费尝试，会把该单元的 `anchor_id` 加入全局 `excluded`。[上下文失败处理][search]

问题是：**第二块刚开始时，`spent` 同样为零。**

于是可能出现：

1. 这个起点本身可以正常构造请求。
2. 开发了一块，局部历史变长。
3. 第二块首次请求装不下。
4. 系统永久排除这个起点。

我用真实提示构造器和控制器做的构造重放确认了这条路径。在离线 TokenLLM 的计数下：

| 请求情形 | 输入 token |
|---|---:|
| 从同一起点新开一个请求 | 2,717 |
| 第一块最后一次请求 | 19,895 |
| 第二块第一次请求 | 24,341 |

默认输入上限为 24,320。最后一个请求超限后，起点被加入 `excluded`。

这些数字来自离线构造样例，不代表生产模型上的发生频率；但它确认了一个明确的状态问题：

> **一个局部开发记录太长，会被处理成这个程序不再适合作为全局搜索起点。**

这两件事之间没有成立的因果关系。

合理的边界应当是：只有“最小任务契约＋该份编辑基底”本身都无法容纳，才有理由判定这个基底在当前交互方式下不可用。某个单元附带历史装不下，应当触发材料调整或该单元暂停。

### 3. 历史不只是“太多”，还存在“真正相关的被挤掉”

当前关联规则把两类关系混在同一列表：

- 与当前 anchor 有实际代码来源关系；
- 只是拥有相同作用轴。

随后统一取最近三个关联单元。[关联构造][allocate]、[关联截取][search]

我构造的一个合法状态中：

- 单元 1 实际产生了当前起点；
- 单元 6、11、16 只是同作用轴，涉及不同程序；
- 关联列表为 `[1, 6, 11, 16]`；
- 最终展示的是 `[6, 11, 16]`。

**真正的形成历史在没有上下文压力时就已经被排除。**

这说明“相关”需要按决策价值排序。实际来源关系、当前问题的失败尝试，与宽泛的作用轴相似，不能拥有同等优先级。

### 我建议怎样统一解决这一组问题

完整事实档案继续保存。当前提示则围绕下一次决策组织：

1. **完整当前编辑基底**，保证 edit 定位可靠。
2. **当前问题和真实求解器契约**。
3. **最近改动及反馈**，说明当前状态怎样形成。
4. **对本次决策不可缺少的原提案、被修复删除的计算、相关失败**，优先用准确代码片段和实际差异表示。
5. 其他历史用紧凑记录表示，并优先选择真实来源关系。

某份旧程序确实需要作为另一编辑基底时，再保证它被完整展示。不能把未完整提供的代码误列为可直接编辑的基底。

这里先做确定性的去重、差异表达和来源优先级就够了。**无需马上增加摘要 agent、语义记忆系统或新的模型判断器。**

## 四、第三个问题：代码去重同时承担了程序状态管理，语义不一致

当前 `_record_trial()` 只有在程序属于 `new and valid` 时才更新 worktip。对于已知程序，无论有效还是失败，都走重复分支，并清空 `pending_failure`。[状态更新实现][state]

去重有明确价值：避免重复评价、避免把同一代码反复算作新发现。

但它不应该同时决定“当前正在开发哪份程序”。

定向重放确认了两种情况：

| 场景 | 当前实际行为 | 应有的状态含义 |
|---|---|---|
| 从有效版本 B 编辑回已知有效版本 A | A 被判重复，worktip 仍停留在 B | 如果这次回退被接受，当前工作状态应当回到 A |
| 修复失败程序时，再次输出同一份已知失败代码 | 判定 known failure，并清空 pending failure | 失败并未解决，应保留失败状态，或明确放弃该修复 |

这里需要分清三个判断：

1. 这份程序以前是否见过？
2. 这份程序是否有效？
3. 这次操作是否把它选作当前工作结果？

例如，回到旧版本不产生新发现，通常也不需要重新评价，但它完全可以是一次有意义的开发状态转换。

**建议保留去重与缓存，单独按照实际交付结果更新工作状态。** 重复失败不会自动变成“已经没有待修复问题”；有效回退也不应因为不新颖而失效。

这属于状态定义需要修正。现有检查通过，与这种问题并不矛盾：检查可以准确验证现有规则，却不能替代对规则语义的审视。

## 五、第四个问题：质量分组、排名和续投资格承担了过多相互关联的职责

当前前沿机制有一个合理动机：避免同类程序仅凭数量获得更多采样机会。

但实现随后把几件事连在一起：

1. 按完整训练成绩向量分组；
2. 按平均 fitness 排序；
3. 同平均分时按稳定 hash 排序；
4. 截取前八组；
5. 按 \(1/r\) 分配组采样概率；
6. 用是否属于这八组决定一部分续投资格。[质量分组与排名][policy]

### 同分的任意顺序，被放大成了不同的资源权重

我用九组**平均 fitness 完全相同、逐实例成绩向量不同**的程序重放了实际策略。

在一个固定种子下：

- 排名第一组的采样概率约 **36.8%**；
- 排名第八组约 **4.6%**；
- 第九组不进入前沿。

第一组与第八组相差 **8 倍**。这个差异来自同分时的 hash 顺序，没有来自平均质量的依据；在候选池不变时，这种顺序会保持。

成绩向量不同，可能意味着实例间互补，保留这些程序是合理的。但平均目标相同，并不能支持把其中一组当作质量上高出另一个采样等级的程序。

### 可以用很小的修改恢复职责一致

- 相同平均目标的组，具有相同质量权重。
- 前沿边界的并列应公平处理，例如保留边界上的全部同分组。
- hash 用于稳定标识或可复现处理，不赋予质量含义。
- 前沿用于选择成熟起点，不独占未成熟开发问题的继续资格。

这里无需发明复杂的“长期潜力分数”。

另外，**并不是当前所有公式都值得删除**：

- donor 的逐实例互补度
  \[
  C(a,d)=\frac{1}{N}\sum_i[q_i(a)-q_i(d)]_+
  \]
  有清楚的含义，可以作为参考选择的启发。它不证明某个部件具有因果价值，这一点现有提示已经提醒模型。
- 块收益 \(G_b\)、每次尝试收益 \(\rho_b\) 适合诊断投入和结果。
- 当前没有直接用 \(\rho_b\) 做逐块贪心追涨，这一点值得保留。[全局设计 §9.3–9.7][design]

真正应警惕的是：**一个观测指标从描述质量，逐渐扩展为开发资格、长期价值和历史相关性的共同裁判。**

## 六、我建议把 V10.24 收敛成一个怎样的最小一致机制？

上述问题有共同根源：

> **一条本来只适用于局部的规则，获得了过大的决策权。**

首轮文本格式决定未来预算，上下文错误决定全局起点资格，代码新颖性决定当前工作状态，同分 hash 顺序决定质量优先级。

因此，这轮重构应统一这些边界。

### 1. 一个开发单元，只承担一件事

一个单元围绕一个具体问题工作，核心状态是：

- 问题及其预期求解效果；
- 当前工作版；
- 当前最好结果；
- 待解决的失败；
- 实际尝试与来源记录。

anchor、原始 proposal、donor 都可以作为可追溯的来源角色保留。它们不需要各自衍生一套状态机，也不必每轮都以完整源码重复出现。

问题可以因证据而调整或明确放弃。应当持续保留的是“正在解决什么、为何调整”的可追溯性，避免首轮计划变成必须维护的承诺文本。

### 2. 所有提案来源共用一种有限开发规则

**Refine、Explore、Crossover 继续保留各自的生成目标和材料差异；开发寿命采用共同规则。**

全局控制器只需要处理两种资源决定：

- 新开一个具体问题；
- 给一个已有问题再提供一段开发机会。

作为初始参考，可以暂时保留当前四次一段、至多八次的数值，让各类问题适用同一边界。这样能够先检查状态与证据机制，而不把改变所有数值混进同一次判断。

一段结束时：

- 保存工作状态；
- 有后续机会的单元进入待续投集合；
- 被再次选择时，从原 worktip 和原问题继续；
- 达到资源上限就按真实原因归档。

**段结束不应自动意味着必须改从 champion 重新开题。**

开题与续投保留一个明确的分配规则即可。起步可用固定比例和可复现的简单续投选择，先检验连续开发本身是否有价值。四类槽位、首轮特殊许可证、跨槽预留与回流规则，可以合并为一个全局未用预算池和实际支出账。

这也意味着：没有预留的未来开发，只能记录为待分配机会，不能虚称已经承诺。每次实际授予的开发段，则应有清楚、可兑现的边界。

**最佳比例和开发长度目前仍是需要真实结果回答的问题。** 我不认为再凭直觉写一套更细的数字表，就能够解决这个未知量。

### 3. edit 保持原子性，多轮用于吸收新反馈

当前成组 edit 的执行协议总体应保留：

- 一个明确绑定的基底；
- 一批相关修改；
- 宿主确定性应用；
- 一个完整程序；
- 一次真实评价；
- 更新工作状态和证据。

已知的依赖修改尽量同轮完成。后续轮次用于处理新反馈揭示的问题。

提示继续要求模型说明：

- 本次要改变的计算；
- 它怎样影响求解器；
- 依据了什么实际结果；
- 还存在什么不确定性。

计划内容可以保留在这段分析里，但取消其特殊的预算准入职责。

**不限制 edit 必须小。** 整个循环、辅助函数、数据表示需要一起替换时，就一起替换；适合完整重写时继续允许 full。

### 4. 上下文按当前决定组织，档案按事实完整保存

同一套记录同时支持两种需要：

- 对研究者：完整恢复每次实际发生的事。
- 对模型：看清下一步决定所需的证据。

这不要求两者使用同样长度和同样排版。

取舍顺序应由实际来源和当前问题决定。上下文容量不足，首先改变材料表达或暂停局部开发，不自动扩大成全局程序排除。

### 5. 保留可靠性设施，减少推测性的策略细则

确定性 edit、真实计费、源码保真、事件记录、恢复一致性，都有直接职责。它们应当保留。

可以按下面这张表收敛：

| 当前部分 | 我的建议 |
|---|---|
| TaskCard、输出消费关系 | 保留，作为生成目标的事实基础 |
| worktip／最好结果分离 | 保留，修正重复代码与回退的状态语义 |
| 原子成组 edit、full 后备 | 保留 |
| 原提案、失败与兄弟尝试 | 完整存档；提示按当前决策选择表达 |
| Refine／Explore／Crossover | 保留生成差异，共用开发生命周期 |
| 首轮两块 Plan 特权 | 取消；计划作为开发内容 |
| 四槽账期、预留、跨槽尾部和回流 | 合并为简单资源分配与实际支出 |
| 五作用轴 | 保留为思考入口，先降为可选启发；不把开题次数均衡当作经验学习 |
| 成绩向量分组与前沿 | 保留合理去重作用，修正并列；不独占续投资格 |
| 完整状态记录与恢复 | 保留，作为可靠运行的基础 |

## 七、下一轮大 Mission 应当闭合什么？

这次最值得闭合的核心问题是：

> **在相同总投入下，准确的开发状态、可用的历史证据和有限的连续开发机会，能否使有价值的计算更稳定地进入最终算法？**

为了回答它，应当把下面这条结构性问题链一次处理完：

**开发资格 → 工作状态 → 上下文可持续性 → 全局资源竞争 → 最终算法形成。**

只修 edit 解析，不处理回退状态，下一阶段会遇到状态不一致；只增加连续轮次，不调整提示材料，下一阶段会遇到上下文关闭；只保证续投，不检查开题机会成本，下一阶段又可能发现整体强结果更少。

这正是需要避免的串行修补。

具体应当沿完整闭环推进：

1. **先完成统一机制的集成。** 把有效回退、重复失败、跨块恢复、上下文超限范围和同分资源权重这些已明确的边界一起处理。
2. **再做完整搜索。** 沿用已有任务与评价协议，观察各任务、各重复的最终冻结结果，同时记录输入、输出、调用、评价和墙钟成本。单一候选预算下领先，也要核对真实成本是否显著增加。
3. **独立复盘成功与停滞轨迹。** 检查新计算有没有被保留、修复有没有改变它的作用、后续收益来自哪里。若实际过程是恢复旧程序后调参，就按这个真实过程解释。
4. **修复后重新 profiling。** 看主要损失究竟来自交付、无效计算、材料膨胀、开发机会不足，还是在无价值问题上投入过多，再收敛少数真正必要的分配参数。

已有文档已经安排了完整搜索、提案与开发条件、续投选择三个层面的验证，这个方向可以继续使用。[全局设计 §12][design] 我建议围绕上面这个核心问题组织它们，避免扩展成一大张缺乏共同解释的消融表。

**我对 V10.24 的最终意见是：保住它已经形成的开发内核，把连续开发、材料容量和资源分配作为同一个问题一起重构。** 让每个部件只承担自己能够合理判断的事情：edit 负责落地，工作状态负责连续，历史负责提供证据，调度负责有限机会。这样既能减少脆弱的控制依赖，也更有可能从真实实验中看清，这个机制为什么有效、在哪里失效、下一步该怎样改。
