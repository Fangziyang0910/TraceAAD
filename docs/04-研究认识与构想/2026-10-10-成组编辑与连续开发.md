# 成组编辑怎样进入连续算法开发

2026-10-10。根据用户补充的[完整讨论](资料/2026-10-10-V10.24-编辑机制补充原文.txt)，已将 V10.24 从默认完整代码交付改为：**成熟程序默认成组 edit，初始化及适合整体重组的情况保留 full；一批关联编辑共同形成一个完整程序，再进入现有开发与评价。** [主设计](2026-10-09-从求解行为到开发决策的V10.24全局设计.md)与实现已同步。

## 认识的变化

原设计把完整代码当成较稳妥的交付形式，却没有充分处理“哪些内容还要由模型重新生成”。即使提示要求保留成熟计算，完整输出仍会让这些代码再经过一次生成。edit 将没有指定修改的源码交给宿主确定性保留，让生成更集中于本次变化。这里改变的是提案分布与实现方式，不只是输出压缩。

\[
h'\sim p_\theta^{\mathrm{full}}(\cdot\mid h,C),\qquad
\Delta\sim p_\theta^{\mathrm{edit}}(\cdot\mid h,C),\quad
h'=\operatorname{Apply}(h,\Delta).
\]

程序保留不等于行为保留；共享函数的一处改动可以影响所有调用者。编辑也不天然非贪心。一行幂变换可以改变采样分布，多处重构也可以保持算法行为。因此，“结构完整”表示完成同一作用需要的依赖，不表示改动越小越好。

三种收益需要区分：edit 减少重复交付及无关改写；多轮开发用落地程序承接后续思考；评价反馈提供上一轮未知的实际结果。输出 token 减少不会自动变成更多推理，也不能单独证明终局算法更强。

## 哪些证据支持调整

本轮核对了原论文中的对应段落与历史仓库记录。

- [To Diff or Not to Diff?](https://arxiv.org/html/2604.27296v1)的 Qwen2.5-Coder-7B 表中，FullCode、ContentDiff、FuncDiff、AdaEdit+FuncDiff 平均 pass@1 分别为57.07、54.43、57.32、57.95。结构与自适应格式值得参考；这些结果涉及专门训练，不能直接视为当前未按该方案训练的模型收益。我们的 SEARCH/REPLACE 不是该论文的 FuncDiff 实现。
- [EvoTrace](https://arxiv.org/html/2605.20086v1)附录C.3在固定 ahc015 任务上报告，同一 deepseek-reasoner 的 tuning recycling 行占比在 diff 与 no-diff 条件下为20%与2%。这是修改构成的差别，不是成功率提升，提醒我们 edit 可能强化已有的小修改习惯。
- [V10.13-r2 原诊断](https://github.com/Fangziyang0910/TraceAAD/blob/036b055afb8c6ae67ba98ed69fa490f5c73b5e6e/docs/02-实验结果/2026-09-24-V10.13-r2早期运行诊断.md)记载188个有效edit开发候选中50个超父、15个超前沿，也记载空历史读取和外层封装拒收的损耗。同 E50 汇总的调用增加49.1%、输出token减少19.3%、总token增加12.2%；同时改变的机制不止格式，不能把差值全部归因于edit。

这些证据支持改变交付和交互方式，也支持控制额外往返。它们没有证明 edit 总优于 full，或更短输出必然更快。

## 最终执行规则

1. Init 创建完整程序。Refine、Explore、Crossover、Develop、Repair 默认输出 Analysis、Design 和 Edits；各算子仍可交付完整 Code。格式不按算子名字硬分大小。
2. 宿主绑定明确的编辑基底。常规开发为有效 worktip，Repair 为具体失败源码。基底完整显示在提示最前面的代码位置；其他角色明确标成参考快照。
3. 一次响应提交所有已知关联修改。每个 SEARCH 必须在同一个原始基底上唯一、精确匹配，保持缩进；多个区域不能重叠，也不能引用同批前一编辑才生成的文字。
4. 验证整批后一次应用。添加代码使用非空原片段作锚，删除允许空 replacement；相关重叠改动合并成一个较大块。宿主不猜测模糊匹配、不执行半批补丁。
5. 应用后检查 Python 语法和原接口；评价器仍接收完整程序。程序档案保存完整源码，后续请求不需要递归执行补丁链。
6. 实际保存源码不再经 AST 重打印，因此未编辑文本保持原样；源码身份仍按原有 canonical 规则计算，以便识别仅改空白、引号或注释的重复。末尾换行统一处理。
7. 匹配／标记／冲突失败属于 delivery_failed，不产生虚构程序，不覆盖 worktip，不进入算法评价。下一轮读取明确错误、未应用的提交及完整基底，在原问题预算内重新提交。
8. 应用后语法或接口失败产生可回查的完整失败源码，进入既有 Repair；运行失败同理。一次修复没有免费调用，不在内部偷偷评价多个版本。
9. 短代码、大范围重组或定位比重写更复杂时允许 full。只有 full 可用合法 Base 声明改从其他已完整显示的代码出发；edit 默认不写 Base。edit 若声明与宿主基底冲突，不静默改绑。
10. 两块计划、四类代码角色、质量组、候选账和续投资格保留；编辑表示不代替这些战略选择。已承诺 Stage 1/2 仍持续进入后续提示。

## 原子性与反馈的含义

“原子应用”不要求每个中间替换结果可独立运行。所有 SEARCH 在原始基底上定位，验证无冲突后从后往前替换；只对最终结果做语法和接口检查，再评价一次。这样可以在一轮中一起修改数组布局、增益计算、索引和状态更新。

允许说明文字、外层代码围栏及常见 Edits 标题包装，由解析器确定性识别。标记缺失、不完整输出、歧义匹配与冲突则给出具体错误。外围宽容不等于允许宿主猜测代码修改。

继续展示原 proposal 和修复差异，是为了保持算法问题与证据连续；“当前编辑基底”只有一个。角色混淆通过明确绑定解决，必需证据不能为缩短提示而悄悄删去。系统直接提供已知材料，不新增一次读取空历史的调用。

## 预算与资源口径

当前[实验协议](../../experiments/PROTOCOL.md)按生成候选尝试计数，包括无效交付。因此补丁匹配失败仍占四候选块的一次，同时记录零次算法评价。附件中“格式修正不等于算法评价”的区分成立，但不意味着可免费重试。

一组成组编辑是一轮生成、一个候选，成功应用后最多一次候选评价；该评价内部仍按原协议处理全部训练实例。最终冻结重评照旧独立记录。所有后续编辑沿用统一预算，不另开隐藏agent循环。

每次尝试保存 delivery_mode、绑定基底、应用策略、成功块数、是否进入评价及调用token。格式诊断分开汇总尝试数、交付失败、新有效程序、实际评价候选、模型调用与输入／输出token；usage缺失记为空，不用上限伪造节省。整体基础设施重试成本继续保留在原调用日志与汇总中。

效率要比较总投入和结果：同一改动意图能否正确落地，完成后是否保住成熟代码，同预算下有多少强程序产出，以及整路的输入、输出、调用、评价CPU和墙钟时间。不能只报告输出长度。

## 已落实与待判断

交付执行器为[delivery.py](../../traceaad/v10_24/delivery.py)，上下文和提示为[prompts.py](../../traceaad/v10_24/prompts.py)。新交付条件使用 `v1024-atomic-edit-1`，不能把 full-only 检查点无记录地续接到新提示。旧版本继续使用原解析与源码存储行为。

离线测试验证成组原子应用、原始基底定位、未改源码保持、空替换、标记不完整、歧义与重叠、失败反馈、语法失败后的Repair、统一计费、完整代码回退、规范化去重和恢复。完整测试入口见[实验说明](../../experiments/traceaad_v10_24/README.md)。

真实模型的格式熟练程度、提案变化及总资源收益仍需观察。首要判断是相同算法意图能否更可靠落地，然后看完整搜索是否更好。若补丁失败或输入重复抵消输出节省，应根据实际失败修订格式或增加full使用；不能再叠加无差别的反思和工具往返。
