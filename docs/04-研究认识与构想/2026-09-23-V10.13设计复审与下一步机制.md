# V10.13 设计复审：从重复生成走向利用试验反馈

V10.13 是一个值得完成当前正式批次的简洁基线，但还不能称为“彻底修复设计缺陷”的通用算法设计系统。它恢复了清楚的质量分配，避免把形成树误认成算法类别，也减轻了强制文字协议；同时仍把当前 fitness 当成主要机会依据，把固定祖先链当成开发记忆，并在输出层因说明文字拒收可解析代码。下一步最值得投入的不是增加算子名字，而是让实际试验反馈进入下一次设计，让不同算法假设保有生存空间，并把格式、编辑和评价接口做好。

本文是设计与实现审阅，不是 V10.13 质量排名，也不是新批次的冻结方案。建议不回写正在运行的机制。

## 2. 先纠正历史归因

### 2.1 不能把当前 V10.10 文件当作首批实际实现

首批冻结路径 `experiments/traceaad_v10_10/results/runtime_20260910_v1010_formal/llm4ad/method/traceaad_v10_10/trajectory.py` 的 `evidence()` 已按算子选择上下文：

- Refine 读取至多三条 host 形成边；
- Tune/Pivot 不读取形成历史；
- Fuse 使用 host 形成边，并在存在时加入 donor 形成边；
- 形成证据包含源代码与实际 diff，不只是 Idea+fitness。

首批 TSP rep1 的实际 `llm_calls.jsonl` 中，Refine/Fuse 均存在完整 source+diff 历史，Tune/Pivot 没有 Formation History；不是仅从设计文字推断。首批还发生过 context/capacity 修补，OP rep1 E539 后的 runtime 切换记在 manifest。后来复核版和 09-12 工作区修订改成统一短轨迹及不同输出协议，不能混称同一个机制。

因此，“算子条件化上下文首次在 V11.1 出现”“V10.10 的优势已证实来自 ESS-8 加简短提示”都过强。首批本来就存在动作适配、源代码/diff 证据和允许不强行融合等设计。其训练输出上限还为 16K，后续 V10.11/V11.1/V10.13 为 8K。相同 evaluator 预算不代表相同生成预算。

### 2.2 各版本真正留下的判断

| 版本 | 实现特点 | 证据支持的判断 | 不应推出的判断 |
|---|---|---|---|
| V10.10 首批 | ESS-8；Pivot 均匀混合；动作条件化形成证据；有界修复 | 提供有竞争力的组合基线 | 已找到跨任务最优预算或提示 |

| V10.11 | ESS 主体保留，按批次比较上下文 | 上下文收益具有任务和阶段差异 | 已识别每个算子的最佳上下文 |
| V10.12 | 各算子追加两张 Idea+fitness 卡 | 无差别追加材料未形成稳定收益 | 所有外部 Idea 都无效，或代码越多越好 |

| V11.1 | 节点随机选择；Refine/Tune 轨迹、Pivot 卡、Fuse 卡+代码 | 缓解精英锁定，取得跨任务折中 | Fuse 的高超父率就是新机制创造率 |
| V10.13 | ESS-8；局部算子三条历史；Pivot/Fuse 单实码参考 | 实现更简洁，部分工程边界更清楚 | 已继承所有强项或保证多样性 |

V10.12 相对 V10.11 generic 的 CVRP50 为 **9.28705 对 9.33426**，实际略好；100/200 较差。此前综合诊断中“CVRP 三规模均未超过”的表述应纠正。其 VRPTW100/200 是成功三路均值，另一路失败，不能将成功条件下的均值当成四路完整方法质量。

V11.1 的典型折中仍成立：TSP100 为 8.70011 对 generic 的 8.28179；CVRP100 为 15.41968 对 15.84357；OP200 为 52.97294 对 54.20630。各版本重复数 3/4/5 不同，这些是描述性结果，不是算子与上下文的单因素因果结论。

### 2.3 Fuse 的成功口径需要拆开

重新扫描 V11.1 manual 完整 25 路：

| 项目 | 计数或比例 |
|---|---:|
| 有效 Fuse 候选 | 5614 |
| 超过父代 | 3091 / 5614 = 55.06% |
| 超过当时全局前沿 | 166 / 5614 = 2.96% |
| 有 donor 分数的有效候选 | 5321 |
| donor 原本强于父代 | 4194 / 5321 = 78.82% |
| 有 donor 记录且超过父代 | 2981 |

| 超父候选中未超过 donor | 2353 / 2981 = 78.93% |

这说明超父指标混合了“传播已有好方法”和“创造更好组合”。传播本身可能有用，但不能据 55% 认定融合机制已经很好。也不能把其余样本都说成复制：只有 143 个有效 Fuse 与 donor 的 AST 完全相同。记录中 293 个 Fuse 没有 donor 分数；V11.1 修复代码会清空 donor 字段，因此上述双亲比较只覆盖可观测子集。

### 2.4 不能把曾经删除的机制重新包装成新答案

[V10.9 设计](../01-主线版本/TraceAAD-V10.9-机制设计.md) 已包含当前节点直接成败子代、实码 diff、近期候选试用、donor 形成证据和具体部件迁移提示；V10.10 随后删除了直接试错上下文与近期试用。因此，本文讨论这些缺口时，提出的是有条件重新审视，不能称为新发明，更不能因为当前版本缺少它们就认定加回去必然更好。

同样，[V10.1/V10.2 提示配对研究](../03-机制验证/01-提示与上下文/2026-09-03-提示组件配对识别/README.md) 没有找到跨任务统一获益的文本组件。本文提示草案表达了更清楚的设计意图，尚不能打成“100 分提示”。可以优先改的是信息获取方式：按需读局部试验、由系统生成真实 diff、将编辑操作与文字说明解耦；不是重新默认追加一组过去已有的上下文。

## 3. V10.13 做对了什么

1. **分工清楚。** 真实评价决定质量，LLM 负责提出算法改变；不让主观 Idea 标签取代 fitness。
2. **保留随机搜索。** ESS 控制分布集中程度，Pivot 保留均匀分量，避免 V11.0 的逐次 argmax 锁定。
3. **没有把 genealogy 当语义分类。** 父子关系是事实，算法类型不是由树根自动决定的。
4. **上下文角色比无条件加卡清楚。** 当前代码、祖先关系、参考实现各有用途；代码整体保留，容量不足时按块回退。
5. **取消强制行为审计表是合理的。** 生成一个算法不必伴随四个宣称字段。字段存在不能证明实现正确。

这些优点足以支持把当前批次跑完，但“简洁”不是免检条件。可靠性、试验信息利用和探索方式仍有明确缺口。

## 4. 当前最需要处理的缺口

### 4.1 硬性 Idea 门槛重新引入了文字选择偏差

`parsing.py:121–125` 在检查代码前就因 Idea 缺失或超过 2000 字符拒收；`OUTPUT_FORMAT` 只说 short paragraph，没有声明这个硬阈值。

固定 partial 快照有 **217 次长度拒收，217 次都附带可通过 AST 语法解析的代码**。这不证明它们接口正确或得分高，却直接证明这些代码在评价前被说明文字挡住。修复还要求重写整份 Idea+Code，可能改变原算法。

建议：代码接口、语法和可执行性决定是否进入评价；Idea 作为可缺失的元数据。原始响应完整留档，过长 Idea 在上下文视图中压缩或略去；若做格式修复，应尽量只修格式并核对代码哈希。提示写清期望长度，但不把文字长度变成算法质量条件。

### 4.2 祖先记忆不是这个父代的试验记忆

`formation_edges()` 只沿 `parent_id` 回溯。一个父代已经生成了哪些子代、哪些具体变化退步、哪个 sibling 较好，都不会进入下一次局部设计。

在固定快照中，1439 次正常 Refine/Tune 调度里，**510 次在同一路相同 parent/operator 上重复了此前已有的完整 prompt hash，占 35.44%**。完整 V10.11 generic 为 3774/6720，V11.1 为 2363/11395。随机重复采样并非必然浪费；问题是系统没有能力在“继续独立采样”和“利用新试验反馈”之间做选择。

建议以两种记忆互补：

- 形成记忆：当前实现为什么变成这样，保留短链即可；
- 局部试验记忆：同一代码版本最近一到两次相关尝试的实际 diff、整体分数变化、具体错误。

不要把失败写成“这个机制永远无效”。证据应是“在此代码版本上作此改动，观察到此结果”，不作组件级因果断言。没有实际试验便不填字段，不额外生成一堆未经评价的反思。

这项建议应保留按需读取和独立随机提议两条路径；不能把 V10.9 已试过的直接子代上下文重新变成所有轮次的默认必填材料。

### 4.3 ESS-8 保证分布集中度，不保证不同算法假设

四算子各 25%，只有 Pivot 父代混入 50% 均匀。因此不考虑修复和回退，正常父代的总分布为：

\[
p(i)=0.875q(i)+0.125/|A|.
\]

关键不是 12.5% 必然过少，而是**低分节点通过均匀通道被选中时，得到的是 Pivot，而非围绕它精炼的机会**。它可能被再次改换主机制。当前分数偏低而可校准的实现，仍主要靠质量尾部获得 Refine/Tune。

不建议因此恢复强制 Pivot continuation。历史 E2-B' 的 18 锚点、36 路径没有一个 Pivot continuation 提高第一步已取得的净收益；大量 continuation gain 只是跌落后恢复。这个反例约束了新机制的取舍，不能绕过。

建议在将来的独立版本中考虑：少量与算子解耦的近期候选抽样、明确的无父代重新发现、有限 active population 或独立 island。保留质量主导，不按低分或大行为距离奖励“潜力”，不为每个新节点无条件发后续预算。

### 4.4 一个随机 donor 解决了容量问题，没有解决互补性问题

`select_donor()` 只排除 host 自身及同 AST，然后按质量+均匀抽取。它没有关于 host 当前缺陷、候选兼容性或已有试验的证据。当前 Fuse 指令要求 adapt complementary ideas，却没有给出互补关系本身。

建议先允许模型不采用无用 donor，并把目标写成改善 host 的具体弱点。随后可引入少量候选的按需检索：模型先看到简短实码证据/实测信息，选定后再读完整程序。拒绝 donor 不应导致不交候选，也不需要额外论证表。

当前 V10.13 只出现 15/3131 个重复 AST 节点，约 0.48%。因此不能把副本膨胀说成当前主要败因。完整档案与繁衍池仍应分开，但它是结构改进，不是已证实的大收益来源；更不能用 AST 距离推断算法行为多样性。

### 4.5 上下文映射固定得太早，提示中的算法问题又不够具体

Refine/Tune 固定三条祖先，Pivot/Fuse 固定单参考，是可检验的先验，不是已知最优映射。V11.1 实际 history_depth=8，V10.13=3；两版差异并非仅卡片数量。

同一个算子在不同状态下也需要不同材料：根节点没有祖先，但可能有大量开发经验；Fuse 可能需要 donor 的一个函数及其形成证据；Tune 可能更需要之前几个参数设置，而非宏观算法描述。应围绕当前设计问题取材料，算子名称只给默认值。

提示应更具体地讨论算法改进方式，但不规定字段数、改动行数或固定步骤。主要问题见下一节。

### 4.6 中断恢复尚未做到评价记账一致

`_evaluate_and_add()` 完成实际评价后写 node，`_settle()` 写 event 后才保存 checkpoint；`_resume_checkpoint()` 只加载旧 checkpoint，没有核对完整 journal 尾段。

临时故障注入在第二条 event 追加之后、checkpoint 更新之前抛异常，再恢复：**预算配置=2，实际假 evaluator 调用=3，event 的 evaluation_id 和 candidate_id 均为 [1, 2, 2]**。现有“跑完后再次 resume”测试没有覆盖这个窗口。这是直接复现的可靠性缺陷，不是对当前在线批次已发生事故的指控。

建议持久化 candidate/evaluation 的阶段和唯一 ID：准备、已发起评价、已有结果、已提交；原始响应、调度 RNG 和预算 reservation 应可恢复。已记录的评价结果应重放结算，不能重新评价。对结果未落盘但可能已执行的调用，单独记 uncertain/physical 支出并采取明确恢复策略，不能假装不存在。普通本地文件不能自动保证任意中断下的 exactly-once 执行。

### 4.7 设计文档需要与冻结实现统一

- 文档 Pivot/Fuse 写有三条形成边，`prompts.py:114` 实际只给 Refine/Tune。
- 文档初始化容量不足“失败且不删材料”，实际按最旧根开始移除，并记录 fallback。
- 文档修复复用候选身份，实际生成新 candidate_id 并以 repair_of 关联；复用的是 parent/operator/机会归属。
- 文档实现列表有不存在的 `manual_launch.py`，实际入口是 `launch.py`。

这些不直接决定算法得分，但会误导归因、复现和下一轮设计。应在结束当前批次后的版本文档整理中修正，不能靠文档描述替代实际行为。

## 5. 如何打磨提示与上下文

### 原则

目标是让模型理解**值得改善的计算关系**。提示提供思考方向和开放的算法空间，不要求显示逐步推理，不强制行为证明，不让 Idea 自述充当验证器。

我建议公共前缀只加两层信息：

> Design for the stated objective and interface. Use the problem structure, the current implementation, and measured results to choose a promising algorithmic change. Scores describe whole programs; historical ideas are hypotheses, not verified explanations. Make the intended improvement reach the computation that determines the returned result, while remaining effective across valid input sizes and states.

“跨输入有效”是设计目标，不是保证；不能把 held-out 数据放进这些材料。对于 argmax、归一化采样、逐步构造等消费方式，优先使用冻结任务契约已经说明的事实，不按任务名称注入历史赢家或新增隐藏答案。

### 建议的算子文本

以下是下一版可采用的文本草案，未修改当前运行机制。改进重点是开放的算法改进模式，而不是增加硬规则。

**Init**

> Develop a competitive algorithm using the task structure and your algorithmic knowledge. When previous algorithms are available, use them to identify another promising decision hypothesis. Useful components may be reused, but explore a substantive alternative rather than a cosmetic variation. Aim for a method that can work across the valid inputs described by the interface.

**Refine**

> Treat the current algorithm as a working design. Find a promising way to improve how it represents the remaining problem, compares alternatives, or coordinates its components. Make a coherent improvement while retaining computations that remain useful. Use relevant measured attempts to guide the change; their scores assess the complete program, not individual components.

**Tune**

> Keep the main algorithmic structure and improve the calibration of its decision rule. Consider interactions among influential weights, thresholds, scales, and schedules, including whether they should depend on the current input or search state. Prefer changes that can affect the decisions or sampling performed by the caller over transformations that cancel out downstream.

这里不能统一写成“单调变换无效”：对确定性 argmax，严格递增变换保序；但在按分数归一化的随机采样中，幂次等变换可能改变分布。具体语义由接口确定。仓库 OBP 的 `np.argmax(priorities)` 与 CVRP 的归一化随机抽样正好说明二者不同。

**Pivot**

> Reconsider a central assumption of the current approach. Use the task structure and your algorithmic knowledge to build a competitive alternative with a different way of representing the problem, evaluating choices, or organizing the search. References are optional inspiration; they need not define the new design. Reuse useful parts when appropriate, without making novelty itself the objective.

**Fuse**

> Compare how the host and donor make their decisions. Adapt a donor computation when it can address a weakness of the host, reconciling its scale, assumptions, and interactions with the host's existing mechanism. Aim for a coherent algorithm that can outperform both. If the donor offers no useful contribution, improve the host without forcing a combination.

将 scale、assumptions、interactions 写进 Fuse，比“combine strengths”更直接对应真实组合困难，但不要求模型提交三个字段。

### 上下文应是一份短实验笔记

建议的顺序为：冻结任务契约 → 当前完整实现/必要组件 → 与本次动作有关的真实试验 → 可选外部实现 → 算子任务 → 简短输出接口。

局部试验条目应由日志与代码确定性组装，例如“基于 node 42；实际 diff；整体 fitness -x→-y；错误类型”。不要要求 LLM 先写一份像真的因果总结。按需包含一到两条，保留出处，完整材料留在 archive。

Idea 最好是对提交代码中主机制的简短描述：改什么、在什么情况下可能起作用。它不是内部推理记录，缺失不能拦截有效代码。新 Idea 应与实际 diff 对照供人审阅，但不由另一个语言模型投票决定程序是否值得评价。

## 6. 可以引入的新机制及取舍

### 6.1 结构化输出：值得做，但结构化接口，不结构化创造力

建议仅区分 `full` 与 `edit` 两种响应，并携带可选短 Idea：

```text
FullProposal = {mode: "full", idea?: string, code: string}
EditProposal = {mode: "edit", base_hash: string, idea?: string,
                edits: [{search: string, replacement: string}]}
```

父代、算子、donor、预算身份由系统关联，不让模型重新填写。完整代码仍须接受目标函数、依赖、接口和 evaluator 检查。服务若支持语法/JSON Schema 约束，可用于外层对象；具体部署支持范围需要单独检查，不能因为 JSON 能解析就认为代码正确。

XGrammar 说明结构约束可放在解码接口层；它不提供算法语义正确性的保证。这里首先解决的是本项目已经观察到的说明文字和代码块格式拒收。出处见文末外部依据。

### 6.2 Edit mode：优先给 Refine/Tune 使用，保留完整重写

小改动不一定需要重新生成完整函数。模型提交定位块和替换块，系统在确切父代版本上应用，再保存最终完整程序及实际 diff。Refine/Tune 可默认局部编辑，Pivot 默认 full，Fuse 根据整合范围选择。

实现必须检查 base_hash、唯一定位、修改范围及应用后解析；冲突不能模糊匹配。补丁失败可有界回退 full，不能无限免费重试。任务与 evaluator 保持不可编辑。收益假设是减少非目标代码漂移并保留成熟实现，不是“改动越少质量越高”；太小的补丁也可能抑制必要重组。

仓库已有 `baselines/shinka_evo/sampler.py` 的 diff/full/cross 与 SEARCH/REPLACE，可复用设计经验，但不修改对比方法。外部代码编辑研究也指出原始行号 diff 的脆弱性，支持优先考虑块级、函数级编辑及适应性回退，不证明当前模型一定会从编辑格式获益。

### 6.3 有界工具 agent：价值来自取证与执行反馈

若引入 agent，优先一个设计者按需调用少量工具：读取某个 archived program、查看真实父子 diff、读取局部尝试、在许可训练输入上做小型调用检查、提交候选。一次设计设明确工具/token 上限。

这样 agent 可以决定“我还缺什么信息”，而不是每个算子都预先获得相同卡片。工程静态检查、有限输入的正确性检查和正式 fitness 必须分开记账；有得分信息的额外评价不能藏在免费工具调用里。冻结测试集不作为工具开放。

SWE-agent 的可借鉴点是执行接口和反馈循环。它对软件修复的结果不能直接当成 AAD 质量证据。多角色辩论、让审查者凭文字评算法优劣不是当前优先项：这些动作没有提供新的外部质量信息。

### 6.4 多样性：优先保护独立搜索，不发明通用语义距离

值得考虑两个互补机制：

- **独立 island + 稀疏迁移**：同一真实总预算内维持少量独立繁衍池和随机状态，内部质量选择，偶尔交换候选。岛是人为搜索隔离单元，不是算法类别，也不等于独立实验重复。过多岛会分散 1000 次预算，不预先指定通用最优数量。
- **持续无父代生成**：探索不仅是拿一个 archive 节点再 Pivot，也包括只根据任务契约提出新解法；可与参照式生成随机混合，减弱所有样本围绕同一骨架变体的风险。

FunSearch 的岛模型提供独立演化与信息交流的设计先例。它不证明岛内行为多样，也不能直接照搬其岛数或重置周期。

完整事实档案继续保留；繁衍池可以有限容量，并避免同一可执行代码因重复出现获得额外概率。若缓存评价，只能在程序、任务配置、数据、随机种子和评价环境一致且可复用的条件下进行，不能按相似 AST 直接跳过。缓存与重采样的预算规则需明示。

### 6.5 LLM 结构发现 + 数值优化：最值得认真考虑的混合方向之一

当前 Tune 仍让模型凭语言猜参数。可让 LLM 提出可解释的参数化结构和合理约束，再由小预算随机/数值搜索校准；全部数值候选计入相同 evaluator 预算，改结构后再校准，不能给每个差骨架都附送优化额度。

你已有 CALM 初始化记录显示参数开发能带来真实改进，但该实现含任务专属 seed，不能照搬来证明通用性。新方案的结构应由通用生成流程产生。此分工更直接利用模型的结构知识与搜索器的试验能力；参数之间强耦合、结构本身错误时，数值搜索仍可能无效。

### 6.6 反例驱动反馈与实例级选择

比单个平均分更有信息量的是：同一训练实例上，候选在哪些情形退步、违反了什么契约、哪个状态暴露了问题。可以从已有训练评价保留少量代表失败和父子差异，提供给下一次设计；不额外把整批轨迹塞入 prompt。

若 evaluator 已提供逐实例结果，可研究实例表现向量上的 Pareto/lexicase 类选择，保护在部分训练条件上有优势的程序，不必定义任务无关行为距离。若当前接口只有标量，就先承认需要新增可观测接口和成本，不能假装信息已经存在。较差样本更可能支配选择噪声，需防止对固定训练反例过拟合。

这属于下一版本的评价反馈设计，不能中途改变当前任务合同。训练侧按需取证，最终测试集只用于报告。

### 6.7 可转移的改进经验，而非长期堆积 Idea

更长期的记忆单元可以是“在什么代码/约束下，作什么实码改变，实测结果怎样”，连接 host、donor、child 和后续使用。只有形成边不够，Fuse 的 donor 也是贡献来源。记录可索引的修改事件，不给文字思想强行分配因果信用。

若做检索或模型训练，按任务族/实例生成器拆分，防止把测试赢家作为经验注入。可学习的是改进模式，不是记住五个任务的冠军代码。提示自演化、LLM ensemble 和偏好微调都能考虑，但会增加元优化与计算预算；当前不应排在输出和记忆缺口之前。

V10.13 冻结配置的 `enable_thinking=False` 也值得纳入设计空间：这不意味着模型没有推理能力，但不同动作未必适合相同推理预算。可考虑只让复杂 Pivot/Fuse 使用更充分的推理或第二次实现检查，普通 Tune 保持轻量。额外 token、调用和耗时必须独立报告，不能将它们藏在相同 E1000 后面宣称搜索机制免费提升。

## 7. 我建议的实现优先级

| 优先级 | 下一步动作 | 它减少的不确定性 | 完成标准 |
|---|---|---|---|
| P0 | 代码接受与 Idea 元数据解耦；格式修复保护代码 | 候选是否因无关文字消失 | 可执行接口检查独立；同一代码不因 Idea 长度被重写 |
| P0 | 阶段化 journal 与恢复核对 | 真实评价预算是否可审计 | 故障注入不重用 ID；已落盘结果不重评；未知调用单独记账 |
| P0 | 文档按冻结实现纠偏 | 分析的是哪个真实版本 | 上下文、初始化、repair 身份与入口一致 |
| P1 | 按需局部试验记忆 + 算法改进导向提示 | 模型是否能利用已发生试验 | 不机械恢复 V10.9 默认追加；内容来自实际 diff/分数；保留随机采样路径 |
| P1 | Refine/Tune 可选 edit mode | 成熟实现是否被无关重写破坏 | 精确应用与回退，最终完整程序可重放 |
| P2 | 少量独立 island、持续无父代探索或近期候选机会 | 搜索是否过度共享同一锚点 | 不靠语义标签分组；所有机会从原预算扣除 |
| P2 | 参数化算法 + 小预算数值校准 | LLM 是否在代做低效数值试验 | 结构和校准可分辨，数值评价完整计入 |
| P3 | 按需工具 agent、实例反馈、改进事件检索 | 固定上下文是否缺少关键证据 | 有界交互、引用真实证据、成本可追踪 |

这不是要求现在启动消融。当前批次自然完成后，以同真实评价预算、训练曲线、重复结果和 held-out 判断 V10.13 的质量；文本和接口修复先作本地回归，正式机制变化留在新的冻结版本。没有一个提示模板能保证对任意 task 都优秀；合理目标是让系统在接口明确、评价有效的任务上，能够发现不同解法、利用试验、持续改进并接受独立泛化检验。

我最赞同你坚持的方向，但应增加一项：**多样性、预算、算子提示和上下文，必须通过实际试验反馈连接起来。** 当前系统擅长保存程序和分数，下一步应该更擅长把已经花掉的试验预算转化为下一次设计的信息。

## 外部依据与边界

以下只作为机制先例，均于 2026-09-23 核查；不代表对 TraceAAD 的效果已经验证。

1. XGrammar，arXiv:2411.15100；以及 XGrammar-2，arXiv:2601.04426：语法/结构化生成接口。
2. ShinkaEvolve，arXiv:2509.19349；官方仓库 `SakanaAI/ShinkaEvolve`：diff/full/crossover、种群与参考管理。本项目有可读的本地基线实现。
3. To Diff or Not to Diff?，arXiv:2604.27296：块级/函数级编辑与 full/edit 适应选择，研究场景不等同于启发式算法搜索。
4. SWE-agent，arXiv:2405.15793：取证、编辑、执行测试的 agent 接口，不能将软件修复成绩直接外推为算法质量。
5. FunSearch，Nature，DOI:10.1038/s41586-023-06924-6：独立岛演化和交流，不能外推为任何任务的多样性保证。
