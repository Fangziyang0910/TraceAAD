# CPU 和 GPU 独立调度设想

2026-10-08。状态：已在 V10.21 实现按实例共享 CPU 与按端点共享模型槽位；尚未迁移正式实验。

**为并行实验设置两个独立调度器：CPU 调度器管理评价任务，GPU 调度器管理模型请求。两者各自根据当前负载排队和分配资源，先做好各自的调度，不做跨资源协调、流水线规划或全局最优调度。** 目标是用简单的资源管理提高实验执行效率。

## 实验并行的背景

方法正常运行时，一台机器执行一个算法改进进程。当前启动的 18 路是为了同时完成多组独立实验、缩短实验周期。18 路是实验环境中的并发数量，不是方法本身必须采用的运行方式。

每一路交替执行模型生成和 CPU 评价：先请求 LLM 生成程序，再评价程序，根据结果继续下一次算法改进。因此，启动 18 路不等于同时有 18 路模型请求。讨论时的运行观察是，同一时刻大约只有 5–6 路请求 GPU，其余处于 CPU 评价阶段。

目前各路独立安排执行，评价使用单 worker。CPU 有余量时，单次评价仍可能逐个执行实例；GPU 有余量时，也需要从各路已经准备好的模型请求中安排工作。设想是把这些资源分配交给各自的公共调度器。

## 实验通过请求使用资源

每一路实验保留自己的搜索状态和生成、评价顺序。需要模型输出时，向 GPU 调度器提交一次生成请求；需要评价程序时，向 CPU 调度器提交一次评价请求。实验等待对应结果，再推进自己的搜索。

所有实验共享这两个入口。实验路数、同时执行的模型请求数和 CPU worker 数分别管理，不再通过给每路固定资源配额来安排执行。

| 调度器 | 接收的工作 | 负载较轻时 | 负载较重时 |
| --- | --- | --- | --- |
| CPU 调度器 | 一次程序评价 | 使用可用 CPU；对可并行的评价适当增加 worker，加快该次评价 | 控制同时运行的评价数量和 worker 总量，超出容量的任务排队 |
| GPU 调度器 | 一次 LLM 生成请求 | 有服务容量就从队列发送请求，在可用模型端点之间分配 | 控制在途请求数量，超出容量的请求排队 |

## 评价调用的可配置参数

超时时间和 worker 数量作为评价调用的执行超参数，由调用方显式传入，不写死在评价流程中。

| 参数 | 含义 |
| --- | --- |
| `timeout_seconds` | 每个实例的墙钟时限，默认10秒，包含候选函数与固定框架，不包含排队 |
| `n_workers` | 本次评价的并发上限；共享CPU调度器在这个上限内按可用核心和其他任务需求分配 worker |

**多 worker 指实例之间的并行。** 每个 worker 用同一个候选程序处理一个实例，完成后继续领取尚未评价的实例，最后汇总各实例的结果。例如，16 个实例配置 4 个 worker 时，最多同时评价 4 个实例，每个实例由一个 worker 执行。

评价请求携带这些参数交给 CPU 调度器。每个实例完成后归还核心，等待中的评价优先获得资源，占用较少的评价先得到下一核心；没有其他需求时，同一次评价可扩大并行度。运行中的实例不抢占。日志记录配置上限、实际峰值worker数、核心编号与排队时间，评价计时与计分按对应的[实验准则](../../experiments/PROTOCOL.md)定义。

## 两个调度器独立决策

CPU 调度器只根据自己的资源、运行任务和等待队列决定如何分配 worker。GPU 调度器只根据模型服务容量、在途请求和等待队列决定何时发送请求、发送到哪个端点。

两者不预测另一侧何时需要工作，也不为了另一侧的利用率调整自己的任务优先级。每次有任务提交或资源释放，就在自身容量范围内安排可执行的工作。CPU 和 GPU 的总体能力有上限，现阶段先把各自的空闲资源用起来，避免引入复杂的联合调度。

## 当前确定的范围

这项设想属于多实验共享资源的执行层。各实验继续负责算法改进，两个调度器负责排队与分配，实验领取资源后执行并返回结果。每台机器运行自己的一套两个资源池，自动检测可用CPU，也允许指定核心数量或编号；模型端点和槽位在启动时配置。自适应依据是本资源池的运行任务、等待需求与空闲额度，不比较机器之间的单核性能。

例如，server3完成12路的生成与评价，本机完成另外6路的生成与评价。实验路数、CPU核心额度、GPU请求槽位分别设置。即使两个机器访问同一模型端点，也只需事先把各自槽位额度分好，不增加跨机器协调器。启动入口支持按重复编号分工，保留对应的实验种子。完整命令与记录字段见[V10.21实验入口](../../experiments/traceaad_v10_21/README.md#每台机器独立调度-cpu-与模型请求)。
