# 微调训练与搜索机制并行路线：文献判断、创新边界与实验决策

## 核心判断

微调训练这条路有研究价值，而且比“把更多历史放进提示”更可能形成长期能力积累。但它不能被表述为尚未有人做过的空白：EvoTune、CALM、Fine-tuning LLM for AAD、AHD-Agent 和 Hero 已分别覆盖搜索数据蒸馏、在线 DPO/GRPO、离线偏好微调、搜索控制策略训练和可复用 solver 生成。

因此，TraceAAD 不应把“我们也做微调”作为创新，也不应在没有隔离实验的情况下把微调、预算、算子和轨迹放进同一个大闭环。更合理的判断是：

> **并行推进是正确的项目组织方式；联合验证必须滞后于单因素验证。**

一条线研究固定模型下的搜索机制，另一条线研究把搜索经验写入生成器参数。两条线共享同一 evaluator、候选日志和 held-out 协议，但各自冻结对方变量。只有两条线都产生独立增量后，才做组合实验。

## 为什么微调有真实价值

固定模型的上下文搜索只能在每次请求时重新解释历史。参数训练可能把一批反复出现的可执行结构、错误修复模式和改进方向压缩进生成先验，使相同真实评价预算更快产生有效候选。它的潜在收益不是“模型知道某个最优算法”，而是提高以下条件概率：

1. 输出满足任务接口并能执行；
2. 在给定父代和算子下产生真正的代码变化；
3. 变化符合当前设计状态，而不是重复模板；
4. 候选在未见实例或规模上仍然有效。

这与搜索机制的职责不同。搜索决定评价机会给谁、保存哪些路线、何时探索和何时停止；微调改变候选生成分布。可以把两者写成：

$$
\text{搜索控制器 } \mu(a\mid s) \quad+\quad
\text{生成策略 } \pi_\theta(y\mid s,a).
$$

其中 $s$ 是任务、当前程序、形成关系、失败和评价状态，$a$ 可以是父代、算子或继续开发动作，$y$ 是 Idea 和代码。微调首先应该学习 $\pi_\theta$，不能顺便宣称它已经学会了 $\mu$。

## 近期文献已经做到什么

| 路线 | 代表工作 | 训练对象 | 主要证据 | 仍然缺什么 |
| --- | --- | --- | --- | --- |
| 离线参数适配 | [Fine-tuning LLM for Automated Algorithm Design](https://openreview.net/pdf?id=cbpQSrDV8S)，ICLR 2026 | 代码生成 LLM | 用搜索得到的算法构造 DAR 偏好对，以 DPO 微调；报告随机采样、迭代搜索和 CVRP→TSP/规模变化泛化 | 训练数据仍来自已有搜索；程序族泄漏、任务相似性和 DPO 内部因素需要更严格拆分 |
| 在线搜索—训练闭环 | [EvoTune](https://arxiv.org/abs/2504.05108)，COLM 2025 | 代码生成 LLM | 进化搜索产生候选，RL 周期性更新生成器；与无训练进化基线比较 | RL、全历史采样、退火和重启等机制成套引入；训练算力未与搜索评价预算统一核算 |
| 在线启发式共进化 | [CALM](https://openreview.net/pdf?id=x6bG2Hoqdf)，ICLR 2026 | 本地 7B LLM | 用 prompt–response–performance 三元组做 GRPO，并与仅 verbal guidance 的方法比较 | 训练数据闭环、相对父代 reward、collapse 和算子管理仍高度耦合；未证明每个 reward 项独立必要 |
| 长程搜索控制 | [AHD Agent](https://arxiv.org/abs/2605.08756) | Agent policy | RL 训练模型决定生成、评价、反思和工具调用 | 更多动作、更长轨迹和更多 evaluator 调用可能贡献了收益；需要 frozen-policy、等预算对照 |
| 训练可复用 solver | [Beyond Inference-Time Search](https://arxiv.org/abs/2605.18374) | 直接生成 solver 的代码模型 | GRPO 训练后，一份冻结 solver 可跨实例复用；报告 compile-once 和额外域结果 | 任务 scaffold 和 reward 对领域敏感；训练成本与部署成本必须分开 |
| 发现—训练—再发现 | [Self-Developing](https://arxiv.org/abs/2410.15639) | 算法生成器 | 生成模型合并算法，以模型成绩形成 DPO 偏好，再继续生成 | 跨轮提高可能部分来自累计采样；缺少严格 DPO-off 对照 |

由此可得三个结论。

第一，用户之前认为“现有工作还比较初级”有一半是对的：这些方法已经证明训练闭环可行，但对训练对象、训练数据、搜索控制和泛化的因果归因仍不充分。第二，微调已经从概念验证进入可竞争方向，不能再把“首次把轨迹用于微调”作为新颖性。第三，真正未解决的是**什么经验应该写入参数、在什么条件下写入、写入后是否能跨状态和任务迁移**。

## TraceAAD 可以怎样进入，而不是重复已有工作

最有潜力的切入点不是“轨迹 → DPO”这条字面链条，而是**条件化算法改进策略**：

$$
\pi_\theta(\text{patch/code}\mid
\text{current code},\text{operator},\text{structured evidence}).
$$

其中 structured evidence 由形成轨迹、代码差分、失败事实、前后 fitness、实际求解决策变化和约束组成。形成轨迹只是一个通道，不再被当成所有历史的同义词。

这个方向有四个可以形成贡献的地方：

1. **训练对象明确。** 生成器学习在给定父代和算子下进行有效改写；搜索控制器仍负责机会分配。这样可以解释微调究竟改变了哪一个决策。
2. **样本单位明确。** 不按全局 best 粗暴模仿，而是用同一状态下的候选对、父子差分和后续开发结果构造偏好。一个即时退化但带来后续前沿的 stepping stone，不能与不可执行程序混为同类负样本。
3. **收益定义更严格。** 训练目标不只看单步 fitness，还要检查代码是否真的改变了决策、候选是否被继续开发、固定窗口后的 frontier 是否增长，以及 held-out 是否迁移。
4. **搜索与参数学习可比较。** 在同一真实评价预算下，比较“经验留在上下文”和“经验写入权重”两种利用方式，回答参数化记忆何时值得付出训练成本。

这会把研究问题从“哪个提示更好”提升为“经验应该存在哪里”。可能的存储位置包括当前上下文、外部记忆、搜索控制器统计量和模型参数；它们的效用、成本和遗忘风险可以被直接比较。

## 两条线应如何并行

### 线 A：微调生成器，不改变搜索控制器

先做离线 DPO 或 LoRA，而不是直接上在线 GRPO。原因是当前已有 V10.11/V11 日志可以提供数据，离线方案的训练数据、模型版本和搜索预算更容易审计；在线训练会同时改变数据分布、策略和搜索状态，难以解释。

第一版只比较三种生成器：

- `Base`：冻结预训练模型；
- `DPO-generic`：使用程序质量和可执行性构造的一般偏好对；
- `DPO-structured`：在相同状态下使用形成证据、代码差分、失败和后续收益构造偏好对。

每条数据至少保存：任务契约、父代代码、算子、上下文摘要、候选代码、解析/运行状态、真实 fitness、相对父代变化、代码行为变化、后续开发次数和 held-out 结果。训练/验证/测试必须按实例或程序族切分，不能随机切相邻父子节点，否则模型只是在记忆代码家族。

第一轮不需要大规模训练。可以从 TSP、CVRP、OBP、VRPTW 中抽取已完成搜索状态，先构造几百到几千个状态内偏好对，测试训练是否改变：

1. 可执行率和超时率；
2. 同一父代/算子下的即时改进率；
3. 代码行为变化率，而非仅文本差异；
4. 后续固定窗口内的 frontier gain；
5. 未见规模和未见实例的 held-out；
6. 参数训练成本、训练后推理成本和候选评价成本。

若 `DPO-structured` 只提高训练集 best，而没有提高 held-out 或候选级即时效果，就说明训练数据存在过拟合或标签泄漏。若只提高可执行率但不提高算法质量，应把它定位为 code-validity adapter，不能宣称学会了算法改进。

### 线 B：冻结模型，只改搜索机制

这条线继续处理你已经积累的预算、算子和上下文问题，但必须固定生成模型和训练状态。先比较：

- V10.11 的质量抽样；
- V11 的高分选择；
- 带最低探索配额的节点/路线抽样。

上下文固定为一个版本，不能在调度实验中同时替换轨迹、档案卡和 Fuse 参考。主要指标是 E100/E250/E500/E750/E1000 的 frontier 曲线、路线覆盖、低质量路线首次开发延迟、parent gain、frontier gain、重复间方差和 held-out。

这条线的目标不是先发明更复杂的调度公式，而是判断机会分配是否产生独立增量。V11.1 当前批次仍是 `partial`，不能作为已验证的调度结论，也不能拿来训练正式模型数据；正式恢复前还需要修复日志和 checkpoint 的崩溃一致性缺口。

### 线 C：两条线的交互实验放在最后

只有当线 A 和线 B 各自出现独立增量，才比较四组：

| 生成器 | 搜索机制 | 目的 |
| --- | --- | --- |
| Base | Base search | 总基线 |
| Fine-tuned | Base search | 参数学习单独收益 |
| Base | Improved search | 搜索机制单独收益 |
| Fine-tuned | Improved search | 组合收益与交互项 |

组合实验要检验的不只是最终 best，还包括交互项：微调是否让探索配额更容易转化为有效候选，搜索机制是否减少微调后的模式坍缩。若组合收益不超过两个单独收益的可加范围，不能把“协同”写成贡献。

## 为什么不建议现在直接边搜边训

在线训练当然值得尝试，但不应作为第一步。它至少有四种混杂：

1. 训练 rollout 会额外消耗真实 evaluator 预算；如果名义搜索仍写成 1000 次，实际可能是 1000 次搜索加数百次训练采样；
2. policy 更新改变后续候选分布，后续数据又依赖新 policy，难以区分早期样本、训练算法和搜索控制的作用；
3. 只训练成功样本会造成幸存者偏差，只训练失败样本又可能放大模板性错误；
4. 微调后的模型可能在训练任务上更强，却失去新颖性、跨规模泛化或探索能力。

因此，在线 GRPO 应作为第二阶段：先由离线实验确定训练数据单位、失败分类、算子条件和奖励口径，再用小预算比较 `online update` 与 `frozen model`。训练成本、训练 rollout evaluations、在线搜索 evaluations、GPU 时间和推理时间必须分账。

## 应该把轨迹放在哪里

轨迹仍然可以是主线的一部分，但有三个层次必须分开：

- **推断期轨迹**：给当前请求提供连续形成关系，检验单步候选效应；
- **训练期轨迹**：作为偏好对的条件和信用信息，学习生成器参数；
- **搜索控制轨迹**：记录父代、算子、机会、失败和后续收益，训练或设计预算策略。

这三种轨迹不能混用。生成器训练看到的是“在这个父代和算子条件下，什么改动有效”；控制器训练看到的是“在这个状态下，给哪条路线机会有长期价值”；求解行为轨迹则是候选实现后的诊断信号，不能直接当作形成谱系。

## go/no-go 标准

- **微调主线保留**：在至少两个任务、两个未见状态集合上，`DPO-structured` 相对 `Base` 同时改善候选级即时收益和 held-out，且没有明显降低行为多样性或探索覆盖。
- **微调降级为可执行性适配**：只改善解析/运行成功率，质量和 frontier 没有改善。
- **微调停止作为主线**：只在训练任务或相邻程序族上改善，未见实例退化，或训练成本抵消了等预算收益。
- **搜索机制主线保留**：在冻结生成器和上下文下改善等预算 frontier，并降低重复间方差或路线饿死现象。
- **组合主张成立**：四组实验中存在超出单独收益可加解释的稳定交互，并在 held-out 保持。

如果这些条件都不满足，不能继续增加新算子、更多训练轮次或更长轨迹来掩盖不确定性。

## 最终建议

你的新想法是对的，但需要改成“并行研究、分层验证”，而不是“同时在一个系统里边搜边训”。当前最合理的项目主线是：

> **固定模型的搜索机制研究 + 搜索经验驱动的生成器适配研究，最后研究二者的交互。**

微调方向有搞头，甚至可能比单纯轨迹提示更有长期价值；但它的创新不在于采用 DPO/GRPO，而在于证明结构化算法改进经验如何被参数化、何时泛化、以及与有限预算搜索如何分工。你现有的轨迹、算子和上下文工作不是废料，它们可以变成训练数据定义和条件生成状态；但只有在上述对照下，才能知道它们究竟是在帮助模型学习，还是只是在提示中增加信息量。
