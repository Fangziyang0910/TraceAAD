# V10.24：围绕具体问题的有限开发

本页为历史研究记录。相关旧实现和实验入口已移除，源码请查 Git 历史；当前运行入口见 [V12.0](../../experiments/traceaad_v12_0/README.md)。

历史实现规格：`v1024-shared-development-3`、`v1024-context-3`、`v1024-atomic-edit-1`。六任务各三路、每路 1,000 候选的完整搜索未显示跨任务稳定优势。[结果与成本](../03-现象与检验/2026-10-10-V10.24完整搜索与开发成本.md)

## 设计问题

一个程序的首版成绩同时受到计算思想、实现正确性和成熟程度影响。V10.24 以具体改进问题组织连续开发，保存首版、失败、修复及后续结果，检验少量持续投入能否改善有限预算下的算法产出。它不根据计划格式或首版是否超过前沿来授予第二段预算。

开发状态与评价缓存分开；完整编辑基底与可选历史分开。Question 保存待解决的问题，Change 描述当前修改，Evidence 记录结果如何影响下一步判断。真实代码变化、模型解释和整份程序的评价分别保留。

诊断依据见[前 300 候选分析](2026-10-09-开发对象与搜索决策的诊断和修改建议.md)，交付规则见[成组编辑](2026-10-10-成组编辑与连续开发.md)。

## 1. 开发单元：工作状态与评价缓存分开

一个单元围绕一个具体改进问题工作。来源算子只定义第一轮的目标与材料，之后统一使用 Develop 或 Repair。

| 字段 | 当前含义 |
| --- | --- |
| source | 开题来源 Refine／Crossover／Explore，不决定寿命 |
| anchor_id | 开题时的有效起点，固定且可追溯 |
| proposal_id | 首个实际交付的程序 ID，包含无效或已知源码；无源码时为空 |
| worktip_id | 最近一次有效交付的程序，包括回退到已有版本；可以弱于最好结果 |
| champion_id | 本单元实际交付的有效结果中最好者，可以是缓存程序；不是新发现计数 |
| pending_failure | 尚未解决的失败源码；有效交付才清除，无源码交付失败不改变它 |
| question | 保存首个非空 Question；旧式回复缺失时只用 Effect，不拼接 Change；交付失败也不丢失已提出的问题 |
| trial_ids | 全部尝试、模型解释、真实父代、源码差异与结果，不因回退或缓存而清空 |
| linked_unit_ids | 实际产生或使用当前程序的旧单元；提示优先显示产生起点的单元 |
| block_ids / status | 已授予段及 active／waiting／closed；waiting 不表示已承诺预算 |

三个判断独立进行：源码见过没有、是否有效、是否成为当前工作结果。相同源码直接复用评价，但本次生成仍付费。有效回退更新 worktip；已知失败更新 pending_failure。只有新有效源码能记为块内新发现与新增前沿收益。

Edit 始终绑定一个完整显示的基底，常规为 worktip，Repair 为 pending_failure。默认提示只提供这一份可编辑源码，历史角色用带方向的差异表示，不列入 `available_bases`。完整 Code 仍可实现大范围重组或回退，但不能以未完整提供的历史 ID 冒充合法父代；声明不可用 Base 时记录回退原因，按完整代码本身评价。声明冲突的 edit 不静默改绑。

模型可以调整实现并在 Evidence 中解释原因。问题已解决、没有有依据的下一次检验或明确放弃时，使用 `Status: change_request ...`；本次结果照常评价、计费、入档，随后关闭单元。每次战术 Change 不会覆盖原问题；完整逐轮分析保存并作为可选证据。资源上限结束表示停止当前投入，不表示思想被证伪。

## 2. 预算、起点与参考：各自只承担一种职责

### 2.1 单一预算池与共同开发上限

沿用1000次候选主协议，初始化目标8个有效根、最多16次尝试。初始化、交付失败、重复、Repair、Develop 均收费。服务故障的实际调用仍保留在调用日志，不伪记为算法失败。

\[
R=B-A,\qquad L=\min(4,R).
\]

A 是已完成的候选数；每次实际授予长度 L 的一段。每单元最多两段，即默认最多8次尝试。尾部不足4次时一次授予剩余长度，继续同一问题，不拆成多个单步精炼。每次只按真实尝试扣款；未花预算自然留在 R 中，不需要释放、跨槽分摊或回流账。

### 2.2 新开与续投的唯一分配规则

控制器从“新开”开始，随后在新开与续投之间交替。

- 新开：来源按 Refine → Crossover → Explore 循环，各自从成熟前沿选择 anchor。
- 续投：从 waiting 集合选择等待最久者，同龄按单元 ID；恢复原 question、worktip、pending_failure 和全部档案。
- 当前类型没有可用对象时使用另一类；两者均无对象才结束搜索。
- 首段正常结束进入 waiting；第二段完成、明确放弃或局部上下文无法继续时关闭。
- 续投不检查 Plan、是否超 anchor、是否在前沿，也不限制来源算子。

当前1:1交替是简单的初始配置，不是最优比例。在通常运行中，一个首段会紧接着得到第二段，相当于每个问题最多8次连续机会；等待集合与实际授予仍分别记录。它有意先消除来源资格差异，没有声称已经解决长期机会估计。未来调整比例应依据完整预算产出，不通过增加首轮许可证实现。

**机会成本必须明算。** 若所有单元都用满8次，除初始化与尾部外，每100候选约新开12.5个问题；三来源均匀时，Explore 约4.17次。这比旧四槽方案的Explore约6.25次更少。旧V10.23前300统一截点为1149/5400≈21.28次Explore首版／百候选。它们不是思想数量比较，却说明统一开发会进一步减少开题宽度。只有最终强算法产出与总成本改善，才能说明这项交换有价值。

### 2.3 同分公平的质量前沿

候选池为有效初始化根与各单元 champion。先去重源码，再按原始训练协议、种子、实例顺序的完整成绩向量分组；相同平均分但不同向量仍是不同组。

默认取前8个组位置，同时保留第8位置处全部并列组。质量排名使用竞赛排名：

\[
r_g=1+\#\{h:q_h<q_g\},\qquad
P(g)=\frac{1/r_g}{\sum_{h\in\mathcal F}1/r_h}.
\]

因此同平均目标具有同权，9个同分组全部保留且各得1/9概率。稳定 hash 仅用于标识和确定遍历顺序。组内优先选择此前作为开题 anchor 次数最少的程序，再用本路 RNG 打破并列。相同成绩向量不是相同思想；这个规则只抑制数量优势，不估计长期潜力，也不判断续投资格。

### 2.4 参考与作用入口

五个作用角度仍是信息与表示、输出作用、可见状态与随机性、预测与分解、计算组织。Explore 可参考任一角度，也可提出其他符合TaskCard的问题；没有轴配额、最少次数准入或隐含信息增益。模型必须解释实际输出如何改变固定求解器。

不同源码的有效档案可作为 donor。逐实例互补度保持：

\[
C(a,d)=\frac1N\sum_i[q_i(a)-q_i(d)]_+.
\]

取前3位置及边界全部同互补度者为一侧，其余为另一侧；两侧各半、侧内均匀，另一侧为空时只用现有一侧。这样同互补度不会因 hash 被划成不同资源等级。平均分较差或 C=0 不硬排除。互补度不是某个代码部件的因果证据。

Crossover 首次请求需要完整 donor 源码；装不下时明确记为 Refine 回退，不伪记模型看过 donor。后续证据可以用差异表示，不强制每轮重复 donor。配对实例成绩按剩余容量提供。

### 2.5 收益与诊断

\[
G_b=\max(0,F_b-\min_{p\in P_b}q(p)),\qquad
\rho_b=G_b/c_b,\qquad
\Delta_e=q(a_e)-q(c_e).
\]

F_b 是开段时全局最好值，P_b 只包含段内新有效源码，c_b 包含所有实际尝试。无新有效程序时G=0；空段rho为空；无有效交付时Delta为空。缓存回退可以改变状态，但不产生虚构新收益。各段G的和应等于初始化之后全局最好值的下降；rho用于诊断，不驱动贪心续投。

报告按新开／续投分成本，再按来源和实际算子分解；还要记录交付失败、真实评价、输入／输出、调用、评价CPU、墙钟和最终冻结质量。waiting只能表示未执行机会，不能补写未观察的结果。

## 3. 上下文：完整事实档案，可用决策材料

六任务TaskCard、接口、输出消费关系、评价限制和分数方向不变。只读当前评价可见信息，不将冻结或测试结果加入在线材料。

每轮完整保留宿主绑定的编辑基底。其余材料按实际决策优先级装入，使用真实服务 tokenizer 检查输入上限：

1. 任务契约、完整基底、当前具体问题、已授予段的剩余尝试、本单元全部已试结果的紧凑清单（最多8次）。
2. 首次 Crossover 的完整 donor；无法容纳则以显式回退执行 Refine。
3. 最近两次真实变化、首个提案、修复造成的变化，再到本单元较早尝试。
4. 产生当前起点的实际来源记录，先显示产生该程序的那一次，再看其他相关尝试；关联试验最多采用已有 `history_depth=8`。
5. proposal、champion、anchor、worktip、donor 相对当前基底的去重差异；可选作用入口。

详细试验包含实际 diff、反馈、模型当时的分析，以及失败edit尚未应用的文本。装不下时退到准确的结果记录；对于大型diff只保留能够完整容纳的hunk，并明确标为局部差异，不截断源码片段后冒充完整改动。材料有重复角色时按程序ID去重；当前完整基底不再按多个角色重复提供。

输入上限仍为24,320，输出上限8,192。档案保存所有事实；提示保存实际展示的试验ID、完整源码ID、片段定位、遗漏材料、裁剪原因、prompt_hash与context_version。未展示的记录不声称模型已经看到。空间不足不会触发额外摘要或修复模型调用。

### 3.1 超长的作用范围

先检查最小任务契约、完整基底和交付指令。如果这些本身都装不下，记录 `base_context_too_long`，只排除该实际基底ID。不能将它错误归因到原anchor。

如果基底能装下，但当前问题与必要反馈仍无法容纳，则记 `local_context_too_long`，仅关闭这个开发单元。第二段历史过长不会排除anchor。若一个新开请求在零次尝试时局部失败，仅把相同来源／起点组合记为已失败请求；尝试其他来源或起点，防止零成本重开死循环。这个限制从关闭记录导出，不新增全局程序黑名单。

### 3.2 原子成组 edit 与完整代码后备

同一响应可修改多个有关联的循环、函数或表示；不要求改动小。宿主在同一原始基底上验证所有SEARCH唯一匹配、不重叠，整批应用后检查接口与语法，仅评价完整结果。未改源码保持原样；规范化身份单独用于缓存去重。

匹配失败无源码、不进入评价，保留原工作／失败状态；应用后的无效源码进入Repair。两者都计一次候选。后续轮次吸收新的真实反馈，不另开免费内部搜索。Init默认完整Code；成熟程序也可用完整Code进行大范围重组。

交付协议仍为 `v1024-atomic-edit-1`。开发／上下文协议为 `v1024-shared-development-3` 与 `v1024-context-3`，旧运行不能无记录续接。恢复先核对协议身份，不尝试猜测转换旧的预留状态。

## 4. 实现闭环

```text
按原协议取得有效根
while 仍有候选且存在可用请求：
    结算已结束段的真实成本和前沿增益
    首段完成则等待；第二段或明确放弃则关闭
    交替选择新开问题或恢复最早等待的问题
    授予 min(4, remaining) 次，未来段仍未分配
    绑定完整工作基底，按来源与当前反馈选择上下文
    生成一次成组edit或完整Code
    原子应用、检查完整结果、查缓存；新源码才评价
    有效交付更新worktip及最好结果；失败保留修复目标
    原子保存候选、实际diff、结果、真实支出和开发状态
按原训练前五重评冻结，独立测试另行执行
```

| 文件 | 职责 |
| --- | --- |
| traceaad.py | 共同生命周期、单一预算、缓存交付状态、事件与恢复 |
| delivery.py | 精确定位、成组原子应用、接口与语法检查 |
| policy.py | 原始成绩分组、同分权重、有限控制字段 |
| prompts.py | 任务事实、单基底上下文、确定性证据取舍、完整算子 |
| diagnostics.py | 用途与来源成本、交付成本、上下文状态、收益核对 |
| 实验入口 | 六任务、恢复、诊断与冻结后评价 |

公共评价器、数据、种子、冻结规则和其他版本未修改。每次事件保存受影响单元、段与调度状态，事件可重建完整检查点；恢复本路RNG和精确工作基底。完整代码、真实评价与局部选择概率均可追溯，但模型具体生成概率未知。

## 5. 验证与下一步能改变什么判断

完整搜索结果见[搜索与成本](../03-现象与检验/2026-10-10-V10.24完整搜索与开发成本.md)，未显示跨任务稳定优势。

实现检查覆盖三来源平等续投、弱工作版跨段延续、有效缓存回退、重复失败修复、交付错误后的正常资格、同分边界、精确成本、尾段、放弃、历史压缩、局部超长作用范围、来源优先、各阶段恢复、事件重建、旧版本与公共入口。

验证研究假设分三层，顺序由结果决定：

1. **完整搜索。** 固定 V10.23 代码、模型与当前协议，对比完整 V10.24；当前最低 co6×3×1000，逐路报告训练曲线、最终冻结测试、最差观察值、实际候选/token/CPU 成本。三路不是可靠尾部分位数估计。若研究稳定性需要更多重复，事先固定数量。
2. **提案来源×开发规则。** 同一批固定状态产生旧／新提案，包含全部无效、重复和退化首版。每个实际 proposal 都分别进入旧／新开发材料与工作状态规则；统一四／八候选总成本，包含共享 proposal，固定同样的开发长度。两臂不共享后续结果。回答“新提案是否需要新的开发条件”，而不是只比较筛出的成功例子。
3. **调度的真实闭环。** 固定 V10.24 生成与上下文，首先判断共同开发增加的收益能否补偿开题减少；需要调整时只改变新开／续投比例或共同上限。保持总预算、生成与上下文条件一致。旧日志重排不能替代重新生成的结果。

观察沿因果链组织：首次提出 → 首次有效 → 首次胜 anchor → 首次入围前沿 → 最终采用。未发生保留缺失，不只展示成功谱系。统计“实际作用变化”须核对代码，不能把轴标签或算法名当真值。

新问题更多但结果更差，先查接口理解和实现；相对 anchor 更常成功但终局无收益，先查弱起点恢复与机会成本；训练更好但测试退步，查训练适应与泛化；部分运行仍弱，定位缺首次发现、实现还是续投。只在这些区分能改变决定时增加局部实验。

## 6. 学习决策模型的位置

首版不增加模型选择器或独立反思调用。以后学习的样本应是：

\[
(\text{state, joint request, context version, committed horizon, actual cost, block outcome}).
\]

共同状态要包括前沿、剩余预算与其他可选问题；动作要包括真实起点、问题、参考和材料。当前事件保留可计算的组／组内／donor 概率和确定性选择依据。LLM 问题与代码的生成概率未知，不能把局部概率乘起来宣称已知精确联合动作概率。

预测不同状态下的分数，不等于识别同一状态下不同请求的价值。要学习续投，需补同状态、固定预算的结果；没有执行的请求仍然未知。引入模型以后应比较规则控制器、仅状态模型与包含代码的模型。决策模型作为独立实验检验。

## 7. 当前结论与明确边界

最值得相信的是：函数的有效作用范围决定探索空间，历史会塑造提案分布，失败与修复折叠会破坏开发对象，超过弱父代不等于取得采用价值。它们共同支持重构搜索单位与上下文，而非只改一个算子比例。

计划格式不作为续投资格，源码新颖性与工作状态分开，上下文超长仅影响当前基底或开发单元，同分程序具有相同质量权重。

当前最重要的未知量是：共同开发的收益是否抵得过开题宽度下降，以及选取的历史是否真正改变了模型下一次计算。1:1、四／八次、前沿8位置都是初始参数。原始长程序仍可能超过最小契约容量；确定性diff取舍也未必选中最有价值的片段。下一步依据真实完整搜索的终局产出与成本判断，不预先添加语义控制器。

## 附录：当前实现使用的完整英文算子与输出字段

动态材料按第10节构造。Init用OUTPUT，其余默认EDIT_OUTPUT；没有Plan预算准入提示。以下常量从当前源码提取。

### Init

> ```text
> Create a complete useful starting implementation. Use the supplied solver facts to explain how its output affects the final solution. Avoid repeating the concrete computations shown without a reason.
> ```

### Refine

> ```text
> Refine one concrete part of the anchor's computation. A parameter, representation, implementation or output mapping can be the right target. Complete all edits needed for this one change and preserve independent useful computations. Explain the downstream effect, not the edit size.
> ```

### Explore

> ```text
> Identify and investigate one concrete solver-effect question. Choose one concrete mechanism and implement its first test on the anchor, keeping mature independent parts. A small change with a meaningful effect is valid. Completion, simulation and local improvement are also allowed. If ranking, normalization, masking or unavailable state cancels the proposed effect, choose a compatible implementation.
> ```
