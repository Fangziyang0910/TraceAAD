## 1. 从一般算法设计开始：究竟优化什么

### 1.1 我们交付的是求解行为

记问题实例为 x，生成的函数为 p，固定外层框架为 S。实际比较的是：

\[
F(p)=\frac{1}{N}\sum_{i=1}^{N} L\bigl(S[p](x_i)\bigr).
\]

六任务均越低越好。p 的输出既不一定是解，也不一定直接代表目标值。它可能是下一节点、采样先验、扰动作业或候选移动优先级。因此，开发中最先需要说明的是：

> 输入中哪些信息可用？函数改变什么量？外层框架怎样使用这个量？由此怎样改变最终解？

这条因果链决定了哪些改动有作用。单看函数形式，会同时产生两类误判：把输出值的大变化当成行为变化；把一行很小的变化当成没有算法意义。

例如，对确定性的 argmax 选择，严格单调变换在不改变数值有效性与并列关系时通常不改变选择。对 ACO 的正权重采样，则有：

\[
P(j\mid i)\propto\tau_{ij}^{\alpha}h_{ij}^{\beta}m_{ij}.
\]

忽略截断、附加候选及浮点效应时，同一行乘正数会在归一化中抵消；将 h 改为 h 的幂一般会改变相对概率。实际 OP 评价器还加了 epsilon、截断并扩展候选，所以不能把理想表达式的等价直接宣布为实际程序等价。源码依据为 [OP 的采样与先验处理](../../benchmarks/op_aco/evaluation.py)。

**有用的探索应覆盖能改变外层求解行为的自由度。** 它可以改变信息的估计方式，也可以改变计算的使用位置、概率分布、扰动方向、阶段条件、候选筛选或计算复用。构造和模拟只是其中一部分。

### 1.2 算法结构、实现和使用方式共同决定收益

一个好结构可能因为实现错误、重复计算或接入方式不合适而失败。一个复杂结构也可能即使实现正确仍然不值得采用。需要区分：

1. 目标行为是否针对真实限制；
2. 代码是否真的实现该行为；
3. 该行为是否改善最终目标；
4. 实现代价是否满足约束。

这四件事不是四个独立的评分项。它们是一条因果链。提高正确率不能自动弥补作用方向错误；提高计算量不能自动弥补信息缺失；更快也不能补偿搜索质量被破坏。

TSP 第三路 155→159→160 是一个具体例子。155 用五轮 2-opt 得到 5.8905；159 将轮数改为十轮后超时；160 向量化移动收益计算，保留十轮计算，得到 5.8187。这里有效的改进是实现与搜索强度相配合，不是“时间提示更强”或“算子更大胆”。

算法工程将设计、分析、实现和实验评价组织为反馈循环。我们应借鉴这个循环，而不是只借鉴某一种变异规则。[Sanders，Algorithm Engineering](https://epubs.siam.org/doi/10.1137/1.9781611972900.6)

### 1.3 复杂度不只是 n 的函数，也取决于调用位置

一次性生成静态先验，可以投入与逐决策调用完全不同的计算。重复从头模拟和一次预计算后反复查询，也不能用同一个“增加计算”概念概括。

| 任务 | 函数的实际作用 | 首先要理解的开发对象 |
| --- | --- | --- |
| TSP | 构造过程中选择下一节点 | 候选排序与剩余路径质量之间的关系；局部补全怎样帮助当下决策 |
| CVRP | 每实例一次生成 ACO 边先验 | 容量可行的路线结构如何转成有效边偏好，而非只优化独立边 |
| OP | 每实例一次生成 ACO 边先验 | 奖励、可达性、边间相对概率与采样集中程度怎样配合 |
| FSSP | 为局部搜索返回扰动矩阵与作业集合 | 怎样离开当前局部最优；扰动目标与真实 makespan 的关系 |
| 图着色 | 构造阶段排序，减色阶段排序修复移动 | 两阶段目标不同；何时允许暂时冲突，怎样最终消除冲突 |
| JSSP | 对 Giffler–Thompson 冲突集合排序 | 可见的机器／作业状态怎样帮助选择；函数不能改外层候选集合和调度规则 |

这些是从当前接口提取的事实，不是预先向各任务塞入一种推荐算法。统一方法应统一开发过程，具体计算必须由接口条件决定。

### 1.4 暂时下降与没有价值是两件事

有的改进要同时具备 A 与 B 才有效。A 的单独实现可以暂时变差，或分数不变。只保留逐步最优版本，可能删掉继续实现 B 的起点。

但“有可能是垫脚石”也不能给任意差程序无限预算。合理做法是对一个具体解释承诺有限机会，保存结果，随后与其他机会比较。**非贪心来自保留并检验依赖关系，不来自给差分数加一个神秘的潜力分。**

## 2. LLM 参与后：搜索空间并非固定邻域

传统搜索常把变异视为固定规则。这里实际生成分布是：

\[
p'\sim G_{\theta}\bigl(p'\mid\text{任务契约、实际代码、证据、目标、输出要求}\bigr).
\]

换上下文，就换了可到达程序的分布。父程序、算子、参考和历史不能分别优化后假设相加有效。它们共同决定模型认为“下一步应该写什么”。

我们已有直接证据：V10.20 的 Deepen 读到大量精炼历史时，仍做小修改；改换材料后才产生明显更多计算。形成历史有助于恢复有效细节，也可能把模型锁在已有改法里。**历史既是证据，也是示范。**

LLM 还会出现三种特别重要的偏差：

- 它容易满足眼前的措辞。要求“新的计算种类”，会排除那些只需一行却能改变整体行为的改动；要求每次超过当前版，会鼓励恢复成熟旧代码。
- 它能给改动写出顺畅解释，但解释未必描述实际执行的计算。Design 与 Analysis 必须和源码、结果分开存。
- 它容易把少数结果写成普遍规律。一次失败只证明这个实现、这些条件下没有得到预期结果，不能直接变成“这种方法无效”。

因此，元层面的工作不是不断添加反思文字，而是约束反思的对象：它应比较哪些具体解释、引用什么已经发生的改动、据此改变哪个下一步决定。

## 3. TraceAAD 的特性：优势应从哪里来

TraceAAD 的价值不应等同于“比其他方法存更多历史”。它有机会利用形成过程，识别一个程序怎样获得当前能力、某种改法为什么失败，以及下一次改写应保留或替换什么。

这要求三点：

1. **记录的是可核对的开发证据。** 实际代码、差异、评价条件、逐实例结果与失败信息是事实；算法说明是解释。
2. **过程能跨过单步最优。** 最好程序用于交付，工作程序用于继续开发。二者可以不同。
3. **预算投给具体开发机会。** 不因产生了一个新程序 ID 就忘记前面已经试过什么，也不因共用一个祖先就把所有后代都视为同一思想。

不建立永久的“思想种群”。一个开发记录围绕当下可检验的问题，例如“把整条先验的相对概率调得更集中是否改善采样”。一旦实际计算被替换，记录应说明问题已经改变。交叉允许多个来源，来源图不等于因果贡献图。

## 4. 重新诊断 V10.23：四处相互强化的错位

### 4.1 探索的目标与任务可改进空间错位

V10.23 的 Explore 明确偏向 constructing、simulating、improving what follows。这对 TSP 有帮助，但不是六种接口共同的充分探索方向。前 300 次候选中，Explore 首版在 FSSP 超时 142/182，在图着色超时 129/174，在 JSSP 超时 103/198。

不能由此得出“取消模拟”。TSP 三路都已出现候选补全与局部搜索，说明系统能较稳定进入某些有效计算。更准确的诊断是：**当前探索把一种成功路径推广成了统一语法，忽略了其他有效行为变化。**

仓库最新[当周周报](../06-总结与周报/2026-W41.md)另记录了 OP 整体先验幂变换和 FSSP 随机扰动的局部干预。这些记录强化了上述判断：一行变化也可能改变重要的求解行为。本轮读取了周报及消费者源码，没有重新运行这些干预，本文不将它们当作本轮新增重测。

### 4.2 开发名义上多步，内部仍从最好版本贪心推进

[`_develop()`](../../traceaad/v10_23/traceaad.py)始终从 `exploration['best']` 出发。更差或同分的新版本即使实现了后续需要的计算，也不能默认成为下一步工作版本。这是一个独立于步数的限制。把三步改成十步而不改变状态表示，仍是十步贪心改写。

目前的“保留新计算”也缺少可持续追踪的对象。OP 第三路 235 的逐边补全超时，236 将其删成公式；237 的 Develop 只看到 206→236 的折叠历史，原始提议从材料中消失。指令仍然要求继续新计算，但材料已不支持这一要求。

### 4.3 收益定义容易奖励恢复，而非新增能力

前 300 次、18 路共 136 组三步开发中，93 组改善首个有效版；首版落后于探索起点的 117 组，仅 13 组后来超过起点。直接开发贡献与后续间接贡献必须区分，这些数值不能当作删除开发的因果证据。但它们已经说明“较差首版后来变好”不是充分的投入依据。

CVRP 第三路 190→193 超过了原起点，但实际删掉了新补全计算。这可以是搜索成果，却不能成为“补全思想得到开发”的证据。

### 4.4 调度奖励的对象与最终目标错位

当前父代概率为：

\[
P(i)\propto e^{-\beta(q_i-q_{\min})}\frac{k_i+3r}{n_i+3},
\qquad r=\frac{\sum_i k_i+1}{\sum_i n_i+2}.
\]

质量温度通过不同分数值上的 ESS≈8 校准。这个设计有合理处：兼顾质量与尝试经验，并避免直接用未经缩放的分数。问题主要不在 beta 的形式：

| 现有量／规则 | 它实际表示什么 | 为什么不适合作为全局开发价值 |
| --- | --- | --- |
| k/n | 从一个精确程序出发、超过该程序的频率 | 不含改进幅度、多步结果与完整成本；较差程序恢复更容易 |
| 各算子合并计数 | 多种生成分布混合后的历史 | Explore 的失败会影响 Refine 获得机会 |
| 每个新 ID 独立统计 | 该份代码的尝试数 | 相近变体可以重新取得冷启动先验；一类变体越多，占据的总概率也可能越大 |
| 固定 0.45／0.30／0.25 | 每次动作类别的边际频率 | 不表示一个具体问题需要什么算子与多少后续机会 |
| 1/8 探索获得三步开发 | 随机覆盖部分探索 | 没有把提出、修复、兑现所需机会作为整体安排 |
| 修复后给原尝试记一次成败 | 一次提议加修复的最终结果 | 若仍按一次普通尝试理解成本，会低估真实候选消耗 |
| 参考的分数中位数与代码距离 | 质量与文本差异筛选 | 不说明借哪项计算，也不保证求解行为互补 |

代码哈希去重能消除完全重复，不能消除上述统计单位问题。这些机制叠加后，系统更容易反复生成熟悉的小变体，再用这些变体构成下一步的主要上下文。

证据与逐路统计见[原诊断](2026-10-09-开发对象与搜索决策的诊断和修改建议.md)和[300 次快照](../../experiments_result/traceaad_v10_23/diagnostics/design_review_300.json)。

## 5. 优秀工作提供的是设计约束，不是零件清单

| 工作 | 作者实际处理的对象 | 对本设计的具体影响 |
| --- | --- | --- |
| [Selecting Computations](https://arxiv.org/abs/1207.5879) | 计算的价值来自它怎样改善最后的决策，讨论 selection 与普通 bandit 的差别 | 以预算结束时的交付质量为目标，不能默认最大化每次即时改进就对齐目标 |
| [ReEvo](https://arxiv.org/html/2402.01145v2) | 用好坏代码对比形成短期反思，并积累长期提示；有特定设置下的消融 | 历史要包含可比较的代码与结果；反思是生成条件，不是已验证的因果规律 |
| [DeltaEvolve](https://arxiv.org/html/2602.02919v1) | 以不同精度的语义变化组织演化上下文 | 把“改变了什么”作为证据单位；压缩时保留源码差异与可回查来源 |
| [MCTS-AHD](https://arxiv.org/html/2501.08603v1) | 保留树上多个位置，以后续结果更新祖先并渐进扩展 | 当前分数不能替代后续开发价值；但最大后代分数不证明祖先中的某项计算有因果贡献 |
| [Clade-AHD](https://arxiv.org/html/2602.00549v2) | 汇集带深度衰减的后代证据，并以 Beta 信念与 Thompson sampling 选择 | 应超出单节点经验；但有交叉、删除和上下文变化时，谱系不能直接当作稳定、独立的统计臂 |
| [BaSE](https://arxiv.org/html/2605.29268v2) | 在多条演化轨迹之间分配调用，局部演化规则另行固定 | 机会分配和局部开发是两个层次。它的收益不证明我们应直接拆成多条独立运行 |
| [LACE 作者实现](https://github.com/PJ-NTU/LACE) | 按不同作用组织局部修改、重设计和互补组合，最终使用求解器组合 | 借用“不同决策需要不同材料”。TraceAAD 交付单程序，不能照搬组合目标或相应运行预算 |

补充材料还促使我核对了两项不同层面的工作：[AlphaEvolve](https://arxiv.org/abs/2506.13131)用直接代码修改与评价反馈组织演化，其可迁移之处是代码和评价共同定义发现过程；[ShinkaEvolve](https://arxiv.org/abs/2509.19349)分别处理父代采样、代码新颖性筛选和模型集成选择。后者的 bandit 用于选择 LLM，不能直接被说成已经解决本项目的开发预算分配。本次核对的是这两篇作者摘要；附件对其他论文的更细解释保留原出处，不冒充本轮重新全文复核。

这些文献支持重新组织问题，但没有哪篇证明下面整套 V10.24 规则有效。尤其不能把后代回传、语义记忆、bandit 和反思全部叠加，便称为全局优化。

## 6. 全局目标与近似边界

设 H 为截至当前的完整可见记录，b 为剩余候选预算。动作 a 包含开发对象、参考、算子和上下文。以当前训练目标为在线代理，理想控制问题是：

\[
V_0(H)=\min_{p\in\mathcal A(H)} F(p),
\]

\[
V_b(H)=\min_{a:c(a)\le b}\mathbb E\left[V_{b-c(a)}(H\cup O_a)\mid H,a\right].
\]

这里 O 包含有效程序、失败以及由此改变的下一步材料。初始化尚无有效程序时，终端损失视为无穷；取得有效根后才进入常规开发。

这个表达式说明三件事：

- 即时成绩差，不代表后续价值低；
- 获得信息只有在改变后续选择时才有价值；
- 同一动作的价值依赖剩余预算以及可替代的其他动作。

**它是设计目标，不是声称系统能精确求解的公式。** 当前没有可靠的转移模型，也没有足够数据估计每个开发过程的终端收益分布。不能写一个“预期收益＋新颖性＋信息增益＋潜力”的加权式，再给四项填主观数字冒充求解。

当前实现采取可执行近似：所有来源共用有限开发长度；开题与续投采用固定交替；质量前沿只选择成熟起点；模型根据实际代码与证据提出改动。首轮计划、即时质量、新颖性和上下文长度，各自不再承担超出本身含义的资格判断。这个控制器不声称能够预测长期价值。

最终泛化仍由冻结后的独立测试评价。只看固定训练结果无法保证消除对训练实例或固定随机种子的适应；本设计不暗中改变评价协议来解决这个问题。

## 7. 本轮重构的依据与取舍

[机制审阅原文](资料/2026-10-10-V10.24-机制审阅原文.txt)针对 `b9a649c6`。其中报告的外部测试与 token 数是审阅者的记录；本轮另外核对了实际代码，并新增独立重放，不把原文完成声明当成本地执行事实。

共同问题是局部规则获得了过大的决策权：首轮计划格式决定后续资源；代码新颖性决定当前工作状态；局部材料超长决定全局起点资格；平均分相同的 hash 顺序决定采样权重。它们需要一起改，才能保持连续开发。

| 原实现 | 当前规则 | 对应问题 |
| --- | --- | --- |
| 只有 Explore 进入普通续投 | Refine、Crossover、Explore 共用最多两段 | 计算依赖不由算子名称决定 |
| 首轮 Plan 授权、预留、四槽与回流 | 一个剩余预算池；开题与续投交替 | 文本计划不证明资源价值，交付失败不额外丧失资格 |
| 当前前沿决定续投资格 | 所有完成首段的未放弃问题均可等待 | 低分工作版仍可能包含下一步所需计算 |
| 仅新有效程序更新 worktip | 所有有效交付均更新，包括缓存回退 | 去重不决定工作状态 |
| known failure 清除失败 | 保留具体失败源码继续 Repair | 重复失败并未解决问题 |
| 多角色完整源码与全部 diff 必须同时显示 | 完整编辑基底；其余按来源与反馈选择表达 | 档案完整不等于每次提示完整复读 |
| 平均分并列按 hash 排名 | 并列质量同权，边界并列全部保留 | 标识不应创造质量差异 |
| 五轴按开题次数均衡 | 五轴仅作可选思考入口 | 投入次数不是覆盖知识或学习成果 |

原子 edit、源码保真、真实候选计费、完整事件与断点恢复继续保留。未增加摘要模型、语义记忆服务或潜力评分器。

## 8. 开发单元：工作状态与评价缓存分开

一个单元围绕一个具体改进问题工作。来源算子只定义第一轮的目标与材料，之后统一使用 Develop 或 Repair。

| 字段 | 当前含义 |
| --- | --- |
| source | 开题来源 Refine／Crossover／Explore，不决定寿命 |
| anchor_id | 开题时的有效起点，固定且可追溯 |
| proposal_id | 首个实际交付的程序 ID，包含无效或已知源码；无源码时为空 |
| worktip_id | 最近一次有效交付的程序，包括回退到已有版本；可以弱于最好结果 |
| champion_id | 本单元实际交付的有效结果中最好者，可以是缓存程序；不是新发现计数 |
| pending_failure | 尚未解决的失败源码；有效交付才清除，无源码交付失败不改变它 |
| question | 保存首个非空 Question；旧式回复缺失时只用 Effect，不拼接 Change；交付失败也不丢失已提出的问题 |
| trial_ids | 全部尝试、模型解释、真实父代、源码差异与结果，不因回退或缓存而清空 |
| linked_unit_ids | 实际产生或使用当前程序的旧单元；提示优先显示产生起点的单元 |
| block_ids / status | 已授予段及 active／waiting／closed；waiting 不表示已承诺预算 |

三个判断独立进行：源码见过没有、是否有效、是否成为当前工作结果。相同源码直接复用评价，但本次生成仍付费。有效回退更新 worktip；已知失败更新 pending_failure。只有新有效源码能记为块内新发现与新增前沿收益。

Edit 始终绑定一个完整显示的基底，常规为 worktip，Repair 为 pending_failure。默认提示只提供这一份可编辑源码，历史角色用带方向的差异表示，不列入 `available_bases`。完整 Code 仍可实现大范围重组或回退，但不能以未完整提供的历史 ID 冒充合法父代；声明不可用 Base 时记录回退原因，按完整代码本身评价。声明冲突的 edit 不静默改绑。

模型可以调整实现并在 Evidence 中解释原因。问题已解决、没有有依据的下一次检验或明确放弃时，使用 `Status: change_request ...`；本次结果照常评价、计费、入档，随后关闭单元。每次战术 Change 不会覆盖原问题；完整逐轮分析保存并作为可选证据。资源上限结束表示停止当前投入，不表示思想被证伪。

## 9. 预算、起点与参考：各自只承担一种职责

### 9.1 单一预算池与共同开发上限

沿用1000次候选主协议，初始化目标8个有效根、最多16次尝试。初始化、交付失败、重复、Repair、Develop 均收费。服务故障的实际调用仍保留在调用日志，不伪记为算法失败。

\[
R=B-A,\qquad L=\min(4,R).
\]

A 是已完成的候选数；每次实际授予长度 L 的一段。每单元最多两段，即默认最多8次尝试。尾部不足4次时一次授予剩余长度，继续同一问题，不拆成多个单步精炼。每次只按真实尝试扣款；未花预算自然留在 R 中，不需要释放、跨槽分摊或回流账。

### 9.2 新开与续投的唯一分配规则

控制器从“新开”开始，随后在新开与续投之间交替。

- 新开：来源按 Refine → Crossover → Explore 循环，各自从成熟前沿选择 anchor。
- 续投：从 waiting 集合选择等待最久者，同龄按单元 ID；恢复原 question、worktip、pending_failure 和全部档案。
- 当前类型没有可用对象时使用另一类；两者均无对象才结束搜索。
- 首段正常结束进入 waiting；第二段完成、明确放弃或局部上下文无法继续时关闭。
- 续投不检查 Plan、是否超 anchor、是否在前沿，也不限制来源算子。

当前1:1交替是简单的初始配置，不是最优比例。在通常运行中，一个首段会紧接着得到第二段，相当于每个问题最多8次连续机会；等待集合与实际授予仍分别记录。它有意先消除来源资格差异，没有声称已经解决长期机会估计。未来调整比例应依据完整预算产出，不通过增加首轮许可证实现。

**机会成本必须明算。** 若所有单元都用满8次，除初始化与尾部外，每100候选约新开12.5个问题；三来源均匀时，Explore 约4.17次。这比旧四槽方案的Explore约6.25次更少。旧V10.23前300统一截点为1149/5400≈21.28次Explore首版／百候选。它们不是思想数量比较，却说明统一开发会进一步减少开题宽度。只有最终强算法产出与总成本改善，才能说明这项交换有价值。

### 9.3 同分公平的质量前沿

候选池为有效初始化根与各单元 champion。先去重源码，再按原始训练协议、种子、实例顺序的完整成绩向量分组；相同平均分但不同向量仍是不同组。

默认取前8个组位置，同时保留第8位置处全部并列组。质量排名使用竞赛排名：

\[
r_g=1+\#\{h:q_h<q_g\},\qquad
P(g)=\frac{1/r_g}{\sum_{h\in\mathcal F}1/r_h}.
\]

因此同平均目标具有同权，9个同分组全部保留且各得1/9概率。稳定 hash 仅用于标识和确定遍历顺序。组内优先选择此前作为开题 anchor 次数最少的程序，再用本路 RNG 打破并列。相同成绩向量不是相同思想；这个规则只抑制数量优势，不估计长期潜力，也不判断续投资格。

### 9.4 参考与作用入口

五个作用角度仍是信息与表示、输出作用、可见状态与随机性、预测与分解、计算组织。Explore 可参考任一角度，也可提出其他符合TaskCard的问题；没有轴配额、最少次数准入或隐含信息增益。模型必须解释实际输出如何改变固定求解器。

不同源码的有效档案可作为 donor。逐实例互补度保持：

\[
C(a,d)=\frac1N\sum_i[q_i(a)-q_i(d)]_+.
\]

取前3位置及边界全部同互补度者为一侧，其余为另一侧；两侧各半、侧内均匀，另一侧为空时只用现有一侧。这样同互补度不会因 hash 被划成不同资源等级。平均分较差或 C=0 不硬排除。互补度不是某个代码部件的因果证据。

Crossover 首次请求需要完整 donor 源码；装不下时明确记为 Refine 回退，不伪记模型看过 donor。后续证据可以用差异表示，不强制每轮重复 donor。配对实例成绩按剩余容量提供。

### 9.5 收益与诊断

\[
G_b=\max(0,F_b-\min_{p\in P_b}q(p)),\qquad
\rho_b=G_b/c_b,\qquad
\Delta_e=q(a_e)-q(c_e).
\]

F_b 是开段时全局最好值，P_b 只包含段内新有效源码，c_b 包含所有实际尝试。无新有效程序时G=0；空段rho为空；无有效交付时Delta为空。缓存回退可以改变状态，但不产生虚构新收益。各段G的和应等于初始化之后全局最好值的下降；rho用于诊断，不驱动贪心续投。

报告按新开／续投分成本，再按来源和实际算子分解；还要记录交付失败、真实评价、输入／输出、调用、评价CPU、墙钟和最终冻结质量。waiting只能表示未执行机会，不能补写未观察的结果。

## 10. 上下文：完整事实档案，可用决策材料

六任务TaskCard、接口、输出消费关系、评价限制和分数方向不变。只读当前评价可见信息，不将冻结或测试结果加入在线材料。

每轮完整保留宿主绑定的编辑基底。其余材料按实际决策优先级装入，使用真实服务 tokenizer 检查输入上限：

1. 任务契约、完整基底、当前具体问题、已授予段的剩余尝试、本单元全部已试结果的紧凑清单（最多8次）。
2. 首次 Crossover 的完整 donor；无法容纳则以显式回退执行 Refine。
3. 最近两次真实变化、首个提案、修复造成的变化，再到本单元较早尝试。
4. 产生当前起点的实际来源记录，先显示产生该程序的那一次，再看其他相关尝试；关联试验最多采用已有 `history_depth=8`。
5. proposal、champion、anchor、worktip、donor 相对当前基底的去重差异；可选作用入口。

详细试验包含实际 diff、反馈、模型当时的分析，以及失败edit尚未应用的文本。装不下时退到准确的结果记录；对于大型diff只保留能够完整容纳的hunk，并明确标为局部差异，不截断源码片段后冒充完整改动。材料有重复角色时按程序ID去重；当前完整基底不再按多个角色重复提供。

输入上限仍为24,320，输出上限8,192。档案保存所有事实；提示保存实际展示的试验ID、完整源码ID、片段定位、遗漏材料、裁剪原因、prompt_hash与context_version。未展示的记录不声称模型已经看到。空间不足不会触发额外摘要或修复模型调用。

### 10.1 超长的作用范围

先检查最小任务契约、完整基底和交付指令。如果这些本身都装不下，记录 `base_context_too_long`，只排除该实际基底ID。不能将它错误归因到原anchor。

如果基底能装下，但当前问题与必要反馈仍无法容纳，则记 `local_context_too_long`，仅关闭这个开发单元。第二段历史过长不会排除anchor。若一个新开请求在零次尝试时局部失败，仅把相同来源／起点组合记为已失败请求；尝试其他来源或起点，防止零成本重开死循环。这个限制从关闭记录导出，不新增全局程序黑名单。

### 10.2 原子成组 edit 与完整代码后备

同一响应可修改多个有关联的循环、函数或表示；不要求改动小。宿主在同一原始基底上验证所有SEARCH唯一匹配、不重叠，整批应用后检查接口与语法，仅评价完整结果。未改源码保持原样；规范化身份单独用于缓存去重。

匹配失败无源码、不进入评价，保留原工作／失败状态；应用后的无效源码进入Repair。两者都计一次候选。后续轮次吸收新的真实反馈，不另开免费内部搜索。Init默认完整Code；成熟程序也可用完整Code进行大范围重组。

交付协议仍为 `v1024-atomic-edit-1`。本轮开发／上下文改变另记为 `v1024-shared-development-3` 与 `v1024-context-3`，旧运行不能无记录续接。恢复先核对协议身份，不尝试猜测转换旧的预留状态。

## 11. 实现闭环

```text
按原协议取得有效根
while 仍有候选且存在可用请求：
    结算已结束段的真实成本和前沿增益
    首段完成则等待；第二段或明确放弃则关闭
    交替选择新开问题或恢复最早等待的问题
    授予 min(4, remaining) 次，未来段仍未分配
    绑定完整工作基底，按来源与当前反馈选择上下文
    生成一次成组edit或完整Code
    原子应用、检查完整结果、查缓存；新源码才评价
    有效交付更新worktip及最好结果；失败保留修复目标
    原子保存候选、实际diff、结果、真实支出和开发状态
按原训练前五重评冻结，独立测试另行执行
```

## 12. 验证与下一步能改变什么判断

当前已实现并运行离线机制检查；尚未用真实模型取得 V10.24 的搜索效果结论。最新测试范围与命令集中在[实验入口](../../experiments/traceaad_v10_24/README.md)，避免在多份设计文档维护不一致的通过数。

实现检查覆盖三来源平等续投、弱工作版跨段延续、有效缓存回退、重复失败修复、交付错误后的正常资格、同分边界、精确成本、尾段、放弃、历史压缩、局部超长作用范围、来源优先、各阶段恢复、事件重建、旧版本与公共入口。

验证研究假设分三层，顺序由结果决定：

1. **完整搜索。** 固定 V10.23 代码、模型与当前协议，对比完整 V10.24；当前最低 co6×3×1000，逐路报告训练曲线、最终冻结测试、最差观察值、实际候选/token/CPU 成本。三路不是可靠尾部分位数估计。若研究稳定性需要更多重复，事先固定数量。
2. **提案来源×开发规则。** 同一批固定状态产生旧／新提案，包含全部无效、重复和退化首版。每个实际 proposal 都分别进入旧／新开发材料与工作状态规则；统一四／八候选总成本，包含共享 proposal，固定同样的开发长度。两臂不共享后续结果。回答“新提案是否需要新的开发条件”，而不是只比较筛出的成功例子。
3. **调度的真实闭环。** 固定 V10.24 生成与上下文，首先判断共同开发增加的收益能否补偿开题减少；需要调整时只改变新开／续投比例或共同上限。保持总预算、生成与上下文条件一致。旧日志重排不能替代重新生成的结果。

观察沿因果链组织：首次提出 → 首次有效 → 首次胜 anchor → 首次入围前沿 → 最终采用。未发生保留缺失，不只展示成功谱系。统计“实际作用变化”须核对代码，不能把轴标签或算法名当真值。

新问题更多但结果更差，先查接口理解和实现；相对 anchor 更常成功但终局无收益，先查弱起点恢复与机会成本；训练更好但测试退步，查训练适应与泛化；部分运行仍弱，定位缺首次发现、实现还是续投。只在这些区分能改变决定时增加局部实验。

## 13. 学习决策模型的位置

首版不增加模型选择器或独立反思调用。以后学习的样本应是：

\[
(\text{state, joint request, context version, committed horizon, actual cost, block outcome}).
\]

共同状态要包括前沿、剩余预算与其他可选问题；动作要包括真实起点、问题、参考和材料。当前事件保留可计算的组／组内／donor 概率和确定性选择依据。LLM 问题与代码的生成概率未知，不能把局部概率乘起来宣称已知精确联合动作概率。

预测不同状态下的分数，不等于识别同一状态下不同请求的价值。要学习续投，需补同状态、固定预算的结果；没有执行的请求仍然未知。引入模型以后应比较规则控制器、仅状态模型与包含代码的模型。当前正在进行的决策模型实验独立保留，不因本版设计自动改变条件。

## 14. 当前结论与明确边界

最值得相信的是：函数的有效作用范围决定探索空间，历史会塑造提案分布，失败与修复折叠会破坏开发对象，超过弱父代不等于取得采用价值。它们共同支持重构搜索单位与上下文，而非只改一个算子比例。

本轮消除了四种不成立的推断：计划写全不代表值得更多预算；源码已知不代表工作状态不变；历史装不下不代表起点不可用；同分hash先后不代表质量不同。修复这些边界可以由程序轨迹验证，但不等于证明搜索效果更强。

当前最重要的未知量是：共同开发的收益是否抵得过开题宽度下降，以及选取的历史是否真正改变了模型下一次计算。1:1、四／八次、前沿8位置都是初始参数。原始长程序仍可能超过最小契约容量；确定性diff取舍也未必选中最有价值的片段。下一步依据真实完整搜索的终局产出与成本判断，不预先添加语义控制器。

## 附录：当前实现使用的完整英文算子与输出字段

动态材料按第10节构造。Init用OUTPUT，其余默认EDIT_OUTPUT；没有Plan预算准入提示。以下常量从当前源码提取。

### Init

> ```text
> Create a complete useful starting implementation. Use the supplied solver facts to explain how its output affects the final solution. Avoid repeating the concrete computations shown without a reason.
> ```

### Refine

> ```text
> Refine one concrete part of the anchor's computation. A parameter, representation, implementation or output mapping can be the right target. Complete all edits needed for this one change and preserve independent useful computations. Explain the downstream effect, not the edit size.
> ```

### Explore

> ```text
> Identify and investigate one concrete solver-effect question. Choose one concrete mechanism and implement its first test on the anchor, keeping mature independent parts. A small change with a meaningful effect is valid. Completion, simulation and local improvement are also allowed. If ranking, normalization, masking or unavailable state cancels the proposed effect, choose a compatible implementation.
> ```

### Crossover

> ```text
> Identify one concrete computation in the reference that could help the anchor. Explain its connection point, required inputs/state and downstream effect. Implement the integration and resolve normalization, filtering and return-contract interactions. Paired scores suggest complementarity but do not identify the causal component. A weaker reference can still help.
> ```

### Develop

> ```text
> Investigate the current solver-effect question using the observed trials. The first Change was a tested hypothesis, not an instruction to repeat. Explain what the results support or contradict, which useful computations remain, and what the next change will test. Temporary score loss is allowed; the host separately retains the best result. A rollback may support a different next test, but returning to a known program produces no new evidence. Do not cycle between tested alternatives. If the question is resolved or you have no justified next test, declare change_request to close this unit; you may return the unchanged bound program. Replacing an implementation does not show that the original mechanism matured.
> ```

### Repair

> ```text
> Repair the failed implementation using the actual failure evidence. For execution failure inspect repeated work, shared/batched/incremental computations and the placement of internal search. Retain the intended output effect where feasible. State which computations you retain, change or remove. Replacing code can serve the same question; explicitly declare change_request if you abandon that question. Call progress does not estimate an overshoot factor.
> ```

### OUTPUT

> ```text
> [Output Format]
> Analysis: (about 120 words total)
> Base: <one ID from available_bases; explain a return to anchor/champion in Evidence>
> Question: <solver behavior to investigate, separate from this particular implementation>
> Change: <one concrete computation and code location>
> Effect: <how the returned value changes the solver's behavior>
> Evidence: <relevant observation, base choice and remaining uncertainty>
> Status: <continue_request or change_request, followed by a reason>
> Design: <at most 60 words describing what the actual code below computes>
> Code:
> ```python
> <complete self-contained implementation with the original interface>
> ```
> Write no comments or docstrings in the code, and nothing after the code block.
>
> ```

### EDIT_OUTPUT

> ```text
> [Output Format]
> Analysis: (about 120 words total)
> Question: <on the first trial, the solver-effect question; on later trials, retain that question>
> Change: <one solver-effect change, including all code locations that must change together>
> Effect: <how the returned value changes the solver's behavior>
> Evidence: <observed results and what remains uncertain>
> Status: <continue_request for another test; change_request to close a resolved or abandoned question, with a reason>
> Design: <at most 60 words describing the resulting algorithm>
> Edits:
> <<<<<<< SEARCH
> <exact existing text, with indentation and enough context to match uniquely>
> =======
> <complete replacement computation>
> >>>>>>> REPLACE
>
> Default to a batch of structurally complete edits to the host-bound editing base.
> Submit every known dependent change in this same response. All SEARCH fragments
> must match the ORIGINAL bound source, not the result of another edit in this batch.
> Regions must not overlap; combine dependent or overlapping regions into one block.
> Use an existing nonempty fragment as an anchor for additions; an empty replacement
> deletes that fragment. The host applies the whole batch atomically and evaluates
> one complete result. Source outside the edited regions is retained by the host.
> Do not optimize for the fewest changed lines. Whole loops, helpers and functions
> may be replaced together when that completes one coherent algorithm change.
> If the program is short or a broad rewrite is clearer, use Code: followed by one
> complete Python code block INSTEAD of Edits. Only for complete Code, an optional
> Base: ID in Analysis may select another fully supplied base; explain it in Evidence.
> Edits always target the host-bound base: omit Base, and do not copy a hash.
> Copy SEARCH from that current source, never from a historical diff or failed edit.
> Prefer short unique SEARCH fragments to copying long unchanged bodies. Preserve
> all source whitespace in SEARCH. Check that the replacement is not already present.
> Keep the original interface and include required imports/helpers. Add no comments
> or docstrings. Formatting wrappers are optional; return only one delivery mode.
>
> ```
