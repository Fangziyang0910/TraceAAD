# 从求解行为到开发决策：V10.24 全局设计

2026-10-09。**设计提案，尚未实现、运行或证明优于 V10.23。** 本文替代同日[局部修改建议](2026-10-09-开发对象与搜索决策的诊断和修改建议.md)中的实施路线，保留其中的事实诊断。评价器、训练／测试划分、1000 次候选口径、最终单程序选择均遵守[实验准则](../../experiments/PROTOCOL.md)。本次不修改正在运行的搜索或决策模型实验。

**我的判断：V10.23 的主要限制，是把算法开发组织成了围绕单份程序的短期改写。它没有充分表示“这项改动为什么可能改变求解行为、当前实现处于什么阶段、还需要哪些计算才能兑现、是否值得继续投入”。V10.24 应将一次有依据、有期限的开发作为搜索决策单位。**

全局重构围绕一个闭环：理解输出怎样影响固定求解器 → 提出具体的改进解释 → 实现与修正 → 以实际结果更新解释 → 在不同开发机会之间分配后续预算。这里的解释可以很小：改变 ACO 先验的集中程度，可能比新增一套模拟器更重要。不能按代码长度、算法名称或计算量给想法分等级。

## 1. 从一般算法设计开始：究竟优化什么

### 1.1 我们交付的是求解行为

记问题实例为 x，生成的函数为 p，固定外层框架为 S。实际比较的是：

\[
F(p)=\frac{1}{N}\sum_{i=1}^{N} L\bigl(S[p](x_i)\bigr).
\]

六任务均越低越好。p 的输出既不一定是解，也不一定直接代表目标值。它可能是下一节点、采样先验、扰动作业或候选移动优先级。因此，开发中最先需要说明的是：

> 输入中哪些信息可用？函数改变什么量？外层框架怎样使用这个量？由此怎样改变最终解？

这条因果链决定了哪些改动有作用。单看函数形式，会同时产生两类误判：把输出值的大变化当成行为变化；把一行很小的变化当成没有算法意义。

例如，对确定性的 argmax 选择，严格单调变换在不改变数值有效性与并列关系时通常不改变选择。对 ACO 的正权重采样，则有：

\[
P(j\mid i)\propto\tau_{ij}^{\alpha}h_{ij}^{\beta}m_{ij}.
\]

忽略截断、附加候选及浮点效应时，同一行乘正数会在归一化中抵消；将 h 改为 h 的幂一般会改变相对概率。实际 OP 评价器还加了 epsilon、截断并扩展候选，所以不能把理想表达式的等价直接宣布为实际程序等价。源码依据为 [OP 的采样与先验处理](../../benchmarks/op_aco/evaluation.py)。

**有用的探索应覆盖能改变外层求解行为的自由度。** 它可以改变信息的估计方式，也可以改变计算的使用位置、概率分布、扰动方向、阶段条件、候选筛选或计算复用。构造和模拟只是其中一部分。

### 1.2 算法结构、实现和使用方式共同决定收益

一个好结构可能因为实现错误、重复计算或接入方式不合适而失败。一个复杂结构也可能即使实现正确仍然不值得采用。需要区分：

1. 目标行为是否针对真实限制；
2. 代码是否真的实现该行为；
3. 该行为是否改善最终目标；
4. 实现代价是否满足约束。

这四件事不是四个独立的评分项。它们是一条因果链。提高正确率不能自动弥补作用方向错误；提高计算量不能自动弥补信息缺失；更快也不能补偿搜索质量被破坏。

TSP 第三路 155→159→160 是一个具体例子。155 用五轮 2-opt 得到 5.8905；159 将轮数改为十轮后超时；160 向量化移动收益计算，保留十轮计算，得到 5.8187。这里有效的改进是实现与搜索强度相配合，不是“时间提示更强”或“算子更大胆”。

算法工程将设计、分析、实现和实验评价组织为反馈循环。我们应借鉴这个循环，而不是只借鉴某一种变异规则。[Sanders，Algorithm Engineering](https://epubs.siam.org/doi/10.1137/1.9781611972900.6)

### 1.3 复杂度不只是 n 的函数，也取决于调用位置

一次性生成静态先验，可以投入与逐决策调用完全不同的计算。重复从头模拟和一次预计算后反复查询，也不能用同一个“增加计算”概念概括。

| 任务 | 函数的实际作用 | 首先要理解的开发对象 |
| --- | --- | --- |
| TSP | 构造过程中选择下一节点 | 候选排序与剩余路径质量之间的关系；局部补全怎样帮助当下决策 |
| CVRP | 每实例一次生成 ACO 边先验 | 容量可行的路线结构如何转成有效边偏好，而非只优化独立边 |
| OP | 每实例一次生成 ACO 边先验 | 奖励、可达性、边间相对概率与采样集中程度怎样配合 |
| FSSP | 为局部搜索返回扰动矩阵与作业集合 | 怎样离开当前局部最优；扰动目标与真实 makespan 的关系 |
| 图着色 | 构造阶段排序，减色阶段排序修复移动 | 两阶段目标不同；何时允许暂时冲突，怎样最终消除冲突 |
| JSSP | 对 Giffler–Thompson 冲突集合排序 | 可见的机器／作业状态怎样帮助选择；函数不能改外层候选集合和调度规则 |

这些是从当前接口提取的事实，不是预先向各任务塞入一种推荐算法。统一方法应统一开发过程，具体计算必须由接口条件决定。

### 1.4 暂时下降与没有价值是两件事

有的改进要同时具备 A 与 B 才有效。A 的单独实现可以暂时变差，或分数不变。只保留逐步最优版本，可能删掉继续实现 B 的起点。

但“有可能是垫脚石”也不能给任意差程序无限预算。合理做法是对一个具体解释承诺有限机会，保存结果，随后与其他机会比较。**非贪心来自保留并检验依赖关系，不来自给差分数加一个神秘的潜力分。**

## 2. LLM 参与后：搜索空间并非固定邻域

传统搜索常把变异视为固定规则。这里实际生成分布是：

\[
p'\sim G_{\theta}\bigl(p'\mid\text{任务契约、实际代码、证据、目标、输出要求}\bigr).
\]

换上下文，就换了可到达程序的分布。父程序、算子、参考和历史不能分别优化后假设相加有效。它们共同决定模型认为“下一步应该写什么”。

我们已有直接证据：V10.20 的 Deepen 读到大量精炼历史时，仍做小修改；改换材料后才产生明显更多计算。形成历史有助于恢复有效细节，也可能把模型锁在已有改法里。**历史既是证据，也是示范。**

LLM 还会出现三种特别重要的偏差：

- 它容易满足眼前的措辞。要求“新的计算种类”，会排除那些只需一行却能改变整体行为的改动；要求每次超过当前版，会鼓励恢复成熟旧代码。
- 它能给改动写出顺畅解释，但解释未必描述实际执行的计算。Design 与 Analysis 必须和源码、结果分开存。
- 它容易把少数结果写成普遍规律。一次失败只证明这个实现、这些条件下没有得到预期结果，不能直接变成“这种方法无效”。

因此，元层面的工作不是不断添加反思文字，而是约束反思的对象：它应比较哪些具体解释、引用什么已经发生的改动、据此改变哪个下一步决定。

## 3. TraceAAD 的特性：优势应从哪里来

TraceAAD 的价值不应等同于“比其他方法存更多历史”。它有机会利用形成过程，识别一个程序怎样获得当前能力、某种改法为什么失败，以及下一次改写应保留或替换什么。

这要求三点：

1. **记录的是可核对的开发证据。** 实际代码、差异、评价条件、逐实例结果与失败信息是事实；算法说明是解释。
2. **过程能跨过单步最优。** 最好程序用于交付，工作程序用于继续开发。二者可以不同。
3. **预算投给具体开发机会。** 不因产生了一个新程序 ID 就忘记前面已经试过什么，也不因共用一个祖先就把所有后代都视为同一思想。

不建立永久的“思想种群”。一个开发记录围绕当下可检验的问题，例如“把整条先验的相对概率调得更集中是否改善采样”。一旦实际计算被替换，记录应说明问题已经改变。交叉允许多个来源，来源图不等于因果贡献图。

## 4. 重新诊断 V10.23：四处相互强化的错位

### 4.1 探索的目标与任务可改进空间错位

V10.23 的 Explore 明确偏向 constructing、simulating、improving what follows。这对 TSP 有帮助，但不是六种接口共同的充分探索方向。前 300 次候选中，Explore 首版在 FSSP 超时 142/182，在图着色超时 129/174，在 JSSP 超时 103/198。

不能由此得出“取消模拟”。TSP 三路都已出现候选补全与局部搜索，说明系统能较稳定进入某些有效计算。更准确的诊断是：**当前探索把一种成功路径推广成了统一语法，忽略了其他有效行为变化。**

仓库最新[当周周报](../06-总结与周报/2026-W41.md)另记录了 OP 整体先验幂变换和 FSSP 随机扰动的局部干预。这些记录强化了上述判断：一行变化也可能改变重要的求解行为。本轮读取了周报及消费者源码，没有重新运行这些干预，本文不将它们当作本轮新增重测。

### 4.2 开发名义上多步，内部仍从最好版本贪心推进

[`_develop()`](../../traceaad/v10_23/traceaad.py)始终从 `exploration['best']` 出发。更差或同分的新版本即使实现了后续需要的计算，也不能默认成为下一步工作版本。这是一个独立于步数的限制。把三步改成十步而不改变状态表示，仍是十步贪心改写。

目前的“保留新计算”也缺少可持续追踪的对象。OP 第三路 235 的逐边补全超时，236 将其删成公式；237 的 Develop 只看到 206→236 的折叠历史，原始提议从材料中消失。指令仍然要求继续新计算，但材料已不支持这一要求。

### 4.3 收益定义容易奖励恢复，而非新增能力

前 300 次、18 路共 136 组三步开发中，93 组改善首个有效版；首版落后于探索起点的 117 组，仅 13 组后来超过起点。直接开发贡献与后续间接贡献必须区分，这些数值不能当作删除开发的因果证据。但它们已经说明“较差首版后来变好”不是充分的投入依据。

CVRP 第三路 190→193 超过了原起点，但实际删掉了新补全计算。这可以是搜索成果，却不能成为“补全思想得到开发”的证据。

### 4.4 调度奖励的对象与最终目标错位

当前父代概率为：

\[
P(i)\propto e^{-\beta(q_i-q_{\min})}\frac{k_i+3r}{n_i+3},
\qquad r=\frac{\sum_i k_i+1}{\sum_i n_i+2}.
\]

质量温度通过不同分数值上的 ESS≈8 校准。这个设计有合理处：兼顾质量与尝试经验，并避免直接用未经缩放的分数。问题主要不在 beta 的形式：

| 现有量／规则 | 它实际表示什么 | 为什么不适合作为全局开发价值 |
| --- | --- | --- |
| k/n | 从一个精确程序出发、超过该程序的频率 | 不含改进幅度、多步结果与完整成本；较差程序恢复更容易 |
| 各算子合并计数 | 多种生成分布混合后的历史 | Explore 的失败会影响 Refine 获得机会 |
| 每个新 ID 独立统计 | 该份代码的尝试数 | 相近变体可以重新取得冷启动先验；一类变体越多，占据的总概率也可能越大 |
| 固定 0.45／0.30／0.25 | 每次动作类别的边际频率 | 不表示一个具体问题需要什么算子与多少后续机会 |
| 1/8 探索获得三步开发 | 随机覆盖部分探索 | 没有把提出、修复、兑现所需机会作为整体安排 |
| 修复后给原尝试记一次成败 | 一次提议加修复的最终结果 | 若仍按一次普通尝试理解成本，会低估真实候选消耗 |
| 参考的分数中位数与代码距离 | 质量与文本差异筛选 | 不说明借哪项计算，也不保证求解行为互补 |

代码哈希去重能消除完全重复，不能消除上述统计单位问题。这些机制叠加后，系统更容易反复生成熟悉的小变体，再用这些变体构成下一步的主要上下文。

证据与逐路统计见[原诊断](2026-10-09-开发对象与搜索决策的诊断和修改建议.md)和[300 次快照](../../experiments_result/traceaad_v10_23/diagnostics/design_review_300.json)。

## 5. 优秀工作提供的是设计约束，不是零件清单

| 工作 | 作者实际处理的对象 | 对本设计的具体影响 |
| --- | --- | --- |
| [Selecting Computations](https://arxiv.org/abs/1207.5879) | 计算的价值来自它怎样改善最后的决策，讨论 selection 与普通 bandit 的差别 | 以预算结束时的交付质量为目标，不能默认最大化每次即时改进就对齐目标 |
| [ReEvo](https://arxiv.org/html/2402.01145v2) | 用好坏代码对比形成短期反思，并积累长期提示；有特定设置下的消融 | 历史要包含可比较的代码与结果；反思是生成条件，不是已验证的因果规律 |
| [DeltaEvolve](https://arxiv.org/html/2602.02919v1) | 以不同精度的语义变化组织演化上下文 | 把“改变了什么”作为证据单位；压缩时保留源码差异与可回查来源 |
| [MCTS-AHD](https://arxiv.org/html/2501.08603v1) | 保留树上多个位置，以后续结果更新祖先并渐进扩展 | 当前分数不能替代后续开发价值；但最大后代分数不证明祖先中的某项计算有因果贡献 |
| [Clade-AHD](https://arxiv.org/html/2602.00549v2) | 汇集带深度衰减的后代证据，并以 Beta 信念与 Thompson sampling 选择 | 应超出单节点经验；但有交叉、删除和上下文变化时，谱系不能直接当作稳定、独立的统计臂 |
| [BaSE](https://arxiv.org/html/2605.29268v2) | 在多条演化轨迹之间分配调用，局部演化规则另行固定 | 机会分配和局部开发是两个层次。它的收益不证明我们应直接拆成多条独立运行 |
| [LACE 作者实现](https://github.com/PJ-NTU/LACE) | 按不同作用组织局部修改、重设计和互补组合，最终使用求解器组合 | 借用“不同决策需要不同材料”。TraceAAD 交付单程序，不能照搬组合目标或相应运行预算 |

这些文献支持重新组织问题，但没有哪篇证明下面整套 V10.24 规则有效。尤其不能把后代回传、语义记忆、bandit 和反思全部叠加，便称为全局优化。

## 6. 全局目标与近似边界

设 H 为截至当前的完整可见记录，b 为剩余候选预算。动作 a 包含开发对象、参考、算子和上下文。以当前训练目标为在线代理，理想控制问题是：

\[
V_0(H)=\min_{p\in\mathcal A(H)} F(p),
\]

\[
V_b(H)=\min_{a:c(a)\le b}\mathbb E\left[V_{b-c(a)}(H\cup O_a)\mid H,a\right].
\]

这里 O 包含有效程序、失败以及由此改变的下一步材料。初始化尚无有效程序时，终端损失视为无穷；取得有效根后才进入常规开发。

这个表达式说明三件事：

- 即时成绩差，不代表后续价值低；
- 获得信息只有在改变后续选择时才有价值；
- 同一动作的价值依赖剩余预算以及可替代的其他动作。

**它是设计目标，不是声称系统能精确求解的公式。** 当前没有可靠的转移模型，也没有足够数据估计每个开发过程的终端收益分布。不能写一个“预期收益＋新颖性＋信息增益＋潜力”的加权式，再给四项填主观数字冒充求解。

V10.24 首版采取可执行近似：用有限长度的开发承诺容纳依赖关系，用小型活动集合进行机会比较，用预算底线防止一种判断垄断全程。LLM 比较具体代码和证据，不输出未经标定的成功概率。它的战略判断本身也是待检验机制。

最终泛化仍由冻结后的独立测试评价。只看固定训练结果无法保证消除对训练实例或固定随机种子的适应；本设计不暗中改变评价协议来解决这个问题。

## 7. 核心状态：最好版本与工作版本分开

只增加一种必要的搜索对象：**开发记录**。已有不可变程序库、事件与调用档案继续复用。

| 字段 | 含义 |
| --- | --- |
| source_id | 这次开发从哪份成熟程序开始；不会随回退重设成绩基线 |
| question | 当前要检验的行为改进解释，不是永久思想标签 |
| proposal_id | 最初实现，包括超时／无效代码 |
| working_id | 当前要继续加工的实现，可暂时较差或无效 |
| best_id | 该记录中新生成的最好有效程序；尚无有效产物时为空，source 仍在全局档案中保留 |
| reference_ids | 实际借用的其他程序及对应部件 |
| attempts | 该记录中的全部实际尝试，包含修复、重复、分叉和未被采用者 |
| next_dependency | 下一步具体需要实现或辨清什么；它是模型的待检验解释 |
| spent / block_left | 实际候选消耗／本段尚余次数 |
| status | 活动、暂停或结束，以及原因 |

每次产生的程序都进入事实记录；有效程序照常参与全局最好值更新。一般将最新实现作为工作版，下一步也可以明确选择恢复到记录中的旧版。未能解析出程序时保留上一个工作版，失败请求本身照常记录和计费。**不再自动用最好版覆盖工作版。** 无效工作版只能被修复、替换或放弃，不能作为有效交付物。

开发不是保卫最初想法。若证据支持放弃，允许恢复旧计算，并明确结束原问题；好结果仍入档。这样不会为了“思想保留率”牺牲质量，也不会把恢复旧程序记为新思想成功。

同一记录内换版本、修改参数或进行修复，都不重置消耗和失败历史。若声明新问题却实际重复旧改动，材料中仍保留原记录，不能获得一份被清空的经验。

## 8. 战略层：分段承诺，而非逐候选追涨

### 8.1 首版默认规则

提出以下可直接实现的初始政策，而不是等待训练新模型：

- 沿用最多 16 次初始化尝试取得 8 个有效根的现有规则；初始化消耗计入 1000 次。
- 同时呈现最多 **4 个活动开发记录**：一个当前前沿的精炼记录，至多三个挑战记录。归档记录不删除，必要时恢复。
- 基本开发段为 **h=4 次候选**。提出、修复、失败、重复都计入；不是四个有效结果，也不是三步开发外加免费修复。
- 每个完整周期分配 16 次候选额度：**前沿精炼 4 次、挑战 4 次、自由分配 8 次**，通常执行为四个开发段。挑战用于尚未充分检验的不同改进解释，可提出、继续或恢复；不能只复制前沿的小变体来占位。
- 自由段由模型在当前可见机会中联合选择记录、修改方式和参考。首次生成同时给出简短选择依据与代码，不增加独立的调度模型调用。
- 进入一段后，不因第一份代码分数较低就自动跳走。该段用于完成一个可识别的工作目标。若契约矛盾、原问题已被否定或确无可继续的实现，则提前结束；未用次数尚未消耗，留给本周期同一角色的下一项工作。该角色额度不足四次时，下一段相应缩短。
- 剩余不足 2h 时停止开启新问题，完成已有承诺，优先兑现最接近可用结果的改动与前沿精炼。剩余不足 h 时，最后一段缩短；最终冻结规则不变。

这样给出两个预算下限：初始化之后，每个完整周期至少四次服务于已有成果、四次服务于未充分检验的替代解释；另有一半机会随证据调整。最后不足一个周期时按兑现已有工作的规则处理。这些是防止模式坍缩的初始保险，不是声称 25%／25%／50% 最优。

**本设计最有依据的是“状态、材料、承诺和终端目标要一致”；4 个记录、4 次一段及上述份额是明确暴露的工程起点。** 不应把这些数字包装成底层规律。先检验整套闭环，再检验这些常数的敏感性。

### 8.2 怎样比较下一段，而不偷偷恢复单步贪心

自由段的选择依次回答：

1. 这个记录针对的求解行为限制是什么？当前代码与评价支持该解释，还是已经反驳它？
2. 下一段具体能完成什么？补齐必要计算、修复实现、改变接入方式，还是只重复已有参数扰动？
3. 完成以后怎样可能达到或超过当前前沿？不能只说“比这个很差的工作版好”。
4. 同样四次机会投给当前前沿或另一个记录，有什么更强的理由？
5. 剩余预算是否允许实现依赖链，并利用本段得到的经验？

无需每次生成长篇计划。四句可核对的比较比十个主观分数更有用。没有足够依据时，优先尚未获得基本检验机会的记录；仍同等时用固定随机流打破平局，不制造虚假精度。

挑战段的候选优先覆盖当前活动集合中投入较少、问题仍未解决的记录，也允许开启不同的行为解释。若活动集合已满，需要明确暂停一个记录；优先暂停问题已被否定或下一步只是重复已有失败的记录。没有这种证据时，暂停最久未使用的非前沿记录，保留其全部材料，以便后来恢复。

这不是无条件相信模型更会调度。数值结果、预算边界和材料选择由代码执行；模型只负责那些必须结合计算内容才能提出的比较。模型可能选错，所以只一次承诺一个短段，并始终保留前沿与挑战两类机会。

### 8.3 允许长程开发，但不允许空头潜力

四次不是开发总上限。同一问题可以获得多个段，连续实现多个依赖。每次续段都必须面对之前的实际改动、工作版与最好版差距，以及别处的机会。

支持继续的证据可能是：此前缺失的容量约束现已正确接入；核心计算已从无法完成变为能完整评价；目标实例上的退化已定位到一个具体连接错误；一个关键版本虽不优，却产生了下一步确实会用到的中间量。

单独的“最近涨过分”“代码更新颖”“说明写得更合理”都不充分。没有成绩兑现又没有可检查的新依据时，暂停该记录，不把一句新叙述当成重开冷启动。

### 8.4 三种成本分别记录

\[
C_{\mathrm{search}}=\sum \text{已生成候选数}\le1000.
\]

同时记录 LLM 输入／输出 token 与评价 CPU 消耗。搜索候选预算、模型推理成本、生成算法的运行约束不是同一量。不把它们随意相加成一个分数。

战略选择并入每段第一份代码的调用，可避免额外规划调用；多程序上下文仍会增加 token，必须报告。若将来改成独立反思／规划调用，也必须单列所有调用与 token，不能把它们当免费算力。

## 9. 公式的取舍：保留可解释的量，删除伪价值分

### 9.1 不再使用单节点改进概率作为主选择权重

V10.24 不沿用 `exp(-beta*gap) × 超父成功率` 做全局调度。不把它再乘上“新颖性”或“潜力”。单节点成功率可作为事实摘要，但不是开发价值估计。

也不直接把整棵谱系的好后代全部回填成一个 Beta 后验。不同后代可能已换掉关键计算，选择机会也不均匀；加一个衰减常数不能自动修复这些条件。

### 9.2 以固定起点记录成果，避免奖励恢复

对开发记录 d，在一段开始时记全局前沿 F*，段后记录内新生成程序的最好值 Fd；Fsource 为最初起点，Ffirst 为首个有效版。source 本身不冒充新产物，尚无有效产物时以下对应量记为缺失，并保留失败事实：

\[
\Delta_{\mathrm{source}}=F_{\mathrm{source}}-F_d,
\]

\[
\Delta_{\mathrm{front}}=\max(0,F^*-F_d),
\]

\[
\Delta_{\mathrm{recover}}=F_{\mathrm{first}}-F_d.
\]

三者分别表示相对起点的净改变、对本段前沿的贡献、对首版的恢复。无有效首版时 recover 不定义，不能填零冒充观察。六任务可能有负分，直接做差，不除以原分数制造符号错误。

这些量用于记录与机会比较，不强制加权成一个奖励。长期结果按实际发生的时间更新，不把同一次前沿增益重复奖励给所有祖先。

若按整条运行逐次统计前沿改进：

\[
\sum_t(F^*_{t-1}-F^*_t)=F^*_0-F^*_T.
\]

这是日志应满足的账目一致性，不是“最大化即时增益即能找到最优策略”的证明。

### 9.3 逐实例反馈用来解释差异与寻找参考

对当前程序 p 与参考 r，记录相同实例上的配对差：

\[
d_i=f_i(p)-f_i(r).
\]

展示均值、胜负场数以及最大的正负差，避免只展示有利实例。一个可用于检索的软信号为：

\[
C(p,r)=\frac1N\sum_i\max(0,d_i)
=F(p)-\frac1N\sum_i\min\{f_i(p),f_i(r)\}.
\]

它表示“若有一个知道每例该选谁的理想组合，参考能补多少缺口”。**它不是合并两份代码后能获得的收益，也不定位因果部件。**

为当前选择提供至多两个参考候选：一个按 C 排名的代表，一个实际计算不同的代表。现有代码相似度只能帮助提出后者，不能证明语义差异。仍允许 C=0 的参考：原 1012 次交叉中，参考没有任何实例胜场的 183 次里，有 18 次子代超过双方。

参考与父代一起决定是否借用。若找不到明确部件与接入理由，可以不交叉，不强迫拼接。

### 9.4 暂不增加四类公式

- 用新颖性抵消差成绩的总分；
- 从一两个增益点线性外推最终潜力；
- 把每个代码后代当独立观测的置信区间；
- 用大量零收益下的准确率或 Brier 代替选择价值。

已有[决策模型中间检查](../02-实验结果/2026-10-09-决策模型100步中间检查.md)也没有证明代码与历史预测超过简单状态规则。V10.24 不依赖该训练成功。将来接入时，模型应评价指定材料、指定开发长度下的选择，而不是用 V10.22／V10.23 单步标签直接驱动新生成分布。

## 10. 上下文不是档案摘要，而是一次决策的工作材料

### 10.1 三层材料

**事实层**继续使用不可变程序、真实 diff、候选事件和完整模型调用。失败版永远可回查，Repair 是单独一条改动边。

**开发层**保存同一问题下的尝试，包括不在最好谱系上的版本。每个条目只需：起点与终点、实际计算变化、结果、模型当时预期。结果不得被后续解释覆盖。

**本次上下文**按要作出的决定选材料。它不必等于最新八条，也不必等于从根到当前的整条路径。

### 10.2 必须出现与可以省略的材料

普通开发请求包含：

1. 函数契约与输出消费方式；
2. 当前工作版完整代码与评价；
3. 当前开发问题和源程序的相关计算；
4. 原始提议及修复对它的实际改动，若这仍影响下一步；
5. 最近一次有信息的失败与一条支持／反对当前解释的历史；
6. 当前最好版与全局前沿差距；
7. 本段剩余次数及本次目标。

段首战略请求另展示至多四个活动记录的卡片与可选代码。只允许从实际展示完整代码的候选中选择本次代码起点；未展开记录可以列为待查看机会，不能假装模型读过源码。默认卡片顺序按固定随机流轮换，避免永远把最好者放在最醒目位置。

同源程序先用完整工作版加精确 diff 表达，避免重复放四份大部分相同的代码。跨来源的参考若要实际借用，必须给足完整依赖；不能凭一句 Design 让模型猜实现。

### 10.3 压缩次序由信息作用决定

沿用 `max_input_tokens=24320` 与现有输出上限。组装后真实计数，不靠条数猜长度。超长时依次移除：重复说明、较早且不相关的材料、额外参考、较低优先的可选记录。必须保留任务契约、当前代码、本段目标与直接相关失败。

原始失败提议不能被一句“后来已修复”吞掉。必要时给出可重建计算的精确改动及其上下文，而不是抹去它。若最小材料仍放不下，记录为上下文容量问题并暂停该请求；不静默切换 Explore，也不把它记为算法失败。

### 10.4 经验按条件表达

好的经验条目示例：

> 在程序 A 的逐边补全中，B 删除补全后能够完成评价，但分数从……变为……；C 的向量化保留了……。目前尚未检验仅对候选边补全。

不好的条目示例：

> 补全太慢，应采用简单公式。

前者可被新证据更新。后者会把一次实现失败扩大成搜索空间禁令。

跨记录检索首版只使用现有来源关系、实际代码差异和逐实例差异，返回具体案例。没有必要先建向量数据库或全局“成功思想榜”。某一段结束后，生成文本中的经验也只能作为带出处的解释，不能替代事实层。

## 11. 战术层：三个修改算子，加一个可行性处理

**Develop 改为开发过程的状态，不再是第四种随机修改算子。** 一个开发过程可以提出结构改动、修复实现、精炼参数或借入部件。算子描述本次代码变化，开发记录描述为何连着做这些变化。

| 动作 | 解决的问题 | 必要材料 | 不应强迫的行为 |
| --- | --- | --- | --- |
| Refine | 已有行为有价值，怎样让实现或使用更有效 | 工作代码、关键形成变化、相关失败 | 不要求只改一个语法位置；允许一个目的下的联动修改 |
| Reframe（替代 Explore） | 当前函数作用于外层求解的方式遗漏了什么 | 输出消费契约、代码、已尝试维度、相关反例 | 不强制增加模拟、增加复杂度或立刻胜出 |
| Transfer（替代 Crossover） | 另一个程序的具体计算能否解决当前限制 | 双方代码、结果差异、接入位置 | 不强制同时保留双方全部做法；不以文本差异代替互补理由 |
| Repair | 当前实现违反契约、运行错误或不能完成评价 | 失败代码、错误、原提议、工作目标与最近有效版 | 不默认为获得有效分数就应删除核心计算；也不死守不可行结构 |

Refine 与 Reframe 依据修改的作用区分，不按代码行数。把整体 h 变为 h 的幂，若是在调已有集中度就是 Refine；若首次发现先验集中度是尚未处理的行为问题，则可属于 Reframe。标签服务于组织材料，不作为贡献大小的指标。

### 11.1 共同提示

以下为拟定核心正文。实际 task contract 直接使用经过核对的接口事实，不加入特定算法答案；保持当前协议“提示不提时间”。失败可报告完成了哪些调用及错误位置，不写秒数或提速口号。

```text
You are developing a function used inside the fixed solver described below.
The objective is the quality of the solver's final valid solution.
All reported objective values are lower-is-better.

Use the supplied code and evaluation records as evidence. Design notes and
earlier explanations are hypotheses, not verified descriptions of execution.
Trace how the function's returned values affect the solver's decisions.
Use only the information and decisions available through this interface.

The best evaluated program is retained separately from the working program.
A working version may be temporarily worse while implementing a concrete
development step. Do not restore the best version solely because it scores
better. If the current development claim should be abandoned, say which
evidence changed your decision and identify the computation you replace.

Preserve useful computations outside the change you intend to make.
Do not claim that a proposal has improved the objective before it is evaluated.
Return one complete executable program using the required interface.
```

这段提示不要求输出长推理。它明确评价对象、事实边界和工作版与最好版的区别。

### 11.2 段首战略选择与代码共用一次请求

```text
Choose the next development block from the admissible records below.
This block allows at most {block_size} candidate attempts, including repairs
and unsuccessful attempts. The run has {remaining_candidates} attempts left.
The block role is {frontier / challenge / free}.

Compare the selected opportunity with the strongest visible alternative.
Identify the solver behavior it can improve, the code or result supporting
that claim, and the concrete step this block can complete. If its working
version is worse, explain what must change for it to become competitive.
State one observation that would change your continuation decision.
Do not invent a probability of success or an expected score.

Select only a source whose implementation is supplied. Choose Refine,
Reframe, Transfer, or a necessary Repair. Produce the first candidate now.
```

输出采用少量可解析元数据，紧接短 Analysis、Design 和完整 Code：

````text
Record: <existing ID or NEW>
Parent: <supplied program ID>
Reference: <supplied ID or NONE>
Action: <Refine | Reframe | Transfer | Repair>
Decision: <at most four sentences: evidence, alternative, block objective,
           and what would change the continuation decision>
Analysis: <at most three sentences about the actual implementation change>
Design: <one or two sentences describing what the returned program computes>
Code:
```python
<complete program>
```
````

实际模板外层使用不同长度的 Markdown fence，避免嵌套歧义。ID、角色、剩余预算由宿主验证，不能由模型扩权。无效输出仍按一次候选处理，不能免费重试策略选择。协议层网络重试沿用已有机制，不混入算法候选统计。

宿主能硬性验证的是 ID、允许的动作类别和预算，不能仅凭 Reframe 标签证明发生了新的行为探索。因此，预算底线保证对应角色获得调用机会；是否实现了其目的，仍要由实际改动与行为检查，不能把标签比例报告成有效探索比例。

### 11.3 Refine

```text
Improve the existing mechanism in the working program.
Use the observed changes and results to choose one coherent implementation
or usage improvement. Keep unrelated effective computations intact.
Several coordinated edits are allowed when they serve the same change.
Explain how the changed computation reaches the function's output and the
outer solver's decisions. Use relevant failed attempts to avoid repeating
the same ineffective change without a new reason.
```

### 11.4 Reframe

```text
Reconsider how this function influences the fixed solver.
Identify one behaviorally meaningful limitation of the current implementation,
or one unresolved alternative explanation supported by the supplied evidence.
Implement a different way to address that limitation within the same interface.

The change may be small or large. Additional simulation is appropriate only
when its result can inform the decisions this function is allowed to affect.
Do not equate a longer program or a new named method with a better proposal.
Keep useful computations that the replacement still needs.
State what the first implementation will test and what could remain to develop.
```

这里刻意不把所有可用改法列成十种算法清单。输入里的函数角色、实际失败和未决问题负责具体化方向。构造／模拟仍然可用，但不再占据默认正确答案的位置。

### 11.5 Transfer

```text
Use a specific computation from the reference only if it addresses a concrete
limitation of the working program. Identify the computation, where it connects,
and which assumptions must hold at that connection.
The reference's instance-level results show where to investigate; they do not
prove that any single component caused the difference.
Build one coherent program. Do not concatenate two complete methods merely
because both are supplied. If no useful transfer is supported, make a justified
Refine or Reframe change and report that action explicitly.
```

### 11.6 Repair：按失败原因分派，归入当前开发预算

```text
The supplied working program failed with the reported observation.
Locate the failing computation and distinguish an implementation error from
a limitation of the proposed computation itself.

For a contract or runtime error, repair the violated assumption while keeping
unrelated calculations intact.
For an incomplete evaluation, inspect repeated work, recomputation, and the
placement of the expensive calculation. Seek an implementation or restricted
use that retains its intended decision-relevant information. Reducing the
amount of search may change solution quality; make that trade-off explicit.

If you replace the proposed computation, state that the development claim has
changed. Do not describe removal of the computation as successful preservation.
Return the full corrected or deliberately revised program.
```

不再对所有失败机械附送一次独立 Repair。错误进入工作记录，由下一次机会选择有理由的修复；明显局部错误通常继续修，接口不支持的计算不反复救。失败时若开发段尚有预算，下一次请求仍属于该段。

## 12. 一次搜索如何运行

```text
initialize under the existing candidate accounting
keep every attempted program and evaluation in the immutable archive
create a frontier record; admit challenge records as opportunities arise

while candidate budget remains:
    role = next block role, adjusted for the final remaining budget
    pack eligible records, code, relevant evidence and alternative opportunities
    commit at most min(4, remaining role quota, remaining budget) attempts

    for step in this block:
        if step is first:
            jointly choose record + source + action and generate a candidate
        else:
            generate a continuation, justified rollback, transfer or repair
        evaluate and store the actual code change and outcome
        update the global best and the record's best, when valid and improved
        retain the working version independently from those best versions
        update the next implementation question using the result
        stop early only when the development question is resolved or abandoned

    retain the block's evidence and actual cost
    compare continuation with other opportunities at the next block decision

freeze the top-five-based training winner exactly as the current protocol states
evaluate the frozen program once on the independent same-scale test set
```

实现时评价顺序是每份代码生成后立即评价，包括每段最后一份，不能因循环边界漏掉首个或末个候选。以上伪代码展示控制关系，实际事件提交、异常隔离与恢复继续复用 common 层。

## 13. 用已有成功与失败检验设计是否自洽

### 13.1 OP 的补全被修复删掉

235 仍作为原始提议保存，236 的删除作为独立证据展示。下一段可以选择重写补全的实现、限定使用位置，也可以认为其作用不合适而改查概率集中度。两者都合理，但后者会结束原补全问题，而不是继续声称补全在发展。

这解决“材料里没有开发对象”的矛盾，不保证该补全值得救。

### 13.2 TSP 从五轮到十轮的实现变化

超时版本不因无分数被折叠消失。Repair 看到原有搜索、增加的轮数和失败位置，有机会修改移动收益计算。保存最好版意味着探索这个实现不会丢掉原来的 5.8905；工作版独立意味着不会仅因超时就把新计算彻底撤回。

### 13.3 CVRP 早期容量结构尚未完善

“忽略容量的完整回路”不是一种已成熟路线构造算法。下一步需核对实际容量约束和输出边先验的接入。若修正后仍暂时落后，可以在已承诺段内继续；续段则要比较与现有角度／savings 规则的差距和替代投入。

不能把该历史成功反推为“任何弱首版都值得四次”。承诺用于防止第一步就被截断，后续仍必须面对实现与结果。

### 13.4 FSSP 的输出首先是扰动

若当前规则总在同类作业上做确定性扰动，下一问题可能是怎样改变逃离局部最优的路径，而不是怎样更精确地预测当前 makespan。Reframe 可以改扰动分布及其与作业选择的关系。计算正确的完整模拟未必服务这一角色。

### 13.5 某个模型不断讲“潜力”却不能兑现

模型不能增加预算、删除失败或重置 source。其续投依据与实际结果一起展示，其他机会始终在段首可见。前沿精炼和挑战底线减少单一判断的垄断范围。

这仍不能保证模型不误分自由预算。若完整运行发现自由段长期投给无成果记录，首先要否定这一语义调度实现，而不是再加一个未经验证的潜力评分器。

## 14. 怎样验证全局机制，而非只优化局部指标

### 14.1 首先检查机制有没有真实发生

在现有成功与失败状态上检查完整开发段的行为：工作版能否跨过暂时下降；原始失败计算能否进入下一步；模型能否从输出消费方式提出不同改法；是否明确承认恢复旧计算；全部候选与 token 是否如实计费。

这是实现验收和机制诊断，不作为完整系统有效性的结论。不再只拿“算子一次超过父代的概率”决定整套方向。

### 14.2 用完整搜索检验战略效果

按固定六任务、每任务三路、每路 1000 次候选比较 V10.23 与冻结的 V10.24。模型、评价协议与执行条件保持一致，方法配置按运行保存。任务分别看，不用混合原始分数求总均值；同种子是实验分组，不能假定两种自适应策略经历相同生成随机性。

主要结果仍是各路训练与冻结测试质量。额外看：弱路是否改善；有效行为变化是否更早出现；同类失败是否在新 ID 上反复重演；开发预算是否从恢复首版转为产生可采用结果；新增收益是否依赖特定任务或单路偶然结果。三路足以暴露明显问题，不足以据此承诺稳定的尾部改善。

“首次提出”“实际实现”“被继续采用”“进入最终程序”分别记录。同一开发中计算被删掉后产生更好代码，也计入质量成果，但不算原计算被保留。只用 lineage 或代码相似度自动统计这些过程会混淆对象，应抽查实际代码。

### 14.3 需要解释差异时，检验两组设计的交互

把改动分成两个有内部依赖的整体：

- A：任务行为导向的提示、工作／最好双版本、完整开发证据；
- B：分段承诺、小型活动集合、前沿／挑战底线与机会比较。

用 A/B 的 2×2 配置检查它们是否互相依赖。B 放在旧生成条件下可能只是在更合理地分配错误提案；A 放在旧调度下可能没有足够机会兑现。不能只看“单独加 A”“单独加 B”后都不显著，就否定联合机制。

这个比较以整条搜索为实验单位；候选、开发段和 16 个实例都不是独立搜索重复。按任务与运行批次分组，随机交错条件的执行顺序，避免负载或时间段与方法绑定。只在整体结果或具体异常需要时展开，不先规划一长串算子消融。

### 14.4 哪些结果会改变设计

- 若材料完整、工作版独立，但新计算仍不能兑现：主限制更可能在提案与接口适配，不能继续只增加开发长度。
- 若模型能提出好改法，但自由预算持续选错对象：保留开发表示，替换语义调度，而不是推翻整个表示。
- 若训练更好而独立测试更差：检查是否更快地适应了固定训练条件，不能归为搜索成功。
- 若质量提升只来自更长模型上下文：同时比较实际 token／总调用成本，重新判断效率。
- 若系统总能恢复强程序，却很少产生新的有效行为：它改善了可靠性，仍未实现更好的算法发现。

## 15. 实现边界与复用位置

这是设计，不在本次直接实现。若进入实现，改动应集中为 V10.24 的状态与控制、材料构造、提示及必要事件字段，避免把方案写成新的基础设施框架。

| 位置 | 必要改动 | 应复用的部分 |
| --- | --- | --- |
| `traceaad/v10_24/`（待建） | 分段控制、开发记录、版本与提示配置 | 现有版本包模式与启动入口 |
| `traceaad/common/search.py` 相关调用 | 提供工作版／最好版独立更新、段内计费与恢复所需接点 | 模型调用、代码解析、评价隔离、有效程序存档、最终冻结 |
| `traceaad/common/prompts.py`、新版本 builder | 不折叠开发必需的失败；按决定装配证据 | 完整代码格式、实际 diff、token 计数与统一任务契约 |
| `traceaad/common/selection.py` | 旧规则保留给旧版本；新版本不调用它作主调度 | `better`、规范化代码、相似度的检索用途 |
| 事件、恢复状态与可视化读数 | 记录 block、working、best、source、暂停与真实成本 | 既有 append-only 事实和源码哈希，不重复存代码 |
| 实验入口、配置、方法测试 | 新版本独立注册；验证恢复与预算、末段、失败材料和旧版隔离 | 原协议、数据、模型条件、同规模测试流程 |

必要验证包括：恢复后不会重复承诺预算；失败／重复／修复都计数；同分工作版可继续而全局 best 不退化；Repair 不吞原提议；模型引用未展示 ID 会被拒绝；超长不会静默换算子；旧版本行为不被共享层修改破坏。不为记录字段写大量镜像测试。

本版不要求：新的向量库、永久思想标签、一个专门训练的调度模型、在线改 evaluator、完整 MCTS、额外的反思代理或最终求解器组合。它们都不是闭合上述开发过程的必要条件。

## 16. 当前最值得相信的结论

**V10.24 应围绕“具体求解行为的有期限开发”重构。** 上层比较开发机会，中层保存工作对象与证据，下层选择恰当计算改法。最好程序用于交付，工作程序用于发展。历史既帮助解释，也会塑造生成分布，因此必须按决定组织。公式负责可核对的目标、差异和成本；暂时无法估计的长程价值，不用未经标定的数字掩饰。

我对这些结构性判断的把握高于对某个调度常数的把握。最需要完整搜索检验的是：同一个 LLM 能否在这些材料下做出有用的机会比较，以及保护开发过程所得的收益能否补偿减少的独立提案数量。这两个问题具体决定本方案的效率和稳定性。
