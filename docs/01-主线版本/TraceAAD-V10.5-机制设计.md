# TraceAAD V10.5 完整机制设计

## 0. 结论与五个问题的直接回答

**V10.5 推荐采用：中等强度的算子指引、紧凑形成事件轨迹、单次调用联合生成 Idea 与 Code、Refine/Pivot/Fuse = 50%/15%/35%，以及按算子区分父节点选择。** 保留已有质量分配基座，仅在 Pivot 中用一半机会从全档案均匀选父，为换向提供更宽的起点。一次候选、一次真实评价、立即重新分配。

这不是“已由实验识别的最优参数”，而是当前证据下最值得优先采用的完整方案。概率调整本身就是实质机制变化，有充分理由试验，不能因其简单而否定。首选固定比例；自适应是次优备选，不成为首发依赖。

## 2. 问题一：上下文与指引的失衡，以及最优、次优方案

### 2.1 根本问题：限制了设计身份，却没有清楚区分硬边界与搜索偏好

**V10.1 的问题不在“详细”本身。** Refine 不得替换核心原则、Pivot 必须机制新颖、Fuse 必须保留 target 的实质机制，这些规定会改变可生成算法集合。对于一个较差 target，强制保留其机制可能妨碍从 donor 获得更好的结构；对于 Pivot，必须足够不同会把“改得新”引入隐含目标。

**V10.2 加入了更多容易相互牵制的要求。** 模型同时要保持、替换、融合、避免堆叠、允许有益复杂度、克制注释。某些要求有合理动机，但组合起来容易把注意力转向满足文字约束。配对识别显示它们会改变候选分布，却没有跨任务一致的方向。

**V10.3 的删除也不是自动最优。** 它保留了大方向，但很少交代如何理解历史失败、何种边界必须守住、哪些实现自由应当保留。一句“发挥算法判断”没有提供新的任务信息，无法保证模型将自由用在真正影响决策的地方。

**共同问题是优化了说明的多少，尚未稳定地优化说明的职能。** 必须限制的是不可用信息、非法输出、接口和实际执行成本；应当软引导的是继续开发、换向和组合的区别；应当开放的是公式、参数、数据结构、局部搜索与计算组织。

### 2.2 首选：三层约束、紧凑事实、一次决策

三层边界如下：

| 层 | 放什么 | 强度 |
| --- | --- | --- |
| Task Contract | 实际可见状态、函数签名、输出合法性、目标、真实超时/资源条件 | 必须满足；保持现有任务定义 |
| Operator | 本轮从何种设计方向改进；每个算子两三句 | 生成引导，不设语义验收分类器 |
| Implementation | 如何实现该方向、采用哪些公式/计算结构 | 交给模型；不规定代码行数、保留组件数量或新颖标签 |

保留“一份完整当前代码 + 最近形成事件 + 本轮算子”；Fuse 额外保留“一份 donor 代码”。不放历史代码、donor 轨迹、全部已试子代或另一份全局总结。

历史只提供“引入了什么、评价发生了什么变化”，不把模型的设计自述当成已经证明的组件归因。过去退步并非永久禁区：修正其原因后可以重试。Refine 借历史理解可继续发展的结构；Pivot 借历史理解限制，而不是照着历史重复，也不是为了避开所有历史机制而强制离开好方向。

### 2.3 轨迹的具体表示与信息预算

采用 V10.4 的形成事件语义，**保留的改进是事件对齐，不保留长设计全文**：

```text
# Formation History
Step 1 | Refine | Fitness: -6.42 -> -6.36 | improved
Idea: Reweight the terminal connection cost using the remaining candidate count.

Step 2 | Pivot | Fitness: -6.36 -> -6.39 | regressed
Idea: Replace the terminal estimate with a two-step lookahead.
```

规则：

1. 取当前节点向上最近至多 8 条父子边，包含形成当前节点的最后一条边；从旧到新排列。
2. 每条边的 Idea 属于 child，fitness 明确是 parent → child，算子来自真实节点元数据。
3. 不仅保留成功边。零增益和退步都是形成事实；不因其结果为负而删除。
4. 历史区目标不超过 2048 个实际 tokenizer tokens。超限从最旧完整事件起删除；不在公式或句子中途硬截断。
5. 极端情况下，单条历史 Idea 已超出历史上限，则将该条 Idea 替换为明确的“设计文本因长度省略”，保留算子与父子 fitness；原始文本仍存档。新运行的短 Idea 应极少触发此分支。
6. 当前代码已经单独呈现。若最后一条形成事件已含 current.idea，Current 区不再重复同一 Idea。根没有形成事件时，Current 可显示根的简短 Idea。

2048 是上下文管理初值，不是有效性的已识别最优点；`8 条`与`2048 tokens`解决不同问题，分别控制历史范围与长文本风险。当前代码与 donor 的完整性优先于多保留一条旧事件。

顺序固定为：Task Contract → Current Code → Reference Code（仅 Fuse）→ Formation History → Design Direction → Output。让紧凑历史紧邻本轮设计指令，避免被 donor 长代码隔开。

长上下文可能存在信息位置敏感性，已有问答/检索研究提供这一一般风险的证据；它不是对 Qwen3.8-27B 本任务的直接证明，因此上述排序仍是设计选择。[Liu et al., TACL 2024](https://aclanthology.org/2024.tacl-1.9/)

### 2.4 次优：V10.1 的最小修订

如果优先减少改动，可保留 V10.1 的祖先列表、单句 Idea 和 Prompt 顺序，只做两处修订：Init 的目标由“novel”改为“competitive”；Fuse 不再强制保留 target 中某个机制。Refine/Pivot 仍维持明确区别。

优点是贴近已有较强性能基线，定位变化容易；缺点是形成当前节点的事件仍不够直观，输出与算子约束仍偏硬，无法直接解决未来长历史与阶段分离的问题。故不作为本文主配置。

## 3. 问题二：非等概率算子分配

### 3.1 现有数据已足以支持改变默认比例

V10.1 同父节点三算子提供了比较机会。历史联合分析中，Pivot 改善率约 0.5%–2.4%，且有较多大幅退化和失败；但它贡献了 23 次全局突破和若干关键早期换构。Refine 与 Fuse 承担大部分后续兑现。

新快照在前三个版本可共同读取的 400-eval 窗口也显示算子作用不同。例如 V10.3 的 TSP，按全部生成尝试计，R/P/F 的父代改善率约 13.5%/4.8%/33.2%，但全局突破次数为 9/7/16；OP 为 10.5%/1.8%/26.2%，全局突破为 12/4/14。改善率和前沿价值不能用同一个数代替。

**选择动作的目标是下一份预算对最终 best 的贡献。** 概念上可写作：

$$
\Delta V_t(n,o,d)
=\mathbb E[B_{1000}\mid\mathcal H_t,\text{下一次选择}(n,o,d)]
-\mathbb E[B_{1000}\mid\mathcal H_t,\text{参考选择}],
$$

其中未来继续按约定 policy 执行。该量不是现有数据可可靠在线估计的分数，但它说明两点：低命中、长尾探索不能只看平均单步增益；不断把差父代搬到 donor 水平，也不等于提升最终 best。

不能通过把历史频率重加权来声称已经模拟出另一比例的完整搜索结果。比例改变后，树、donor、后续状态和提案分布都会变化；这恰恰是固定比例可能产生实质效果的原因。

### 3.2 首选：固定 50% / 15% / 35%

顺序为 Refine、Pivot、Fuse：

$$
\pi=(0.50,\ 0.15,\ 0.35).
$$

理由：

- 将 Refine 设为主要开发动作，增加对已具备竞争力方案的连续兑现机会。
- Pivot 从三分之一降至 15%，减少当前低命中探索的机会成本，但不删除换向通道。
- Fuse 保留 35%，接近原有份额，利用其已观察到的前沿贡献；不因高父代改善率把它推成绝对主导。

这组数是**带证据动机的设计先验**。15% 没有被识别为数学最优；如果少量关键 Pivot 是某任务主要增益来源，下降过多会损害上尾表现。需同时看均值、较差重复和最好重复，而不是只追求稳定地收敛到较低水平。

若 8 个根均一次评价成功，剩余约 992 次评价，在生成/评价均成功且 donor 可用的理想情形下，预期约为 R=496、P=149、F=347。实际采样的是生成机会，解析失败不消耗评价，因此正式日志必须同时报告“生成份额”和“真实评价份额”。

没有可用 donor 时，Fuse 的概率全部转给 Refine：R/P=0.85/0.15。**不按 R/P 剩余权重重新归一化**，避免 donor 缺失意外提高 Pivot 预算。

最小比例敏感性对照只增加一个候选：`0.40/0.25/0.35`，固定 Fuse，只在 R 与 P 之间移动 10 个百分点。不进行无边界比例搜索，也不把固定比例实验说成无意义调参。

### 3.3 次优：只自适应 R/F，保护 P 的固定份额

若需简单自适应，仍固定 `p_P=0.15`。对 R、F 各维护最近至多 100 次实际评价结果；解析失败另记，不进入这份以 evaluator 成本为单位的成功率。

令 `s_o` 为该窗口内严格超过调用前全局 best 的次数，`n_o` 为实际评价次数，失败评价计入分母。定义：

$$
u_o=\frac{s_o+1}{n_o+20},\qquad
\widetilde p_R=0.85\frac{0.50u_R}{0.50u_R+0.35u_F},
$$

$$
p_R=\operatorname{clip}(\widetilde p_R,0.30,0.65),\qquad
p_F=0.85-p_R.
$$

先验对应 20 次评价中 1 次前沿成功，用于平滑，不宣称是真实成功率。无数据时得到主配置的 0.50/0.15/0.35。每 50 次真实评价后更新一次，其余时刻保持概率，避免每次偶然结果驱动抖动。初始化不进入 R/F 窗口；没有 donor 时仍转给 Refine，按实际执行算子记录。

为什么次优：它只增加两份短窗口，足够简单，但前沿事件稀疏、状态随时间变化、R/F 的 donor 条件不同；它没有识别长期价值，也不能证明某算子能力更强。P 不参与成功率淘汰，避免把稀有发现动作自动饿死。只有固定比例出现明确、可重复的任务错配时，再优先试这个备选。

## 4. 问题三：V10.4 两阶段生成究竟哪里出了问题

### 4.1 证据强度最高的问题：1024-token 饱和与未完成设计放行

| VRPTW | 18 | 17 | 18 |
| 合计 | 90 | **81** | **84** |

这是确定性分层位置抽查，不是随机总体估计；90% 是样本内恰好达上限的比例。现有 wrapper 只返回 `message.content`，没有保存成功响应的 `finish_reason` 与 usage，故不能把这 81 条全部正式标记为服务端长度截断。

但多个真实响应明确在句子或公式中途结束。例如 CVRP rep2 第一条 Init 响应恰好 1024 tokens，在“避免除法……”的算法步骤中结束；OP rep1 第一个扩展在幂指数表达式中途结束。`_idea_from_response` 仅去 thinking 标签、检查非空；这些未完成设计随后进入 Code。

对应实现：V10.4 生成器、LLM wrapper。抽查路径、行号和响应结尾见 snapshot 的 `idea_token_samples`。

**这里已经足以确认实现缺陷：短上限配合不限篇幅的设计请求，而下游不检查完成状态。** 尚未量化修复这个缺陷能恢复多少目标质量。

### 4.2 第二个已确认问题：节点 Idea 的角色变了，历史发生累积膨胀

按“每路节点 Idea 字符数的中位数，再跨 15 路取中位数”统计：

- V10.1：338 字符；V10.2：326；V10.3：340。
- V10.4：3840 字符，约为 V10.3 的 **11.3 倍**。

V10.4 将第一阶段长设计全文直接存入 `node.idea`。后代再把最近 8 条长设计全文放入历史；Current 区还会重复当前 Idea。生成 step 0–399 内，TSP/CVRP/OP/VRPTW 各路历史区字符数中位数约 2.9万–3.2万；OBP 约 1.26万–1.67万。

**因此 V10.4 不只是把一次调用拆成两次，还把简短的形成事实变成了多篇设计论述的重复输入。** 把 Idea 上限直接增加到 4096 而继续存全文，会把另一条问题通道进一步放大。

Code 阶段不读取历史，只读取长 Idea 与当前/donor 代码。与改进形成过程有关的信息，必须先经过第一阶段的选择和文本化再进入实现；被遗漏的历史约束不能在实现时重新核对。这里的“信息瓶颈”仅指历史与方向信息，并不是说 Code 看不到原始当前代码。

### 4.3 第三个已确认问题：设计与代码并不总是一致

真实例子：`20260904b_vrptw_v104_rep1`，LLM log 第 291/292 行，对应生成 step 133、评价日志 step 134。

Idea 认为剩余客户少或容量紧张时应更容易回仓，并解释在 `return_cost < beta * customer_cost` 下需要较大的 beta。代码却使用：

```python
threshold = 0.85 - 0.35 * urgency
if return_cost < threshold * best_last_stop_cost:
    return depot
```

在固定、非负的比较成本下，urgency 上升使右侧阈值变小，回仓条件更难成立，与它自己的说明方向相反。该子代 fitness 为 **-26.884795**，父代为 **-20.889879**。

这是可直接验证的局部设计/实现偏差；它与该次性能退化共同出现，但尚未通过只修正这一处后的反事实评价，确定该偏差解释了多少退化。不能把全体 V10.4 的表现归于此例。

另一个 TSP 例子在 Idea 中描述 geometric lambda decay，实际代码采用线性插值。它再次说明：独立计划并不会自动保证代码忠实执行，也不会自动保证计划本身正确。

### 4.4 另外三个必须区分的因素

1. **算子定义漂移。** V10.4 Pivot 从“不同主机制”弱化为“发现不足、发展更强思想”，与 Refine 更接近。@400 的 CVRP Pivot 父代改善率从 V10.3 约 1.0% 变为 V10.4 约 16.0%，却没有获得更好的总体 @400 best。既可能是上下文变好，也可能是改动更保守或状态不同，不能用该改善率证明探索更强。
2. **Init 同时变了。** 第一阶段长设计和第二阶段实现作用于 8 个根，后续终局差可能从不同根分布开始。应在相同根/锚点上区分阶段机制。
3. **没有新增外部验证。** 第二次调用只重新组织和实现同一批信息，没有独立评价计划的正确性；可能改善实现，也可能固化一个错误假设。分离增加了接口，不自动增加算法证据。

配置核查显示 V10.3/10.4 客户端实际为 `enable_thinking=False`，同时显式使用 temperature=1.0、top_p=0.95、top_k=20。因此不能把 1024-token 现象归因为“隐藏 thinking 吃光预算”。应区分采样配方的名称与实际 thinking 开关。V10.5 延续该执行配置；若切换 thinking 模式，另列独立因素。

### 4.5 首选：单次调用联合生成，Idea 保持简短

一次调用看到任务、当前代码、形成事件、算子与可选 donor，输出简短机制摘要和完整代码。设计与实现共享上下文，消除独立 1024-token 计划关口；Idea 只承担形成记录的职责。

这不是要求模型“不进行算法设计”。设计自由应体现在可生成的机制、公式和代码中，不能用暴露多少设计段落衡量。共同上下文也不保证正确，单阶段仍可能产生不一致；选择它是因为它去掉了已发现的额外故障通道并降低调用开销。

“思想表示有价值”与“思想必须通过独立 API 调用产生”是不同命题。EoH 也把自然语言思想与代码作为联合算法表示，但这一点本身不为 V10.4 的阶段接口提供有效性证明。[Liu et al., ICML 2024](https://arxiv.org/abs/2401.02051)

### 4.6 次优：修复后的两阶段

如保留两阶段，至少同时满足下列职责边界：

| 项目 | 修复方案 |
| --- | --- |
| 设计输出 | 请求约 100–200 词的完整机制说明，先给核心决策/公式，避免背景论述；初始 max_tokens=2048 |
| 完成性 | 记录 provider 的 finish_reason；若 length，最多对同一状态重新生成一次，max_tokens=4096；仍截断则该次未生成有效候选，不交给 Code |
| Code 输入 | 同样提供紧凑形成历史、算子和原始代码；计划是提案，允许为可实现性修正 |
| Code 输出 | 实际实现的简短 Idea + 完整代码，不再只有代码 |
| 节点记录 | node.idea 取实际实现摘要；第一阶段全文只进调用日志，绝不递归写入形成历史 |
| 一致性 | 同次实现指令要求核对公式、阈值方向与接口边界；不增加第三个 critic 调用 |
| 成本 | 所有两阶段与重试调用均记入真实 LLM 成本，evaluator 仍统一 1000 次 |

长度修复、历史压缩、Code 补上下文应分别设对照。否则“修复版两阶段”胜出也只能说明修复组合有效，不能识别哪一项起作用。

## 5. 问题四：父节点预算分配是否做得足够好

### 5.1 判断：没有证据可以把这一层宣布为已解决

V10.1 是纯质量 ESS-Boltzmann；V10.2 已加入逆平方根访问次数修正并改为单子代后重选。因此预算分配并非从未动过，而是**改动的有效性与稳定性没有被独立确认**。

质量高的程序是合理的设计起点，但当前 fitness 不等于下一次扩展的收益。已有分析中存在重复选择充足却长期不再突破的路线，证明“继续给同一个好区域机会”不保证有好提案；也存在早期从较差根换构成功的路线，证明所有动作都只看高质量区域会漏掉有效起点。

### 5.2 五个具体缺口

1. **算子无条件选父。** 开发强程序和从较弱脚手架换向，未必需要相同父节点分布；现行选择先决定高质量 parent，再等概率安排三个动作。
2. **ESS 跟档案大小增长。** `E=0.1N` 将搜索分散程度绑在累计节点数上。第 900 次评价出现 90 个有效竞争节点，不意味着剩余 100 次预算应覆盖 90 个方向。这是设计假设，尚非已经证明的性能主因。
3. **访问次数只对应 node ID。** 同一方向产生新节点后计数归零，无法消除方向重复；但把所有同代码节点合并又会抹去不同形成历史。应保留生成状态的区别，不把 AST 去重当作行为去重。
4. **ESS 只校准修正前分布。** V10.2/10.3 记录的质量 ESS 不等于乘入访问修正后的最终 ESS。监控必须同时记录二者，不能把前者达标称为实际选择的所有性质都正常。
5. **低质量状态没有明确的可兑现机会下限。** 数学上的 Boltzmann 正概率可小到有限预算内几乎不被抽中，甚至数值下溢；“保留在树里”不能代替一次实际机会。但历史也未支持给所有差 Pivot 绑定固定多步预算。

谱系 family 不是行为簇。旧分析中的 family ESS≈1 暴露集中现象，却不能单独证明这个集中有害；成功 CVRP 也会后期集中，平台上的多族分散也可能没有价值。**要区分有产出的集中与停滞重复，而不是把分散程度本身设为优化目标。**

### 5.3 首选：保留质量基座，先选算子，再为 Pivot 扩大起点

设上下文可容纳的有效节点集合为 $\mathcal A_t$，大小为 N；排除仅因完整代码无法放入合法请求而不能扩展的节点，全部评价事实仍保留。

沿用 V10.2 的基座：

$$
p_q(n)=\frac{\exp[\beta(f(n)-f_{max})]}{\sum_m\exp[\beta(f(m)-f_{max})]},
\qquad E=\min(N,\max(0.1N,2)).
$$

最高 fitness 并列数为 $k_{max}$ 时，使用可达目标 $E^*=\max(E,k_{max})$。校准非负 $\beta$，再按已有父节点选择次数修正：

$$
p_0(n)=\frac{p_q(n)/\sqrt{c(n)+1}}{\sum_m p_q(m)/\sqrt{c(m)+1}}.
$$

先以固定比例选请求算子（requested operator），然后：

$$
p(n\mid R)=p(n\mid F)=p_0(n),
$$

$$
p(n\mid P)=0.5p_0(n)+0.5\frac1N.
$$

这只增加一次简单混合，不需要路线价值、成熟度、UCB、行为聚类或新 credit。代码可以先抽 P 的 quality/uniform 路由，再抽 parent；两种实现分布等价。

含义是将总生成机会的 **7.5%** 明确用于宽起点 Pivot；其余 92.5% 的父节点仍来自质量分布。较差程序的可运行组件可能成为更好结构的起点，但它不会因差而得到更多分数。

父节点最终确定后 `c(n)+=1`，无论来自哪条路由、是否生成有效代码。所有算子仍保留形成历史；不同时改变 Pivot 的历史长度，以免把起点分配与上下文效应混为一体。

上述条件分布以请求算子为条件。若 Fuse 因无 donor 回退为 Refine，按实际 Refine 统计时，parent 分布会包含这些回退状态；不能再将其无条件写成恰好 p0。必须同时记录请求与执行算子。

**作用边界：**这是宽起点的探索通道，不是差 Pivot 子代的 Refine 保底。对单个弱节点，仅靠 uniform 部分，在 m 次机会中被选中的概率下界为 $1-(1-0.075/N)^m$（N 不变的简化条件下）；大档案中仍可能很小。故它不保证延迟兑现，也不解决全部谱系垄断。推荐它是因为它把很小、可解释的预算用于检验窄起点的机会成本，而不是声称一步修复所有分配问题。

主要风险是弱脚手架浪费 Pivot，以及从高质量 parent 发起的 Pivot 变少。如果预算对照显示宽起点没有贡献，直接将混合比例设为 0；不再加一层“新方向价值预测”去挽救。

### 5.4 次优与后续备选

**次优是保持原 p0，先只改生成与算子概率。** 这样更接近已有基线，能直接回答固定比例是否有效；它同样是一套可正式运行的 V10.5 保守配置，不是缺少机制的半成品。

若重点诊断后期过散，可在这个保守配置上单独替换 ESS 目标：

$$
E=\min\bigl(N,\max(2,\min(0.1N,32))\bigr).
$$

保留原访问修正；记录最终 ESS。32 是预先固定的探索性上限，不声称最优。并列最优数超过 32 时仍使用可达下界，不能假装实现了硬 ESS 上限。该方案可能加强既有方向垄断，因此不与宽起点混合一起作为首发默认。

不推荐恢复“差候选固定开发 H 步”、家族生命周期、多层 UCB 或 subtree max-backup。仓库已有多次这类尝试及信用错位经验；当前需要的是可解释的机会分配，不是重新把未来潜力装进更多代理变量。预算分配经验

## 6. 问题五：V10.5 主配置的完整协议

### 6.1 固定参数

### 6.2 完整生成指令

Task Contract 复用当前任务信息与接口，不改变评价器。补充的共用说明放在 Design Direction 区，与算子一起出现，避免重复出现在多个区块：

```text
Improve evaluated solution quality within the task's information and runtime
limits. Use the formation history to understand the changes and their observed
outcomes; a previously unsuccessful mechanism may be revisited when its
limitation is addressed. Choose the computational structure and implementation
details that best serve the proposed improvement.
```

Init 单独使用，不添加不存在的历史：

```text
Design a competitive algorithm for this task using the available function
interface. Develop one coherent approach and implement it as a complete
executable function.
```

Refine：

```text
Develop the current algorithm's main approach by addressing the limitation you
judge most consequential. You may substantially revise formulas, auxiliary
mechanisms, or computational structure when this better realizes that approach.
```

Pivot：

```text
Develop a promising alternative with a different primary decision mechanism
from the current algorithm. Use the current implementation and its formation
history to identify what limits this approach, while retaining any components
that remain useful for the alternative.
```

Fuse：

```text
Use the current and reference algorithms to identify complementary useful ideas
and develop one coherent algorithm that aims to improve on the stronger input.
Keep, replace, or recombine components according to their roles in the resulting
decision process; neither implementation has to retain its original structure.
```

Output：

````text
Return one algorithm in exactly these two parts:
Idea: <1-3 concise sentences describing the implemented mechanism and the
decision change it is intended to produce>
```python
<complete executable implementation of the target function, with any required imports and helpers>
```
Keep the Idea brief, roughly within 100 words. Use code comments for important
implementation constraints when useful, without repeating the design discussion.
````

这里的简短限制针对可反复使用的记录，不限制代码复杂度。没有“不得复杂计算”“必须保留多少父代逻辑”“必须彻底全新”等约束。具体任务允许的启发式预计算或局部搜索仍可采用，但受实际接口和执行预算约束。

单次输出的 Idea 仍是模型自述，不保证准确；明确要求记录实际实现可减少角色歧义，不把它升级为因果标签或后验人工标注。解析器兼容多句 Idea，用代码围栏作为正文边界；不再用只捕获首行的正则丢失第二句。

### 6.3 上下文超限的确定性处理

仅沿用现有普通 `#` 注释过滤作为 Prompt view，字符串与 docstring 不变，存储和评价代码不变。它是兼容选择，不被声称为已证明的质量优化。

实现审查补充：V10.5 将通过目标接口和语法检查的完整模块文本直接交给统一 SecureEvaluator，并保存同一文本。不能用旧版函数重构转换器丢弃装饰器、辅助类或函数后的模块级赋值；统一评价器自身的执行与计分规则继续保留。

使用已有 `count_prompt_tokens` 对完整 chat 请求计数，满足：

$$
T_{prompt}+16384+256\le32768.
$$

处理顺序：

1. 先按历史区 2048-token 上限组织完整事件，再检查完整请求。
2. 超限时依次去掉最旧完整事件；原始历史始终存档。
3. Current/Donor 代码、任务接口、算子和输出契约不切片。
4. 选择 donor 前，确认最低上下文（不含历史）能容纳；在所有合法且可容纳 donor 中按 fitness 取 top-5。优质 donor 太长不应使整路搜索停止。
5. 对该 parent 无可容纳 donor 时，实际执行 Refine；记录 requested_operator=Fuse、executed_operator=Refine 和原因。不是静默转换。
6. 若 parent 单独就无法放入最低上下文，不进入当前扩展候选集；其代码及 fitness 仍保留，并可成为最终输出。若无任何可扩展节点，保存状态后明确报错，不伪称完成预算。

上下文裁剪不增加评价调用。tokenizer 计数属于服务辅助调用，与生成调用分开记录；相同代码与固定块可缓存，避免每轮重复请求所有档案节点。完整请求仍做最终精确检查。

### 6.4 搜索伪代码

```text
initialize RNG and empty single-parent tree
while fewer than 8 valid roots and evaluations < 1000:
    generate one Init Idea + Code
    if valid complete code:
        evaluate once; increment evaluation counter
        if finite valid fitness: store a root
if fewer than 8 valid roots:
    save incomplete state and report initialization budget exhaustion

while evaluations < 1000:
    A = valid archived nodes whose minimum parent prompt fits context
    compute p0 over A using ESS-Boltzmann and existing selection counts

    requested_operator ~ Categorical(R=.50, P=.15, F=.35)
    if requested_operator == P:
        parent ~ .5*p0 + .5*Uniform(A)
    else:
        parent ~ p0
    increment this parent's selection count once

    if requested_operator == F:
        D = fitting cross-lineage donor candidates
        if D is empty: executed_operator = R
        else: donor ~ Uniform(top5(D)); executed_operator = F
    else:
        executed_operator = requested_operator

    build compact formation history and one complete prompt
    checkpoint pending selection, prompt and post-selection RNG state
    generate one Idea + Code; persist raw response and completion metadata
    if complete parseable code and correct interface:
        evaluate once; increment evaluation counter
        if finite valid fitness:
            store one child with target as its sole parent
    log result, clear pending operation, checkpoint
```

Fuse donor 只作为信息来源，不改变单父树。每个已真实评价且有效的候选均可入树，包括退步、持平和代码重复的节点；不以低 fitness、代码长度或“算子不够像 Pivot”额外拒绝。

### 6.5 预算、失败与恢复

- 一次正式 evaluator 调用就是一个 slot，包括失败、非法运行结果和超时；候选重评也消耗 slot，不暗中免费复算。
- LLM 传输错误、解析失败、明确未完成输出不调用 evaluator；分别计入 LLM 调用/尝试成本。连续无有效输出的保护沿用现有上限 50。
- 单次响应 `finish_reason=length` 视为未完成，记录原因并放弃本次生成；下一轮重新分配。需要恢复的传输故障沿用同一 pending 请求，不重复增加父节点访问次数。
- 若 provider 不返回 completion 状态，日志明确 `unknown`，只按完整围栏、可解析实现和接口校验处理，不把未知标成 `stop`。
- 保存“选择完成”和“响应完成”两个边界，恢复时已有完整响应直接进入解析/评价，不重新抽算子、parent 或 donor。
- evaluator 提交前写入带唯一 candidate_id 的 evaluation_started 记录；正常返回后保存 outcome 与槽号。若进程在提交与持久化返回之间崩溃，先从 evaluator 日志恢复真实调用与结果；无法确认时占用一个 unknown reservation，防止预算超支，不免费重评。unknown reservation 与已确认实际调用分开记账；仍有此类不确定项的运行不能标记为完成了 1000 次真实评价。若已确认调用发生但结果丢失，则可计真实调用、结果标 outcome_unknown，单列报告。
- 实际代码实现应复用统一评价与进程管理设施，不在 V10.5 内再写第二套 evaluator。

### 6.6 需要记录的最小诊断信息

节点继续保存 `id, code, idea, fitness, evaluation_id, parent_id, operator, donor_id`。额外信息写入事件/调用日志，不把监测指标重新变成在线奖励：

| 类别 | 字段 |
| --- | --- |
| 决策 | requested/executed operator、三算子概率、parent 路由、parent/donor ID、选择前次数 |
| 分配 | N、beta、质量 ESS、修正后 ESS、实际条件分布 ESS、抽中 parent 的最终概率 |
| 上下文 | 模板版本/hash、实际 prompt tokens、保留事件 ID、删减原因、donor 回退原因 |
| 生成 | 原始 Prompt/Response、模型 ID、sampling 参数、finish_reason、usage、耗时 |
| 评价 | candidate_id、slot、调用前 global best、parent/donor fitness、结果或失败种类 |
| 结果指标 | 改善父代、超越双亲、突破全局、增益幅度、最终 best 的形成路径 |

三种结果分别统计，避免互相替代：

$$
I_{parent}=\mathbf1[f_c>f_p],\quad
I_{both}=\mathbf1[f_c>\max(f_p,f_d)],\quad
I_{frontier}=\mathbf1[f_c>B_{before}].
$$

非 Fuse 不计算 donor 指标。浮点比较沿用原始严格大小关系以保持口径；另记录原始 delta，分析时可报告去除数值噪声后的敏感性结果，但不悄悄改变在线 best 更新。

## 7. 如何验证选择，而不是再次走向多因素混合归因

### 7.1 第一优先：利用日志区分两阶段故障，不重做轨迹存在性验证

本次已完成的只读工作是长度审计、预算对齐、配置核查和设计/实现案例检查。后续新生成诊断应固定 parent、donor、operator、同一版方向措辞与相同形成事实；预先按任务/算子分层抽状态，并随机化调用顺序。

建议四臂：

| 臂 | 条件 | 要回答的问题 |
| --- | --- | --- |
| T0 | 当前 V10.4：长历史、Idea 1024、Code 无历史/算子 | 可复现的旧阶段端点 |
| T1 | 仅增加 Idea 完成性与充足生成预算，其他同 T0 | 未完成设计是否是主要损失通道 |
| T2 | 在 T1 上只向 Code 补充相同形成历史与算子 | 实现阶段的信息缺失是否有影响 |
| T3 | 在 T2 上只把历史叙述压成按固定格式记录的简短事件 | 历史膨胀是否有影响 |

这里的历史压缩在固定状态上应由可核验人工摘要或预先冻结的统一转换生成，并保留事实一致性；不让每个条件临时额外调用 LLM 随意解释历史。无法取得一致摘要的状态不要混入该成分对照。

另比较“修复后两阶段”与“同上下文、同方向、单次 Idea+Code”两个端点，区分接口本身与已知缺陷。局部诊断预算单列；每次 evaluator 调用照实记录，不能冒充完整 1000-eval 正式重复。保留所有失败，不能只在两边都成功的样本上给出唯一结果。

不预先承诺大量固定状态生成。先用覆盖五任务、三算子的少量重复定位截断与一致性，再决定是否值得扩大；长输出对完整搜索的影响最终由正式对照确认。

### 7.2 正式机制对照：先提示，再比例，再选父

所有完整搜索臂仍为 1000 次真实评价。建议最小完整矩阵为四臂 × 五任务 × 三重复，共 60 路：

| 臂 | 生成上下文 | 算子比例 | 父节点分配 |
| --- | --- | --- | --- |
| A | V10.3 单阶段提示 | 等概率 | 原 p0 |
| B | V10.5 紧凑事件与中等指引、单阶段 | 等概率 | 原 p0 |
| C | 同 B | 0.50/0.15/0.35 | 原 p0 |
| D（主配置） | 同 B | 0.50/0.15/0.35 | Pivot 半均匀混合 |

`B−A` 评价上下文/说明这一组合，`C−B` 直接回答比例是否有效，`D−C` 回答算子条件选父是否值得。B 同时改变多个文本呈现，不把 B−A 归因给某一句话；若需文本级解释，再用固定状态对照。

为隔离扩展机制，可在每个 task×repeat block 内共用预先冻结的 8 份根代码，**各臂各自实际评价这些根并计入 1000 次预算**。根代码生成是共享准备成本，单列；这批对照是“给定共同根”的机制效果。另用独立 Init 的端到端运行确认 V10.5 Init 是否改善整套方法，不能用共享根实验回答初始化问题。

当前配置 seed 主要控制本地搜索与任务随机性，不能仅凭相同整数认定 LLM 服务生成完全配对。新实验若服务支持采样 seed，应显式记录；即便支持，也以共同状态、多次采样及随机化调用顺序为主要控制，而不是期待不同长度 Prompt 产生相同随机续写。

硬件后端、量化版本和启动批次按 task×repeat 区组平衡或轮换；不把一个版本全部放到另一种后端。上下文超限等工程修复应作为公共基础设施一致应用于对照臂并记录，避免只给新臂额外优势。

### 7.3 主要判据与稳定性

首要结果是 1000-eval best 及其未知实例、跨规模测试。训练曲线同时在 100/200/400/600/800/1000 检查点读取，不按最快完成的子集比较。

稳定性至少分开三件事：

- **较差重复是否改善**：均值提高不能完全来自一个幸运的最好 run。
- **上尾能力是否保留**：减少 Pivot 后若所有 run 更一致但最强算法能力下降，不称为全面改善。
- **是否正常完成**：模型/上下文/评价失败导致的中止不能从正式统计中默默剔除；同时报告完成率和最后已知 best。

三重复用于首轮方向判断，不足以稳定估计尾部分位数。报告每路原值与配对差，不把同一路的很多节点当作独立重复；只有结果值得继续且不确定性影响决策时，扩大完整重复数。

算子分析必须同时报告“每生成尝试”和“每真实评价”的成功与前沿贡献。P 的后续作用可追踪子树中后来的突破，但不把所有后代增益自动记作祖先 P 的因果功劳。

LLM 调用数、实际输入/输出 tokens、总生成耗时与 evaluator 时间单列。两阶段即使在相同 1000-eval 下胜出，也需要说明额外计算成本；必要时另作同 LLM-token 成本曲线，它不替换正式 1000-eval 主口径。

最终 held-out 用于冻结后的确认；选择比例与模板使用训练/开发口径，避免反复看同一个最终测试集来调版本。

### 7.4 预先明确的取舍规则

1. C 优于 B，且下尾/跨规模无明显损害：保留固定非等概率；无需为了新颖性再加自适应。
2. D 相比 C 没有可重复收益、宽起点大部分成为无效支出：选择 C 作为最终 V10.5，删除混合路由。
3. C 在开发稳定性上改善、但 P 相关上尾明显下降：试验已指定的 0.40/0.25/0.35，不直接恢复复杂调度器。
4. 修复后两阶段仍无足以补偿成本的收益：保持单阶段。若稳定胜出，再以其替换生成模块，不同时修改概率与分配。
5. B 的提示组合没有改善：回到 §2.4 的 V10.1 最小修订。轨迹仍保留，不把一次呈现设计失败解释为轨迹无效。

## 8. 对当前研究思路的纠正

**最需要纠正的不是“还不够重视轨迹”，而是把算法设计能力、生成文本形式和有限预算收益过早地等同起来。**

- 必要限制应保证可实现与可评价；强制创新、强制保留父代机制或“融合必须长成某种样子”会额外限制可达解。
- 简短 Prompt 不自动意味着模型更自由，长 Idea 也不自动意味着思考更充分。V10.4 当前甚至把未完成设计和实现前论述当成了后续历史。
- 历史算子表现足以支持概率调整，但新 Prompt 会改变算子实际行为。固定比例应被当成有作用的搜索参数，并在新生成机制下确认。
- 质量分配是合理基座，不是未来机会价值的完整估计；偶发强 run 说明某些路径可达，尚不说明它们能被稳定发现。
- 稳定性与能力上限需要同时保留。消除低命中探索可能减少方差，却让所有运行稳定地停在较弱方案；反过来，为所有差方向支付固定后续成本也可能挤掉有效开发。

V10.5 的核心取舍是：**保留轨迹带来的设计依据，保留模型选择算法细节的空间，把更多评价交给开发动作，并用一个可解释的小比例通道扩大换向起点。** 其每个新增规则都对应上文一个具体问题；备选机制不同时进入主配置。
