# TraceAAD V10.13：让 LLM 提出改进，让进化搜索分配机会

## 设计定位

V10.13 重新定义上一版的综合机制。上一版把形成树中的路线当成机会分配和参考多样性的组织单位，这是错误的：`parent_id` 只说明一个程序从哪个程序产生，不能说明两个节点属于同一类算法，也不能说明路线之间存在可比较的语义关系。V10.13 不使用路线分群、行为簇、行为签名或 BehaveSim 式的行为距离。

V10.13 也不要求模型完成一份行为审计表。模型只输出两样东西：一段简短 Idea 和一份完整代码。它的创造力来自模型内部的算法知识、任务理解和随机生成；搜索机制负责保存真实评价结果、按质量分配后续机会，并通过不同算子提出不同类型的改进。

核心循环是：

```text
LLM 提出算法改进 → 代码通过解析并接受真实评价
    → evolutionary archive 保存候选和 fitness
    → ESS-8 质量分配选择下一次父代
    → 算子提示决定下一种改进动作
```

V10.13 的目标不是用更多规则替代算法设计，而是让规则只承担 LLM 不擅长的部分：预算、记录、筛选、父代选择和失败恢复。算法思想、改进方向和实现方式交给 LLM 与随机进化过程共同产生。

“在任何任务上都优秀”仍然是待验证的研究目标，不是有限预算机制能够保证的性质。V10.13 先消除已经确认的结构性干扰：错误的路线语义、过度复杂的行为契约、无条件参考卡片和与动作无关的冗余上下文。

## 设计依据

### V10.10 保留的部分

V10.10 的优势来自简单组件之间的配合：

- 真实 evaluator 预算清楚；
- 初始化和正常开发共享同一评价预算；
- 四个算子保持固定机会，防止早期偶然结果关闭某种改进动作；
- ESS-8 让质量优先，但不把整个 archive 压缩成一个精英；
- 当前代码和短形成历史提供足够的连续改进信息；
- Idea 与代码一起保存，但解析只要求可执行输出；
- 失败有明确记录，修复最多一次，修复不重新抽取父代。

这些结构直接进入 V10.13。V10.13 不把 `attempts` 作为“新颖性”或“路线价值”分数，也不把程序是否属于某个结构类别交给一个脆弱的静态规则判断。

### V10.11 暗示的上下文事实

V10.11 的比较仍说明上下文需要和动作匹配：连续改进更需要当前程序及其短形成关系，主机制替换和融合需要另一个可执行程序作为灵感和对照。这个结论只支持“算子使用不同材料”，不支持“路线是类别”或“task 名称应该进入路由器”。

V10.13 因此只保留四种很直接的上下文：

- `Refine`：当前程序和短形成历史；
- `Tune`：当前程序和短形成历史；
- `Pivot`：当前程序和一个 archive 参考程序；
- `Fuse`：host 当前程序和一个 donor 程序。

参考程序由质量偏置和均匀成分共同抽取。它只是本轮 LLM 的输入材料，不是语义类别代表。

### V10.12 的失败说明上下文不能靠堆卡片获得

V10.12 将 Idea+fitness 卡片追加给所有算子，没有稳定收益。问题不在“卡片数量还不够”，而在卡片没有明确承担一个设计动作：模型不知道是要继续当前程序、替换主机制、调参数，还是从卡片迁移计算。

V10.13 不加入多张 profile card、行为摘要或卡片整合协议，而是让需要参考程序的算子直接看到一份完整可执行的 donor/reference，并用简短提示说明这份程序的用途。

### EoH 可借鉴的地方

EoH 的强项是把 LLM 生成写成几个简单的进化操作：从多个程序提出新形式、基于一个程序修改、调整主要参数、简化或组合程序；然后把候选交给 population survival 和 evaluator。它没有要求 LLM 输出一套复杂的中间证明。

V10.13 借鉴其“少数清晰操作 + 真实评价筛选”的结构：

| V10.13 | 可借鉴的 EoH 操作 | 作用 |
|---|---|---|
| `Refine` | m1 | 修改当前程序的一个重要部分 |
| `Tune` | m2 | 调整影响决策的主要参数 |
| `Pivot` | e1 | 从当前问题出发提出不同主机制 |
| `Fuse` | e2 | 参考另一个程序并形成协调算法 |

V10.13 不直接复制 EoH 的 population API、并发模型或任务接口，因为 TraceAAD 还需要目标函数锚定、真实评价预算、形成父指针和 checkpoint 恢复。

### BehaveSim 的边界

BehaveSim 的行为比较和分支反馈可以启发“候选实际行为很重要”这一研究问题，但它不是一般任务上的通用机制。不同任务的输出语义、实例分布和行为等价关系不同，静态代码形状或固定行为距离无法可靠地定义多样性。

V10.13 不调用 BehaveSim，不计算行为签名，不做行为聚类，不把行为相似度放入预算或 prompt。行为是否有价值只由 evaluator 结果和后续泛化决定；代码和 Idea 作为原始证据保留，供 LLM 在形成历史中自然使用。

## 第一性原理：LLM 和 evolutionary search 各做擅长的事

### LLM 的职责

LLM 擅长从任务描述、程序、已有算法知识和少量结果中提出新的决策机制。它可以联想到启发式、局部搜索、构造规则、概率策略、参数关系和程序重组。这个过程需要随机性和开放空间，提示应表达“要完成的改进动作”，而不是要求模型逐项填写机制证明。

### evolutionary search 的职责

Evolutionary search 擅长在有限评价预算内反复产生、评价、保留和选择候选。它不需要理解算法语义，也不需要猜测模型的想法是否正确；只依据可审计的 fitness 和父代关系分配下一次机会。

### 两者的接口

接口只有三项：

1. **候选程序**：LLM 返回完整代码，解析器确认目标函数和语法；
2. **真实 fitness**：evaluator 把程序转为可比较的质量信号；
3. **下一次机会**：archive 选择器按 fitness 分布抽取父代，算子提示决定改进类型。

树结构只保存形成关系，`parent_id` 不承担类别或多样性语义。`attempts` 只记录父代被选次数，便于分析实际预算流向，不进入选择分数。

## 完整机制

### 1. 任务、评价和预算

V10.13 复用现有任务模板、任务文本、实例、随机种子、目标函数签名、安全评价器和运行时冻结设施。正式默认参数为：

```text
每路真实 evaluator 预算：1000
初始化有效个体：8
形成历史：最近 3 条父子边
父代质量分布：ESS-8
Refine/Tune/Pivot/Fuse：各 25%
Pivot 的父代：50% ESS 质量 + 50% 均匀
Pivot 参考、Fuse donor：50% ESS 质量 + 50% 均匀
```

预算单位是实际 evaluator 调用：

- 有效初始化、正常候选、评价失败、超时、非法返回和修复后的评价都消耗一个 evaluator 预算；
- LLM 调用失败和解析失败不消耗 evaluator 预算，但保留调用记录；
- 一个失败候选最多触发一次修复；
- 修复继承原候选的 parent、donor、operator 和候选身份，不重新分配父代机会；
- 未知评价器故障阻断运行，不能让 LLM 猜测并掩盖基础设施问题。

### 2. 初始化：顺序产生 archive

前八个有效候选是 `Init`。第一个只看到任务契约；后续初始化候选看到前面已经评价的初始化程序及其 fitness，作为进化搜索的初始材料。

初始化提示仍只要求模型提出一个有竞争力的算法并实现它。初始化程序全部进入 archive；不根据 AST、行为形状或文字类别去重和分组。容量超出时按照既有完整提示检查失败，保留原因，不静默删掉程序材料。

### 3. Archive 父代选择：V10.10 的 ESS-8

设当前有效 archive 为 (A_t)，节点 (i) 的 higher-is-better fitness 为 (f_i)。使用当前 fitness 直接建立质量分布：

[
q_i(\beta)=
\frac{\exp(\beta(f_i-f_{\max}))}
{\sum_{j\in A_t}\exp(\beta(f_j-f_{\max}))}.
]

每一步通过数值求解 (eta)，使：

[
\operatorname{ESS}(q)=\frac{1}{\sum_iq_i^2}
\approx\min(|A_t|,8).
]

当所有 fitness 相同、节点不足或并列使目标不可达时，使用可达到的分布。对 fitness 做正比例缩放或加常数不会改变质量排序和 ESS 目标，适合五个任务的不同分数尺度。

- `Refine`、`Tune` 和 `Fuse` 的父代直接按 (q) 抽取；
- `Pivot` 使用 (0.5q+0.5U)，给替代机制保留固定的 archive 探索；
- 节点被选为父代时 `attempts += 1`，但不进入 (q)；
- 新节点从 `attempts=0` 开始，和全部 archive 节点按相同质量规则竞争；
- 相同代码节点不合并、不共享 attempts；只有 donor 选择会排除与 host 完全相同的代码，避免 Fuse 直接复制。

这是一种简单的质量分配，而不是对未来收益的确定性预测。它把判断“一个想法是否值得继续”留给真实 fitness 和后续 LLM 改进，而不是用路线、行为标签或复杂在线控制器提前替代。

### 4. Reference 和 donor 选择

`Pivot` 和 `Fuse` 各最多使用一个 archive 程序：

1. 排除当前 parent；
2. 排除与当前 host 完全相同的代码；
3. 按候选 fitness 的 ESS-8 分布计算质量偏置；
4. 与 50% 均匀分布混合后抽取一个程序。

这不是类别采样，也不是“来自不同路线”的保证。它只是 evolutionary archive 向 LLM 暴露一个有质量偏好且保留随机性的可执行参考。没有可用 donor 时，`Fuse` 回退为 `Refine`；`Pivot` 可以在无参考时直接提出替代算法。

### 5. 算子和上下文

#### Refine

输入：任务契约、当前程序、当前 fitness、最近最多 3 条形成边、输出格式。

提示重点：找到当前算法中值得改善的一部分，做一次真实的算法改动，保留有效结构。它对应 EoH 的单程序修改操作，但不要求模型说明修改标签或行为证明。

#### Tune

输入与 Refine 相同。

提示重点：保持主决策方法，尝试更好的影响性参数、阈值、权重或调度。数值调整必须能够改变返回决策，但模型不需要逐项列出参数清单。

#### Pivot

输入：任务契约、当前程序及其 Idea、当前 fitness、最近最多 3 条形成边、一个 archive reference 及其 Idea（如果有）。

提示重点：围绕任务限制提出不同的主决策机制。参考程序只是算法灵感，模型可以借鉴、变换或完全不用其中的实现；搜索不把“必须融合参考”变成额外输出规则。

#### Fuse

输入：任务契约、host 当前程序及其 Idea、host fitness、最近最多 3 条形成边、一个 donor 程序及 donor fitness/Idea。

提示重点：比较两个程序，借鉴 donor 中有用的计算，形成以 host 为中心的一个协调算法。提示只保留一句防止机械拼接的说明，不要求模型输出 host limitation、donor feature 或 integration point 的结构化字段。

#### 形成历史

形成历史只展示父子关系中的 operator、前后 fitness 和原始 Idea。它是短期搜索记忆，不是经过验证的因果解释。Refine/Tune 使用它来保持局部改进连续性；Pivot/Fuse 将一个可执行参考程序作为主要外部材料。完整历史代码和日志留在 archive 与 journal 中，普通 prompt 不展开祖先代码，避免把上下文变成代码档案搬运。

### 6. 最小输出协议

模型输出：

~~~text
Idea: <一段简短的算法描述>
Code:
```python
<完整实现>
```
~~~

Idea 只需要帮助下一轮理解程序的主要算法，不要求 Change、Evidence、Behavior、Preserve，不要求说明推理过程，不要求证明 Idea 与代码的语义一致。代码是真实评价对象；Idea 是上下文材料和研究记录。

解析器仍检查必要的工程边界：

- 恰好一个完整 Python 代码块；
- 目标函数名称和参数签名正确；
- 代码能够被 AST 解析；
- 自动合并必要的辅助定义；
- Idea 有限长，防止响应变成另一份长文档。

这些是让输出能进入 evaluator 的接口检查，不是算法创作规则。格式失败后，修复提示只回送原始失败输出和实际错误，要求保留原算法意图并重新返回 Idea+Code。

### 7. 完整搜索顺序

```text
初始化未完成？
  是 → 生成 Init，评价并加入 archive
  否 → 抽取算子
       → ESS-8 抽取 parent
       → Pivot/Fuse 时按质量+均匀抽一个 reference/donor
       → 组装该算子所需的最小上下文
       → LLM 返回 Idea+Code
       → 解析、评价、记录、保存 checkpoint
```

生成失败时优先处理一次修复；修复失败后进入下一次正常算子抽取。新候选、退步候选和成功候选都进入完整 archive，真实 fitness 决定后续机会，不预先删除“看起来不够新”的程序。

## 相对上一版 V10.13 草案的删减

| 草案机制 | 处理 | 原因 |
|---|---|---|
| 初始化路线及路线级预算 | 删除 | parent link 是数据结构，不是语义类别 |
| 路线生产率、停滞、路线 ESS | 删除 | 用伪语义分组替代真实 fitness，增加控制层和不确定性 |
| AST 行为签名与行为摘要 | 删除 | 跨任务不能稳定表达行为等价和多样性 |
| 多张跨路线参考卡片 | 删除 | 卡片数量增加提示噪声，不能保证可迁移的算法计算 |
| Change/Evidence/Behavior/Preserve | 删除 | 增加 LLM 输出负担，把创造过程变成结构化填表 |
| Fuse/Pivot 的多重采用协议 | 删除 | 只保留“如何完成该算子动作”的简短提示 |
| 路线和行为字段的持久化 | 删除 | 只保存真实搜索需要的节点、父代、算子、donor 和 fitness |

## 可审计的过程证据

V10.13 只记录有助于判断进化搜索是否工作的过程数据：

- `selection`：ESS、parent 概率、donor 概率和 archive 大小；
- `events.jsonl`：算子、父代、donor、fitness、parent improvement、frontier improvement；
- `nodes.jsonl`：完整程序、Idea、fitness 和形成关系；
- `llm_calls.jsonl`：提示哈希、token 数、响应、repair 阶段；
- `tree_state.json`：archive、attempts、RNG、预算和最后结算事件。

这些数据说明“搜索如何运行”，不把 parent 命中率、Idea 长度、代码结构或解析率直接当成算法质量。正式结论仍以相同真实评价预算的重复均值、best-so-far 曲线和 held-out 泛化为准。

## 设计边界

V10.13 不承诺任何任务上的必然最优，也不把 EoH、BehaveSim 或任何一个历史系统的结构照搬为 TraceAAD 的通用控制器。它做的事很少但清楚：LLM 提出候选和改进，evolutionary archive 用真实评价管理机会，算子提示把搜索动作区分开，日志和 checkpoint 让结果可复核。

如果正式结果仍然失败，优先检查三条证据链：

1. LLM 是否在对应算子中产生了真实不同的算法改动；
2. ESS-8 是否把评价机会交给了产生高质量后代的 archive；
3. 短上下文和单参考是否帮助了迁移，而不是让模型复制或遗忘任务约束。

只有这些事实被确认后，才有理由改变算子比例、质量分布或上下文数量。继续添加行为标签、路线控制器或输出字段，不能替代真实的算法改进。
