# LLM-AAD 中的输出模式与生成—执行协议调研：完整交付、结构编辑与有界恢复

**整理日期：2026-09-27**  
**文档性质：文献与实现线索整理、当前源码对照、协议设计建议及验证路线；不代表新协议已实现或已优于现有方法。**

配套阅读：[种群、父代与预算管理](LLM-AAD中的种群管理机制调研.md)、[算子设计与上下文组织](LLM-AAD中的算子设计与上下文组织调研.md)。本文补上修改从模型响应变成可执行候选的交付层。

## 摘要

TraceAAD 不宜把输出模式固定成 code-only、完整重写或多轮 agent 中的一种。更合理的设计是：**可执行程序是硬交付，简短修改说明是可选元数据；短程序完整生成，长程序优先按自然结构编辑，确有复杂依赖或诊断需求时才购买受预算约束的局部 agent 开发。** 所有后端最终进入同一套程序重建、独立验证、尝试记录与成本结算流程。

输出载荷、代码表示、交互过程和失败恢复是四个不同维度。Idea＋局部补丁可以一次生成，code-only 也可以配合多轮工具调用。模式名称不能代表成本或能力；整套算法有效也不能证明其中一种输出形式普遍最优。

协议本身会影响实际搜索分布。长程序更易被截断、补丁更易定位失败时，调度器观察到的低收益可能含有交付偏差，而非纯粹的算法潜力不足。应区分未完整生成、歧义载荷、补丁失败、语法/接口失败、运行或约束失败，以及有效退步；评判重点是固定真实成本下的最终质量与有效改进效率，而非首次输出长度或单纯解析率。

本轮建议先把 Full 模式内核做成可审计协议，再增加结构化 Edit，最后仅对必要任务开放有界 Agent。核心边界是：唯一完整载荷、真实基底、原子重建、准确完成状态、分层错误、共享恢复额度、真实源码快照以及内外一致的预算账本。本文还区分表达、结构、计算和上下文四种膨胀，反对未经验证地将代码长度惩罚或删除所有注释/docstring 当作通用优化。

## 2. 输出模式的四个独立维度

| 维度 | 决策问题 | 可选形式 |
|---|---|---|
| 输出载荷 | 除程序外需要什么？ | 无说明、短 Idea/Change、完整计划、事后描述 |
| 代码表示 | 如何表达新程序？ | 完整代码、完整函数/结构块替换、SEARCH/REPLACE、原生编辑工具 |
| 交互过程 | 一次完成还是反馈后继续？ | 单次联合生成、plan→code、code→description、多轮编辑与测试 |
| 交付与恢复 | 何时提交、失败怎样处理？ | 原子重建、完成状态检查、验证、有界修复、格式回退、终止 |

例如“短 Idea＋SEARCH/REPLACE＋一次调用”与“无解释＋多轮工具编辑＋最终快照”都成立。称为 diff 的方案还可能按行号、内容、语法块或函数定位，不能不说明语义就互相比较。

Tune、Refine、Pivot 是语义修改范围；Full、Edit 是表达方式；Agent 是多轮交互政策。Tune 可以全文输出，Pivot 也可能只替换一个评分函数。允许编辑的算法范围由任务契约规定，不因输出完整 Python 就自动开放整个求解器。

研究目标是：在相同模型、任务、状态证据和预算下，哪种组合最容易将有价值的修改落实成完整、正确、可验证的程序，并支持后续开发。

## 3. 相关方法的实际做法与边界

### 3.1 code-only、联合说明与两阶段生成

| 方法 | 输出/交互方式 | 不能直接推出的结论 |
|---|---|---|
| EoH | 同一请求内简短思想描述＋规定接口代码 | 不证明计划必须单独调用，也不证明 Idea 普遍提高质量 [1] |
| ReEvo | crossover、elitist mutation 要求代码块；短期/长期反思由其他调用提供 | code-only 的输出不等于系统没有语言推理辅助 [2] |
| MCTS-AHD | 先实现，再用额外调用做至多三句 thought alignment | 描述对齐不是执行验证，额外调用需计成本 [3] |
| AlphaEvolve | SEARCH/REPLACE 或完整代码，限定可演化区域 | 不能据此一律采用 diff 或认为完整代码更自由 [4] |
| ShinkaEvolve | 支持 diff、完整重写、crossover 等配置 | 生成代数不能直接还原模型调用数 [5] |
| AIDE | draft、improve、debug 开发流程，调试深度受条件限制 | Agent 不等于不受约束地延长会话 [6] |

本地 ReEvo 基线提示可见 `Output code only`，EoH 提示包含思想描述与实现步骤，但这是本地基线快照，不代表所有论文版本的配置。整法成绩通常同时改变选择、上下文、反思和预算，不能独立归因输出样式。

### 3.2 AIDE：辅助说明也可能制造重采样

附件称其读取的 `aide/agent.py` 中，`plan_and_code_query` 一次生成计划与代码，默认至多尝试三次，成功返回同时要求代码和前置自然语言；有完整代码但无说明时仍可能重新采样。本轮未找到相应本地源码，保留为具体快照的待核验转述，不泛化到所有 AIDE 版本。

这个例子提示：越多必填字段，越可能因非算法原因浪费候选预算。TraceAAD 不应因为 Idea、标题或证据编号缺失就丢弃唯一明确、完整且满足接口的代码。若确需辅助元数据，缺失标为空，不为补一句说明再生成程序。

### 3.3 ShinkaEvolve：看最终解析配置与真实调用

本地可核验配置显示：`max_patch_attempts` 在配置类与文档默认表中为 1，`small_budget.yaml` 覆盖为 10；文档还列出 `max_patch_resamples=3`、`max_novelty_attempts=3` 及示例/默认表中的 `max_tokens=16384`。[5]

这些是当前本地快照，不是所有任务或论文原始实验的统一参数。不能只报告一个默认值；也不能不读控制流就把几个上限相乘当作实际调用数。应记录最终解析配置、实际进入的循环、每次重采与费用。

“100 代”可能包含补丁重采、语法修复、新颖性重采或诊断调用，不能直接等同于 100 次 LLM 或 100 个候选。

### 3.4 Aider 与编辑协议：名字相同，事务语义可能不同

附件所述 Aider 文档区分完整文件、SEARCH/REPLACE、简化 unified diff 和 architect/editor；一些模型会用“其余原代码在这里”一类注释省略实现，编辑格式可能影响这种行为。[7] 本轮未重新获取其在线文档，以下视作协议设计线索。

一个可复现编辑方案至少需要明确：怎样定位、零匹配或多匹配如何处理、是否容忍空白差异、多块按何种顺序应用、是否允许重叠、失败是否保留部分修改。原生工具也不能免于这些语义，只是由工具定义承担。

### 3.5 结构编辑研究：最短补丁不一定最可靠

附件对《To Diff or Not to Diff?》的概括包含完整代码、行号定位、内容定位和结构感知 diff，并提到 BlockDiff、FuncDiff 及自适应选择。[8] 过于零碎的片段可能损害可靠性，省掉行号本身未必解决定位和依赖问题。

可吸收的假设是：完整函数或连贯结构块可能更符合模型表达代码的方式。但材料指出主要结果包含专门微调；不能声称只给任意模型换提示就能得到相同收益。本轮未核验原文版本和实验数字，不添加精确提升或最佳阈值。

### 3.6 有界 agent 的接口与代码复杂度研究

SWE-agent 强调浏览、编辑与反馈接口的重要性；附件还转述其对“每个微小编辑必须立即可运行”的限制，认为这种约束可能阻碍多处协调修改。[9] TraceAAD 应检查完整修改事务，不要求每个临时编辑步骤都通过运行，但任何被实际测试的新快照必须登记。

Code Evolution Graphs 用结构特征分析代码演化，在其任务中观察到反复生成常伴随复杂度增加，而新增复杂性有时损害性能。[10] 关系依任务而变，不支持“一律更短更好”。应区分表达成本、程序结构和实际计算预算。

## 4. 协议也是搜索机制

### 4.1 有价值的修改必须穿过交付链

```mermaid
flowchart LR
    A[模型响应] --> B[完成状态与载荷检查]
    B --> C[重建完整程序]
    C --> D[独立验证与评价]
    D --> E[事实档案与后续开发]
```

没有穿过这条链的算法思想无法获得后续发展机会。解析与编辑适配器不只是中性的工程外壳，它们会选择性地保留或丢失不同复杂度、形式和长度的候选。

例如两个区域当前质量相近，但一个程序更长、依赖更多；统一小输出额度下，它可能频繁截断。调度器把这些都当成无潜力观测，便会对该方向降权。这部分低收益来自交付条件，不能直接等同于算法结构不可开发。

协议诊断应单列失败阶段，并在比较格式时固定父代与算子。最终系统效率可以包含这些失败成本，但机制解释必须知道损失发生在哪里。

### 4.2 评价有效改进成本，不只看输出长短

补丁少一半输出 token，若经常两次修复，不一定更省钱；Agent 修好更多程序，若额外测试和调用成倍增加，也不一定更有效。输入中的基底代码、工具说明、诊断和缓存计费同样影响总成本。

评价顺序是：固定真实成本下的最终质量与稳定性，其次有效新程序和净改进的产出效率，最后才是解析率、首次响应长度和补丁成功率。

语法通过率高却大多复制父代，不能定义为强输出模式；快速修好大量低分程序也不必然推进最好值。

## 5. 三类交付后端

### 5.1 Full：完整程序与可选短注记

短函数和小型模块默认一次联合生成，契约为 **Code 必需，Change/Idea 可选**。这与当前 V10.13 的可选 Idea 方向一致；附件关于 V9.5 的历史说法不作为当前实现依据。

建议请求模板：

```text
提交一份满足任务接口的完整可执行候选。
代码前可用一至两句说明拟修改的机制；缺少说明不影响合法代码交付。
不要输出长篇分析、多个备选实现或未经执行验证的成绩。
不要用“其余部分不变”、旧代码备份或占位注释代替完整实现。
保留必要接口与依赖。
注释限于非显然机制、单位、边界、不变量和必要假设。
允许删除、替换已经失效的旧逻辑，不要求不断叠加机制。
```

短注记用于意图检索和复盘，不是实际 diff 或权威行为解释。不得仅为补注记重开调用。

限制公开说明长度也不等于取消模型的内部推理计算。可见输出与后端推理 token 可能使用不同预算语义，需要按具体模型接口记录；不能仅看到代码输出短就宣称思考或计费少。

### 5.2 Edit：完整函数或结构块优先

长程序且修改位置明确时，优先比较完整函数/结构块替换或模型熟悉的原生编辑工具。结构单元比全文短，又比碎片行级编辑更连贯。

定位完整函数仍需唯一限定：文件路径、作用域/类、函数名和基底版本；不能忽略同名方法、嵌套函数、装饰器或默认参数。新增 import、全局状态、辅助函数和调用方适配必须一起纳入事务，不能仅替换函数体后假设依赖自动成立。

原生工具有训练和使用先验时，可保留其协议，由宿主适配为统一程序快照。统一的是记录、评价和预算，不必强制所有模型使用自创 DSL。

#### 5.2.1 SEARCH/REPLACE 的首版事务语义

建议固定以下规则，作为待实现/待验证规格：

1. **基底固定。** 请求绑定真实代码快照及 hash；上下文不得只给压缩视图后要求精确匹配。
2. **范围合法。** 仅编辑任务开放的文件/区域；评价器、数据和基底元数据不属于可修改对象。
3. **唯一匹配。** 每块 search 在规定源文本中恰好匹配一次，零匹配、多匹配分别报告；首版不做模糊猜测。
4. **顺序固定。** 可采用按列表顺序在临时副本上应用；后块看到前块结果，必须在协议中说明。若改用全部针对初始基底，需另定重叠处理，不能混用。
5. **全有或全无。** 全部块重建成功才形成提交快照；任何一块失败则丢弃临时改动，宿主基底不变。
6. **记录精确结果。** 保存原补丁、应用顺序、基底、重建源码及错误。成功重建不代表语法、任务约束或性能通过。

这里的“原子”是重建提交语义；评价失败的源码仍作为失败尝试保存，不是从历史抹去，也不意味着它可以进入有效精英集合。多文件编辑同样以一组协调文件变更为事务。

### 5.3 Agent：局部、有限、返回真实快照

仅对多文件依赖、需环境读取、错误定位或多处协同实现的任务考虑局部 Agent：

```text
读取必要源码与环境信息
→ 在暂存区完成一组协调修改
→ 注册完整候选快照
→ 获取真实诊断
→ 在剩余授权内修复或继续
→ 返回按既定规则选出的已评价快照
```

外层限制候选数、模型调用数、token/费用、执行计算量和截止时间。Agent 不接管全局种群，不自行续票，不把所有精英广播到每条路线，不修改评价器。只读工具不等于候选生成，但仍记录成本与时间。

允许中间编辑暂时不可运行，验证的是完整事务；但不得绕过候选注册偷偷测试多个未记录版本。自写测试用于诊断，不替代宿主正式评价。

起始父代、当前工作程序和中间最好程序分开保存。最后工作目录可能退步，不能直接作为最终成果；只返回有相应评价记录的合适快照。若没有新有效程序，可返回起始基底并报告无净进展，不能伪称产生了新成果。

### 5.4 后端选择与回退

| 条件 | 优先候选模式 | 必须记录的取舍 |
|---|---|---|
| 短函数/小模块可完整放入输入输出 | Full | 完整载荷与结束状态 |
| 长程序中局部位置明确 | 结构化 Edit/原生编辑工具 | 基底、定位和相关依赖 |
| 多文件、依赖不清、确需工具反馈 | 有界 Agent | 调用、快照、测试与开发上限 |
| 补丁反复失配但全文容得下 | 剩余额度内回退 Full | 回退是一次新调用/尝试，不免费 |
| 全文频繁截断或遗漏未改代码 | 调整交付额度或切换 Edit | 不把截断前缀冒充完整候选 |
| 必需代码仍超上下文容量 | 明确报告不可交付或走预设按需读取 | 不静默删代码或取消该方向资格 |

模式选择政策本身需要记录与消融。若只给复杂低分父代用 Agent，却给简单高分父代用 Full，不能从整体均值推断后端优劣。

## 6. 失败分类与有界恢复

### 6.1 分层错误表

| 事件 | 含义 | 处理与边界 |
|---|---|---|
| Idea 缺失 | 可选元数据未提供 | 唯一完整代码明确时继续，Idea 为空 |
| 多个冲突代码块 | 不能确定唯一交付候选 | 报歧义；不按首块/末块或最好分挑选 |
| 已知截断/生成未完成 | 响应未声明完整交付 | 保存原文，按额度重建请求、换形式或受控续写 |
| 补丁零匹配/多匹配 | 定位与当前基底不一致 | 给准确原文、匹配数与版本，不模糊应用 |
| 语法/接口错误 | 不能成为合法任务程序 | 以失败代码和具体诊断做有限 Repair |
| 运行异常/约束失败 | 特定条件下执行不合法 | 记录相关栈、实例/种子及资源条件，再决定恢复 |
| 有效但退步 | 正常搜索结果 | 保存事实，按主干/试用政策决定机会，不自动修到涨分 |
| 重复/no-op | 没有新程序或实质改变 | 生成成本照记，评价可按缓存政策处理 |
| 429、断连、服务故障 | 基础设施层未完成可靠操作 | 单独重试策略，计调用/时间，不伪造低 fitness |
| 完成状态未知 | 后端未提供充分状态 | 单独标记并按冻结策略处理，不伪装成确认完成 |

可解析不等于完整。截断的代码前缀可能恰好构成合法函数，仍缺失原计划后半段；已知截断时不能只截取能编译部分当作完整候选。相反，没有代码围栏不必意味着截断：若后端正常结束、存在唯一完整 Python 载荷，可按预定宽容提取规则接受。

“完整”也不能被解析器绝对证明，它仍需输出协议、结束元数据、依赖和任务验证共同支持。不要把结束状态正常当作语义正确保证。

### 6.2 Repair 必须看到失败候选

Repair 至少获得真实有效基底、待修复尝试 ID、失败源码、错误阶段、足够定位的栈或违例、最小复现条件，以及仍在检验的结构假设。

只给正确原父代和一句 `NameError`，可能缺失出错的新实现。原始日志保存到事实层，prompt 只选相关代码和诊断；几千行无筛选日志既占预算也掩盖问题。

一次错误约束的是相应实现与执行条件，不自动否定整个思想。修复成功只是恢复可行性，不自动等于超过来源质量或完成票级净进展。

### 6.3 内容恢复共用一个额度

首轮可设最多一次内容恢复，由格式修复、补丁回退和代码 Repair 共享。复杂任务可另设更高上限，但必须预先固定并消融。

不能让“格式三次×补丁三次×运行再三次”各自独立循环，最后外层仍只报一个 generation。上限实际怎样组合取决于控制流，日志须直接记录每次调用而非推算。

基础设施重试与内容恢复分开命名，但都服从外层总调用、费用与时间上限。新模型生成消耗调用预算，新候选载荷或编辑事务进入 AttemptRecord；缺失 Idea 不触发恢复。

修复若超出已预留候选或成本额度，应停止，不能以内层“还没成功”为由自动延长外层票。

### 6.4 续写是显式后端能力，不是普通拼接

附件转述 Aider 的长输出续写依赖 assistant prefill、额外请求和接缝处理。即使某些后端支持，也不能默认所有模型可用普通“继续”无缝拼成代码。

启用续写须验证模型支持、固定拼接协议和最多续写次数，保存各片段及最终载荷，累计全部调用与费用，并对整体重新重建与检查。续写可以是同一次候选提交的多个传输片段，但其模型调用不是一笔；期间形成并测试的新版本则必须另记候选。协议必须声明这种计数，避免多调用藏在一个候选数中。

不能用续写后的正常结束覆盖早先截断事实，也不能凭“接起来能编译”认定与原始意图一致。

## 7. 上下文与输出预算

### 7.1 先给交付预留空间

建议按实际 tokenizer、chat template、工具定义和响应语义核算：

$$
T_{\mathrm{task}}+T_{\mathrm{code}}+T_{\mathrm{evidence}}
+T_{\mathrm{tools}}+R_{\mathrm{generation}}+M\le W.
$$

$W$ 是后端总窗口，$R_{\mathrm{generation}}$ 按实际接口预留可见代码输出及适用的推理空间，$M$ 为模板包装和估计余量。还需满足后端独立输出上限，不能只有总和合法就假定一定可交付。

附件提到部分 OpenAI 推理接口可能在无可见代码时耗尽生成额度，返回 `incomplete` 且已有费用。本轮未重新核验接口版本；这里保留其工程含义：空响应需结合结束状态与 usage 诊断，不能统一当作服务未响应或免费解析失败。各服务商字段、推理计费和上限语义应由具体适配器确认，不跨后端硬套。

附件中的旧版 32,768 总窗口、8,192 输出只是特定历史配置，不是通用默认。当前仓库既有 tokenizer 路径也有显式字符估算路径，实验记录应包含计数方法与误差余量。估算值不应标成精确 token；获得真实 usage 后保留两者差异。

### 7.2 上下文不足时保留真实代码和任务契约

先删重复日志与无关历史，再降低旧事件分辨率，必要时切换编辑后端或按需读取。接口、待改代码、必要依赖和关键异常优先保留，不能为全局经验让位。

程序变长造成交付困难时，显式记录原因、模式选择与预算；不要静默取消优秀程序的父代资格。否则表面上的种群淘汰含有未经分析的格式限制。

如果有完整程序但输出空间明显不足，调大上限也是成本改变，应在对照中记录，不把成功率改善全归因于新提示。

### 7.3 多轮重建开发状态，不无限追加聊天

每轮围绕当前代码、任务契约、未解决诊断、当前假设和少量相关历史重建请求。旧日志放在事实存储，按需检索，压缩摘要保留来源和版本，不覆盖原始事件。

读取、摘要、压缩或规划若需要模型调用，计入 Episode 的成本；外置存储不代表获取信息免费。没有已证实的普适最佳窗口，更多上下文可能帮助依赖理解，也可能引入干扰或挤掉输出空间。

## 8. 代码与上下文膨胀

### 8.1 四类膨胀分别测量

| 类型 | 例子 | 不能混用的指标 |
|---|---|---|
| 表达膨胀 | 冗余注释、长说明、changelog、旧版本备份 | 注释 token 不等于求解复杂度 |
| 结构膨胀 | 重复组件、分支层数、死代码、机制只增不减 | LOC 不等于运行计算量 |
| 计算膨胀 | 更多重启、内部多候选择优、更深局部搜索 | 短程序也可能消耗很多计算 |
| 上下文膨胀 | 全历史、重复错误、越来越多 insight | 事实可永久保留，当前 prompt 仍应有限 |

Code Evolution Graphs 的任务依赖结果不支持简单的长度优化。因此不默认将目标改成：

$$
\operatorname{fitness}-\lambda\,\operatorname{code\ length}.
$$

若任务确实包含代码长度或资源目标，应单独定义多目标取舍及验证，不在输出协议里悄悄加入。

### 8.2 表达压缩与语义简化分开

保留非显然单位、边界、不变量和必要假设的注释，减少逐行复述、未经验证的性能自评、长篇分析和历史代码备份。说明可作为外部元数据保存，不必塞进每份可执行源码。

Refine 明确允许删除、替换和规约。新机制替代旧机制后，不要求为“保留成果”永久保留失效路径；成果由历史档案保存。

但删功能、合并组件、改控制流或删除可能被读取的文档字符串，都属于需要重新评价的程序变化。简化提示在部分实验有价值，不能当作无需执行检验的优化器。

### 8.3 原始响应、执行源码与展示视图分离

| 对象 | 保存什么 | 不允许的替代 |
|---|---|---|
| `RawResponse` | 原始模型响应、片段、结束状态、使用量 | 只保留清洗后的代码，丢失交付事实 |
| `EvaluatedSource` | 实际送入正式评价的完整源码或多文件快照 | 用后续美化、重构或注释删除版本代替已评源码 |
| `ContextView` | 供下一次模型读取的筛选/压缩展示 | 当作已执行源码或精确 patch 基底 |

附件提及旧 V9.4 曾在评价前经 AST 规范化删除注释和 docstring，本轮没有核验该旧文档。这个做法不能推广为任意 Python 程序的语义保持操作：`__doc__` 可以被读取，编码声明影响源码读取，框架可能用注释标记可演化区域，其他工具也可能消费源码注解。

当前 AST 重建、模板拼接或其他宿主变换如果是任务协议的一部分，必须版本化并保存其**变换后的实际执行源码**；不能给原始响应直接贴上变换程序的分数而不记录映射。也不需要由此假设所有空白规范化都有害，关键是边界明确、过程可复现。

ContextView 可压缩非编辑历史，但提供精确 SEARCH 的待改区域必须是实际基底原文。去注释展示后生成的 SEARCH 可能无法匹配真正代码，因此“省上下文”和“精确定位”有直接冲突，需要按用途分视图。

### 8.4 同分择简与计算公平

确定性、相同评价条件下完全同分，可按预先定义的复杂度指标择简；这仍只是在相应评价域上同分，不等于全输入语义等价。

随机评价中，“没有显著差异”不等于性能等价。应预先给出可接受性能差和资源约束，通过配对重复评价判断简化是否不劣，报告效应和区间。

若一个程序靠十倍重启得到更好质量，需要在相同求解资源上限下比较；否则测到的可能是额外计算，而不是更好的算法机制。搜索外层模型预算与候选内部求解预算也必须分别记录。

## 9. 与事实图、开发票和评价器的共同协议

### 9.1 完整链条

```text
行为前沿保留方向
→ 预算层选择真实锚点与用途、预留额度
→ 算子规定修改范围，证据包提供依据
→ 选择 Full / Edit / Agent 后端
→ 检查完整性、重建快照、注册尝试
→ 独立检查/评价、有限恢复
→ 实际程序、全部尝试、费用和来源写回事实图
```

每个后端交付都绑定真实锚点，修复绑定失败尝试；不同表现形式不能产生一套独立于外层的免费搜索。

### 9.2 四类记录与预算账户

| 对象 | 必要记录 |
|---|---|
| 开发机会 / Episode | 来源锚点、通道/票 ID、候选/调用/token/计算/时间额度与余额 |
| LLMCall | 生成、规划、反思或工具决策的实际请求、模型、usage、费用、延迟、结束状态 |
| AttemptRecord | 每个候选载荷或原子事务，包括无效、歧义、重复和修复；失败恢复关系 |
| EvaluationRecord | 精确源码快照上的静态检查、smoke、完整评价、种子与重复运行及成本 |

一次候选可能包含多个调用，某次调用也可能只规划而没有候选；不同维度不能强行一一对应。纯基础设施无响应失败不伪造算法节点，但仍有调用日志；解析失败也保留尝试事实，不获得虚构 fitness。

多轮工具只读不一定扣候选额，但必须扣调用/费用或时间；每个被测试的新代码快照都登记。正式评价、smoke、局部诊断不能因为不是最终成绩就从成本账本消失。

三次候选票若依次为 Pivot 崩溃、Repair、Refine，已用完三次机会。不能按“只有一个有效改进”宣称还剩两次。相同快照的重复评测不新增代码候选，但消耗评价预算。

### 9.3 中间最好、工作状态与成果归属

Agent 每产生一个经过既定评价的有效快照，就保存其源码和成绩。工作锚点可按试用政策沿暂时退步的程序推进，已知最好另存；结算按预定训练侧规则返回实际评价过的快照，不以测试集选版本。

单次 episode 的发现不能重复计给主父代、修复器、donor 和所有祖先。各调用的作用可保留为关系，但全局纪录只更新一次；局部修复率与净质量增益分开。

### 9.4 评价独立性是科研有效性的一部分

正式成绩来自宿主评价器，不来自模型说“通过测试”或程序自行打印高分。模型自写测试只提供辅助诊断。

按材料建议，生成代码执行环境应保持只读评价器与数据边界、无默认凭证访问、明确资源限制；不允许修改评分规则、最终测试数据或绕过注册执行隐藏候选。本节是拟议实验协议要求，不据当前类名或包装器推定隔离已经完备。

若协议接受错误程序或额外测试未计费，就会把错误目标或更多计算误认为研究收益。这与安全边界有关，也直接影响方法比较的有效性。

## 10. 实现草案：统一结果、错误与恢复状态

本节根据提供材料补成可审计草案，不是已实现类定义，也不是未提供下载模板的原文。辅助字段由宿主补全，避免再次让复杂 JSON 成为拒收有效代码的原因。

### 10.1 模型侧最小交付与宿主记录分离

模型侧只需按照所选后端交付一份完整代码或编辑载荷，可选短注记。Episode ID、基底 hash、预算账户和后端版本由宿主可靠绑定；模型回显有助检查，但不能只信它自报的基底。

```yaml
DeliveryRecord:
  episode_id: "外层授权"
  anchor_state_id: "真实来源状态"
  base_artifact_id: "真实基底程序"
  base_source_hash: "宿主绑定"
  backend: "full | edit | agent"
  backend_protocol_version: "重建/工具适配规则"
  llm_call_ids: []
  raw_response_refs: []
  completion:
    normalized_state: "complete | incomplete | unknown | infrastructure_error"
    provider_status: "原始状态另存"
    usage: {}
  candidate_payload_ref: "候选代码或事务；无载荷时为空"
  optional_change_note: null
  reconstruction:
    status: "not_attempted | success | failed"
    edit_base_hash: null
    applied_blocks: []
    failed_block: null
    evaluated_source_ref: null
    source_hash: null
  validation_record_ids: []
  error:
    stage: null
    category: null
    diagnostics_ref: null
  recovery:
    parent_attempt_id: null
    content_recoveries_used: 0
    content_recovery_limit: 1
  cost_account_ref: "真实累计支出及预留"
```

`evaluated_source_ref` 表示实际评价版本，重建但尚未评价的快照应另存候选引用并标明状态，不提前赋予成绩。模型输出说明可以用于检索，不用于填正式验证字段。

### 10.2 完成与载荷检查草案

```text
读取原始状态、usage 与完整响应，先记录调用事实
若是基础设施异常：按独立重试规则及总上限处理
若是已知 incomplete：保留片段，不把可编译前缀当完整候选
否则按固定协议识别候选载荷：
    唯一完整 Full 载荷 → 重建候选
    唯一 Edit 事务 → 验证基底并在临时副本应用
    相互冲突的多个候选 → 歧义失败
    没有载荷 → 无载荷失败
    可选 Idea 缺失 → 不构成失败
重建成功后保存源码快照，做静态与接口检查
检查通过再进入固定执行/评价流程
出错时记录阶段与诊断，检查共享恢复余额和外层总余额
能恢复则创建关联的新调用/尝试；不能则终止本步
```

允许在预定义格式中组合一个候选的多个依赖块，但必须能确定唯一重建结果；不能把任意多个候选都运行后选最好，却仍只登记一次提案。去除明确的思考标记、围栏等外壳不应演化成猜测算法语义的静默改写。

### 10.3 Edit 应用与提交草案

```text
确认被授权基底 hash 与实际文件快照一致
复制到暂存区，载入允许编辑范围
按声明顺序处理每个 edit：
    检查路径/区域合法
    检查 search 按当前临时状态唯一匹配
    应用 replacement，记录局部差异
任一定位失败：丢弃整组暂存修改，保留失败事务记录
全部重建成功：形成不可变候选快照并注册
验证该完整快照；无论成功失败都保留真实结果
只有符合活动档案规则时才更新工作/精英状态
```

不得把“基底未改变”与“失败尝试不计费”混淆。重建失败可能不产生有效 artifact，但原响应、事务和费用仍存在。

### 10.4 恢复请求最小内容

```text
真实有效基底及版本
待修复尝试 ID 与失败候选完整代码/相关事务
失败阶段、准确错误、足够定位的栈或匹配计数
复现输入/种子/资源约束
需要保留的修改意图与硬接口
剩余内容恢复、候选、调用和费用额度
本次只交一份修复候选；不报告未运行的成绩
```

错误反馈保留相关原文，不把省略栈或行号后的摘要当作唯一诊断。格式回退与代码修复共用额度，不能从 Repair 再进入另一套无限补丁重试。

## 11. 实现顺序与验证路线

### 11.1 分阶段推进

第一阶段建立 Full 内核：可选短注记、唯一完整载荷、完成状态、原响应与执行源码分离、分层错误、共享恢复额度、调用与评价账本。当前已存在的部分保留，缺失处先用日志核查实际影响，不将文档缺口等同于性能缺陷。

第二阶段添加结构 Edit，保持父代、算子和证据政策不变，检验省掉的复制输出是否被定位失败、依赖遗漏和恢复成本抵消。第三阶段才在确需环境读取或多文件协调的任务上开放有限 Agent。

不把三个阶段一次性上线再只比较最终 best，也不假定 Agent 是高级模式就应成为默认。

### 11.2 五组核心对照

| 维度 | 对照 | 主要问题 |
|---|---|---|
| 说明位置 | code-only、短 Idea＋Code、两阶段 plan→code、事后描述 | 说明是否有增量，额外调用是否值得？ |
| 代码表示 | 全文、完整函数/结构替换、SEARCH/REPLACE、原生工具 | 输出节省是否抵消恢复和遗漏？ |
| 反馈轮次 | 单次、单次＋一次恢复、有界 Agent | 收益来自反馈还是更多采样？ |
| 上下文 | 必需材料、相关历史、等长无关、不同长度 | 内容与长度分别如何作用？ |
| 膨胀控制 | 不控制、限制冗述、允许删除替换、独立简化 | 表达压缩与算法简化是否不同？ |

至少覆盖短函数、较长单文件、多文件三类任务，并分模型报告编辑能力。多文件若尚无成熟任务评价接口，应先建立可比任务，不把单函数结论直接外推。

固定父代/锚点、语义动作、基本证据、输出预算政策和评价条件。若比较交互次数，增加相同调用/费用的独立采样对照；否则 Agent 可能只是花更多钱。工具训练能力不同是边界条件，需记录原生工具与自定义文本协议的差异。

### 11.3 主要终点、诊断与成本

主终点是固定真实成本下按预定训练侧规则选出的算法在独立测试上的表现，辅以训练 best-so-far 曲线、多次独立运行稳定性。最终测试不能反馈到协议选型、模式路由、修复或简化决策。

诊断包括：完整响应率、合法代码误拒收率、歧义率、补丁定位/重建率、接口与运行有效率、恢复成功率、重复/no-op、有效新程序成本和有效净改进成本。不同率明确分母，不能仅统计进入评价的幸存者。

真实成本至少含模型输入/输出/适用的推理 token、计费额、调用次数、缓存使用、工具读取与诊断、smoke 和正式评价、候选内部运行资源、超时及总耗时。成本由供应方 usage 和宿主计量共同记录，缺失时标未知或估算，不填零。

与现有 E1000 比较时，应另外报告实际调用与费用，使用等评价预算及等成本两种视角；不能把解析重试和 agent 测试排除后仍声称完全匹配预算。

### 11.4 竞争解释与可证伪预测

| 主张 | 竞争解释 | 削弱主张的结果 |
|---|---|---|
| Idea 改善实现 | 额外 token 或调用数量带来收益 | 等成本 code-only 同样好，或说明与实际变化脱节 |
| 结构 Edit 更高效 | 只是对简单局部改动选择性使用 | 匹配任务与改动范围后成本优势消失 |
| Agent 的反馈有价值 | 更多采样而非反馈导致更好结果 | 相同调用/费用的独立生成达到同等结果 |
| 新协议降低方向偏差 | 失败来自复杂算法本身 | 完整交付后仍相同无效率，且格式干预不改变条件结果 |
| 简化有利 | 只是降低内部求解计算或样本噪声 | 配平资源后质量下降，或非劣结论不成立 |
| 高通过率提高终点质量 | 大量通过者只是重复父代 | 新程序和净增益率不增，终点无改善 |

在实验前固定恢复上限、候选定义、基底规则、成本口径、返回策略、重复数和停止条件。到达预算停止，基础设施异常单列，已知干预未执行时先修正流程。若模式只改善交付率而终点仍不提升，应检验其保留的候选是否有研究价值，而非继续靠加大重试维护原解释。

## 12. 当前结论

默认一次交付完整代码，允许短注记但不依赖它；长程序按自然结构编辑，复杂任务才进入局部且有额度上限的 Agent。三种后端统一绑定真实基底、原子重建、独立验证、分层恢复与完整计费。

这与前两篇形成完整研究闭环：保留有价值的方向，分配实际机会，提出有证据的修改，再可靠地将修改落实为可验证且可继续开发的程序。必要推理与反馈应服务于这一目标，不能让格式要求、无界恢复、上下文堆积或隐性计算代替算法收益。
