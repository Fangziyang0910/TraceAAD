# 反馈与实现协议

[相关工作目录](README.md) · [方法总览](AAD代表方法与机制.md)

交付协议规定模型输出什么，以及怎样解析和执行这些输出。失败反馈与处理规则决定候选失败后是否修复、重试或停止。这些环节共同影响候选的有效率和每次尝试的资源消耗。具体方法见[程序交付综述](LLM-AAD中的输出模式与生成执行协议调研.md)。

## 算法设计范围与代码交付形式

任务接口限定允许修改的计算范围。`EoH` 与 `MEoH` 将生成函数嵌回模板，`FunSearch` 开放固定骨架中的函数槽位，因此即使输出完整 Python 程序，模型也可能只被允许设计其中的局部计算。

完整代码便于表达结构变化，精确编辑便于保留宿主代码并减少无关重写。`AlphaEvolve` 支持 `SEARCH/REPLACE` 和完整代码，以不同形式交付允许范围内的修改。

额外字段保存设计意图，也增加解析约束。解析成功率描述能否提取程序，合法程序接受率描述提取后能否接收，算法质量描述评价结果。这三个指标需要区分。

## 设计说明与搜索经验的保存

自然语言说明为搜索保存意图和经验。Idea 描述候选设计，`ReEvo` 的反思提炼质量差异，`MCTS-AHD` 的摘要保存程序信息；代码与执行反馈提供对应的实现和行为依据。

说明的用途影响其生成方式与成本。`MCTS-AHD` 通过额外摘要调用保存经验，`AlphaEvolve` 的编辑协议表达代码修改。短说明节省上下文，长说明可以保留具体计算，也可能重复背景，选择说明长度时，需要权衡信息是否完整与资源消耗。

## 失败类型与反馈用途

失败发生的环节决定反馈内容。格式与运行错误为修复提供依据，质量变化为算法修改提供反馈，重复和基础设施故障则对应不同的评价与结算策略。

| 反馈 | 反馈内容 | 后续动作 |
| --- | --- | --- |
| 解析失败 | 响应尚未形成可接收的候选 | 确定性提取与接口检查；必要时一次格式修复 |
| 运行异常、超时、非法返回 | 候选未完成任务要求 | 根据报错位置、接口条件或时限进行有界修复 |
| 有效但质量下降 | 本次算法改动在评价集上退步 | 保存父子计算差异，供继续开发或换向 |
| 重复代码 | 再次提出已知程序 | 记录重复，并按去重策略决定是否再评价 |
| 基础设施故障 | 本次评价缺少可信结果 | 修复设施并按预算规范结算 |

反思、修复与重采样分别利用不同反馈。`ReEvo` 从质量差异提炼改进意见，调试器根据错误恢复可执行性，丢弃失败候选则将预算交给其他尝试。修复成功说明程序恢复了可执行性，不能直接说明算法质量提高。两类改进都需要计入相应的生成或评价成本。

## 评价预算与生成成本

模型调用、候选生成、实际评价和有效评价，是不同的资源计数单位。未进入评价的请求仍消耗模型调用与时间，修复和重采样则可能为同一候选增加额外开销。

重复代码已经形成合法候选，其评价成本取决于去重规则；解析错误尚未形成可评价对象。分别记录这些事件，可以呈现生成成本与评价预算之间的对应关系。
