# TraceAAD 周报｜2026-W41（10月5日—10月11日）

这周我比较了几种继续开发方式，并重新整理了研究主线。现在明确的目标是利用搜索轨迹中的反馈经验改善后续决策。计算保留、真实diff和问题级开发都是可能的机制，不应提前成为整个研究的成功标准。

V10.18中，首版落后于原程序的探索在三步内超过原程序的比例为4.6%，V10.17为21.6%。但两版同时改变了上下文、开发方式、停止规则和预算分配，所以这个差异不能直接归因于原程序是否可见。代码抽查确认部分收益来自恢复成熟部件；恢复本身可以是有效决定。接下来需要比较它的收益和其他预算用途，而不是只要求保留新计算。[开发配置与案例](../03-现象与检验/2026-10-06-新设计开发诊断与改动检验.md)

V10.24完成18路、每路1000候选的搜索，TSP和CVRP偏弱，FSSP与JSSP改善，没有显示跨任务稳定优势。这使我撤回“统一开发过程自然带来更好资源判断”的预设。V10.25两套批次也已停止；原V10.17保留为工作底座，但尚未被确定为最优机制或最终论文版本。[完整结果与成本](../03-现象与检验/2026-10-10-V10.24完整搜索与开发成本.md)

我核对了七种基线的官方执行路径，发现辅助函数、消息角色、逐实例反馈和反思材料的适配错误，并完成修复。新实验共同条件已集中到实验规范；历史成绩仍绑定启动源码和原协议，不能用修复后的实现替旧批次背书。旧本地模型数据已封存，DeepSeek实验的执行状态按批次查询。[基线核对](../03-现象与检验/2026-10-11-七种基线官方实现忠实性审查.md)

10月11日，我按26项审查重构了默认入口、方法说明、结果解释和汇报材料。我复算父代历史对照，纠正了OP均值、CVRP方向及OBP测试设置汇总；也把19/45→2/45放回撤回指令对照。回查原始请求发现V10.15-6的目标句与Analysis使用不同参照，因此暂不把11.2%→2.6%的历史读数归因于单条目标句。旧诊断中的局部观察继续保留，普遍排序、通用禁令和单因素归因退回对应实验范围。同一结果被周报和汇报反复引用，不算新增证据。 随后的内容复查发现方法页和讲稿仍有归因遗漏，我补修了正文，并纠正详细过程中的五处章节链接。[重构与核验记录](../03-现象与检验/2026-10-11-研究主线与文档重构.md)

随后我按轨迹视角重新检查了研究入口。上一轮修正了数值和归因，但讨论仍容易落到父代形成链与单次改写。核对V10.17实现后，我区分了记录与使用：系统保存尝试、来源、失败修复和探索过程，生成只读取部分历史，选择主要使用质量与直接尝试计数，续写采用固定抽签和步数。记录比实际利用的内容丰富，这是待研究的空间，不是已证明的性能问题。

我将早期路线竞争、延迟收益、阶段开发与Continue/Branch重新接回当前问题，并增加跨版本用途、重点检验和相关工作的横向索引。它们共同帮助回答搜索如何利用自己走过的路；具体版本与复杂度不代表认识进步。[轨迹记录与使用](../01-搜索方法/搜索轨迹的记录与使用.md)

下一步先从完整搜索中确定最影响判断的现象：机会为什么持续集中在某些程序，停滞与失败怎样改变后续选择，哪些经历能影响其他路线。再根据问题选择局部对照、多步窗口或完整搜索。固定父代是可选检验，不再提前规定为下一步；本轮没有新增机制或实验。 随后我把调整扩展到各篇方法、结果、诊断、构想与相关工作，分别说明轨迹范围和决策用途，并修正正文里的局部视角偏差；历史规则、表格数值和原始材料保留。

收尾审阅发现，逐篇轨迹说明覆盖了部分历史身份，而且重复提示过多。我恢复版本与适用时点，将开头收敛为各篇独有的定位；中央索引保留完整说明。文档整理到此停止，下一项研究工作是从一条完整搜索的关键决策时刻重读已发生的事件和系统实际使用的信息。

我进一步核对了相关方法的搜索预算和模型消耗。1000次不是统一标准：ReEvo官方默认配置为100次函数评价，MCTS-AHD多数任务为1000次、在线装箱为2000次，PathWise主比较为500次；CALM还明确区分2000次模型查询与1000次基线评价。PathWise的500次评价成本表中，GPT-4o-mini在TSP上的输入／输出用量分别为ReEvo约81.5万／27.7万、MCTS-AHD约69.0万／22.8万、PathWise约209.4万／28.2万。这使我明确区分候选预算、评价次数与模型成本，不能只凭相同候选数判断开销相同。[PathWise预算与成本](https://arxiv.org/html/2601.20539v2)

10月11日本地同步快照中，DeepSeek关闭思考的TSP三路均已记录1000候选：FunSearch为999次请求、约299万token，EoH为1038次请求、约314万token，ReEvo为1777次请求、约660万token。EoH和ReEvo分别有38和66次请求缺少usage，以上是已记录用量，输入包含缓存部分；它们不等同于最终账单。下一步预算建议是机制探索先用100—200候选，主比较考虑500候选，再依据后半程的收益决定是否扩展至1000；同时观察成绩随累计token的变化。本轮只核对材料和成本记录，未修改现行实验协议或在跑预算。

继续按用户指出的差异拆解ReEvo成本后，我修正了“预算翻倍足以解释开销”的理解：本路1000候选的输入、输出分别为论文500评价用量的6.07倍和5.99倍，按预算单位归一后均约3倍。本路前500候选已花输入225.2万、输出77.1万，合计302.3万，为论文109.1万的2.77倍。逐条调用记录的usage之和与累计文件一致，原生reasoning记为0；999次有usage的代码生成平均输出1642token，短期／长期反思平均输出21／54token，反思回复只占输出约1%。但短期反思读取两份完整父代，累计输入217.4万；交叉生成同样读取两份父代，累计输入220.8万，两阶段合计占输入88.6%。目前最值得相信的解释是较长生成代码经父代复用同时放大输出与输入；跨模型分词和论文具体调用计数的影响还不能量化，不能把全部3倍差异归因于代码长度。下一步应优先核对相同提示下的生成代码长度与用量，而非仅缩减候选数。本轮未新增模型调用或修改基线。

我又全量检查了这路ReEvo的999份代码。注释和docstring只占代码token约9.5%，后期降至约7.5%；更大的浪费是没有评价信号的规模分支。947份代码在当前TSP50条件下可展开规模判断并删除未使用分支，可执行文本缩短42.1%。最好程序的有效主干是rank筛选加最近邻完整补全；`m<=80`已返回，后面的“大规模”特征和浅层前瞻不参与本批评价。最好程序及两个阶段样例的432次选点检查中，去掉这些部分前后结果一致。这使我把“主要是模型写得啰嗦”修正为“有参与决策的计算，也有不断被继承但得不到评价反馈的代码”。

提示复查还发现共用解析器把统一任务docstring重新放入每份父代，以及变异阶段没有像官方那样每轮追加固定前瞻先验。角色和反思字数限制已保留。保持父代不变、仅重建官方提示框架，三阶段文本量合计只减少约2%，不能解释3倍开销。下一步应检验未使用代码的继承和重复契约说明；先验遗漏另按忠实性处理。本轮没有修改基线或调用模型。[代码与实际提示复查](../03-现象与检验/2026-10-11-七种基线官方实现忠实性审查.md#9-reevo-tsp代码长度与实际提示复查)

本周详细尝试、运行过程与历史判断保留在[过程记录](2026-W41-过程记录.md)。

由于API额度不足，我中断了EoH、ReEvo、FunSearch和MCTS-AHD的当前批次，保留已产生的程序、评价和token记录，并停止后台同步。后续运行需在额度恢复后重新安排；这批数据按实际中断预算分析，不当作完成1000候选的结果。 调用记录显示，持续中断发生在10月11日日本时间19:14左右（北京时间18:14）：最后成功回复为19:14:40.995，之后已记录的重试均返回上游429。错误记录到19:34–19:37才集中落盘，是因为客户端累计约15分钟退避等待，加上实际请求耗时后才写入整组调用；错误落盘时间不能直接作为服务中断时间。服务返回的文字是rate limit，结合额度不足的报告判断此次中断，未查询账户账单。

我补充了四种基线的轨迹恢复入口。24路中，6路已用完1000候选，14路未完成搜索的EoH、ReEvo与MCTS-AHD已通过种群、反思或搜索树的离线重建；FunSearch另4路需要用CPU补齐未保存的逐实例评分向量。恢复保留已花预算与调用成本，但旧随机状态和执行栈无法补回，因此明确记录为从方法边界继续，而不是声称无缝续跑。补全过程发现部分重测超时，入口会拒绝用不完整评分向量继续；我也修复了满预算后最终训练重评误传日志参数的问题。此前两个重测超时的程序在单独重测时复现了旧分数；我把补全过程限制为每路一次程序、8个实例worker，继续在后台补齐向量。模型请求仍全部暂停，补全结束不会自动调用模型，之后再根据额度安排恢复。

进一步补全发现，FunSearch图着色与JSSP中有程序用time.time()决定执行多少搜索，同一源码重测的目标值发生变化。因为旧逐实例向量未保存，我不能用新向量冒充旧聚类状态，已明确阻止这两路续跑。FSSP也出现旧分数无法重现，具体程序使用未传seed的np.random.default_rng()；这一路同样阻止续跑，目前仅CVRP仍在CPU补全。后续FunSearch会保存每次评价的逐实例向量，避免重复失去恢复所需信息。

经讨论，我调整了FunSearch恢复条件：使用重评得到的新分数与评分向量重建数据库，保留旧程序的岛归属与已花预算，不再要求复现旧聚类。旧评价记录不覆盖，重评失败的程序不进入新数据库，最终训练候选排序使用新分数。这是重建后继续搜索，而不是精确复原。CVRP已补齐，另外三任务继续CPU重评，所有LLM请求保持暂停。

我分批恢复EoH与ReEvo的CVRP、FSSP、图着色和JSSP，共8路。EoH从653、774、432、399候选继续，ReEvo从738、796、391、414继续，总预算仍为各路1000。实际请求保持DeepSeek关闭思考、temperature=1.0、top_p=0.95与16384输出上限，token累计与原记录连续；ReEvo先恢复成对反思再生成子代。恢复入口也修正了压缩旧调用与新增调用并存时的读取，保留全部历史反馈。随后，我按要求恢复FunSearch的CVRP、FSSP、图着色和JSSP，从702、782、592、466候选继续到1000。四路数据库重评均已完成，图着色排除45个重评失败程序，JSSP排除30个；原岛归属和已有预算保留。我核验四路恢复状态均为running，并已有成功模型回复和新增候选，后台同步已恢复。 随后，我回查中断恢复困难，确认FunSearch旧档案缺少逐实例评分向量，而墙钟终止与未固定种子的随机数又使重评结果变化。我在本地改进运行和恢复入口：预算未满时退出不再误标完成，新启动与恢复共用文件锁，强制终止后不再被遗留running状态挡住；批次恢复可以直接复用原tmux会话，并跳过已冻结路次。我还修复了FunSearch在满预算后再次恢复最终选择时丢失重评分数的问题，并串行更新批次清单，避免并发覆盖。106项相关测试通过，包含实际强制终止子进程后的锁释放及已有评分向量不触发重评；未调用模型，也未向正在跑的server3批次推送改动。旧随机状态、执行栈与未记录的岛重置来源仍无法追补，四种方法继续按已记录的方法边界恢复；这一轮另外三种基线尚未接入这个恢复入口。TSP与OP已满预算，不新增请求；MCTS-AHD继续暂停。我同时修正了看板的预算口径：EoH的TSP与OP实际都已花完1000候选预算，864与944只是保存的候选记录数。看板现在读取方法实际预算，并把搜索完成但尚未完成最终重评的路次单独显示为待收尾。

随后，我把CALM、PathWise和Shinka接入同一恢复入口，并补上新实验的搜索检查点。CALM保存候选、评分向量、提示回访与数值微调记录；PathWise保存初始化进度、种群、节点与反思；Shinka保存岛副本、embedding、bandit和meta记忆。三个方法均保存随机状态，恢复不重新评价旧程序，也不重新请求旧embedding。我用连续两次中断与恢复检查预算和初始化，并比较开启／关闭检查点时的模型提示、候选和最终成绩，结果一致。另修复了CALM数值微调中断时预留预算丢失、Shinka拒绝候选尾段预算漏记，以及半行JSONL和追加压缩被中断后影响下一次读取的问题。194项相关测试通过。改动保持原有搜索规则；未完成阶段仍从保存边界继续，旧档案缺失的状态不猜测补齐。本轮未调用真实模型，未向server3推送；后续新实验部署此代码后才会产生这些检查点。
