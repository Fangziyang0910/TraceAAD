# 历史 Prompt 范式固定状态重放方案

状态（2026-09-25 核查）：本页是预设的对照方案，尚未在本目录或 `experiments/` 找到对应的 510 次生成、`prompt_audit.jsonl` 与结果汇总。以下数量、判定规则和产出均为计划，不是已观察结果；若工件保存在仓库外，应补入路径和实际完成状态。

## 目的与边界

本实验把 TraceAAD 历史版本当作 Prompt 设计素材库，比较几类明显不同的上下文组织方式在同一生成状态上的单步 proposal 质量。历史版本的最终 fitness、排名和完整搜索过程只用于确认设计曾实际出现、以及辅助选择代表性范式；不作为 Prompt 优劣证据，也不恢复已经丢失的历史 proposal 质量。

实验要识别的是同一 task、parent、trajectory、donor、operator 下，不同历史 Prompt 范式对 proposal quality 的影响：

$$
\text{same state} + \text{same operator} + \text{different prompt design}
\rightarrow \text{proposal quality}.
$$

它不估计父节点选择、预算分配、算子比例、完整搜索终局或 held-out 泛化效果。

## 代表性范式

主实验预先选取七个范式。每个范式保留历史版本的上下文边界和输出契约，只把动态字段投影到统一的固定状态；不把不同版本的调度器、repair 或模型配置带入。

| ID | 范式 | 固定状态中的上下文 | 代表历史 |
|---|---|---|---|
| P1 | `current-action` | Task Contract、Current、Operator、Output | V2–V4 |
| P2 | `current-history` | P1 加 parent formation history/evidence | V6–V7、V9.5–V9.6 |
| P3 | `structural-donor` | P2 加 structural-parent/knowledge-only 边界；Fuse 再给 donor | V5、V8 |
| P4 | `trajectory-intent` | P2 的 formation path，使用明确 Refine/Pivot 设计意图 | V9.7–V9.18 |
| P5 | `failure-frontier` | P4 加固定的 failure ledger 或 frontier summary | V9.4、V9.13 |
| P6 | `behavior-crossover` | P4 加固定 behavior/compatibility summary；Fuse 给 reference context | V9.19–V9.20 |
| P7 | `explicit-three-operator` | 标题化 Current、Trajectory、Operator、全局原则、可选 Donor、Output | V10.1–V10.2 |

P1、P2、P4、P5、P7 对三个算子都能形成独立处理臂。P3/P6 是 Fuse-only 范式，不在 Refine/Pivot 中人为补造对应处理臂；因此它们只与同一状态的 Fuse 处理比较。V1、V9.1、V9.3、V9.21 的多阶段 `plan-then-realize` 调用另设实验，不混入本次单次 Idea+Code 比较。

## 固定状态与抽样

- 任务覆盖 TSP、CVRP、OP、在线装箱 OBP、VRPTW。
- 每个任务抽取 6 个固定状态，共 30 个 block；每个 block 保存一个 parent、其最近至多 8 条 formation trajectory 和一个可用 donor。Refine/Pivot 只使用 parent 与 trajectory，Fuse 使用同一 block 的 donor。
- 状态来自已完成的 V10.1/V10.2 搜索工件。按任务、来源版本和 parent fitness 的低/中/高层分层，在层内按固定种子抽样并平衡重复。
- 抽样只读取 parent、祖先、donor 的状态字段，不读取原 Fuse 子代成败、子代 fitness、后续排名或最终最好节点作为处理条件。来源版本只描述状态分布。
- 每个 block 的 Prompt 文本、字段值、代码视图、trajectory 截断数和 donor ID 在生成前写入 `prompt_audit.jsonl`，形成可复核的处理清单。

## 配对与运行控制

每个固定状态对三个算子运行 P1、P2、P4、P5、P7，对 Fuse 另外运行 P3、P6，共 `30 × (5 × 3 + 2) = 510` 次生成。每个 block 内随机打乱适用的范式和算子组合运行顺序。

- 固定 task、parent、trajectory、donor、operator、evaluator、LLM backend 和采样参数。
- 生成模型使用 Qwen3.8-27B，temperature 1.0、top_p 0.95、top_k 20；每个 block 使用预先生成的 seed 映射。
- 所有候选先生成并逐条落盘，再由一个本地 evaluator 顺序评价；解析失败、超时和 evaluator 无效均保留原始错误，不用默认值覆盖。
- P2 `current-history` 作为主要参照，P1/P3–P7 为相对参照。主要比较在同一 block 内完成；任务和算子分层报告，不构造跨任务原始 fitness 总分。

## 响应指标

对有 parent 的 Refine/Pivot/Fuse，记录：

1. `delta_fitness = child_fitness - parent_fitness`；
2. unconditional improvement rate：候选有效且严格改善的比例；
3. invalid rate：解析失败与 evaluator 无效的比例；
4. severe degradation rate：`delta_fitness <= -tau_task` 的比例，`tau_task` 在生成前写入配置并对所有范式固定。

另记录有效率、输出 token 数、代码长度和算子行为标签作为诊断量。Init 不在本实验主线中，因为它没有 parent，不能伪造 `delta_fitness`。

## 分析规则

每个 `task × operator` 以固定状态 block 为重采样单位，报告 P1–P7 相对 P2 的均值差、中位数差、配对 bootstrap 区间，以及改善率、invalid 和严重退化率差。原始 fitness 不跨任务汇总；同时给出五个任务的方向表和状态级配对散点。

“稳定影响”只作为描述性筛选标签：一个上下文或指令成分必须在同一算子下至少 4/5 个任务方向一致，且没有伴随明显 invalid 或严重退化上升；未达到条件的成分保留为任务条件化候选，不写成统一结论。若不同范式各自改善不同算子或任务，后续 Prompt 可采用算子条件化组合，并保留冲突成分的独立开关，而不是强行选出一个全局冠军。

最终选择只使用本次 replay 的 proposal-level 证据。历史最终结果可以在附录中作为弱背景，不进入处理效应表或排序。

## 产出与工件规范

- `prompt_audit.jsonl`：每个 block 的完整状态和渲染 Prompt；
- `generations/`：逐条原始模型响应记录；
- `results/results.jsonl`：解析结果、评价得分与主指标；
- `analysis/summary.json`：按任务、算子和范式的配对统计汇总。
