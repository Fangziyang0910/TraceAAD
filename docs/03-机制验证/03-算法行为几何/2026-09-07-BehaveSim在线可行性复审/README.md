# BehaveSim 在线可行性复审与研究决策

## 核心判断

现有实验支持一个有限而有价值的群体命题：在 TSP、OBP、VRPTW 的 TraceAAD archive 中，行为相近的算法，其 fitness 在统计上往往也更接近。这个关系是单向的：

$$
\mathbb E\!\left[|f(A)-f(B)|\mid (A,B)\text{ 为行为近邻}\right]
<
\mathbb E\!\left[|f(A)-f(B)|\mid (A,B)\text{ 为随机配对}\right],
$$

但

$$
|f(A)-f(B)|\text{ 较小}\;\not\Rightarrow\;d_B(A,B)\text{ 较小}.
$$

两个得分相近的算法可以位于完全不同的高质量行为区域。fitness 只能说明“谁已经达到较好质量”，不能替代行为距离，也不能据此把算法归入同一行为区域。

这项信息价值不等于在线可行性。历史实现已经做过评价内轨迹采集、轨迹缓存和距离增量更新；即便如此，完整 BehaveSim 仍缺乏跨任务稳定的低成本保证。因此本轮作出如下研究决策：

> **完整 BehaveSim 保留为条件性的离线群体分析工具，不作为通用 TraceAAD 在线闭环的必要组件。**

TraceAAD 的核心机制继续只依赖所有任务原本就能提供的形成历史、代码、评价结果和真实搜索事件。将来若重新尝试在线行为观测，先验证它能否在明确成本上限内稳定提供信息，再讨论控制收益。

## 1. 复审范围与证据边界

本页复审三类材料：

1. V9.19 旧版 `behavesim_v3_combined_panel` 的设计、运行工件和中断分析；
2. V9.19 后期及 V9.20 的 `behavesim_v4_train_trajectory`、`tracked_eval.py`、距离缓存与 checkpoint 实现；
3. V9.21 明确停用在线 BehaveSim 的设计，以及 9 月 7 日完成的测量校准和全 Archive 群体验证。

历史实现已从当前分支删除，代码事实按提交 `517d6cc6`（V9.19/V9.20）和 `bbf4b61d`（V9.21）复核。运行成本来自旧版中断批次工件的累计墙钟记录。对于 13 路人工中断，现有工件没有足够的逐函数计时，不能断言每一路都由同一个瓶颈直接导致。

## 2. V9.19 前后两套实现不能混为一谈

### 2.1 初版：正式评价后独立运行行为探针

初版 V9.19 使用 `behavesim_v3_combined_panel`。候选完成正式训练评价后，再在固定行为 panel 上运行一次，以取得 PSTraj 并计算行为距离。行为信息确实进入了在线控制：

- `Q + L + U + R_traj` 共同改变父节点分配；
- 行为邻域的开发次数参与区域机会估计；
- 局部失败信号调整 Explore 概率；
- Crossover 在质量与行为距离共同筛选的参考节点中取样。

因此它不是只生成离线可视化的旁路分析。旧版三次运行累计记录为：

| 任务 | profiling 墙钟 | 每个画像节点 |
| --- | ---: | ---: |
| TSP | 1.84 h | 3.60 s |
| CVRP | 13.64 h | 31.71 s |
| OP | 5.27 h | 6.91 s |
| Online BPP | 0.18 h | 0.26 s |
| VRPTW | 0.32 h | 0.46 s |

这些数字只表示 v3 固定 panel 的额外画像成本，不能外推为后续所有 BehaveSim 实现的统一耗时。

### 2.2 后期：在正式训练评价内同步记录轨迹

后期 V9.19 改为 `behavesim_v4_train_trajectory`。五个 tracked evaluator 逐位复刻正式 evaluator 的实例、随机数消耗顺序和 fitness 聚合，同一次训练执行同时返回 fitness 与轨迹：

| 任务 | 同步记录的行为状态 |
| --- | --- |
| TSP | 逐步增长的构造路线 |
| VRPTW | 带 depot 分隔的逐步构造路线 |
| OBP | 每个 item 最终选择的 bin 前缀 |
| OP-ACO | 每轮结束后的历史最优路线 |
| CVRP-ACO | 每轮结束后的历史最优路线 |

这一改动已经消除了“为获得行为再执行一次候选”的额外求解，也使质量与行为来自同一训练实例。V9.20 继续用这些轨迹做行为覆盖和参考检索。

缓存也已经存在。每个有效非重复节点永久保存轨迹；加入新节点 $c$ 时，只计算它到既有节点的距离 $d_B(c,x)$，旧节点之间的距离不重算。checkpoint 保存轨迹、距离矩阵和协议元数据。

因此，后续不能再把“评价时顺便记录行为”或“缓存旧距离”当作尚未尝试的简单修复。它们已经实现并通过了 tracked evaluator 与正式 evaluator 的逐位一致性测试。

### 2.3 V9.21：完整退出在线控制

V9.21 在线只使用标准任务 evaluator，不生成 PSTraj、不计算 BehaveSim、不维护行为距离矩阵，也不额外执行 probe。其设计明确将 BehaveSim 限定为预先匹配的离线过程画像，避免改变 OBP 等任务相对标准 evaluator 的成本口径。

这不是因为行为几何被证明没有信息，而是因为在线方法的核心贡献、成本和跨任务适用性需要重新收敛。

## 3. 记录轨迹与比较轨迹是两项不同成本

评价内采集解决的是：

$$
\text{是否需要为同一候选额外运行一次求解器}.
$$

它没有解决：

$$
\text{如何将新候选的复杂轨迹与不断增长的 archive 逐一比较}.
$$

设有效 archive 最终包含 $M$ 个节点。即使每对距离永远只算一次，完整距离图仍有

$$
\binom{M}{2}=\frac{M(M-1)}2
$$

个算法对。缓存把重复计算降为一次，并没有把成对比较从二次规模变成常数规模。

历史实现还存在若干可优化开销：新节点比较前重新打包旧轨迹、插入时复制完整距离矩阵、区域统计时反复扫描和排序距离。它们值得优化，但与距离内核本身的计算量是两个层次。

## 4. OBP：十二个保存点仍对应最长 5000 的状态

OBP 训练配置包含四个任务实例：1000 items 与 5000 items 各一个 item stream，并分别在 capacity 100、500 下执行。每条轨迹只保留 12 个时间点，但每个状态是截至该时刻的完整 bin 选择前缀。最后一个状态的长度仍为 1000 或 5000。

V9.19 的前缀优化先为两个最终决策序列建立完整 Levenshtein 动态规划表，再从表中读取各前缀对的局部距离并执行 DTW。它避免了对 $12\times12$ 个状态对分别重算编辑距离，却仍需处理完整最终序列：

| 单个算法对中的实例 | 编辑距离表规模（近似） |
| --- | ---: |
| 1000 items，capacity 100 | $10^6$ cells |
| 1000 items，capacity 500 | $10^6$ cells |
| 5000 items，capacity 100 | $25\times10^6$ cells |
| 5000 items，capacity 500 | $25\times10^6$ cells |
| 合计 | 约 $52\times10^6$ cells |

单个 $5001\times5001$ 的 `int32` 表约占 100 MB 十进制内存；四张表顺序建立时，峰值由最大表决定，累计计算量则约为 5200 万 cells/算法对。若 archive 有 1000 个唯一算法，算法对为 499,500 个，对应约 $2.60\times10^{13}$ 个动态规划单元。这个量级是根据冻结代码和任务配置推导的复杂度，不是逐函数实测墙钟。

因此，“只保留 12 个状态”不能解释为“只比较 12 个数”。当前精确、scale-matched 的 OBP BehaveSim 即使没有额外 evaluator 执行，也可能压过搜索本身的辅助计算预算。

## 5. ACO：稳定证据可能需要额外求解成本

OP/CVRP 的主要障碍不同于 OBP。评价内采集可以保存正式评价使用的单条随机流，但单条流未必稳定代表算法行为。最新校准表明：

- OP 在每实例四个 common random streams 后，panel 和 seed-half 稳定性明显改善，但仍有一个 panel Spearman 为 0.776，略低于 0.80 门槛；
- CVRP 在四流后仍有 0.490 / 0.441 / 0.790 的 panel Spearman，并反复出现群体关系失败。

若在线几何要求四个或更多随机流，而正式 evaluator 原本只执行一条流，那么其余流仍是额外求解成本。增加 seed 也不保证最终稳定；CVRP 的问题可能来自 incumbent-route PSTraj 表示不足或 route edit distance 与 ACO 群体过程不匹配。

这说明两个任务可以因不同原因难以在线使用：OBP 的稳定表示需要比较长状态，CVRP 的稳定表示本身尚未建立。

## 6. 历史工程缺陷与固有规模必须分开归因

旧 v3 确实发生过工程故障：

- OBP 候选产生非有限 priority 时，正式 evaluator 的 `argmax` 可以继续，而 profiler 拒绝；
- VRPTW 候选在不同 probe 实例上出现无效决策；
- 最初异常会终止整路运行，后来改为记 `profiling_failed`、消耗该 slot 并继续搜索。

后期也仍有可优化的数据维护开销。这些事实说明旧方案并非已经达到工程效率上限。

但不能据此把全部成本归为一个 bug。初版 15 路中只有 2 路完成、13 路被人工中断；现有日志不足以把所有终止都归因于某个函数。可以确认的只有两点：v3 的额外画像有显著墙钟成本；v4 虽消除了额外画像执行，精确长轨迹比较和随机行为稳定化仍存在真实规模问题。

## 7. 对“通用 AAD”的影响

任务适配器本身不破坏通用性。AAD 原本就需要任务接口与 evaluator。问题在于 BehaveSim 额外要求每个任务回答：

1. 什么是有意义的中间解；
2. 两个中间解如何比较；
3. 保留多少过程信息才能兼顾失真与成本；
4. 随机算法需要多少实例和随机流才能稳定。

当前能力应分成三层：

| 层次 | 当前判断 |
| --- | --- |
| 不同任务共用同一搜索控制逻辑 | 可以做到 |
| 不同任务获得某种行为观测 | 需要逐任务设计与审计 |
| 不同任务都能低成本、稳定地获得可用行为几何 | 尚无保证，现有五任务结果不支持 |

群体统计也不会自然消除测量成本。如果群体坐标仍依赖长执行轨迹、多随机流和大量成对距离，那么“只做宏观统计”依然可能很贵。

## 8. 对当前 TraceAAD 路线的调整

### 8.1 核心在线机制

TraceAAD 在线闭环继续使用跨任务天然存在的信息：

- 算法形成历史与父子关系；
- 代码、Idea 和真实错误；
- evaluator fitness 与可选的原生实例级结果；
- Refine、Pivot、Fuse 的真实生成和评价事件；
- 预算、选择次数、有效率和 best-so-far 进展。

这些信息足以继续研究“给谁机会、采用什么动作、给模型看什么”。完整 BehaveSim 不再是后续控制器或论文主张成立的前置条件。

### 8.2 条件性离线分析

BehaveSim 继续用于已经校准且成本可接受的离线样本：

- 判断相近 fitness 是否来自一个还是多个行为区域；
- 区分代码树分叉与实际行为重复；
- 描述 Refine、Pivot、Fuse 造成的群体扩散、收缩与跨区移动；
- 为论文中的机制解释提供第二视角。

离线 archive-wide 实验支持的是代表性抽样上的群体结构，不要求为每一个在线节点维护完整精确距离图。

### 8.3 在线重新进入的证据门槛

若以后研究轻量在线行为传感器，应先预注册并同时满足：

1. **成本上限**：相对标准 evaluator 报告额外 CPU/GPU 墙钟、峰值内存、存储和延迟，并给出可接受比例；
2. **测量稳定性**：跨 probe、实例规模与随机流的距离排序达到冻结门槛；
3. **信息保真**：代表数限制、低频测量、状态压缩或近似距离与完整离线几何有足够一致性；
4. **增量信息**：在 fitness、时间和形成状态之外，传感器确实回答一个在线决策问题；
5. **等成本效用**：包含全部画像开销后，同总资源对照仍改善终局搜索结果。

限定 archive 代表数、降低观测频率、压缩状态和采用近似距离都可以作为新研究对象。它们可能改变 BehaveSim 的观测含义，必须通过完整几何对照验证，不能假设为无损优化。

## 9. 本轮保留的研究认识

这次复审没有推翻群体几何实验，而是补上了它的使用条件：

$$
\boxed{
\text{群体行为几何有统计信息}
\centernot\Rightarrow
\text{在线维护该几何具有合理成本}
}
$$

当前最稳健的结论是：**fitness 告诉我们算法已经有多好；BehaveSim 在适配良好的任务上告诉我们这些算法分布在哪里；形成历史告诉 TraceAAD 下一次生成从何而来。** 三者回答不同问题。行为几何可用于离线解释，形成历史与评价事件继续承担通用在线控制的基础。
