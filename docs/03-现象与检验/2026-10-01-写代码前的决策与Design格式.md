# 写代码前的决策：Analysis 与 Design 格式实验

2026-09-30 至 10-01。**在本组单步实验中，关闭 thinking 后，写代码前的针对性分析比算法说明的长度更影响生成质量。**收益主要出现在修改给定算法的算子（Refine、Crossover）上；Explore 在本组指标下没有显示相同收益。留给后续算子读取的算法说明（Design）写一两句话即可，长度对效果没有可测影响。Explore 的结构发现需要另用适合的指标检验，见本文的指标与比较条件。

---

## 1. 问题是怎样暴露的

| 版本 | 说明格式 | 暴露的问题 |
|---|---|---|
| V10.15 首批、V10.15-2 | 一句话 Idea，描述"这次改了什么"，写在代码前 | Refine 常把使分数变差的一步原样撤回，生成与祖父节点相同的程序（V10.15-2 前 25% 预算中 307 次）。原因是提示中的 "correct or undo a recent change that made it worse"，已由同父代配对对照确认（撤回 19/45 → 2/45）。 |
| V10.15-3 | 要求 150–250 词的 Idea，描述完整算法，写在代码前 | Idea 成了草稿本：43% 含 "Actually/Wait/Let's" 等自我修正，73% 超过 250 词（最长 1,696 词），79% 含 LaTeX 推导，保留被放弃的方案，与代码不一致。 |
| V10.15-4 | 100–200 词的简洁 Design，只写最终设计，写在代码前 | 说明变干净了，但重复率明显回升（见 §3）。 |

这引出两个问题：说明写多长、多详细会影响效果吗？写在代码前还是后会影响效果吗？

## 2. 假设与竞争解释

- **H1（信息）**：说明作为后续算子读到的信息起作用，越详细越有帮助。
- **H2（规划）**：说明写在代码前，相当于模型写代码前的思维链，起作用的是"先想"。
- **H3（决策）**：起作用的不是思考量，而是针对当前任务作出一个明确的决策（改什么、往哪里改）。
- **H0**：格式对结果没有实质影响，观察到的差异来自噪声或其他协议差异。

H1 预测说明长度影响后续算子；H2 预测思考越多越好；H3 预测简短而有针对性的分析优于冗长或泛泛的思考，且效果依赖算子的决策性质。

## 3. 证据

所有实验都采用**配对设计**：同一个父代上下文在各种格式下各生成一次，其余提示完全相同；按训练评价器评分（为比较格式，超时放宽为 120 s）。主要指标：撤回/重复（生成已评价过的程序）、有效率、是否超过父代、组内名次（同一上下文内按得分排序，失败并列最后），并按上下文 bootstrap 给出 95% 置信区间。

### 3.1 实验一：说明的长度与位置（DeepSeek v4.1 flash，thinking 关闭）

**Refine，90 个上下文（TSP、OBP、VRPTW 各 30）× 7 种格式**：位置 {代码前, 代码后} × 长度 {短 ≈34 词, 中 ≈128 词, 长 ≈256 词}，外加只写代码。

| | 代码前 | 代码后 |
|---|---|---|
| 撤回/重复 | 12–23% | 28–39%（OBP 约一半） |
| 有效率 | 77–83% | 61–72% |

- 位置：配对胜率（代码前 vs 代码后）54% [49%, 59%]，超过父代的比例差 +2% [-5%, +10%]。**质量相近，但代码前明显减少重复。**
- 长度：短/中/长两两胜率 46–48%，差异均不显著；输出 token 462/596/786。
- 只写代码的单次改进率最高（38%）；任一种说明相对只写代码的改进率差为 -7% [-11%, -3%]。**说明本身并不让这一次的代码更好。**

**Explore，50 个上下文 × 3 种参考卡长度**（同一批参考程序分别描述为 ≈31/149/327 词）：三者组内名次 1.95/1.98/2.07，两两胜率 44–49%，无差异。**本实验未支持 H1：说明长度对后续算子没有可测影响。**

### 3.2 自然对照：V10.15-3 与 V10.15-4（Qwen）

两批的代码、提示、种子与后端分配完全相同，只有说明格式不同。按同一 run 的前 681 次尝试：

| | V10.15-3（代码前 ≈316 词、带推敲） | V10.15-4（≈170 词简洁 Design） |
|---|---|---|
| 有效率 | 93.1% | 84.6% |
| 重复率 | 3.2%（22 次） | 10.9%（74 次） |
| 子代超过父代 | 36.7% | 37.5% |
| 输出 token 中位数 | 816 | 600 |

草稿式推敲虽然不整洁，却把重复率压低了约三分之二。**支持 H2/H3：代码前的思考本身有功能。** 这与 DeepSeek 上"长说明不减少重复"不同，说明该效应依赖模型。

### 3.3 实验二：怎样让 Qwen 先思考（Refine，60 个上下文 × 6 种格式）

| 格式 | 有效 | 撤回/重复 | 超过父代 | 输出 token | 耗时 | 组内名次 |
|---|---|---|---|---|---|---|
| 简洁 Design（≈170 词，V10.15-4） | 75% | 25% | 50% | 594 | 18 s | 3.31 |
| 长 Idea（V10.15-3） | 97% | 3% | 57% | 739 | 38 s | 2.85 |
| **几句话分析 + ≤60 词 Design** | **95%** | **5%** | **65%** | **609** | **18 s** | **2.51** |
| 不限长度分析 + ≤60 词 Design | 82% | 17% | 62% | 1,632 | 64 s | 2.97 |
| 只写代码 | 85% | 13% | 50% | 389 | 11 s | 3.48 |
| 原生 thinking + 简洁 Design | 0%（21 次均在 16,384 token 截断） | — | 0% | 16,384 | 528 s | 5.69 |

配对比较：几句话分析 vs 简洁 Design 胜率 62% [51%, 72%]，超过父代比例 +15 个百分点 [+2, +28]；vs 只写代码胜率 69% [58%, 80%]；不限长度 vs 几句话胜率 41% [31%, 52%]。**思考更多并不更好（否定 H2 的"越多越好"），简短而有针对性的分析最优（支持 H3）。** 原生 thinking 在此设置下无法收束。

### 3.4 实验三：分析多少、分析什么、Design 多长（Qwen）

**Refine，75 个上下文（各任务 25）× 8 种格式**，每种相对"几句话针对性分析 + ≤60 词 Design"只改一个因素：

| 格式 | 有效 | 撤回/重复 | 超过父代 | 输出 token | 实际分析词数 | Design 词数 |
|---|---|---|---|---|---|---|
| 只写 ≤60 词 Design | 83% | 16% | 36% | 426 | 0 | 44 |
| 一句话分析 | 88% | 11% | 41% | 512 | 52 | 40 |
| **几句话分析（针对性）** | 92% | 7% | 45% | 596 | 113 | 36 |
| 一段话分析（≤150 词） | 91% | 9% | 44% | 605 | 116 | 35 |
| 泛泛"想想怎么做" | 91% | 9% | 37% | 699 | 156 | 40 |
| 列两三个改动再选一个 | 93% | 5% | 51% | 628 | 135 | 39 |
| 几句话分析 + ≤25 词 Design | 88% | 9% | 41% | 590 | 104 | 16 |
| 几句话分析 + 100–150 词 Design | 92% | 5% | 43% | 786 | 136 | 145 |

- 有分析时重复 5–11%，无分析 16%；超过父代 41–51% 对 36%。
- 分析量：一句话略差；要求"一段话"时模型实际也只写约 116 词，与"几句话"相同，自然落点约 110 词。
- 分析内容：泛泛的思考改进率最低且更贵；"列方案再选"数值最好，但与针对性分析的配对差 +5% [-5%, +16%] 不显著。
- Design 长度（16/36/145 词）对质量没有可测影响，长 Design 多约 190 token。
- 这一轮各格式间的差异多在置信区间内；超出"要不要分析"之外的细节影响都较小。

**迁移到 Explore 与 Crossover（各 45 个上下文 × 4 种格式）：**

| 算子 | 格式 | 撤回/重复 | 超过父代 | 组内名次 | 输出 token |
|---|---|---|---|---|---|
| Crossover | 只写 Design | 7% | 47% | 2.64 | 495 |
| Crossover | **几句话针对性分析** | 7% | **53%** | **2.26** | 669 |
| Crossover | 列方案再选 | 18% | 47% | 2.43 | 638 |
| Crossover | 针对性 + 列方案 | 22% | 51% | 2.67 | 689 |
| Explore | **只写 Design** | 0% | 31% | **2.24** | **385** |
| Explore | 几句话针对性分析 | 2% | 27% | 2.78 | 899 |
| Explore | 列方案再选 | 0% | 40% | 2.38 | 804 |
| Explore | 针对性 + 列方案 | 0% | 24% | 2.60 | 1,086 |

- Crossover：针对性分析名次最好；列方案会让模型更常直接选中参考程序，重复升至 18–22%。
- Explore：几乎不产生重复；只写 Design 名次最好、成本不到一半。以"当前算法受什么限制"为题的分析反而可能把模型锚定在当前算法上。

## 4. 解释

1. **代码前的文字为模型提供显式分析的机会。** 关闭 thinking 时，模型仍从左到右生成，代码前的 token 可以用于分析下一步怎样改。修改给定算法时，如果没有明确改动方向，模型可能生成接近已知程序的版本。简短诊断（受什么限制、改什么）可能减少这种风险，配对结果也观察到重复率下降。
2. **有用的是针对当前决策的诊断，而不是思考量。** 泛泛或不限长度的思考更贵、更发散；原生 thinking 在 Qwen 上无法收束。
3. **工作记忆与存档应分开。** Analysis 只服务于本次生成，用完即弃，不需要整洁；Design 是留给历史、参考卡和修复提示的存档，一两句话即可，长度对后续算子没有可测影响。
4. **算子性质决定是否需要分析。** Refine、Crossover 要在给定算法上做出局部决策；Explore 的指令本身已经要求不同的核心思想，新颖性压力已在指令中，在本次设置下，额外分析没有带来质量收益，却增加了成本。

**与 EoH 的关系。** EoH 在代码前要求一句话的 thought（写在花括号中），并把收益归因于"思想与代码两种视角共同进化"；其唯一的相关消融只在 OBP 上各跑 3 次，比较只用代码、只用思想和两者兼用，未区分"说明作为信息被后续读到"与"写代码前先做决策"两种作用。本研究在 Explore 参考卡上检验了前者（无影响），在 Refine 上检验了后者（显著），这些结果让我们把"先决策"作为 thought 起作用的一种解释。

其他方法对代码前文字的做法见[相关工作调研](../05-相关工作/LLM-AAD中的代码前文字与算法表示调研.md)：EoH 的 E2、MCTS-AHD 的 s1 已在生成指令中要求先分析，AutoMOAE 用独立目标分析指导只输出代码的生成调用，PAEvo 则先生成并保存结构化 plan，再由另一角色实现代码。“先分析或规划再写代码”本身不是新做法。

补核原文后，AutoMOAE 已有有／无分析模块消融，PAEvo 也有 plan 与算法进化的组件消融。它们分别检验整个分析模块和结构化 plan；本地配对进一步区分本次决策、后续读取、文字长度和算子差异。

## 5. 指标与比较条件

- 配对实验度量单次生成的撤回/重复、有效率和超过父代的比例；完整搜索另见[生成目标与计算限制](2026-10-01-生成目标与计算限制.md)。
- 父代随机取自档案，指标看是否超过父代与组内名次，对 Explore 罕见的结构跳跃不敏感。V10.15-5 的固定父代对照改看“是否超过全局最好”：在 TSP 上，以当前程序为锚的结构重写加分析明显优于只写 Design（见[V10.15-5 诊断](2026-10-01-生成目标与计算限制.md) §4），结构发现应使用是否刷新全局前沿的指标。
- 每个上下文每种格式只生成一次；按现有样本量，约 10 个百分点以下的差异无法可靠检出。第三轮中许多细节比较不显著。
- DeepSeek 与 Qwen 在"长说明是否减少重复"上结论不同；结论对具体模型有依赖。
- 初始化与修复的格式按算子性质类推，未做配对检验（每路初始化只有 8–16 次，修复也只在失败后发生，影响有限）。
- 父代取自 V10.15-2/-4 的档案，历史中的说明是旧格式。

## 6. 采用的协议

| 算子 | 回复格式 | 依据 |
|---|---|---|
| Refine | Analysis：a few sentences: what limits the current algorithm, and what change should improve it → Design（≤60 词）→ Code | 实验二、三 |
| Crossover | Analysis：a few sentences: what the reference algorithm does well that the current algorithm lacks, and how to combine them → Design → Code | 实验三迁移 |
| 修复 | Analysis：a few sentences: what caused the failure, and how to fix it → Design → Code | 类推（局部修改） |
| Explore | Design（≤60 词）→ Code | 实验三迁移 |
| 初始化 | Design（≤60 词）→ Code | 类推（生成新算法） |

Analysis 不保存、不再展示；Design 以 "Design:" 标签进入历史、参考卡、参考算法与修复提示。
