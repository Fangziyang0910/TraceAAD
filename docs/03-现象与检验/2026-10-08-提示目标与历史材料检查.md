# 提示目标与历史材料怎样影响算法修改

2026-10-08。检查对象为 V10.21 的六任务上下文、所有生成步骤和真实请求记录。

**时间之外，最值得优先检查的是三种偏好：反复要求保留“核心思想”，要求探索首版直接超过全局最好，以及预设参考程序一定有值得借入的计算。** 形成路径、可执行模板和模型自己的 Design 又给这些目标提供了反复出现的样例。提示中的事实、希望模型做的改动和模型对代码的解释，需要分别看待。

本次确认了提示实际陈述的目标、材料的组成和具体的说明／代码不一致。哪些措辞导致完整搜索退步，仍需固定材料的局部对照区分。本次没有修改搜索提示、评价器或运行进程。

**当前源码与已发出的提示需要分开。** 当前六任务公共段落均只出现一次秒数；`measured()` 只保留分数，调用次数和当前程序耗时也已隐藏；允许“对输入做任何计算”的整句被删除。日志快照中还没有使用这套 score-only 测量的请求。Deepen 有21次请求已使用新的质量目标，944次仍是旧的多用时间目标。因此，不能把这7,838次候选的行为归因于最新完整提示。

## 1. “保留核心思想”同时成为改动要求和解释要求

Refine 的任务句要求 `keep its core idea`。Analysis 再要求解释什么改动保留该核心。Design 格式第三次要求说明 `the core idea`。Crossover 也有同样的三次强调。当前36份重建提示中，六任务的 Refine 和 Crossover 均如此。[目标与输出格式](../../traceaad/common/prompts.py#L33)

普通搜索的份额为 Refine 0.40、Crossover 0.20、Deepen 0.15：前三者合计75%，都明确要求保留当前核心思想或决策规则。短程开发又使用 Refine。[步骤份额](../../traceaad/v10_20/config.py)、[开发调用](../../traceaad/v10_17/traceaad.py#L39)

保留有效计算本来有价值。但“核心思想”没有操作性定义。模型可能把一个已有打分公式当成必须保护的主体，只在外面添加权重、惩罚或小修饰；也可能只是把重写后的程序继续称作同一个核心思想。文本是否声称保留，不能回答实际保留了哪些计算。

**建议先去掉重复的解释要求。** Design 只描述算法和本次主要改动。Refine 可以保留局部开发的目的，但把“保留核心思想”改为保留本次改动不需要替换的计算，且只在任务句说一次。Crossover 是否必须保留父代核心，需要与它的融合目的一起检验，不能直接沿用 Refine 的限制。

## 2. Explore 把探索目标写成首版直接胜过全局最好

Explore 的目标句同时要求：超过全局最好、改变决策方式、不能只是调参。Analysis 要求找出当前算法不能捕捉什么，再提出不同计算。上下文给出当前程序、从它出发的尝试，以及最近8次刷新全局最好成绩的 Design；没有全局最好程序的完整代码。[Explore 目标](../../traceaad/common/prompts.py#L41)、[全局进展与材料](../../traceaad/common/prompts.py#L347)

真实记录中，**1,368次 Explore 有1,120次（81.9%）从弱于全局最好的程序出发**。因此，大多数请求要求模型一步同时补齐起点差距和产生新的最好结果。系统仍会保存较弱的有效首版，但提示把直接胜出写成这一步应达到的目标。后续三步开发只有1/8的探索得到，也不是每个首版都会接受的过程。

这里有两个不同要求：寻找有希望的计算变化，以及让首版立即击败已开发的最好程序。把它们合在一起，可能推动模型重用已知强设计；“不能只是调参”又可能让模型把公式增加一项描述成结构改变。日志能确认这个目标与起点不对称，尚不能单独确认它造成了多少收益损失。

**建议保留改进的最终目的，去掉首版必须直接击败全局最好的措辞。** 同时把“不能调参”换成正面陈述本次要改变的计算。最小对照只改目标句，固定父代、历史和评价；比较实际改动、成熟细节的保留与开发后的收益，而不只比较首版胜率。

## 3. Crossover 预设参考程序有优势，而且当前程序缺少它

任务句要求借入参考程序“做得好”的部分；Analysis 又要求解释参考程序做得好、当前程序缺少什么。选择器只要求参考位于档案分数较好的一半，再从代码差异较大的部分抽取，**不要求它优于当前程序**。[Crossover 提示](../../traceaad/common/prompts.py#L44)、[参考选择](../../traceaad/common/selection.py#L118)

**1,063次 Crossover 中，参考总分更差的有899次（84.6%），更好的155次，同分9次。** 六任务都存在这个现象。较弱程序仍可能含有有用计算；问题在于目前只给出平均分、代码和 Design，没有证据指出某个部件确实更好。

例如 CVRP 第1路第35次：当前程序分数8.1785，参考11.6312。模型判断参考最近邻方法“更好地捕捉局部接近性”，并据此增强距离先验。这是从代码提出的解释，不是两份总分证明的部件优势。相关请求与回复索引保存在快照 `examples.worse_reference`。

**建议把融合改成有条件的判断。** 让模型判断参考中是否有计算值得用于当前程序，再决定保留或替换什么。不要自动把参考总分更差的程序排除，那会同时改变参考选择和可借用材料；先只去掉“参考一定有优势、当前一定缺少”的预设。

## 4. 形成路径和成功记录成为大量示范，短程开发又重新接入它们

下面按真实请求的空白分隔词数计算。历史包括形成路径的 Design 与代码差异、尝试记录、全局最好进展或先前 Deepen 尝试；不是服务端 token 比例。两个中位数分别计算，不用中位词数的比值代替占比中位数。

| 步骤 | 请求数 | 全文词数中位数 | 历史材料词数中位数 | 每份请求中历史占比的中位数 |
| --- | ---: | ---: | ---: | ---: |
| Refine | 3,301 | 4,445 | 3,397 | 75.6% |
| Crossover | 1,063 | 5,441 | 3,901 | 70.5% |
| Explore | 1,368 | 1,694 | 582.5 | 34.2% |
| Deepen | 965 | 1,127 | 0 | 0% |

Refine 最多给8步形成路径与8次尝试；Crossover 最多给双方各4步路径和8次尝试。裁剪时保留最近路径，删除较旧材料；Crossover 裁到仍过长时会转成 Refine。这些规则可能使长程序和长融合更难获得完整上下文，但本次没有把这种可能性当作已确认的收益原因。[拼接与裁剪](../../traceaad/common/prompts.py#L408)

这里最有支持的解释是：历史不只告诉模型哪些分数好，也反复示范过去怎样改代码。此前固定父代重放中，完整历史下 Deepen 与 Refine 都主要小改；去掉历史后，OP、CVRP 的计算增加12–17倍，首版质量却没有变好。因此，材料确实能改变所写的计算，但删除历史也不是现成解决办法。TSP 去掉历史还变差。[已有重放](2026-10-06-V10.20重放与ACO评价噪声.md)

V10.21 的 Deepen 提出时不看形成历史，但若获得短程开发，下一步又调用普通 Refine，并读取完整父代链。这会重新带入 Deepen 之前的修改样例；它与“提出阶段减少旧历史影响”的目的并不完全一致。该现象来自实际调用链，不应误读成 V10.19 的独立开发规则。

**时间删减也没有移除历史中的时间叙事。** 当前重建的 CVRP Refine 样本仍有8条历史 Design 提到时间或预算，代码及 diff 也保留9.5、9.8秒等计时常数。删去每步附加的耗时行，不能自动删除旧目标在生成说明和代码中留下的影响。其他规则同样可能沿 Design 回到后续上下文。

**建议先区分材料的作用。** 固定目标句，比较完整历史和少量相关改动。先核对模型保留、替换的计算及后续收益，不以提示变短或结构变化变多作为成功标准。不要一次删去全部历史。

## 5. Design 会把未实现的机制带入后续请求

图着色第2路第603次 Deepen，Analysis 和 Design 声称实现模拟退火：反复重着色，并概率接受较差移动。**代码没有模拟退火搜索、退火温度或概率接受。** 它仍在构造阶段使用饱和度／度数，在修复阶段使用冲突变化与颜色类大小打分，只按剩余时间开关一个惩罚项。父代585与子代603都得到 −6.520804993，子代通过评价，但没有改变分数。

这条“实现模拟退火”的 Design 又原样进入第604、605、606次请求。系统对代码做了规范化，却没有核对说明是否对应实际计算。[完整回复](../../experiments_result/traceaad_v10_21/diagnostics/context_audit_current_prompts/graph_colouring_rep2_request603_response.txt)

尝试记录通常只有 Design 与结果，没有实际代码差异；Explore 的最好进展也只有 Design 与分数。下一次模型因此可能把“一个称作模拟退火的设计没有改善”当成经验，实际被评价的只是局部公式。这会改变它对已尝试机制的认识。

强制 Analysis 也有相似预设：Refine 必须说当前算法有什么局限，Explore 必须说它不能捕捉什么，Crossover 必须说参考强在哪里。只有总分时，这些句子容易产出具体但未验证的因果解释。应让 Analysis 针对代码中可指出的限制与本次改动；历史中的 Design 则作为生成时的说明读取，不能直接当作已执行机制或已证明原因。

**建议先用现有代码做针对性核对。** 对决定下一步的少量尝试，给出实际差异；检查新增循环是否搜索了候选，以及其结果是否影响返回值。无需立刻增加独立反思模型或全面的语义标签系统。上面的实例已足以说明，统计“Design 提到搜索”不能替代统计“代码实现搜索”。

## 6. 可执行模板与通用 Deepen 可能把接口误读成计算形式

每次请求都包含目标函数的完整可执行基线：TSP 是最近邻，CVRP 是逆距离，OP 是奖励／距离，图着色是 DSATUR式构造与冲突减少，JSSP 是剩余工作量，FSSP 是总处理时长选作业并放大时间。它们既说明接口，也反复提供具体算法样例。[六任务模板](../../benchmarks/tasks.py)

但返回“优先分数”并不要求内部只能计算简单公式。TSP、JSSP 可以先模拟后续再返回一个选择或分数；图着色可以评估后续冲突修复再返回候选优先级；ACO 可以先构造解再编码成边先验。这些计算能否有效，需要看接口消费返回值的方式。

当前源码删掉了“在时限内可以对输入做任何计算”的整句，也去掉了当前程序的调用次数。去掉时间限定合理，删掉允许的计算范围和调用结构则是额外的信息损失。JSSP 的任务说明仍明确允许计算后续调度后果，其他任务的说明并不统一。

Deepen 对六任务使用同一个“保留当前规则并用它引导搜索”的目标，没有说明内部搜索怎样映射回该任务的返回值。图着色的外层只消费候选分数，候选对输入副本的修改不改变外层颜色；因此，模型声称“内部重着色求出一个好解”还不够，必须把搜索结果用于实际返回的候选排序。[图着色消费方式](../../benchmarks/graph_colouring/evaluation.py#L19)

**建议保留清楚的计算范围和调用事实，区分输入／输出契约与内部计算。** 可以先给 Deepen 一句任务相应的返回值连接说明。是否去掉模板的基线函数体，应单独比较接口文档加占位体与完整基线；目前只有锚定的可能性，没有模板对照证明它是主要原因。评价器及其原模板不需要随提示展示方式一起修改。

## 7. 其他内容的检查结论

| 内容 | 结论 |
| --- | --- |
| 函数名、参数、返回形状、有限值、自包含程序 | 对应实际解析器或评价器，是必要契约，应保留。 |
| 固定框架、可行解、原始处理时间、输入副本、全局变量生命周期 | 对应实际执行；重复部分可以去重，不能作为“限制过多”一并删除。 |
| TSP任务和模板中的 `novel algorithm` | 创新要求重复且不影响评分，可以去掉；没有证据表明它比核心保留和材料偏向更重要。 |
| Design最多60词、简短Analysis | 本次未发现足以归因的失真；已有格式配对支持针对当前改动的简短分析。 |
| 不写注释和docstring | 控制输出成本，会影响生成方式，但尚无同条件证据证明它造成搜索退步；优先级低于目标和材料问题。 |
| `Every version and attempt ... evaluated` | 说明结果已经测量，有价值；测量一个程序不等于证明Design解释的机制有效。 |
| 单个平均训练分与 improved／worse | 事实可以保留，但不足以定位哪个实例或部件导致变化。原OP多种子诊断提示要核对微小改善；其旧数据集数字不能直接套用到当前16例协议。 |
| 隐含system提示 | 请求构造把整份提示作为一个user消息发送，没有发现代码另外注入研究目标或算子规则。 |
| 采样参数 | 记录和入口为temperature 0.7、top_p 0.8、presence_penalty 1.5、关闭thinking。属于生成条件；本次没有对照证据把失真归因于它们。 |

## 优先顺序与最小检验

**先处理目标句中的重复和预设，再检查材料如何改变代码。** 三项最小措辞候选分别是：Design不再反复要求“核心思想”；Crossover有条件地判断参考计算是否可用；Explore把新计算作为待评价的改动，最终目标仍是更好的解，而不是要求首版直接击败全局最好。它们可以在相同历史下分别重放，避免混在一次整套版本更新里。

第二步单独检查历史：同样目标下，完整形成路径与少量相关实际差异是否导致不同改法。特别核对短程开发中，新计算是否保留，是否恢复原程序细节，是否只是重新命名局部公式。模板展示、注释和采样留到主要解释清楚后再比较。

对每项干预，判断依据都落在实际代码与收益上：模型改了哪些计算、返回值是否使用了这些计算、相同评价条件下首版及少量开发后的质量如何变化。若改动幅度增加而质量下降，说明旧上下文提供了有用计算，不能把“摆脱约束”直接等同于改进。评价协议保持固定。
