# LLM 自动算法设计方法的候选表示协议

核查日期：2026-09-12。问题：EoH、ReEvo、MCTS-AHD 及相关方法究竟让 LLM 生成函数体、完整函数，还是完整程序，以及模板和 import 由谁负责。

## 结论

这些方法的共同研究对象是“任务模板中一个可执行启发式/算法函数”，而不是任意软件项目。论文通常把候选称为 heuristic、algorithm 或 program，但实现上普遍保留任务接口和评测器；差异主要在于生成协议：有的让模型输出函数体并由系统嵌回模板，有的让模型输出包含目标函数的完整代码，有的把代码与自然语言 thought 分开生成。

因此，看到一段完整 Python 代码不能直接推断方法在进化整个程序；应检查评测入口是否固定模板、是否只抽取目标函数、以及 imports 是否由系统补齐。完整代码协议会把 import、辅助函数和封装错误也交给模型，和“只替换函数体”的协议在失败率和搜索空间上并不等价。

## 方法核查

### EoH / MEoH

EoH 原论文 [Evolution of Heuristics: Towards Efficient Automatic Algorithm Design using Large Language Models](https://arxiv.org/abs/2402.01145) 描述的是由 LLM 产生 heuristic 的迭代进化；官方实现 [ai4co/LLM4AD](https://github.com/ai4co/LLM4AD) 的 `eoh`/`meoh` 采样器先从响应中解析函数，再通过 `TextFunctionProgramConverter.function_to_program` 将函数放回 `template_program`。仓库的 `template_program` 提供任务 imports、函数签名和评测上下文。因此在该实现中，模型生成的是目标函数（通常包括 `def ...` 的完整函数定义或函数体，取决于 sampler 的解析格式），最终被系统重建成完整程序；模板 imports 不需要模型重复生成。

这一协议的关键不在模型文本长短，而在系统边界：只有模板允许的目标函数进入评价，固定接口和环境不随每个候选改变。MEoH 只是增加多目标/多样性等搜索组织，候选封装仍遵循同一类函数到模板的转换。

### ReEvo

ReEvo 原论文 [ReEvo: Large Language Models as Evolutionary Optimizers（arXiv 检索页）](https://arxiv.org/search/?query=ReEvo%3A+Large+Language+Models+as+Evolutionary+Optimizers&searchtype=all) 将 LLM 作为反思、交叉和变异算子，并在组合优化任务上评价新 heuristic。作者代码入口可由论文项目页 [ReEvo project](https://github.com/ai4co/reevo) 追溯。其任务仍以固定 problem description、函数接口和 evaluator 为边界；LLM 响应中抽取算法实现，再交给任务执行器评价。ReEvo 的主要变化是搜索算子和反思上下文，而不是把搜索对象扩展为任意工程程序。

需注意：不同公开版本的 parser 可能要求完整函数定义，或要求特定标记包围函数；这属于文本协议差异。只要 evaluator 仍固定任务模板，研究对象仍是目标启发式函数。引用 ReEvo 时应同时记录具体 commit，因为 prompt/parser 版本会影响 import 是否自动拼接。

### MCTS-AHD

MCTS-AHD 原论文 [MCTS-AHD: Monte Carlo Tree Search for Automated Heuristic Design](https://arxiv.org/abs/2501.08603) 的 §3.1 与附录 E.2 明确描述两次 LLM 调用：第一次同时生成 thought 和 function，第二次根据任务、函数输入输出、第一次 thought 与 code 重新生成对实现的简短描述（thought alignment）。第二次调用不会重写代码，也不是代码修复步骤；最终评价的是第一次生成的函数实现。

本仓库对应实现 `llm4ad/method/mcts_ahd/sampler.py` 的 `get_thought_and_function` 与 `get_prompt_refine` 复现了这一职责拆分。MCTS 负责节点选择和扩展，函数仍受任务模板/评测器约束；thought 是搜索上下文，不是另一个可执行程序。

### FunSearch / AlphaEvolve（相关参照）

FunSearch 原论文 [Mathematical discoveries from program search with large language models](https://www.nature.com/articles/s41586-023-06924-6) 在固定程序骨架和 evaluator 中搜索可替换的函数实现。AlphaEvolve 论文 [AlphaEvolve: A Gemini-powered coding agent for designing advanced algorithms](https://arxiv.org/abs/2506.13131) 进一步允许在适合时使用 SEARCH/REPLACE 编辑，或直接输出完整代码；但其 evaluator、接口和候选可执行性仍由框架控制。它说明“完整代码响应”是一种生成/编辑接口，不等于研究对象脱离固定可评价程序。

## 对 TraceAAD V10.10 的定位

TraceAAD 的概念对象与上述方法一致：固定任务契约下的目标函数算法实现。V10.10 的差异在候选封装协议：模型响应被当作包含目标函数的完整 Python 候选并直接执行，因此 imports 和辅助定义也可能由模型提供。这个选择可支持辅助函数和原始代码保留，但会引入封装错误、扩大表面搜索空间，并使结果与 EoH 的“系统把函数嵌回模板”基线不再严格同构。

若研究问题是父代选择、轨迹上下文或 Refine/Pivot/Fuse 对算法搜索的影响，建议把协议明确写成：`candidate = target function implementation; evaluated_program = fixed template + candidate`，并单独记录是否允许辅助函数。若继续采用 V10.10 的完整代码协议，应把 import/封装失败作为实现协议的一部分报告，不能把所有失败都解释为算法思想失败。

## 证据边界

论文的“program/algorithm/heuristic”术语不能单独证明 import 处理；需要结合官方 parser、template 和 evaluator。ReEvo 的公开代码版本与链接需在实验复现时锁定 commit；本文不把未锁定版本的 parser 细节写成确定事实。本文只比较候选表示协议，不据此判断哪个搜索机制性能更好。
