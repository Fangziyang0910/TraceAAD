# MCTS-AHD 二次摘要、编辑模式与 RL 的取舍

核查日期：2026-09-06。本文记录研究判断与后续决定。最初核查阶段仅新增记录；用户随后授权的公共任务恢复、两次调用与恢复机制现已落实到代码，见当前机制设计。本轮未启动新实验或调用真实生成模型。

## 决策

按用户最新决定，下一轮采用第一次调用先生成设计 idea、再生成完整 code，第二次调用依据最终 code 重新生成实现 idea。前置 idea 指导本次设计；后置 idea 记录实际实现，进入后续形成历史。编辑模式暂缓，待专门调研后再决定是否采用；RL 留待后续。

代码已落实这一机制；此前正式批次仍记录为原有单次 Code→Summary 配方，新协议通过机制指纹与其区分。本轮没有重启该批次或将其旧结果改称新配方结果。

任务信息对齐修订：用户要求沿用旧基线与 V9.16 的共同任务说明和模板。后续核查发现 V10.6 已有专用描述覆盖，公共 VRPTW 文本也在旧实验后改动过；具体范围在 2026-09-06 已完成恢复核查。本轮取消下文曾提出的 OP/TSP 专用信息扩写，诊断发现保留为研究证据。生成与校准均使用相同的历史共同任务信息。

三者作用不同：摘要调用改善搜索记忆的描述，编辑模式改变子代代码的生成方式，RL 改变生成模型的能力和偏好。它们不能互相替代。最终采用标准仍是有限总预算下的搜索表现；摘要忠实度是判断该步骤是否正常工作的中间指标。

## MCTS-AHD 实际做了什么

[论文 §3.1、附录 E.2](https://arxiv.org/pdf/2501.08603)给出两次调用：第一次生成思想和代码；第二次输入任务说明、函数输入输出含义、第一次思想与代码，重新描述实现中的主要设计、变量优先关系、参数和结构。附录提示要求少于三句，正文称最多三句。它没有执行程序来验证每项描述，也没有在这一步修复代码。

本仓库的对应实现吻合这一过程：`MASampler.get_thought_and_function`第一次解析思想与函数，随后以 `get_prompt_refine` 构造第二次请求，最终返回第二次描述和原函数。这里是本地实现核对，不将其当作上游源码证据。

[论文表 5](https://arxiv.org/html/2501.08603v3#S5.SS1)报告：完整方法的 TSP50 / KP100 gap 为 10.661% / 0.059%，移除 thought-alignment 后为 11.640% / 0.061%，越低越好。这为该组件在作者设定下的搜索收益提供了支持；它不是摘要忠实度测量，也没有与我们的同次 Code→Summary 作直接比较。重复次数的报告还存在正文三次、表注五次、完整方法行十次的口径差异，应据实保留，不能据此宣称严格匹配的显著性结论。

**对 V10.6 的推断：** 拆分调用有合理价值，但收益并非第二次调用第一次才看到代码。当前后置摘要也已能读取代码；新增价值主要在于把“设计新算法”与“准确解释给定实现”分为两项任务，并精简描述阶段的上下文。相同模型仍可能重复同一种语义错误，独立请求不等于独立验证。

最新方案借鉴任务拆分，并恢复第一阶段的设计 idea。它使代码生成能条件于明确的算法计划，但能否提高生成质量仍需实验判断。第二阶段可以读取本次设计 idea 作为待核对意图，以实际代码运算为实现依据；它重新解释最终算法。设计 idea 和实现 idea 分别保存于生成记录与节点记录，历史仅展示后者，避免将计划和已实现内容重复送入上下文。

## 为什么不能从错位直接推出“LLM 不懂算法设计”

已有 V10.6 核查同时发现了准确的参数与计算描述，以及以下实质错误：

- TSP 的 `np.partition` 返回值被丢弃，代码实际读取固定列，摘要却称第二近邻；对角线为无穷大使行均值分支失效。
- OBP 的新评分可化为 Best-Fit 的正尺度变换，摘要却称增加了能改变选择的偏好。
- VRPTW 的正向 urgency 项进入最小化评分，摘要把影响方向说反。
- CVRP 摘要遗漏初始化变化，该变化显著改变部分边的中间权重。

这些证据说明，模型对代码的数值语义、作用方向和实现差异掌握不稳定。不能据此断言其完全没有算法设计能力，也不能仅根据摘要确定生成时的真实意图。表现好的程序可以包含无效部件；算法标签是否贴切、具体代码是否按预期工作、整个程序得分是否优秀，是三个不同问题。

任务说明仍然重要：例如返回矩阵如何被求解器归一化、哪些动作被掩码排除，会改变其算法含义。需要补充这些真实调用事实；它们不同于我们自身的种群预算或算子调度术语。完整任务说明也不能保证模型正确使用数组 API 或完成代数化简。

## 独立摘要的最小设计

每次扩展仍选择一个父代、确定算子、生成并评价一个子代。摘要步骤仅写该子代的实现记录。

第一次调用先用一个简洁自然段说明主要决策方法和拟采用的关键计算，再输出完整实现。这个段落承担设计算法的职责，长度随算法需要调整。第二次调用形成约 500 words 的实现 idea，承担详细说明职责。两次调用合起来仍对应一个候选和一次真实评价。

第二次调用的输入为：

1. 与旧基线、V9.16 对齐的任务说明和函数契约，内容以历史共同定义为准。
2. 最终将被评价和存档的完整子代代码；若生成使用补丁，这里读取补丁应用后的完整代码。
3. 有父代时提供完整父代代码，以支持变化描述。父子代码已足够时直接使用现有材料；无需再引入一套由 LLM 推断的变化字段。
4. 本次生成的设计 idea，标明其为设计意图；实现说明以最终代码的计算为依据。

第二阶段的主要任务是写清：实际采用的决策方法、决定输出的公式和条件、相对父代的重要变化。组件对实际选择的作用应根据计算关系解释；预期性能收益应明确属于假设。最终评测分数由系统另行记录，摘要无需归因本次得分升降。输入集合以这些材料为限，历史摘要和预算调度信息留在原有设计阶段。

可采用的正向指引如下，具体输入输出与求解框架事实另由各任务模板提供：

> Explain the algorithm implemented by the final code for the stated task. The design idea provides the intended approach; the code operations determine the implemented method. Describe its main decision rule, the calculations that determine its output, and the important parameters and conditions. Derive each preference from the computation and how the solver uses the output. When parent code is provided, identify the implementation changes that matter to these decisions. State directly established effects as facts and expected performance benefits as hypotheses. Write approximately 500 words in 2–3 paragraphs, scaled to the implementation's complexity.

延续现有约 500 words 软目标、单条 1024 tokens 上限和最近 8 条形成事件；短实现允许更短。第二次调用负责说明，代码修正属于后续生成操作；发现可疑实现也应首先如实描述代码已经做的计算。这避免为了让算法符合文字而悄然改变已评价对象。

独立摘要仍是模型生成的实现说明，不标记为执行事实或已验证知识。摘要缺失时可以按现有 unavailable 标记保存有效代码；其调用与失败计入实际成本，避免把说明失败伪装成算法评价失败。

## 编辑模式的适用位置

[AlphaEvolve §2.3](https://arxiv.org/html/2506.13131v1#S2.SS3)使用 SEARCH/REPLACE，同时允许短程序或适合整体重写时直接输出完整代码。论文没有提供编辑模式改善思想与代码对齐的直接实验；详见专项核查。

因此，edit 可以帮助将生成集中在计划修改的位置，减少无关重写，并提供确定的文本变化记录。但一个正确应用的补丁仍可能写反符号、误用数组或保留已有错误。它也不会自行校正摘要。

用户决定暂不做 edit，后续专门调研后再决定是否采用。此前建议的 Refine 场景只作为未来调研线索，当前各算子继续输出完整实现。

## RL 能解决什么

[SCoRe](https://arxiv.org/abs/2409.12917)表明，专门设计的多轮在线 RL 可以改善数学和代码任务中的自我修正能力。它支持“能力可以通过针对性训练改善”，不能推出“只要加入 RL，代码—摘要一致性就自然解决”。

对当前流程，固定代码 C，摘要 S 在代码生成后产生，当前评价是 R(C,S)=F(C)。改变 S 不会改变这份代码的 fitness。因此当前 fitness 没有区分忠实与错误摘要的直接信号；它不是摘要准确性的标签。共享参数可能带来间接迁移，但并未建立可识别的摘要训练目标。

如果以后以未来后代的表现给轨迹奖励，摘要可能影响后续生成，因此有学习信号；这将引入延迟信用分配，并且“有利于搜索的摘要”仍不等价于“所有陈述都忠实”。当前阶段没有必要先承担这一训练难题。

更适合的顺序是：先稳定算法生成、评价与摘要协议，再决定是否用 RL 学习更好的代码改进策略。准确解释若成为训练目标，则需要与代码事实相匹配的监督或可验证反馈，而不是把高 fitness 样本中的所有说明自动当作正确答案。

## 下一步的决策检查

使用已经冻结的代码做一次小规模离线比较即可先判断独立摘要是否值得进入正式配方，无需重跑搜索或先铺开整套消融。固定模型、父子代码、任务事实与长度目标，比较当前摘要、按新职责独立生成的摘要。若需区分职责改写与独立调用的贡献，再加同次调用新职责条件；这是另一个问题，不是本次采用候选步骤的必要前提。

已发现的反例用于确认具体问题是否减少，另取尚未读过的代码检查泛化。优先检查影响算法理解的错误是否减少、重要变化是否遗漏、原本正确的描述是否被改坏；同时记录调用、tokens 和时间。不能把定向反例上的通过率当总体准确率，也不能靠另一个 LLM 的流畅度打分完成验证。

这一步检验的是成本是否换来了更可靠的描述。若没有改善，则继续简化和完善现有摘要任务；若改善明确，再将两次调用作为下一轮候选配方，看它在实际预算内能否帮助生成更好的后代。最终收益仍由搜索结果决定。
