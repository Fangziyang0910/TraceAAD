# AHD/AAD 代表方法与机制

自动启发式设计（AHD）通常在给定求解框架内设计关键启发式；自动算法设计（AAD）的对象还可以是算法组件、完整求解器、启发式集合，甚至设计器本身。代表工作都把候选设计交给模型或搜索过程，并通过评价结果决定下一步，但它们真正的分歧在于：**允许改变什么、怎样提出新候选、让谁获得下一次机会，以及如何利用已经发生的试验**。这几个问题比单纯比较种群规模更能说明方法之间的关系。

下面按主要贡献组织方法；同一种方法可能同时涉及多条路线。具体论文、实现与实验设置见各方法所链接的主题条目。

## 从语言模型生成到程序进化

| 方法 | 设计对象 | 代表性机制与作用 |
|---|---|---|
| [ELM](程序进化与算子设计.md#paper-01) | 可执行生成程序 | 用模型生成程序 diff，以 MAP-Elites 保存不同行为方向；把语言模型当作进化中的变异器。 |
| [FunSearch](程序进化与算子设计.md#paper-04) | 固定骨架中的关键函数 | 从已评价程序构造提示，借多岛与分数、长度分组持续搜索；将开放生成限定在可执行、可自动评分的函数槽位。 |
| [EoH](程序进化与算子设计.md#paper-05) | 启发式思想及其代码 | 用多种提示完成重组、扩展、修改、调参和简化，再用排名与精英选择组织种群；算子开始明确对应不同设计动作。 |
| [HSEvo](程序进化与算子设计.md#paper-07) | 启发式结构及参数 | 生成和遗传搜索负责结构，和声搜索负责数值校准；把换算法与调参数拆成不同问题。 |
| [AlphaEvolve](程序进化与算子设计.md#paper-12) | 可演化函数及其所在程序 | 根据父程序、参考程序和反馈生成补丁或代码，由程序数据库和级联评价承接后续开发；编辑粒度与评价成本一起进入设计。 |
| [ShinkaEvolve](程序进化与算子设计.md#paper-13) | 可执行优化程序 | 档案与岛保存候选，多模型 bandit 调节生成来源，嵌入拒绝采样减少近重复提议；同时管理生成器和程序库。 |
| [RoCo](程序进化与算子设计.md#paper-39) | 启发式及生成过程 | explorer、exploiter、critic、integrator 分工提出和整合建议；改变单次候选的形成过程。 |
| [TurboEvolve](程序进化与算子设计.md#paper-58) | 多岛中的程序 | 批量生成、聚类播种及跨簇注入，按岛的停滞调节产出；把吞吐量与分支维护纳入进化组织。 |

这条路线的演进不只是“用更强的模型写代码”。FunSearch 强调可评价的函数槽位；EoH 把设计动作拆开；AlphaEvolve 将编辑、数据库和筛选连成循环。它们的直接产物看似都是代码，实际可改变的计算范围及每次生成使用的历史却大不相同。

## 让哪些候选继续获得预算

| 方法 | 分配单位 | 代表性机制与作用 |
|---|---|---|
| [QUBE](机会分配与搜索规划.md#paper-08) | 亲代及其所在簇 | 用历史后代质量估计开发价值，结合 UCB 的不确定性项选父和调整岛；让“值得继续试”由后代证据决定。 |
| [MCTS-AHD](机会分配与搜索规划.md#paper-22) | 搜索树节点和路径 | UCT 选点、渐进扩展、子树回传及多种生成动作；把探索和已有分支的深化组织成树搜索。 |
| [PoH](机会分配与搜索规划.md#paper-23) | 改进建议及其实现路径 | 先提出设计动作，再通过代码实现和规划树比较后续可能；把规划对象推进到“怎样改”。 |
| [PathWise](机会分配与搜索规划.md#paper-24) | 多父设计路径 | 在推导图中选择父代集与改进指令，由生成模型提出候选、critic 总结效果；搜索可沿组合路径积累经验。 |
| [Clade-AHD](机会分配与搜索规划.md#paper-25) | 谱系分支 | 将后代收益聚合到 clade，用 Thompson 抽样分配机会；不只依赖单个节点的当前分数。 |
| [SMCEvolve](机会分配与搜索规划.md#paper-48) | 候选粒子分布 | 重加权、重采样和变异共同决定保留与生成，提供一种统一理解选择压力的方式。 |

分配机制的关键差别是**给谁记账**：当前最高分程序、产生过好子代的亲代、整条路径或整支谱系，各自隐含不同的“未来还有收益”的假设。仅观察最终 best 无法辨别哪一种信用分配起了作用；更直接的是看得到额外机会的分支是否真的产出后续改进。

## 让失败和历史进入下一次设计

| 方法 | 留存的经验 | 代表性机制与作用 |
|---|---|---|
| [ReEvo](经验记忆与条件生成.md#paper-15) | 好坏候选的对比与反思 | 短期对比、长期建议与代码进化交替进行；把评价差异变为下一次生成的文字指导。 |
| [HiFo-Prompt](经验记忆与条件生成.md#paper-16) | 精英的 hindsight 与搜索前瞻 | 提取已知有效经验，再据进展提出探索意图；将回顾与下一步方向结合。 |
| [DeltaEvolve](经验记忆与条件生成.md#paper-20) | 父子之间的语义变化及结果 | 检索“改了什么、后来怎样”，与当前父代共同作为生成条件；经验的单位从程序转向有效改动。 |
| [RefineEvo](经验记忆与条件生成.md#paper-27) | 正负经验和搜索进展 | Planner 选探索或开发，检索相应经验，停滞时调整提示；记忆与动作选择相互配合。 |

反思文本、完整程序和父子改动不是等价的历史表示。要判断历史有无价值，重点看它是否使模型提出了不同的计算、该候选是否可运行并得到真实改进，以及这条路线后来是否获得持续开发。经验可以帮助确定方向，也可能固化早期看似有效的局部模式。

## 保留怎样的差异

| 方法 | 差异的定义 | 代表性机制与作用 |
|---|---|---|
| [MEoH](多样性与搜索行为.md#paper-06) | 质量、运行时间及代码结构 | 以 Pareto 支配和 AST 相异度选父与保留种群；允许不同质量—效率折衷共存。 |
| [CDEoH](多样性与搜索行为.md#paper-09) | 归纳出的算法类别 | 每类保留代表，再结合质量和类别稀有度补足种群；防止单类快速占满保留位。 |
| [PartEvo](多样性与搜索行为.md#paper-60) | 代码或思想形成的 niche | 跨 niche 分配机会，内部择优并提供跨 niche 参考；兼顾方向维护与方向间交流。 |

这里的“多样性”既可能是部署时需要的质量—时间折衷，也可能只是为搜索保留不同出路。分类或结构距离应服务于具体选择规则；标签本身并不等于算法行为真的不同。

## 改变设计对象的边界

| 方法 | 设计对象 | 代表性机制与作用 |
|---|---|---|
| [EoH-S](高层算法与求解器设计.md#paper-10) | 互补启发式集合 | 用实例覆盖评价集合，再贪心维护互补成员；目标从单程序最优转为一组规则的互补。 |
| [RedAHD](高层算法与求解器设计.md#paper-29) | 问题约简、映射、求解模板及启发式 | 连基础求解框架一起搜索；使改变问题表示成为设计动作。 |
| [MoH](高层算法与求解器设计.md#paper-31) | 生成和改进启发式的优化器 | 外层设计优化器，内层跨任务评价其产物；搜索对象提升到“设计过程”。 |
| [InstSpecHH](高层算法与求解器设计.md#paper-32) | 实例子类的启发式库 | 离线生成规则、在线按实例特征选择；优化的是实例覆盖和部署选择。 |
| [A2DEPT](高层算法与求解器设计.md#paper-33) | 完整可执行求解器 | 用程序树保存历史，结合退火接受和历史抽样探索结构变化；跳出固定启发式槽位。 |
| [BEAM](高层算法与求解器设计.md#paper-34) | 求解器结构与函数实现 | 外层搜索结构，内层完善函数并用外部记忆复用组件；将“选框架”和“写好组件”分层。 |

扩大设计对象会增加可发现的变化，也改变评价、修复和部署的难度。固定函数槽位中的优秀变异与完整求解器的结构创新，不能只因都输出 Python 代码就算同一种搜索空间。

## 从执行反馈决定下一步

| 方法 | 反馈对象 | 代表性机制与作用 |
|---|---|---|
| [MeLA](经验记忆与条件生成.md#paper-18) | 不可执行程序和历史试验 | 独立调试器处理候选错误，反思模型汇总错误、思路和精英代码以指导下一轮；区分修好程序和改好算法。 |
| [Hercules](高层算法与求解器设计.md#paper-30) | 精英组件与候选质量 | 抽取精英计算组件指导生成，并在扩展版本中用性能与置信度预测决定何时真评；减少把评价机会交给低潜力候选。 |
| [Teacher-Aware Evolution](搜索经验与模型学习.md#paper-57) | 候选在实际访问状态下的动作 | 将启发式决策与 teacher 偏好比较，形成结构、参数与融合建议；用执行中的选择解释分数之外的改动方向。 |

这些工作提醒我们：评价分数用于选优，报错用于恢复可执行性，执行轨迹和动作差异则可能指出算法究竟哪里要改。不同反馈对应不同的下一步决策，不能只把它们压缩成一个分数。输出格式、解析与候选失败的具体协议另见[反馈与实现协议](反馈与实现协议.md)。

## 让搜索经验改变生成器

| 方法 | 学习对象 | 代表性机制与作用 |
|---|---|---|
| [CALM](搜索经验与模型学习.md#paper-35) | 生成启发式的模型与启发式种群 | 用生成响应和性能反馈更新本地模型，与语言算子、参数搜索共同推进。 |
| [EvoTune](搜索经验与模型学习.md#paper-36) | 生成模型 | 数据库既供提示又供偏好训练，周期更新生成分布；把搜索积累写入模型参数。 |
| [Fine-tuning LLM for AAD](搜索经验与模型学习.md#paper-37) | 代码生成模型 | 用算法偏好微调生成器，再接入不同搜索方式；检验模型能力能否跨搜索流程复用。 |
| [AHD-Agent](搜索经验与模型学习.md#paper-38) | 长程设计策略 | 学习规划、生成、评价与反思的连续动作；让模型不仅写候选，也决定搜索过程。 |
| [Hero](搜索经验与模型学习.md#paper-41) | 可复用求解器的生成策略 | 用课程反馈和强化学习训练一次生成完整 solver；将推断期反复搜索的经验转为训练后的直接产出。 |

这一方向改变的不是当前档案如何选父，而是**下一次面对任务时的生成分布或决策策略**。比较时应分别考察训练所用试验、搜索期评价与训练后新任务的表现，才知道经验是否真正迁移。

## 从这些方法回看初始化

各种搜索都需要可评价的起点，但起点不必是一批同质的随机个体。EoH 式生成后筛选先铺开候选；MCTS-AHD 可以在逐个产生初始根时参考已有程序；FunSearch、AlphaEvolve 和 ShinkaEvolve 则从任务骨架或种子程序扩展。首批生成尝试数、实际评价数、初始有效数和后续档案容量是不同量；具体配置可从各方法链接的论文核对。初始化值得讨论的重点是它提供了哪些可继续开发的方向、占了多少总预算，而非是否满足某个统一的种群大小。

对 TraceAAD，[当前机制清单的初始化部分](../04-研究认识与构想/2026-09-24-V10.13机制清单.md#b-初始化)明确采用 8 个顺序生成的评价有效根。讨论 M2 时可先比较独立生成、顺序参考与超量筛选是否改变了后续可开发的方向；讨论 M12–M14 时再看哪些历史材料真正改变了候选的计算。固定总评价预算、后续开发规则与 held-out 方案后，观察早期分数、持续改进和最终泛化，才能决定初始化要投入多少机会。
