# CVRP rep3 耗时诊断与 MEoH 对 TraceAAD 的启示

证据快照：2026-09-05 23:03:01 +08:00。本文区分已核查事实、代码层面的原因与尚需实验的设计推论。正式 V10.5 运行、评价器和搜索规则均未修改。

**结论：现在确实没有把运行时间反馈给模型或用于搜索分配；但 CVRP rep3 的主要慢点是 LLM 生成，不能直接解释为候选算法复杂度高。引入质量—效率信息值得试验，最合适的是可信的简短多指标反馈，加一个有限份额的效率前沿选父通道。MEoH 提供了动机和机制参考，并没有证明多目标一定改善单目标 fitness。**

## 1. 当前信息到底在哪里

| 信息 | 是否记录 | 是否进入生成上下文 | 是否影响下一步分配 |
| --- | --- | --- | --- |
| evaluator fitness | 是，节点与事件 | 是，当前、donor、形成历史 | 是，质量权重及 donor top-5 |
| 生成耗时、输入/输出 tokens | 是，LLM 日志 | 否 | 否 |
| evaluator 外层 wall time | 是，`eval_seconds` | 否 | 否 |
| 生成函数自身执行时间 | 未单独记录 | 否 | 否 |
| 求解过程、进程启动、等待的拆分 | 未单独记录 | 否 | 否 |
| 超时/运行失败类别 | 是，失败事件 | 不进入有效节点的形成路径 | 该次无有效节点，耗掉评价预算 |
| 代码渐近复杂度、规模增长曲线 | 未测量 | 无明确数值 | 否 |

依据：V10.5 prompt、选择与评价循环、节点结构。准确说法是：**记录了耗时，但决策闭环基本仍只看到 fitness。** 父节点计数惩罚与 Pivot 均匀分支属于分配机制，不是对候选运行成本的利用。

另一个遗漏是 CVRP Task Contract 只笼统要求 efficient NumPy，没有明确给出当前 120 秒评价上限、启发式矩阵每实例只预计算一次、固定 ACO 30 ants × 100 iterations 的实际调用关系。“within runtime limits”本身不能替代这些必要任务信息。任务描述、评价实现。

## 2. CVRP rep3 为什么慢

### 2.1 先拆分模型生成与真实评价

以下是各路已提交到 checkpoint 的累计记录；中位数按各自已完成调用统计，进度不同，因此只作耗时诊断，不是受控版本比较。

| CVRP | 已用评价预算 | LLM 调用中位秒数 | 评价中位秒数 | 输出 tokens 中位数 | 超时次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| rep1 / server3 | 222 | 76.96 | 18.05 | 1510 | 0 |
| rep2 / server3b | 421 | 31.31 | 17.36 | 763.5 | 0 |
| rep3 / server3 | 248 | 64.36 | 18.19 | 1284 | 3 |

rep3 累计 LLM 时间占已记录 LLM＋评价时间的 **77.9%**；该比例不包含 tokenizer、checkpoint 等其他开销。rep3 的典型评价只比 rep2 慢约 0.82 秒，LLM 调用却慢约 33 秒。rep1 的生成还更慢，因此“rep3 特别慢”首先是相对某些运行的生成吞吐差异。

rep3 输出比 rep2 长，服务端点和并发负载也不同。当前日志不能把它们各自的因果贡献完全分离；尤其不能从不同端点的 LLM 延迟倒推出候选程序运行复杂度。

同样地，不能直接用各路当前 best 比效果。在共同 200 次真实评价处，rep1/2/3 best 路长分别为 **9.3081 / 9.0690 / 9.4095**。此时 rep3 确实较差，但这没有识别“复杂造成质量差”的因果关系。

来源：根据当时运行日志提取的冻结时间快照；重复执行会生成新的时间快照，不应与本文冻结数值混用。

### 2.2 三次超时是终止性错误，不只是计算比较重

| candidate_id | 算子 | 实际评价耗时 | 从代码确认的问题 |
| --- | --- | ---: | --- |
| 120 | Refine | 120.13s | 返回 depot 后把 `visited` 清成 `{0}`；在容量不足以容纳全部需求时，一直丢掉已服务客户的全局进度 |
| 121 | Pivot | 120.14s | `while remaining.size > 0` 中从未更新 `remaining` |
| 217 | Refine | 120.06s | `_build_edges` 的 `while customers` 中只删除局部 `rem`，不更新外层 `customers` |

候选原文已从日志核查确认（candidate 120、121、217）。例如第一个训练实例总需求为 253，车辆容量为 50，candidate120 不能在清空 visited 之前访问完所有客户。

这三次合计约 360 秒，不是整个生成流程变慢的主要来源，却是明确可修复的失败模式。把它们统一标成“复杂度高”会选错干预：需要的是正确的单调进度与终止逻辑、可定位的 timeout 反馈，而非单纯压缩代码。

当前失败代码不入有效节点档案，其 timeout 也不出现在形成历史中。因此模型没有从这条信息通道看到“这个具体实现曾经超时”；仅添加成功节点时间仍不能解决该问题。

### 2.3 较复杂的有效代码，其函数成本到底有多大

辅助计时直接运行已存档函数，使用同一 10 个训练实例（50 客户），每个函数预热一次后测量三次。下表为三次合计 wall time 的中位数，含传参拷贝和有限矩阵检查；不运行 ACO、不调用 evaluator/LLM，不计入正式评价预算。它是有限样本的函数成本诊断，不是跨规模复杂度证明或受控端到端基准。

| 代码 | 原记录路长 ↓ | 代码字符数 | 10 实例的函数时间 |
| --- | ---: | ---: | ---: |
| rep2 node363 | 8.9458 | 2894 | 4.67ms |
| rep3 node158 | 9.1933 | 2969 | 14.57ms |
| rep3 node194：加入路线构造与 2-opt | 9.1985 | 6074 | 15.94ms |
| rep3 node197：简化方案 | 11.2232 | 1832 | 8.34ms |

根据计时与原代码核对：candidate241 与 node194、candidate244 与 node197 分别逐字相同。node194 的代码约为 node158 两倍长，但测到的函数时间仅小幅增加；它改善了本次两位输入的质量，却没有超过当时的全局 best。node197 则说明简化并不自动带来更好质量。

**数十毫秒的 prior 构造，不能解释数十秒的 evaluator 或 LLM 耗时。** 当前评价还包括 10 个实例的 ACO、spawn worker 的启动/import、进程调度与收尾。生成的 prior 也会影响 ACO 所构造路线的长度和工作量，所以不能反过来假定所有 ACO 时间都是与算法无关的常数。

诊断脚本首次用包含 imports 的 5 秒外层保护，产生了伪辅助超时；独立调用确认是重依赖导入耗时后，改为 spawn 与 20 秒启动保护。上表均取随后成功完成且不含导入时间的三次函数计时；辅助超时未被当作正式算法超时或性能证据。

## 3. MEoH 到底支持什么

详细原文与作者实现核查另见 MEoH 阅读笔记。依据为 [论文 v2](https://arxiv.org/html/2409.16867v2) 主文、附录、作者代码，而非方法名称的推断。

MEoH 把质量和求解时间组成双目标，在选父和种群截断时使用 Pareto 支配与 AST 相似性；非支配节点的 dominance-dissimilarity 分数相同。当前作者代码测 BPP 完整装箱、TSP 完整 GLS 的耗时，不能等同本项目的外层 evaluator wall time 或一次 prior 调用时间。[作者 BPP 评价器](https://raw.githubusercontent.com/Optima-CityU/LLM4AD/main/llm4ad/task/optimization/online_bin_packing_2O/evaluation.py)、[作者 TSP GLS](https://raw.githubusercontent.com/Optima-CityU/LLM4AD/main/llm4ad/task/optimization/tsp_gls_2O/gls.py)。作者当前代码与论文实验快照也存在设置差异。

论文证明的更强结果是更好的质量—时间折衷，单目标质量有赢有输：TSPLIB≤200 的 gap 从 EoH 0.093% 降到 MEoH 0.018%；随机 TSP1000 则从 2.524% 升到 4.208%。§5.3 比较多目标选择器的 HV/IGD，不能单独证明“只添加时间目标就改善最终 fitness”。此外，附录 prompt 与作者当前 prompt.py 没有父代 fitness/runtime 数值字段，所以它并未验证丰富数值上下文的独立收益。[主文结果与消融](https://arxiv.org/html/2409.16867v2#S5)、[作者提示代码](https://raw.githubusercontent.com/Optima-CityU/LLM4AD/main/llm4ad/method/meoh/prompt.py)。

## 4. 为什么辅助目标仍可能改善单目标搜索

以下是机制推论，尚未在 TraceAAD 实验确认。

**当前 fitness 不等于未来改进潜力。** 一个略差但结构简洁、成本低的算法，可能是容易继续修正的出发点；一个复杂的当前最好算法可能难以继续改动。若只看即时质量，前者虽被保存在全档案，却可能几乎没有扩展机会。成本维度可能保留另一批有效起点，后续 Refine 或 Fuse 再补回质量。

这不是“快 ⇒ 有潜力”的定理。低成本也可能只是删除有效算法步骤；MEoH 附录自身出现了近似空操作的最快端点。辅助目标改变搜索偏好，既可能增加新路线，也可能把预算送给无价值的简单方案。

必须区分两种可能收益：

1. **固定 1000 次评价**：若 best fitness 改善，原因必须来自不同生成/分配带来的搜索路径改变；不能归功于“快所以多评了候选”。
2. **固定墙钟或 LLM 成本**：更低实际总成本可能允许更多尝试，但这是另一个预算问题。当前 CVRP 的函数级毫秒优化，对以 LLM 秒级时间为主的总成本帮助可能很小。

因此“多目标辅助单目标”是值得验证的搜索机制，不是一个已由 MEoH 给出的普遍规律。

## 5. 我推荐怎么改

### 5.1 先把三个时间分清，再决定哪一个进入选择

- `t_generate`：LLM 调用时间及输入/输出 tokens，用于研究成本与服务诊断。
- `t_prior`：生成函数在固定输入上的成本，用于定位复杂度与实现问题。
- `t_solve`：在固定求解工作量下，包含 prior 与 ACO 的核心求解成本；排除服务排队、进程启动和 import 等外层开销。它更适合借鉴 MEoH 的时间目标。

现有 `eval_seconds` 继续保留作为评价开销，但不能未经拆分和噪声校准就拿来作精确 Pareto 排序。对 CPU 任务可同时采集 worker CPU time 与 wall time；固定线程、实例和工作量，以交错参考算法计时得到归一化成本。时间差低于实测波动范围时按近似持平处理。并行线程/CPU time 的汇总口径也要固定，不能跨不同硬件或 worker 数直接混合。

下一批评价内部顺手记录时间，不需额外真实 evaluator 调用。若专门重评旧算法来校准时间，必须计为单列辅助预算，不能偷偷补入正式 1000 次预算或漏报成本。

### 5.2 上下文多给可行动的事实，仍保持紧凑

首发只建议把**质量、归一化求解成本、父子变化**写到当前/donor与形成事件中；`t_prior` 占比只在帮助解释瓶颈时提供。示意格式，不是实际测量数据：

```text
Quality: <route length; lower is better>
Solve cost: <measured ratio to a fixed reference; lower is better>
Parent -> child: quality <change>; solve cost <change>
```

任务契约补充真实调用频率和执行上限。算子保持“质量优先，在质量相当时偏好成本更低；有收益依据时允许增加计算”的软指引。这样模型可以判断额外计算是否兑现为质量，而非机械追求短代码。

对终止性失败，优先改善错误定位与现有评价超时保护；如果要反馈失败，只给同一父代的最近一条**已定位**失败事实，并把它作为独立开关验证。普通 timeout 只能证明到时未完成，不能自动写成死循环。本次三个例子是经人工代码核查后才能给出更具体原因。不能把全局失败库重新塞回每条 prompt。

暂不将代码长度、AST 大小、模型自评复杂度、所谓新颖性都设成额外优化目标。它们与真实算法价值/成本的对应关系弱，而且会增加选择自由度和注意力负担。代码长度/token 成本可以继续作为观察量。

### 5.3 分配采用质量主通道与小份额质量—成本前沿

建议先保留 R/P/F=50/15/35、完整档案、现有次数修正和 Pivot 宽起点，仅在 R/F 选父中加入一个小辅助通道：

$$
p_{RF}(n)=(1-\eta)p_0(n)+\eta p_F(n),\qquad \eta=0.20\ \text{作为待验证初值}.
$$

其中 F 是上下文可用、质量至少达到该路最优初始根、且在质量最大化/可信求解成本最小化上非支配的候选；相同质量和计时容差内的重复点只选一个代表参与辅助通道。`p_F ∝ 1/sqrt(parent_count+1)`，在这些代表上归一化；无可信前沿时回退 p0。父节点最终仍只计数一次。

这里的初始根质量门槛用于避免极快但很差的空操作长期占据辅助通道；它不是已识别的最优阈值，也可能排除有潜力的低质量路线。那些节点仍留在全档案，原有 Pivot 均匀分支保留其探索机会。20% 也只是简单的实验先验，最小对照是 0 与 0.2。

第一轮不同时改变 Fuse donor top-5、算子概率、根生成和种群裁剪。最终交付仍从全档案选择 best fitness，时间在预先约定的质量持平范围内作次级比较。这样可以回答“辅助成本目标是否改善质量搜索”，而不是悄悄把最终研究目标改成 HV。

这一建议借鉴 MEoH 的效率路线保留思想，并不照搬 DD 或 NSGA-II。TraceAAD 已经保留全档案，主要缺的是**给哪些不同路线继续分配机会**，无需为了多目标重建一套复杂种群系统。

## 6. 怎样证明它有没有用

最小可解释矩阵是 2×2，而不是只跑一个同时改所有模块的新版本：

| 实验臂 | 简短质量—时间反馈 | 质量—成本选父 |
| --- | --- | --- |
| A | 无 | 无 |
| B | 有 | 无 |
| C | 无 | 有 |
| D | 有 | 有 |

共同使用有一致计时边界的评价器；其余机制固定。CVRP 可先做四臂 × 三重复的定位实验，但只能回答 CVRP；声称通用收益仍需五任务。每臂固定 1000 次真实评价。共同根对照中，每臂都实际评价并计费，另用独立 Init 验证端到端效果；不能拿共享根实验回答初始化问题。

主指标：共同评价预算下的 best fitness、重复分布、最终 held-out 质量；辅助指标：求解成本前沿、达到预定质量阈值的时间、LLM tokens、失败和超时比例、辅助通道产生的后代/前沿贡献。held-out 仅作最终评估，不把其结果反复反馈到搜索上下文。

如果只有墙钟变好而同 1000-eval fitness 不变，应说效率改善；如果只有 HV 变好而 best fitness 下降，应说折衷集合改善。只有 B/C/D 对 A 的对应受控比较，才能分别支持“信息有用”“分配有用”及其交互。

**当前最优先的问题不是继续增加提示条款，而是让测量对准算法成本，并把少量可靠反馈接入生成与分配。** 当前正式 V10.5 保持原机制继续完成，避免正在进行的重复混入另一套目标定义。
