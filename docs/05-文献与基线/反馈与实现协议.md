# 反馈与实现协议

生成协议决定模型需要完成多少额外工作，反馈协议决定一次失败能留下什么经验。适合 TraceAAD 的接口应让模型集中设计算法，让宿主负责模板、代码提取与运行环境；真实执行结果再进入搜索和修复。

## 设计对象与输出格式

固定任务中的启发式函数、完整求解器和算法集合是不同设计对象。输出一整段 Python，并不意味着搜索空间已经扩展到整个求解器：EoH/MEoH 的函数可以被提取后嵌回任务模板，FunSearch 也围绕固定骨架开放函数槽位。讨论自由度时，应看哪些计算允许改变。

完整代码易于表达结构变化；精确编辑能保留宿主代码并减少无关重写。AlphaEvolve 的 SEARCH/REPLACE 提供了后一种方式，也允许适合整体重写时输出完整代码。两者适合不同改动粒度，TraceAAD 可以把完整代码作为默认、编辑作为可选形式。

接口应只有少量明确接受路径。一个唯一 Python 块通常已足够承载候选；额外 JSON 字段、动作封装和往返读取会增加格式协调成本。应分别观察合法程序拒收、歧义接受与真实算法质量，决定是否增加协议结构。

## Idea 的作用是提出和说明设计

Idea 可以帮助模型组织计算规则、说明关键参数和提出改动方向。它适合作为意图记录；代码和执行反馈则给出这次尝试实际上发生了什么。后续上下文可以把三者放在一起，保留有意义的差异。

第二次摘要调用能纠正部分公式，也可能把错误解释写得更流畅。V10.6 的配对检查因此把问题推向了“摘要应该表达什么”：优先保存具体计算及其相对父代变化，少做没有计算落点的自我评价。MCTS-AHD 的二次摘要与 AlphaEvolve 的编辑机制也服务于不同环节，不能据此把摘要校对变成每次生成的必经步骤。

Idea 的长度应随表达需要而定。统一短上限方便控制成本，却可能截断复合算法；长说明则可能重复任务背景。更有用的要求是写清主决策、关键计算和有意义变化。先比较简短说明、按需说明和无说明，再决定硬性长度限制。

## 失败怎样变成下一次生成的材料

| 反馈 | 说明了什么 | 可采用的后续动作 |
|---|---|---|
| 解析失败 | 响应未形成明确、可接收的候选 | 确定性提取与接口检查；必要时一次格式修复 |
| 运行异常、超时、非法返回 | 候选未完成任务要求 | 给出报错位置、接口条件或时限，进行有界修复 |
| 有效但质量下降 | 本次算法改动在评价集上退步 | 保存父子计算差异，供继续开发或换向 |
| 重复代码 | 再次提出已知程序 | 单独记录，并按重复策略决定是否再评价 |
| 基础设施故障 | 本次没有得到可信的候选评价 | 修复设施并按预算规范结算 |

反思、修复和重采样改变候选生成分布。ReEvo 侧重从质量差异提炼改进意见；带错误反馈的调试器侧重恢复可执行性；简单丢弃则把预算继续交给其他提议。选择哪一种，应看失败是否包含可操作信息，以及修复是否比重新生成更划算。

一次有界修复是值得保留的简洁起点：向模型给出失败程序和具体错误，尽量保留原算法意图；修复后再次运行，仍失败就结束。连续多轮修复可以作为另一个明确实验变量。

## 评价预算与生成成本

文献的计数单位包括模型调用、候选生成、实际评价以及有效评价。比较方法时先统一单位，再讨论效率。TraceAAD 中，解析阶段未进入评价的请求只计生成成本；候选自身导致的执行失败计入搜索评价预算；确认的基础设施故障单独结算。

重复代码与解析错误也应分开：前者可能是合法候选，是否跳过评价取决于去重规则；后者尚未形成可评价对象。预算不计入某项，并不意味着它没有消耗模型调用和时间。

## 对 TraceAAD 的研究选择

近期优先把协议负担降下来，稳定保存“父代—意图—代码变化—执行反馈”。再用同一批响应离线比较解析接受范围，以少量配对生成比较完整代码与编辑、短 Idea 与按需 Idea。离线解析可以回答哪些合法程序被拒收；算法质量仍需要真实评价。
