# 顶会顶刊论文写作指南

**好的研究论文会让同行对一个值得关心的问题有更清楚的认识，或获得一种以前没有的解决能力。** 它可以提出方法，也可以揭示现象、证明性质、建立基准或解决重要应用问题。判断它的价值，要看它解决了什么、相对已有工作推进了什么，以及论文能否让读者相信这些结论。

这份指南写给正在做研究的人，重点是如何判断想法、理解不同社区的读者、组织论文论证。文中的例子偏向大语言模型（large language model，LLM）驱动的自动算法设计，也可以迁移到其他机器学习与优化研究。会刊和轨道的规则会变化，投稿时要核对对应年份的官方说明。

## 1. 什么样的 idea 值得做

### 1.1 先看它改变了什么

评价一个想法时，可以先不看方法有多少部件，问三个问题：**它面对的问题为什么值得解决？和最接近的工作相比，它让我们多理解了什么，或多解决了什么？如果它成立，谁的判断或做法会因此改变？**

例如，“给演化搜索加一份记忆”是一个方法描述。进一步追问，才可能得到研究问题：搜索淘汰了一个候选之后，这个候选留下的尝试是否仍对后续设计有用？保留这些信息是否比只保留当前最好实现更有帮助？这里的关键不在“有没有记忆”这个名字，而在**候选的当前质量与其历史信息的参考价值，是否需要区别对待**。

这种区分可以引出有意思的假设，但不能单靠表述成为发现。还要看这种情况是否真实存在，所保留的信息能否改变后续生成，以及改变是否改善完整搜索。若结果只支持其中一部分，论文就围绕已支持的部分展开。

好的 idea 不一定宏大。它可能是一个很具体的判断：某个流行设计在特定条件下并不必要；一个简单对照揭示了复杂方法真正受益的部分；或一个应用中长期未解决的约束，让现有方法必须改变。**问题的影响可以局限在一个专业社区，但应当让这个社区的人关心。**

### 1.2 几种不同的研究贡献

这些路径没有固定排名。它们的说服力来自不同的地方。

| 贡献类型 | 读者可能带走什么 | 论证重点 |
| --- | --- | --- |
| 新的问题或视角 | 原来可以用另一种方式理解问题，进而考虑不同的解法 | 新视角与已有表述有何区别，它是否带来新的预测、方法或分析 |
| 新的方法或机制 | 有一种更有效的办法处理明确的问题 | 方法如何作用，在什么条件下优于有竞争力的替代方案 |
| 实证发现或负面结果 | 关于已有方法的一个重要判断需要更新 | 比较是否足以排除主要替代解释，结论能推广到哪些设置 |
| 理论结果 | 一个性质、界或不可能性，在清楚的假设下成立 | 证明是否正确，假设与结论是否有意义，结果相对已有理论推进了什么 |
| 应用、系统或能力 | 一个重要任务以前难以完成，现在有了可行解法 | 任务与评价是否贴合实际需要，方案是否在真实约束下有价值 |
| 数据集、基准或工具 | 社区有了更好的材料或方法来研究某类问题 | 它揭示了什么现有评测看不到的问题，其他人能否可靠使用 |

例如，[NeurIPS 2026 的审稿指南](https://neurips.cc/Conferences/2026/ReviewerGuidelines)明确区分理论、应用驱动、概念与可行性、负面结果等贡献类型。理论论文可以由理论结果独立成立；应用论文也可以通过恰当组合已有方法解决真实问题。各类工作都需要与其主张相符的论证，但不需要套用同一种实验清单。

### 1.3 简洁是优点，组合也可以有创造性

一个简单设计如果抓住了关键问题，读者更容易理解，也更容易知道它何时值得使用。但“简单”不是要求每个部件都不可删除，更不是要求一篇论文只能有一个实验。必要的复杂性可能来自任务约束、系统可靠性或理论条件。应该追问的是：**每个重要设计解决了什么问题？去掉它会失去什么？额外复杂度换来了什么？**

组合已有方法也可能是好研究。价值可能来自发现两种方法能解决彼此的限制，或根据新任务约束设计出原来没有的组合。真正薄弱的是只列出“A 加 B”，却说不清为什么这样组合、相对直接替代方案有什么收获。[ICML 2025 的审稿说明](https://icml.cc/Conferences/2025/ReviewerInstructions)和 [NeurIPS 2026 的审稿指南](https://neurips.cc/Conferences/2026/ReviewerGuidelines)都将有理由的新组合列为可能的原创贡献。

同样，“以前没人做过”不是价值本身，“事后看起来很自然”也不能单独证明原创性。要回到最接近的工作，比较研究问题、关键做法和实际结果。

### 1.4 怎样发现并检验一个想法

值得追下去的想法，常常从一个具体的不协调开始：为什么相似条件下结果差别很大？为什么加入更多历史信息反而没有改善？为什么分数暂时较低的方案后来能产生更好的后代？这些现象先指向问题，不自动说明原因。

接下来提出两个最可能的解释，想一个会让两者产生不同预测的对照。例如，同样保留历史时，一种方法只给模型完整代码，另一种方法还提供由尝试结果凝练的说明。如果后者表现不同，可以研究这份说明的作用；如果两者都优于无历史版本，也可能主要是历史本身起作用。

做完局部对照，还要问它是否改变完整搜索。固定搜索状态的比较能帮助判断某次生成受什么信息影响；只有让方法在相应预算下完成独立搜索，才能比较最终搜索表现。两类问题有关，但回答的不是同一件事。

## 2. 从几篇论文看不同的立意

下面先说论文做了什么，再说可以怎样理解其吸引力。后面的解读是研究者视角下的分析，不是对当年审稿人理由的断言。示例改写是为了说明表达差异，并非论文原文。

### FunSearch：把研究对象从答案转向生成答案的程序

[FunSearch](https://www.nature.com/articles/s41586-023-06924-6)把语言模型生成、程序执行评价和种群搜索结合起来，寻找能构造问题解的程序。论文报告了极值组合学中的 cap set 构造结果，也在在线装箱问题上测试了所发现的启发式。

一种缺少重点的介绍是：“我们用大模型生成代码，再用演化算法优化。”更有解释力的介绍是：**当答案容易评价但难以直接构造时，可以搜索生成答案的程序，并用评价反馈逐步改进这些程序。** 这样读者更容易理解为什么搜索对象、评价器和程序库需要一起出现。

这里值得学习的是问题表述与结果之间的联系。论文并没有发明程序搜索或演化计算；它把已有思想与语言模型结合，并用具体发现展示了这条路线能做什么。论文中多个系统设计共同参与了结果，也不能仅凭整体成绩断定某一个部件是全部收益的来源。

### EoH 与 ReEvo：让已有领域问题找到新的表达

[EoH](https://proceedings.mlr.press/v235/liu24bs.html)同时使用自然语言描述的启发式思路和可执行代码来组织演化搜索。论文在三个组合优化问题上比较了生成的启发式。介绍这项工作时，“用 LLM 和演化算法”只说了工具；“让算法设计思路与代码一起参与搜索”更直接地点出其表示方式。

[ReEvo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/4ced59d480e07d290b6f29fc8798f195-Abstract-Conference.html)将语言模型用于超启发式（hyper-heuristics），并通过反思生成指导后续演化的文字。作者用“语言梯度”（verbal gradients）描述这种指导，并在多种算法类型和组合优化任务上报告了结果。这个比喻帮助读者理解信息如何反馈；它本身不意味着反思等同于数学梯度，也不自动证明每条反思的因果作用。

这两篇论文都能放进更早的自动算法设计和演化计算脉络。它们的表达把读者引向不同问题：EoH 关注**如何表示和演化设计思路**，ReEvo 关注**如何利用评价反馈指导后续设计**。比较相近工作时，指出这样的差别比说“我们也是 LLM 加演化”更有帮助。

### MCTS-AHD：让搜索选择的假设显形

[MCTS-AHD](https://proceedings.mlr.press/v267/zheng25o.html)使用蒙特卡洛树搜索（Monte Carlo tree search，MCTS）组织生成的启发式。作者关注的是：如果主要根据当前得分保留候选，暂时表现较弱但后续有潜力的方案可能得不到充分开发。论文用树搜索探索这些方案，并报告了多个任务上的搜索结果。

它的切入点比“把 MCTS 用于启发式设计”更具体：**当前得分是否足以衡量一个候选继续开发的价值？** 这使读者能够理解树搜索要解决什么。与此同时，这个动机针对作者讨论的搜索设置；不能把所有种群方法都概括成只按当前得分淘汰，也不能只凭整体对比证明每次收益都来自保留低分节点。

### 简单基线也能提出重要问题

[PPSN 2024 的一项比较研究](https://arxiv.org/abs/2407.10873)考察了语言模型与演化搜索在自动启发式设计中的作用，设置了简单的 `(1+1)-EPS` 基线，并统一比较多种方法、问题和模型。它要回答的问题不是“再提出一个更复杂的框架”，而是：**搜索本身贡献了什么？已有复杂方法相对简单搜索究竟前进了多少？**

这类工作的价值来自比较改变了读者对领域进展的判断。具体结论仍属于论文测试过的模型、问题和预算，不能概括成“简单搜索总是足够”。

## 3. 审稿人会怎样判断一篇论文

审稿人通常需要先理解论文在解决什么，再判断它相对已有工作的价值，以及最重要的结论是否可信。可以把这些判断归成四个问题：

- **做了什么：** 研究问题、方法或发现能否被准确概括？
- **有什么新意：** 与最接近的工作相比，具体多了什么？
- **为什么值得关心：** 这个推进对相关社区的研究或实践有什么意义？
- **为什么相信：** 理论、实验或实际结果是否足以支撑论文所说的话？

这些问题不是统一的打分公式，但与官方评审维度相近。以 [NeurIPS 2026](https://neurips.cc/Conferences/2026/ReviewerGuidelines) 为例，评审关注质量、清晰度、意义和原创性；[ICML 2025](https://icml.cc/Conferences/2025/ReviewerInstructions)要求审稿人讨论主张与支撑、原创性、意义和清晰度。[ICLR 2026](https://iclr.cc/Conferences/2026/ReviewerGuide)也明确说明，没有达到最佳指标本身不足以构成拒稿理由。官方标准是制度要求，实际评审还会受到领域背景、理解和判断差异的影响。

### 帮读者抓住论文，也帮读者检查论文

审稿人需要理解并概括论文。标题、摘要、引言和主要图表因此值得反复打磨：它们应该让熟悉领域但不了解这项工作的人，知道问题是什么、方法或发现是什么、结果意味着什么。读者理解之后，还需要能在正文找到足够材料，检查关键方法、证明和实验。

一篇论文即使没有明显错误，也可能让人觉得增量有限：例如，指标有所提高，但与最接近的简单方法相比缺少清楚的差别；或者提出了一个新名词，却没有带来新的判断。相反，一个明确、有分量的发现，即使没有提出新模型，也可能使读者愿意认真讨论。

讨论阶段，有审稿人清楚理解并认可论文价值，通常有助于讨论。作者能做的是让价值和关键论证容易被准确复述，而不是把“必须有一位 champion”当成录用规则。评审分歧也真实存在：[NeurIPS 2021 一致性实验](https://blog.neurips.cc/2021/12/08/the-neurips-2021-consistency-experiment/)中，882 篇重复审稿的投稿有 23.0% 得到了不同的接收或拒绝建议；以第一组接收的论文为分母，50.6% 在另一组得到拒绝建议。这两个数字的分母不同，不能互相替代。

### 哪些疑问最影响判断

研究者通常会特别在意以下几类问题：对比是否遗漏了会改变结论的近邻方法；方法是否获得了更多预算或更有利的条件；理论假设是否遮住了实际困难；论文声称的原因能否从实验中区分出来；结论是否超出了研究范围。

不是每项工作都需要回答所有问题。重要的是找到**会改变本文主要判断的那几个问题**。一篇以新理论为主的文章，其关键可能是定理和假设；一篇方法论文可能要解决基线和成本问题；一篇实证论文则可能要让读者相信比较足以区分相互竞争的解释。

## 4. 不同社区的读者关心什么

会刊不是互不重叠的几种口味。下面是选择读者和组织论证时可用的观察，不是录用规律。同一个会议内部有不同领域和轨道；具体论文仍要由对应专家评价。

### 4.1 机器学习与演化计算：从谁的问题出发

| 场合 | 可能首先引起兴趣的问题 | 对作者的启发 |
| --- | --- | --- |
| **NeurIPS / ICML / ICLR** | 这个方法、发现、理论或资源，是否推进了机器学习读者关心的问题？ | 解释清楚研究对象与 ML 问题的联系；根据贡献类型选择理论、实证或应用论证。机器学习会议也重视严谨的优化实验。 |
| **TEVC / ECJ** | 对演化计算或优化算法，我们获得了什么新的方法、理解或能力？ | 让演化计算读者看清搜索机制，与相关算法比较；实验范围、随机性、代价和分析深度应与主张相称。TEVC、ECJ 是期刊。 |
| **GECCO / PPSN** | 这个想法与遗传编程、演化优化、搜索分析或相关应用有什么联系？ | 先选合适的社区或专题，再突出关键问题与结果。它们是会议，也接收理论、方法、分析和应用等不同类型工作。 |
| **AAAI / IJCAI** | 这个工作对 AI 中的搜索、推理、规划、学习或其他具体问题有何推进？ | 让广义 AI 读者理解任务和技术贡献；对相关领域基线与问题定义同样要认真。 |
| **ACL / EMNLP，CVPR / ICCV / ECCV** | 对语言或视觉领域的具体问题、模型、数据和评价有什么帮助？ | 把实际任务、领域相关工作和评测设计讲清楚，按论文贡献选择定量、定性或理论分析。 |
| **KDD** | 对数据挖掘或数据科学中的研究问题或实际应用有何价值？ | 区分研究、应用等轨道：实际约束与部署价值可能是应用论文的重点，不是所有 KDD 论文都要展示部署。 |
| **COLT、JMLR、TPAMI、AIJ、TNNLS 等** | 与各自领域及读者的问题是否匹配？理论、方法或应用贡献是否扎实？ | 按具体会刊的范围和论文类型判断。COLT 是偏学习理论的会议；其余列举的名称是期刊，彼此关注点也不相同。 |

例如，[GECCO 2025 征稿](https://gecco-2025.sigevo.org/Call-for-Papers)同时涵盖理论、遗传编程、组合优化、机器学习和应用；[AAAI 2026 主轨征稿](https://aaai.org/conference/aaai/aaai-26/main-technical-track-call/)面向广泛的 AI 研究；[KDD 2026](https://kdd2026.kdd.org/papers/)区分研究与应用数据科学等轨道。这些范围说明社区关心什么，并不证明每篇论文都必须符合表中的某一种风格。

对同一项 LLM 算法设计研究，面向 ML 读者，可以先解释迭代生成与反馈信息的问题，以及结论对哪些相近任务可能有意义。面向演化计算读者，可以先解释候选如何选择、搜索如何分配、它与已有种群或档案机制的关系。

假设一项研究要考察被淘汰候选留下的信息，两个入口可以这样组织：

- **面向 ML 读者：** 迭代生成能够利用评价反馈，但评价过的尝试如何转化为下一次生成可用的信息，仍是一个具体问题。论文研究某种历史表示是否改善后续生成，并比较完整搜索的结果。
- **面向演化计算读者：** 种群选择决定了哪些候选继续参与搜索，而被淘汰候选的尝试也可能包含有用信息。论文研究这些信息如何在种群更新后被保留，并与相应的选择和档案方案比较。

两个入口强调的读者经验不同，研究和结果仍然相同。这里是示意写法，不预设历史信息已经带来收益，也不意味着其他社区不关心这些问题。

### 4.2 会议和期刊：主要是发表形式不同

会议通常有固定截稿和篇幅约束，作者需要在有限空间内让问题、贡献和关键论证清楚可见。期刊往往更便于展开方法、分析和补充研究，也可能经历修改后再审。不同会刊的篇幅、轮次和处理方式差异很大；期刊同样可能直接拒稿，会议也并非只看故事而不看技术。

选择投稿场合时，先看最相关的近期论文与征稿范围：**谁最在意这个问题？他们会拿什么方法和这项工作比较？我们最有把握的结果能回答他们的什么疑问？** 如果工作最强的是某个受限预算下的性能，就明确这一条件和比较口径；如果最有价值的是一种机制或发现，就把能检验它的研究摆在前面。

## 5. 把研究过程写成论文

### 5.1 先找到论文的中心，再决定从哪里讲起

研究过程常常是试错、修正、回头验证。论文不必照搬这条时间线。读者首先需要知道最终的问题、关键想法和结论，然后再理解它们为什么成立。历史过程只有在帮助读者理解问题或判断结果时才需要出现。

动笔时可以先写一小段草稿：**我们研究什么问题；相比已有工作，提出或发现了什么；最重要的结果是什么；这改变了读者对问题的哪一点认识。** 如果这几句之间接不上，通常需要重新想清问题与结果的关系，而不是先给方法起名字。

“讲故事”是组织已完成的研究，不是替结果编造原因。可以根据结果选择最有说服力的主线，把篇幅留给真正重要的问题；但关键的负面结果、限制条件和最接近的相关工作，不能因为不利于故事就消失。

### 5.2 让主张的力度跟得上研究结果

可以区分三种常见说法：

1. **观察：** 在给定任务和预算下，方法 A 的平均结果优于方法 B。
2. **受控比较：** 在其余指定条件相同的对照中，加入信息 X 改变了结果。
3. **机制解释：** 信息 X 通过某种过程改善了最终搜索。

后两句话需要比第一句更具体的研究支持。受控比较能检验某个改变的作用，但单次消融未必能拆开相互作用，也不自动解释完整因果链；轨迹中出现的相关变化提供线索，也不等于已经证明它造成了提升。

以历史信息为例，在相同状态下比较不同输入，可以研究后续生成是否受历史影响；在完整搜索中比较多次独立运行，可以研究最终效果；分析生成内容和搜索过程，可以进一步寻找作用方式。三者互相补充，不能用其中一个直接替代另一个。

### 5.3 公平比较是为了解释结果

对自动算法设计而言，一次完整搜索的资源不止一种：候选程序评价、模型调用、输入输出 token、评价时间和修复尝试都可能影响结果。不同方法不一定能同时使用完全相同的每一种资源。应先根据研究问题确定主要预算，再交代其他成本；如果某种方法在一个预算下更好、在另一种成本口径下不占优，就把这种关系写清楚。

基线要与研究问题匹配。既要有最接近的有竞争力方法，也要有能检验主要设计是否必要的简单方案。报告独立搜索的重复次数及结果分布；根据问题结构选择合适的不确定性分析和统计比较。测试实例之间的差异不能直接代替独立搜索运行之间的随机性，也不应把某一种检验方法当作所有论文的统一要求。

对于 LLM 驱动的搜索，还要分清训练或开发实例与独立测试实例。新任务、搜索轨迹或跨规模测试可以帮助理解方法，但它们不能单独证明模型预训练时从未接触相关知识。模型服务限流等外部故障，也应与生成、验证或执行失败分开记录。

## 6. 各章节和段落怎样组织

一篇论文可以看作一连串读者会追问的问题：研究什么、为什么值得研究、已有工作做到哪里、本文做了什么、为什么应该相信、结果意味着什么。章节顺序要让这些问题自然衔接。下面以方法论文为主要例子，也说明发现型和理论型论文的变化；每段的作用比段落数量更重要。

### 6.1 先设计整篇论文的阅读路径

动笔前，可以用一页纸写出下面这条路径：

| 位置 | 读者读完后应该知道什么 | 下一步自然的问题 |
| --- | --- | --- |
| 标题与摘要 | 研究对象、主要贡献、最重要的结果 | 这个问题为什么重要，结果是否可信？ |
| 引言 | 领域背景、关键问题、本文思路和结果 | 方法具体如何工作？ |
| 相关工作与问题定义 | 与已有工作的关系，任务和比较条件 | 本文在哪个决策上采取了不同做法？ |
| 方法或理论 | 核心思想、关键步骤或定理及其条件 | 这个做法有效吗，性质如何成立？ |
| 实验或证明 | 主要结果、关键对照、必要分析 | 结果说明了什么，又适用于哪里？ |
| 讨论与结论 | 最重要的认识、边界与意义 | 读者可以怎样使用这些认识？ |

相关工作可以放在引言后，也可以放在方法和实验后；问题定义可以单列，也可以放在方法开头。篇幅紧时，某些部分可以合并。决定位置时，先看读者需要什么背景才能理解下一步。

**一个段落通常推进一个主要判断。** 可以先交代本段关心的问题，再给出事实、推导、方法步骤或结果，最后解释这一步与论文主线的关系。并非每段都要有固定的主题句或结尾句；如果相邻段落在回答同一个问题，就检查它们是否重复，或是否应按“问题—原因—解决思路”分工。

### 6.2 标题与摘要

**标题**让读者识别研究对象和贡献。方法名可以帮助检索，但不应让名字取代信息。可以突出解决的问题、方法的关键思想或主要发现，选择哪一种取决于论文最值得被记住的内容。

**摘要**是一段能够独立阅读的短论证。方法论文常用以下逻辑：

1. 用一两句交代任务及真正相关的困难。
2. 说明本文的关键想法和方法，避免罗列所有部件。
3. 说明在什么任务或条件下得到什么主要结果，给读者一个可以理解的比较对象。
4. 在结果支持的范围内说明意义；如果最重要的是一个发现，可以把发现提前。

摘要中的结论要与正文的评价口径一致。例如，“在固定程序评价预算下提高最终质量”与“降低总计算成本”是两种不同的说法。如果只测量了前者，就不要用后者代替。理论摘要则应说明关键定理、主要假设及其意义，而不必套用方法论文的实验句式。

### 6.3 引言：用六步建立论证

以下是原有的六步框架。每一步都回答一个读者的问题；段落可以合并、拆分或调整顺序。

| 步骤 | 这一段的任务 | 内容如何推进 | 常见偏差 |
| --- | --- | --- | --- |
| **1. 研究背景** | 为什么关心这个任务？ | 介绍任务及与本文有关的核心困难，尽快收束到具体问题。 | 花大量篇幅介绍领域热度，却没有引出本文任务。 |
| **2. 研究现状** | 现有方法做到哪里？ | 概括与本文最相关的思路及已有进展，说明它们如何处理这个问题。 | 按发表时间堆论文名，或把已有方法全部写成失败案例。 |
| **3. 现有局限** | 还有什么问题没有解决？ | 指出具体条件下的困难及其后果；如果原因尚待验证，把它写成问题或假设。 | 仅说“前人没有用 X”，或把部分方法的限制扩展到整个领域。 |
| **4. 核心洞察** | 为什么可以换一种做法？ | 解释一个关键区分或观察，以及它为何指向新的解决思路。 | 把方法部件提前换个名字复述一遍，没有解释新认识。 |
| **5. 方法概述** | 本文实际做了什么？ | 介绍主要机制，连接前面的洞察；保留读者理解方法所需的关键步骤。 | 用大量缩写和操作细节淹没核心思想。 |
| **6. 贡献与结果** | 我应该记住什么？ | 总结具体贡献及最有分量的结果，写清结论成立的条件。 | 把做过的实验数量当成贡献，或提出正文无法支持的结论。 |

例如，假设论文研究“被淘汰的搜索经历是否有助于后续算法生成”，可以这样安排六个段落：

1. **背景：** 自动算法设计在有限评价预算下，反复生成并评价候选程序。
2. **现状：** 一些方法根据评价结果选择候选，再利用保留的程序生成新候选；已有工作也探索了历史信息和反馈的作用。
3. **问题：** 一个候选即使不再适合继续开发，围绕它形成的尝试仍可能包含对后续设计有用的比较。哪些信息值得继续使用，是一个需要检验的问题。
4. **洞察：** 候选作为开发起点的价值，与其尝试作为参考信息的价值，可以分别考虑。
5. **方法：** 介绍如何组织候选及其经历，并在更新候选时处理这些信息。
6. **贡献与结果：** 说明实际完成的方法和实验，再报告已经观察到的结果及其条件。

这是一段**示意结构**，不预设该假设已经成立，也不代表已有方法都丢弃历史。写实际论文时，第 2、3 段必须根据最接近的文献和真实观察改写，第 6 段只能填写已完成的结果。

其他类型的引言可以改变起点。**发现型论文**可以先提出一个已有领域判断，再展示与之不一致的现象，说明为何需要系统检查；**理论论文**可以先提出明确问题和关键定理，再解释假设、直觉及相对已有结果的推进；**应用论文**可以从真实任务约束及其为何改变方法选择讲起。

### 6.4 相关工作：界定范围、选择论文、组织引用

相关工作（related work）的作用，是让读者知道本文接续了哪些研究，最相近的工作已经做到哪里，本文又具体推进了什么。它需要把自己的研究放进领域脉络，也需要让熟悉近邻工作的读者看到准确的区别。

#### 6.4.1 先从论文的问题出发，划定相关范围

领域里的论文可能很多，但相关性不是看题目里有没有相同关键词，而是看一篇工作与本文在**研究问题、关键决策或所用信息**上有什么关系。可以依次问：

1. 哪些工作解决同一个问题，或回答与本文直接竞争的研究问题？
2. 哪些工作虽然任务不同，但采用了与本文核心机制相近的表示、更新或决策方式？
3. 哪些工作是本文继承的概念、方法、任务、数据或评价方式的来源？
4. 哪些方法是读者理解本文进展时自然会想到的替代方案或比较对象？

由此得到几类文献。它们可以相互重叠，并不意味着正文需要为每类单列一节。

| 文献与本文的关系 | 为什么相关 | 通常怎样处理 |
| --- | --- | --- |
| **直接近邻** | 研究问题和关键机制高度重叠，可能影响本文的定位 | 精读方法与实验；准确比较共同点和关键差异，最重要者也应在引言交代 |
| **替代解法** | 面对相同任务或困难，但采用不同思路 | 说明其解决方式；适合时作为实验基线，不能比较时解释原因 |
| **机制或概念先例** | 提供本文使用或借鉴的重要思想，任务未必相同 | 引用原始来源，并说明共同的机制及迁移后的区别 |
| **相关方法路线** | 与本文共享问题背景，但只涉及部分环节 | 按思路归组，选择有代表性的工作介绍 |
| **任务与评价来源** | 提供使用的数据、基准、指标或实现 | 在问题定义、实验设置或相应方法处标明来源 |
| **宽泛背景** | 同属大领域，但不影响理解本文问题、方法或结果 | 只有在帮助建立背景时才保留，不因热门或高被引而机械加入 |

判断范围时，可以做一次反向检查：**如果去掉这篇文献，读者是否会误解已有进展、误判本文差别，或无法追溯本文使用的重要方法和评价？** 如果答案是肯定的，它通常值得保留。反过来，一篇论文在领域里有名，不自动意味着它对本文有同等重要性。

#### 6.4.2 如何比较两项看似相近的工作

阅读近邻时，先看它实际解决的问题，再拆解方法。下面几个维度尤其有用：

- **研究对象：** 优化的是候选程序、生成过程、提示词、测试实例，还是单个程序内部的代码？
- **表示与信息：** 保存的是当前候选、完整历史、父子关系、文字摘要，还是它们的某种组合？
- **决策与更新：** 何时选择、删除、冻结、压缩或重连？操作改变的是搜索资格、存储结构，还是提供给模型的上下文？
- **经验的使用：** 经验从什么材料形成，存在哪里，后续由谁读取？
- **实验与结论：** 对比了哪些方法、任务和预算？实验直接支持整体效果、局部组件作用，还是作者提出的某种解释？

这一步能避免按术语硬配。比如，两篇论文都使用“树”，一棵树可能表示完整算法的派生关系，另一棵可能表示单个程序的语法结构；两篇都说“剪枝”，操作也可能分别是冻结搜索、删除历史分支或移除不可达代码。术语相近不代表作用相同；术语不同也不代表没有先例。

比较时先承认相同点，再说明差异落在哪个对象或操作上。**方法不同是可以直接描述的事实；某种差异是否带来更好结果，需要由相应分析或实验判断。**

#### 6.4.3 以 EvoTrace 的研究问题为例

假设论文围绕“带经验的树状种群及其动态反思简化”展开，以下工作值得作为起点。它们的作用不同，不能因为都属于 LLM 或演化计算就一笔带过：

| 关注的问题 | 可以先核对的工作 | 引用时应说明什么 |
| --- | --- | --- |
| **LLM 如何参与程序与启发式搜索** | [FunSearch](https://www.nature.com/articles/s41586-023-06924-6)、[EoH](https://proceedings.mlr.press/v235/liu24bs.html) | 前者结合程序库、语言模型和评价；后者将自然语言思路与代码用于演化。它们为任务和方法背景提供位置。 |
| **树、图与候选种群怎样组织搜索** | [MCTS-AHD](https://proceedings.mlr.press/v267/zheng25o.html)、[PathWise](https://proceedings.mlr.press/v306/gungordu26a.html)、[PhyloEvolve](https://arxiv.org/html/2601.14523v1) | MCTS-AHD 用树组织启发式搜索；PathWise 结合推导图与种群；PhyloEvolve 使用演化森林、轨迹摘要和剪枝。这些都是直接比较结构和历史利用时应认真讨论的近邻。 |
| **分支如何分配搜索机会** | [Clade-AHD](https://arxiv.org/html/2602.00549v2) | 它依据分支统计选择与冻结子树。冻结主要改变后续扩展资格，不能仅凭“pruning”一词把它说成路径收缩。 |
| **如何从反馈中形成并复用经验** | [ReEvo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/4ced59d480e07d290b6f29fc8798f195-Abstract-Conference.html)、[RefineEvo](https://proceedings.mlr.press/v306/wu26ap.html) | ReEvo 将反思用于启发式演化；RefineEvo 使用正负经验池和规划。比较时要说明经验产生和使用的方式。 |
| **经验如何跨发展过程或分支保存** | [DeltaEvolve](https://arxiv.org/abs/2602.02919)、[MEMOIR](https://arxiv.org/abs/2605.17539) | 前者组织表示修改及其效果的语义差分；后者设置分支局部记忆和跨分支摘要。二者都应在讨论历史表示与经验转移时核对。 |
| **更早的谱系维护基础** | [Phylotrack](https://arxiv.org/abs/2405.09389)及其[谱系维护代码](https://github.com/devosoft/Empirical/blob/56d1679efa31bb27e013e7910afdd7b94b1587cc/include/emp/Evolve/Systematics.hpp#L1472) | 论文介绍在线谱系跟踪；所链接的固定代码提交包含单子节点收缩。要区分跟踪基础设施与本文的候选选择、反思及经验承接。 |

例如，PhyloEvolve 已经将演化森林、结构剪枝、轨迹和摘要用于代码优化；PathWise 也已结合推导图、种群和反思。因此，“我们用树或图组织搜索”“我们使用历史经验”都不足以概括与这些工作的区别。更具体的比较应落在：**一次种群更新如何确定保留节点、需要整理的历史区域，以及经验由哪个保留位置承接。** 这是对当前设计的描述；这种做法是否改善搜索，要由实验回答。

上表是围绕当前问题挑选的**示例与阅读起点**，不是完整文献清单。示例于 2026-11-14 结合本地调研、PMLR 正式发表页及 arXiv 原文定向核对；例如，PhyloEvolve、PathWise 和 Clade-AHD 的 arXiv 编号分别为 `2601.14523`、`2601.20539`、`2602.00549`。PhyloEvolve、Clade-AHD、DeltaEvolve 和 MEMOIR 的链接指向所核对的 arXiv 版本；发表状态和版本在正式投稿时应再核实。树状结构与剪枝的进一步来源可查[本地调研](记录/2026-11-11-树状种群与剪枝简化的相关工作调研.md)。

#### 6.4.4 文献很多时，怎样从检索走到取舍

先写出本文最重要的研究问题和两三个关键操作，再从已有近邻开始扩展。一次实用的检索过程可以这样进行：

1. **用不同表述搜索同一个问题。** 例如搜索历史利用时，除了 `memory`，还要考虑 `trajectory`、`lineage`、`reflection`、`experience` 等；搜索树结构时，要区分算法谱系树、程序语法树和种群通信拓扑。
2. **从代表作向前追溯。** 查看它的相关工作、方法来源和采用的基准，找到更早的概念与技术来源。
3. **从代表作向后追踪。** 查找引用或扩展它的近期工作，尤其关注与本文研究问题和操作相近的方法；索引可能不完整，可以结合会刊论文集、预印本及作者公开资料交叉查找。
4. **按问题而非标题筛选。** 先看摘要和方法概览；对可能影响定位的论文，继续读方法、实验、消融和必要的公开实现。只读摘要通常不足以判断具体操作是否相同。
5. **整理比较关系。** 对每个近邻记下它解决的问题、关键机制、使用的信息、评价条件、与本文的关系，以及支撑判断的原文位置。保留这些记录，写作时就不必凭印象概括。
6. **在写作和投稿前复查。** 重点检查近邻是否有新版本或新工作，并核对引用版本与元数据。检索过程可以持续更新；普通研究论文的相关工作不需要伪装成覆盖所有论文的系统综述。

没有适用于所有论文的引用数量，也没有“近三年以外都不相关”的规则。一个较早的基础方法可能直接影响本文的定义，近期工作也可能只是共享关键词。篇幅有限时，优先保证最接近的研究和真正承担论证作用的来源得到准确讨论。

#### 6.4.5 一段相关工作怎样写

一段话最好围绕一个共同问题或方法选择组织，而不是依次写“某某提出 A、某某提出 B、某某提出 C”。一个常见的推进方式是：

1. 交代这组工作共同研究什么问题。
2. 归纳主要做法，并在对应事实后引用代表性论文。
3. 对与本文最接近的工作，具体说明其对象、操作或信息范围。
4. 如有助于理解，说明本文关注的具体问题与它们的关系；不必每一段都强行以“然而，现有方法存在不足”结尾。

例如，围绕上面的结构化搜索，可以这样组织一段：

> 一些 LLM 驱动的算法设计方法利用派生结构组织搜索。[MCTS-AHD](https://proceedings.mlr.press/v267/zheng25o.html)使用搜索树选择并发展启发式；[PathWise](https://proceedings.mlr.press/v306/gungordu26a.html)结合推导图与种群，并在生成过程中使用历史信息。[PhyloEvolve](https://arxiv.org/html/2601.14523v1)维护演化森林，对节点、分支和树进行剪枝，并利用轨迹摘要。EvoTrace 关注另一项具体更新：由保留的候选结构确定被移除经历的整理范围和承接位置。

这一段先交代共同问题，再分别说明各项工作的实际做法，最后介绍本文关注的决策。它没有把前人概括为“不使用历史”，也没有从结构差别直接推出性能优势。实际论文还应依据所引用版本和最终设计，对最接近的差异作进一步核实。

#### 6.4.6 引文放在哪里，怎样支持具体表述

| 引用位置 | 引用承担的作用 | 写作要点 |
| --- | --- | --- |
| **引言** | 建立研究背景，交代最接近的已有进展 | 在说明相关事实或方法的句子附近引用；问题陈述与主要差别要能独立读懂 |
| **相关工作** | 展示研究路线、共同点与具体区别 | 按共同问题组织；差异重要时单独说明具体工作，而非把大量引用堆在段尾 |
| **方法与理论** | 标明继承的算法、定义、公式或构件来源 | 在真正使用它的位置引用，并说明本文如何沿用或修改 |
| **实验** | 标明基线、数据、基准、指标和对比结果的来源 | 区分使用官方实现、自行复现和直接引用已发表结果 |
| **讨论** | 将本文发现与已有观察、理论或解释联系起来 | 区分一致或冲突的结果，以及任务和条件的差别 |

例如，采用 BibTeX 和 LaTeX 模板时，可以把引用直接放在它所支持的判断附近：

```latex
LLM-based approaches combine program generation with iterative evaluation
and search \cite{funsearch,eoh}. MCTS-AHD organizes heuristic search in a
tree \cite{mctsahd}, whereas PathWise combines an entailment graph with
population updates \cite{pathwise}.
```

这里第一组引文共同支持“生成、评价与搜索”的概括；第二句分别标明两个方法的具体做法。示例键名对应本项目的 `paper-references.bib`，其他项目要改成自己的键名。数字制、作者—年份制以及 `\cite`、`\citet` 等命令的显示效果由具体模板和引用包决定，不必自行在正文硬写编号。

**一项事实要由真正支持它的文献支撑。** 如果一个句子包含几个不同判断，不要把一组文献统一放在末尾，让读者猜哪些来源支持哪一句。共同陈述确实适用于多篇论文时可以合并引用；方法和结果差别明显时，应拆开表述。

例如，写“这些方法都通过反思压缩被删除的树节点 [A, B, C]”之前，需要确认 A、B、C 是否都做了这些事。如果一篇使用搜索树、另一篇使用经验池，应分别写出各自做法。引用作者的实验结果时，也要保留原论文的任务、对比与评价条件，不能把作者对原因的推测写成已被证明的机制。

引用文献与选择实验基线相关，但不完全相同：概念先例值得引用，却未必能在本文任务上直接运行；适合比较的基线不仅要引用，还需要按照第 7 节说明实现与预算。使用综述可以帮助了解领域，但对关键做法、结果和优先权，尽量追溯原论文或原始实现。

#### 6.4.7 常见问题与最后核对

- **不要把“没有看到”写成“从未有人做过”。** 尤其是树、记忆、反思等宽泛概念，应先核对直接近邻。可以具体说明本文处理的对象和操作，再让读者判断差异。
- **不要为了突出本文抹掉已有进展。** 先说清前人真正做了什么，再解释本文的不同问题；竞争工作也是理解领域的重要基础。
- **不要把论文的命名当成机制事实。** 例如“pruning”可能只是冻结扩展；“memory”也可能指数据库、提示词或参数更新，需要看其定义。
- **不要只引用支持自己的一侧。** 与本文接近但结果不同的工作，可能恰好揭示任务、预算或方法条件的重要差别。
- **检查每条参考文献的身份和版本。** 作者、题名、年份、会刊、页码、DOI 或稳定链接应来自可靠记录；正式发表版本可用时优先核对并按目标会刊格式引用，避免将同一论文的预印本和正式版当成两篇不同工作。

例如，RefineEvo 除了预印本，已有 [ICML 2026 正式论文集页面](https://proceedings.mlr.press/v306/wu26ap.html)。引用时应检查当前文稿的 BibTeX 是否仍只指向旧版本，并根据目标格式更新。引用数量、排序和样式由论文本身和会刊模板决定；关键是读者能找到原文，也能看清每条引文支持什么。

### 6.5 问题定义与预备知识

这一部分按读者理解方法所需的顺序写：任务输入是什么、输出是什么、评价目标是什么、有哪些约束和预算、生成或学习过程能看到哪些信息。若已有标准定义，说明沿用内容和本文改变的条件；若提出新问题，要解释新设定为什么必要。

符号应帮助明确对象和关系。先用自然语言解释，再引入后续会反复使用的记号；一个符号在全文保持同一含义。理论论文还需在定理前交代适用假设；实验论文则要让问题定义与实际评价一致。

### 6.6 方法：让读者知道信息怎样变成决策

一个常见的方法章节可以沿以下顺序展开：

1. **总览段。** 给出方法接收什么、输出什么、核心决策是什么，以及各主要步骤如何连接。方法图可以辅助，但正文也要解释思路。
2. **表示与状态。** 定义方法使用的对象和信息：哪些来自当前候选、哪些来自历史或外部评价，彼此是什么关系。
3. **关键步骤。** 按决策顺序分小节解释。每个小节先说它解决什么问题，再说明输入、处理方式和输出，最后交代与下一步的关系。
4. **整体流程与实现。** 需要时用伪代码或实例串联，并给出关键超参数、计算成本或实现选择；较长的提示词和实现细节可以放入附录。

写某个设计时，不必机械地逐项回答所有问题。重点是让读者看清：为什么需要这一步、它实际做什么、什么内容属于设计动机、什么效果已经过检验。方法部分可以说明预期作用，效果是否出现应交给后文的分析。

理论论文可以使用相似的阅读路径：先解释定理回答什么问题及其直觉，再给出正式陈述、假设、与已有结果的关系和证明思路。技术性证明可依会刊规则放在附录，但正文应保留理解主结果所需的条件。

### 6.7 实验章节：按研究问题组织结果

实验部分的开头让读者知道评价了哪些任务、方法、预算和指标。详细设置可以放入单独小节或附录，但应能在正文找到理解主要比较所需的信息。随后按研究问题组织结果；不必为了形式硬列固定数量的 RQ。

每个结果小节可以按这个顺序推进：

1. **问题与比较：** 要判断什么，比较哪些条件，采用什么指标？
2. **主要观察：** 图表中的哪个变化直接回答了这个问题？先说结果，再解释。
3. **解释与范围：** 最合理的解释是什么？是否存在重要例外、代价或尚未区分的其他解释？
4. **与主线的联系：** 这个结果改变了对方法或研究问题的什么判断？只在需要时引出下一项分析。

例如，“我们研究了经验是否有用，结果见表 3”信息太少。更清楚的写法是：“在相同搜索状态下，我们比较读取真实经验与不读取经验的后续生成质量。表 3 报告各状态上的比较结果；这些结果回答经验是否改变局部生成，但完整搜索是否受益仍需后续实验。”具体方向和数值应在获得结果后填写。

### 6.8 讨论、局限、结论与附录

**讨论**将分散结果放回同一个研究问题。可以先用一段综合主要发现，再用一段比较可能原因或与已有研究的关系，最后讨论哪些条件可能改变结论；内容少时也可以合并。观察、解释和尚待检验的假设需要让读者分得清。与主张相关的反例或代价应在正文出现。

**局限**说明会影响使用或理解结果的条件，例如测试过的任务范围、额外模型成本或尚未检验的机制。它的作用是帮助读者正确判断适用范围；不需要把所有未来工作都列出来。是否单列由论文内容和会刊要求决定。

**结论**通常回到问题、概括本文最重要的成果、说明它带来的认识或能力。不要在结尾第一次引入新实验或正文尚未支持的主张。

**附录与补充材料**适合容纳完整实验设置、额外结果、超参数、提示词、长证明和复现细节。关键假设、主要方法和理解核心结果所必需的条件，应按会刊规定保留在正文。

### 6.9 从研究判断写到英文段落

英文写作时，先确定这一段承担什么判断，再选动词和时态。一个实用顺序是：提出问题或判断，交代支撑它的事实、方法或结果，最后说明其含义。长段落可以按逻辑拆开；短段落也可以服务于一个需要突出的问题。不要为了追求变化，在同一概念上反复更换术语。

以下句子只是表达方式示例，方括号内需要按实际研究填写：

- **提出问题：** *We investigate whether experiences from discarded candidates improve subsequent program generation.* 这句话提出待研究的问题，没有预先宣称经验一定有用。
- **说明比较：** *For each search state, we compare generation with and without the recorded experience under the same evaluation protocol.* 读者能看到比较对象与条件；如果条件并未完全一致，就应具体写出差别。
- **报告观察：** *On [task], under [budget], the proposed method achieves [result], compared with [result] for [baseline].* 任务、预算、指标方向和比较对象应让数字可以被理解。
- **提出解释：** *This pattern suggests that [interpretation] may contribute to the improvement.* 如果只有相关现象，用 `suggests` 等措辞保留解释的性质；若有直接干预，可以明确说明干预检验了什么。

一段结果分析可以由“比较条件—主要观察—对问题的回答”构成，再根据需要补充例外或其他解释。英文段落同样应以准确传递研究为目标，而不是套用固定句数、规定每句的主语，或用强烈形容词替代结果。

## 7. 怎样设计一组有说服力的实验

实验设计从研究问题开始：**如果不同的结果出现，我会怎样改变对方法的判断？** 一组实验不必覆盖所有可能因素，但应能回答论文最重要的问题，并处理会改变结论的其他解释。

下面以方法论文为例。理论或数据集论文同样可以使用“问题—比较—结果解释”的思路，但核心检验可能是证明、数据质量或评价方法，而不是方法排名。

### 7.1 从研究问题走到具体比较

先把宽泛的问题拆成可观察的判断，再决定需要什么对照。

| 想回答的问题 | 需要比较什么 | 结果能告诉我们什么 |
| --- | --- | --- |
| 整体方法有用吗？ | 完整方法与相关强基线、简单基线，进行独立完整搜索 | 在给定任务、预算和实现条件下，最终表现及其变化 |
| 某个设计是否影响结果？ | 完整方法与定义清楚的变体，尽量保持其余条件可比 | 指定改动在该比较条件下产生的整体影响 |
| 信息是否改变下一次生成？ | 从同一批搜索状态出发，改变提供的信息，重复生成与评价 | 给定状态下，输入信息对局部生成结果的影响 |
| 为什么可能有用？ | 结合中间过程分析与能区分竞争解释的干预 | 对作用过程形成更具体的判断，而不仅是描述相关性 |
| 什么时候有效，代价是什么？ | 比较有关的任务、预算、模型或资源口径 | 观察到的适用范围、稳定性及性能与成本的关系 |

先写下论文最想支持的一两句话，再为每句话设计比较。例如：

> **研究假设：** 被移除候选留下的经历，可以为后续程序生成提供有用信息。
>
> **竞争解释：** 提升可能来自更多上下文、更强的提示词、额外模型调用，或另一种候选选择方式。
>
> **需要的研究：** 固定状态下检验提供什么信息会改变生成；完整搜索比较最终效果；记录生成经历、模型调用与程序评价的全部成本。

如果固定状态对照有差异，完整搜索却没有改善，这不是互相矛盾：局部收益可能被后续选择、预算消耗或搜索路径抵消。要先看实际发生了什么，再判断下一步；也不能从一次局部成功直接推出最终搜索收益。

### 7.2 任务、数据与评价对象

**任务怎样选。** 先看论文声称解决哪一类问题，再选择能代表关键差异的任务。例如，算法搜索中不同任务可能具有不同的反馈噪声、程序接口、可行性约束和评价成本。多个同质实例可以检验一个任务内的稳定性，但不能自动代表多个问题家族。不要只把有利任务放进正文，也不要为了凑数量加入与问题无关的基准。

**开发、选择和测试怎样分开。** 研究者用开发数据理解问题、调整实现与选择超参数；最终测试数据用于评价已经选定的方案。自动算法设计还需说明：搜索时使用哪些实例评价候选，如何选出最终程序，最终程序在哪些未用于选择的实例上测试。如果反复查看同一测试集并据此改方法，它已经参与开发，不能再当作独立测试。具体划分取决于任务，不一定都要采用同一种固定比例。[Cawley 与 Talbot](https://jmlr.org/papers/v11/cawley10a.html)讨论了模型选择过程如何导致评价偏差。

**指标对应什么。** 区分搜索过程中的表现、最终选出程序的质量、程序执行效率和搜索成本。目标方向、聚合方式、失败处理及比较时点要一致且明确。例如，按训练分数选出的最好程序，应在相同规则下进行最终测试；不能从所有测试结果里挑出最好的那次再报告为方法的典型表现。

若希望跨任务汇总，先分别报告各任务结果，再解释归一化或排名的含义。不同任务的目标尺度可能差很多；归一化需要说明参考值和计算方式，也要处理参考值为零或不可得的情况。平均排名有助于概览，但会隐藏效果大小和具体失败任务。

### 7.3 如何选取对比方法

基线（baseline）的价值在于回答不同问题，而不在数量多。可从下面几类中选择与论文相关的代表：

| 对比对象 | 它帮助回答什么 | 选择时看什么 |
| --- | --- | --- |
| **最接近的方法** | 相比已有类似思路，本文具体推进了什么？ | 信息来源、搜索机制、任务和模型条件是否接近 |
| **领域内有竞争力的方法** | 相对实际会被采用的方案，本文表现如何？ | 公认强方法或针对该任务有效的近期方法，包含必要的非 LLM 方法 |
| **简单基线** | 复杂设计是否比简单办法更有价值？ | 随机搜索、简单局部搜索、只保留当前最好候选等是否适合任务 |
| **已有方法的适当改进** | 收益是否只是来自一个容易加入的常见技巧？ | 对最相关的简单扩展做合理配置，避免只比较未改进版本 |
| **同框架变体** | 在共同框架内改变某个设计会怎样？ | 作为机制研究的辅助，不能代替与外部方法的比较 |
| **参考值或上界** | 问题还有多大改进空间？ | 人工方法、已知最优或额外信息参考是否可用，是否公平可得 |

选择时先确定最可能改变结论的对手：如果简单基线已经接近完整方法，研究重心可能要转向解释复杂度的收益和代价。如果某个参考方法使用了本文不可获得的信息或更大预算，仍可以展示，但应清楚标明，不能把它当作完全同条件的结果。 如果引用论文中已公布的数字，先核对任务实例、模型、评价函数、预算及选优规则；与自行重跑的结果分开标注。关键条件不一致时，可以作为背景参考，不能直接据此判定方法优劣。

**如何实现和配置基线。** 优先使用可信的公开实现和作者建议设置；适配任务时保留方法的关键机制。记录版本、修改、提示词或输入、超参数、评价接口及失败处理。若需要调参，为各方法提供合理的开发数据和调参机会，并交代调参范围与成本；不应只认真调新方法。某方法无法直接运行时，先说明原因，再选择可复现的适配或其他对照，不能静默替换成弱版本。

“公平”也不意味着强行把所有方法改成同一提示词或同一个算子。提示词和搜索规则可能就是某些方法的一部分。**整体方法比较**应保留合理的原方法，并对齐重要任务与资源条件；**机制对照**可以在共同框架中进一步控制提示和组件。两种比较回答不同问题。

### 7.4 预算和成本怎样对齐

先明确研究在比较什么资源下的表现。对于 LLM 驱动的算法设计，至少可能涉及：候选程序评价次数、模型请求次数、输入和输出 token、模型成本、程序执行时间，以及端到端墙钟时间。生成反思、无效代码、修复、失败重试或初始化是否计入，要在实验前确定并一致记录。

| 主要比较口径 | 适合回答的问题 | 仍需报告什么 |
| --- | --- | --- |
| 相同程序评价预算 | 评价昂贵时，谁能用相近的评价次数找到更好的程序？ | 模型调用、token、反思及其他额外成本 |
| 相同模型调用或 token 预算 | 模型推理资源受限时，谁更有效？ | 程序评价次数、执行成本及调用长度差异 |
| 相同时间或货币预算 | 在特定系统和价格条件下，谁更实用？ | 硬件、并行度、服务条件、价格及其变化 |

不同方法不一定能同时对齐所有预算。可以选择与研究问题最相关的主口径，再用其他成本指标或多预算曲线展示权衡。报告总成本时，需区分研究过程中的开发与调参成本、运行方法时的搜索成本，以及最终生成程序的使用成本。

外部服务故障、限流或调度问题应与方法自身的生成、验证和执行失败分开。不能把未完成运行当成正常终点，也不能只挑运行顺利的结果；应记录原因，按预先确定的恢复或补跑方式处理，并说明最终纳入的完整运行。

### 7.5 消融实验：先定义移除了什么

消融（ablation）研究某个组成部分或设计选择在特定方法中的作用。最常见的做法是从完整方法移除它，也可以比较不同设计版本。但删除一个组件有时会连带改变输入长度、调用次数、搜索状态或其他步骤；此时结果反映的是**整个改动包**，不能自动归因给其中单一因素。

设计一次有解释力的消融，可以按四步走：

1. 写清要检验的设计和预期作用，例如“反思内容是否改变后续生成”。
2. 定义变体实际保留和移除了什么，以及删除后空缺如何处理。
3. 列出会随之变化的内容：模型调用、输入长度、可用信息、父代选择和计算预算等；尽可能控制，无法控制的就记录。
4. 预先想好各种结果如何影响判断。若两种方法差异很小，也要考虑样本量和不确定性，不能立即断言组件毫无作用。

**删除和替换回答的问题不同。** 删除反思同时减少了信息和开销；用其他等量文本替换，主要帮助观察结果是否只是由额外上下文带来；用原始历史替换反思，可以比较两种信息表示，但信息选择、长度和措辞仍可能不同。没有哪个变体天然是“完美消融”。

如果方法包含两个可能相互作用的设计 A 和 B，且四种组合都能构成有意义、可运行的方法，可以做一个 `2 × 2` 比较：都不用、只用 A、只用 B、两者都用。先比较“只用 A”和“都不用”，再比较“两者都用”和“只用 B”，就能看到 A 在有无 B 时的效果是否不同；比较这两个差值及其不确定性，可以研究二者是否存在交互。仅比较完整方法与两个删减版本，通常不足以完整判断交互。若某个组合在概念上不成立，就明确问题，选择其他可解释的比较，不必为了凑表强行构造。

### 7.6 受控对照：用一个具体示例说明

假设我们想研究“真实搜索经历是否帮助下一次程序生成”。先收集一批**按事先说明的规则选取的搜索状态**，每个状态固定任务、当前程序、可用历史、评价器和后续预算。然后在同一状态下比较以下输入；不同状态和模型输出仍需适当重复。

| 条件 | 给模型的信息 | 它主要帮助回答什么 |
| --- | --- | --- |
| A | 任务与当前程序，不提供额外经历 | 不使用额外经历时的局部生成表现 |
| B | A 加该状态的真实经验 | 加入这份经验后，局部生成是否改变 |
| C | A 加长度相近、与该状态无关的文本 | 差异是否可能来自额外文本或输入长度 |
| D | A 加来自其他状态的经验 | 与当前状态匹配的经验是否比错配经验更有帮助 |
| E | A 加相近长度的原始尝试记录 | 经验摘要与直接提供历史，在该信息和长度限制下如何比较 |

解释结果时要具体：B 与 A 的差异是“加入整份经验”的效应，其中可能同时包含更多内容和不同长度；B 与 C、D 的比较进一步帮助研究信息内容和匹配关系，但无关文本、错配历史本身也可能影响模型，因此结论仍受控制条件限制；B 与 E 的差异涉及摘要和原始历史的内容选择，不能只归因于“压缩”二字。

实施时，可以从不同独立搜索及不同预定阶段抽取状态，并记录每个状态来自哪次搜索。不要只挑已经成功或最能支持假设的状态；在每个状态下，为各条件进行足够的重复生成，分别记录有效率和质量。来自同一次搜索的多个状态可能相关，分析和区间估计需要保留这一层关系。

这些条件可以揭示**固定状态下**的生成差异。完整方法还可能改变哪些状态会出现、哪些候选被选中以及反思消耗多少预算。要研究最终搜索质量，就需要在相应资源条件下开展多次独立完整搜索，并把创建经验的模型调用和其他成本纳入比较。

同一状态可以作为一个配对单位，让不同条件都从它出发；各条件在该状态下的多次生成也要保留状态归属。实验顺序可在可行范围内交错或随机安排，减少服务时段、模型版本或机器负载与某个条件完全重合。**相同的随机种子编号不自动构成有效配对**：只有共享的任务实例、初始状态或其他设计因素确实使两次观测对应，配对才有明确意义。

### 7.7 泛化、预算与参数敏感性

泛化研究先说清想推广到哪里：同一任务的新实例、更大规模、不同分布、另一类任务，或另一种模型。这些变化并不等价。先按预定规则独立准备相应测试条件，再比较选出的程序；不要根据测试结果反复挑选方法或提示词。

敏感性分析考察关键设计在不同设置下如何变化。先选择有明确含义、可能改变结论的参数，例如历史长度或种群容量，再解释取值范围是否覆盖实际会使用的条件。改变参数可能同时改变模型输入长度或评价次数，应记录额外成本；如果想分辨参数本身的作用，可再设计对齐资源的比较。参数选择使用开发数据，最终结果在独立测试条件下评价。

多预算比较既可以观察同一批完整搜索在预定中间时点的表现，也可以在不同预算下分别运行搜索。前者展示同一条搜索过程的阶段性表现；如果方法本身会根据总预算调整策略，后者研究的是另一种设定。两者的结果和成本应分别说明。

### 7.8 重复、波动与统计判断

先确定独立重复的单位。对于最终搜索效果，独立搜索运行通常是关键单位；同一次搜索中产生的许多候选共享历史，不能当作同样多次独立搜索。同一搜索生成的程序在多个测试实例上的结果共享该次运行；如果不同运行又使用同一批测试实例，观测同时共享运行和实例，是交叉结构。分析应保留这些关系。

如果只想研究固定测试集上不同搜索运行的波动，可以先按运行汇总；这个结果针对该测试集。若还想推断新测试实例上的表现，需要在实验和分析中同时考虑运行与实例的变化，不能把所有“运行 × 实例”的分数当成互不相关的独立样本。同一状态下反复生成也需要保留状态及其来源搜索的关系。

报告时说明重复次数、波动范围和比较对象。标准差（standard deviation，SD）描述观测结果的离散程度；标准误（standard error，SE）描述估计均值的不确定性；置信区间（confidence interval，CI）依赖所用估计方法及抽样假设。三者不能互换。小样本时展示每次独立运行的结果往往比只给一个均值更有信息量。

重复次数应由希望区分的效果大小、预期波动和可用资源共同决定。可以利用先导实验估计波动，再设计正式比较；若资源有限，就如实报告结果的不确定性。频繁查看结果并只在显著时停止，会改变常规统计判断的含义；如计划中途分析，应使用与停止规则相符的方法。

选择统计方法前先看比较单位和问题：两个方法在同一批独立任务上的配对差异、同一任务上的独立搜索重复、多方法跨任务比较，需要的分析可能不同。配对检验需要有意义的配对；多次比较要考虑错误发现风险。可根据设计选择差异的区间估计、合适的参数或非参数检验。没有显著差异不等于已经证明两者等效。Demšar 的[多数据集比较研究](https://jmlr.org/papers/v7/demsar06a.html)提供了 Wilcoxon 符号秩检验、Friedman 检验及后续比较的参考；使用前仍要核对其比较单位和假设是否适用于当前实验。

### 7.9 从结果回到结论

读完一组实验后，分别问：整体方法相对谁、在哪些条件下表现怎样？关键变体改变了什么？中间过程提供了哪些解释线索？是否存在代价、例外或尚未区分的原因？

结果可能支持比原计划更具体、也更有价值的结论。例如，一种经验表示在某些状态下改变了生成，但完整搜索没有稳定收益；那么“经验能够影响局部设计”与“经验改善搜索”就应分开讨论。论文的主线可以随真实结果调整，但选择主线之后，仍应呈现会改变读者判断的主要结果。

优化算法的任务选择、资源核算与可复现比较，可进一步参考 [Benchmarking in Optimization](https://arxiv.org/abs/2007.03488)；关于调参、重复和实证研究设计，也可参考 [Empirical Design in Reinforcement Learning](https://jmlr.org/papers/v25/23-0183.html)，并按自身任务判断哪些建议适用。

## 8. 怎样把图表做得清楚、有说服力

好的图表让读者迅速看出**比较对象、主要变化和重要例外**，同时保留判断结论所需的条件。设计时先确定要回答的问题，再选择图型；不要为了显得丰富，把排名、均值、误差线和大量说明全部塞进一张图。一个图可以有多个面板，但这些面板最好共同回答一个清楚的问题。

### 8.1 先规划整篇论文的图表

在写正文之前，可以为每个主要结果安排一种最合适的表达。以下是方法论文的常见选择，不要求每篇论文都有全部图表。

| 要让读者理解什么 | 可以采用什么 | 设计时先想清楚 |
| --- | --- | --- |
| 问题与方法的核心思想 | 问题示意图、方法流程图或一个贯穿实例 | 哪个决策或信息流是方法的关键 |
| 最终表现与主要基线 | 结果表、带区间的点图 | 比较对象、任务和指标是否一眼可辨 |
| 搜索过程与预算关系 | 随预算变化的曲线 | 横轴计量什么，曲线表示哪一个统计量 |
| 关键设计的作用 | 消融表、配对点图或分面图 | 每个变体改变了什么，是否能直接比较 |
| 机制或失败模式 | 状态变化图、散点图、代表性案例 | 展示的是相关现象还是受控干预 |
| 性能与开销 | 成本—质量散点图或并列面板 | 代价是搜索成本还是最终程序运行成本 |
| 适用范围 | 不同任务、规模或预算的分面图 | 各面板是否采用可比较的尺度和条件 |

先画出草图，再决定哪些信息放在图内、图注、正文或附录。图负责呈现关系，正文解释为什么重要，图注交代看懂图所需的条件。并非每个数字都需要在图、表和正文重复一遍。

### 8.2 方法图：画出决策与信息流

方法图适合回答“系统如何从输入走到输出”。对算法设计论文，可以先画出候选、评价反馈、历史信息和下一次生成之间的关系，再突出本文真正改变的决策。读者不必先记住所有内部模块名称，才能理解整体思路。

安排图面时：

- 从读者熟悉的起点展开，使用清楚的顺序、箭头和必要标签；相同类型的对象保持一致的形状或颜色。
- 重点标出核心操作、信息来源和输出。辅助组件、重复的实现细节和较长文字可以交给正文。
- 箭头要有明确含义：是程序被修改、信息被读取，还是评价结果被反馈？不同关系可以使用不同线型或标注。
- 如果方法涉及变化过程，一个小型具体例子往往比一排抽象模块更容易解释清楚。示意图中的数值和结果应标明是示例，不应让人误认为真实实验。

第一张图不一定必须是方法图。对于发现型论文，一张能让读者看到核心现象的结果图，可能比架构图更能说明问题。

### 8.3 结果表：先保证比较关系清楚

表适合呈现较多任务和方法的精确结果。常见的组织方式是行放方法、列放任务或指标，标出指标方向；与核心问题直接相关的基线放在读者容易比较的位置。名称和分组应与正文一致。

| 方法 | 任务 A，质量 ↓ | 任务 B，质量 ↓ | 搜索成本 |
| --- | --- | --- | --- |
| 简单基线 | 结果及波动 | 结果及波动 | 对应成本 |
| 最接近的方法 | 结果及波动 | 结果及波动 | 对应成本 |
| 本文方法 | 结果及波动 | 结果及波动 | 对应成本 |

这张表只是版式示意。实际表格应说明：数值越大还是越小越好、每个值如何汇总、波动表示什么、重复单位和次数、预算与成本口径。如果质量和成本不能压在同一表中，也可以拆开，但读者应能找到两者的关系。

可以用粗体标记数值最好的一项，但**数值最好不自动意味着差异可靠或实际重要**。若标注统计检验结果，说明比较对象、方法和多重比较处理。不要只呈现平均排名而隐藏各任务结果；也不要使用过多小数或装饰性颜色制造精度。

### 8.4 结果图：根据问题选择图型

**比较不同方法的最终结果。** 方法和任务不多时，点图可以在同一尺度上显示估计值及其区间；独立运行次数较少时，可以叠加每次运行的点，让读者看到波动和异常。对于有意义的配对，可以连接同一状态或任务上的两次观测；没有真实配对关系时不要连线。

**展示搜索过程。** 横轴可以是程序评价次数、模型调用、token 或时间；纵轴可以是按规则选出的当前最佳程序质量。每个时点先按预定规则处理每次独立运行，再汇总成均值或中位数曲线，并注明阴影表示的区间和重复次数。如果要展示测试集上的质量，应先按开发或训练指标选出该时点的程序，再评价对应程序；不能在测试结果中沿轨迹挑出最优值。测试时点应预先确定，测试结果只用于报告，不再反过来调整方法。

不同运行长度不同时，要说明为什么缺失、每个时点还有多少完整运行，以及汇总如何处理。不要把故障中止的运行画成已经达到预算，也不要在没有说明的情况下连接缺失区间或用其他运行补齐。平滑可以帮助观察长期趋势，但要注明方式，避免掩盖不稳定或制造不存在的提升。

**比较分布和行为。** 箱线图、散点图或直方图适合展示波动、差异和异常；具体选择取决于样本数量和问题。样本很少时，展示实际点通常比画出看似平滑的分布更直观。散点相关可以提示进一步研究，但单凭相关不能证明作用方向或原因。

**比较性能与成本。** 把成本放在横轴、质量放在纵轴，可以看到不同方法的权衡。标清成本单位及质量方向；一个方法在不同预算下可以对应多个点或曲线。若计算条件或硬件不同，图注要说明，不能把不同成本口径直接视作等价。

### 8.5 不确定性、坐标与视觉编码

**误差和阴影。** 图中要说明它们表示 SD、SE、置信区间、分位数区间还是其他量，并交代重复单位和样本量。想比较两个方法的差异时，直接分析差值及其区间通常比凭两条误差线是否重叠下判断更清楚。[NeurIPS 的论文检查说明](https://neurips.cc/public/guides/PaperChecklist)也要求交代误差线的含义。

**坐标轴。** 标出变量、单位和方向。柱形图的长度通常从零开始；点图或折线图可以使用非零范围，但要给足上下文，避免通过截断夸大差异。使用对数坐标时说明含义，并处理零和负值。多个面板用于直接比较时，尽量使用相同尺度；确需不同尺度时，要让差异容易被发现。

**颜色与线型。** 用颜色区分有意义的类别；同一方法在全文尽量保持相同颜色。再结合线型、点形或直接标签，避免只靠颜色识别。顺序数据使用有顺序的色阶；围绕零等有意义中心的变化可使用发散色阶。检查缩印后的对比度、灰度可区分性和色觉差异；灰度检查有帮助，但不能代替完整的色觉可访问性检查。

**版面。** 按论文最终显示尺寸检查字体、线宽、留白和图例。用少量清晰的视觉层级突出重点，网格和背景保持克制；删除不传达信息的阴影、立体效果和重复注释。多个面板应有一致的标签、间距和对齐关系，不必为了铺满版面增加无关内容。

### 8.6 图注怎样写

图注应让读者在不反复翻正文的情况下理解图里是什么。通常需要交代：比较对象和任务、横纵轴或面板含义、关键实验条件、统计量和不确定性的定义。若采用特殊归一化、平滑或筛选，也应说明或指向具体方法。

一个图注的写法示例是：

> **图 X｜不同方法随评价预算的搜索表现。** 横轴为累计程序评价次数，纵轴为按训练评价选出的程序在独立测试实例上的目标值，越低越好。曲线为独立搜索运行的均值，阴影表示所指定的区间；各方法的重复次数及其他成本见表 Y。

这是图注结构示意；使用时必须把“所指定的区间”等占位内容替换为真实定义。可以在图注中概括主要观察，但不要把尚未检验的原因写成图中直接证明的事实。

### 8.7 制作与导出

图表应能追溯到原始结果及其处理过程，包括筛选、归一化、汇总、误差计算和平滑方式。先检查数据与图中数值一致，再调整视觉样式。

线条和文字为主的图通常适合 PDF 或 SVG 等矢量格式；照片和高密度图像可能包含栅格内容。栅格图应按最终显示尺寸准备足够像素，单纯放大已有低清图片不会增加细节。检查字体、裁切、透明度和颜色在导出文件及论文最终尺寸下的实际效果。具体格式、分辨率和尺寸要求以目标会刊当年的说明为准；例如可参考 [Nature 的图稿说明](https://research-figure-guide.nature.com/figures/preparing-figures-our-specifications/)，但不能把它当作所有会刊的统一标准。

进一步的图形表达建议见 [Ten Simple Rules for Better Figures](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1003833)；对小样本数据如何展示分布，可参考 [Beyond Bar and Line Graphs](https://pmc.ncbi.nlm.nih.gov/articles/PMC4406565/)。

## 9. 回应评审与投稿前回看

读到评审意见时，先分辨它在质疑哪一个判断：是研究意义、与已有工作的区别、方法细节，还是结果的可靠性？对于会改变结论的疑问，优先给出直接回答和已有材料的位置；规则与时间允许时，再补充最能解决疑问的分析。合理的错误应明确修正；存在分歧时，解释理由并指出分歧所在。

拒稿可能暴露研究缺口，也可能反映表达不清或评审判断不同。不要把所有误解都归咎于读者，也不要假设所有批评都正确。对照论文和实验，判断修改问题、补充研究或更换读者，哪一项最可能改善下一次交流。

投稿前，可以再问自己五句话：

1. 论文回答了什么问题？关心这个问题的人为什么会在意答案？
2. 相对最接近的工作，本文具体推进了什么？
3. 最重要的结论能由哪些理论、实验或实际结果支持？有没有同样合理的其他解释？
4. 读者能否理解关键方法与比较条件，并分清已经观察到的结果和尚待检验的解释？
5. 论文呈现的范围、成本与限制，是否足以让读者正确使用这些结论？

具体格式、匿名、附录、代码数据和声明等要求，最后以目标会刊当年的投稿说明为准。

## 10. 继续阅读

- [Simon Peyton Jones：How to Write a Great Research Paper](https://www.microsoft.com/en-us/research/academic-program/write-great-research-paper/)：从研究者向读者传达想法的角度看论文写作。
- [Mensh 与 Kording：Ten Simple Rules for Structuring Papers](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1005619)：从读者如何理解信息的角度讨论全文结构和论证顺序。
- [Sörensen：Metaheuristics—the Metaphor Exposed](https://onlinelibrary.wiley.com/doi/full/10.1111/itor.12001)：讨论元启发式研究中以新隐喻代替机制解释的问题。

第 2 节的论文和第 3、4 节的官方说明均可从正文直接打开；研究者的写作建议也有各自的适用范围，读时可以对照自己的论文判断。
