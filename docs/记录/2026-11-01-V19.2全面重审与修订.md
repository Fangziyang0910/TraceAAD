# V19.2 全面重审与修订

日期：2026-11-01

## 1. 重审结论

V19.2 原本想解决的是程序库竞争过于稀疏的问题，但旧设计把三个不同问题混在了一起：

1. 程序当前已经有多好；
2. 继续开发它所在方向是否容易产生有质量的结果；
3. 对这个父代使用哪一种算子更合适。

旧公式虽然使用了轨迹信用，但仍让每个程序独立参与竞争，且信用可以沿完整祖先链传播。这样会产生两个偏差：连续产生很多 Refine 子代的方向会被拆散，Explore 或 Crossover 已经形成的新方向又可能把结果错误归因给更早的父代。

本次修订把预算分配改为：

\[
\text{开发段} \rightarrow \text{父代} \rightarrow \text{算子}.
\]

开发段负责汇聚连续开发的机会，父代负责在段内代表当前实现，算子负责决定下一次干预方式。这个结构只使用已有的父代、交叉参考、算子和评价记录，不识别抽象算法思想，也不增加程序字段。

## 2. 为什么需要这次修订

### 2.1 现有实验暴露的是“开发管理”问题

Base 的轨迹审计显示，优秀计算有时已经出现，但没有得到连续开发。例如 TSP seed1 的程序 P392 实现了小规模剩余路径的记忆化精确 DP；它出生时成绩接近当时前沿，之后仍有大量预算，却只得到一个直接子代，且没有得到交叉参考。这个现象说明：

- 设计思想没有出现，和已经出现但没有被开发，必须区分；
- 全库排名会随新程序加入而稀释早期候选；
- 给程序保存进程序库，不等于给它足够的后续开发机会。

审计还发现，部分程序的 design 说明没有稳定落实到 code，或者在 Refine 和 repair 中丢失关键计算。预算分配不能单独解决生成器的实现偏差，但它必须避免把稀疏机会误判为方向没有价值。

### 2.2 V15 的优点与边界

V15 的实际优势来自两个相互配合的机制：

- 让不同方向在相近投入下竞争；
- 将冠军方向集中开发，同时保留少量替代方向。

这使一个方向能够形成连续的开发曲线，而不是让全库中的每个程序都获得一次孤立尝试。V15 也说明，精炼和探索不是相互排斥的：好的方向需要连续 Refine，搜索又必须保留能产生转向的机会。

V15 的边界是谱系或年龄规则较强，不能把谱系直接当作算法思想；同一谱系可能在后续发生实质转向，后期程序也可能天然较好。V19.2 因此只把连续 Refine 作为统计汇聚单元，不把它解释为思想身份。

### 2.3 V16 的教训

V16 将近期改善速度外推为后续潜力。这个思路可以保留暂时落后的方向，但在有限预算下容易把机会分散给许多挑战谱系；当外推依据很少时，局部改善可能被误认为稳定趋势。

V19.2 不外推未知的改善曲线，只使用已经发生的开发结果，并用探索项给样本不足的段和组合保留机会。它把“可能有潜力”与“已经观察到连续产出”分开处理。

### 2.4 V17、V18 和 Base 的共同问题

同龄竞争可以缓解成熟程序对未充分开发方向的压制，但它需要一个无法直接获得的变量：哪个程序代表新的算法思想。仅凭出生时间或程序编号无法区分“新思想”和“成熟思想的新实现”，所以 V19.2 不引入固定的前期、中期、后期，也不把每个新程序额外执行一次。

V18 的部分任务表现说明，简化选择规则、起点质量、提示上下文和持续开发会同时影响结果；不能把停滞归因给单一开关。Base 则直接显示，全库排名在程序数量增长后会不断稀释早期方向的机会。

## 3. 相关方法带来的可迁移认识

| 方法 | 有用的认识 | 在 V19.2 中的取舍 |
|---|---|---|
| CALM | 简单的质量导向循环在起点和任务匹配时也可能很强 | 保留直接质量竞争，不增加无必要的层次 |
| RefineEvo | 连续精炼能把一个可行想法逐步落实为更强实现 | 用 Refine 连续段汇聚后续开发 |
| DeltaEvolve | 修改记录和高价值历史能帮助模型复用局部改动 | 保留 analysis、design 和评价轨迹，但不依赖代码相似度检索 |
| ReEvo | 双源组合可以直接利用分散在不同分支中的机制 | Crossover 开启新开发段，并优先跨段选择参考 |
| MCTS-AHD | 后续结果可以反向影响更早的搜索决策 | 采用折扣信用，但在算子转向处截断 |
| Clade-AHD | 以局部群体或谱系汇聚统计有助于缓解单点稀疏 | 采用更小的开发段单元，不宣称在推断算法思想 |
| OpenEvolve、EoH、HSEvo | 多样性、精炼和组合需要同时存在 | 保留三种算子及其软先验，不再额外添加独立动作层 |

这些工作共同说明，AAD 的选择不能只问“当前哪个程序分数最高”。但它们也没有提供一个可直接观察抽象算法思想的变量。V19.2 的科学问题因此收窄为：如何用程序之间可观察的生成关系管理开发预算。

## 4. 旧 V19.2 的三个结构缺陷

### 4.1 动态倒数排名改写历史质量

旧质量使用当前程序库中的排名倒数。一个程序的历史结果在后来加入新程序后会改变数值，轨迹信用因此失去固定含义。

修订后，质量由初始化有效个体的中位数和四分位距建立固定尺度：

\[
q(p)=\frac{1}{1+\exp((f(p)-m_I)/s_I)}.
\]

所有后续程序都使用同一任务内尺度；评价结束时冻结尝试质量。

### 4.2 完整祖先传播越过了设计转向

旧规则把 Explore 和 Crossover 的后续结果继续传回更早祖先。这把“新方向的后续开发”误当作“旧方向的延续”。

修订后：

- Refine 可以沿连续 Refine 链折扣传播；
- Explore 自己成为新段根；
- Crossover 的直接结果向两个来源各分配一次信用；
- 交叉后的 Refine 只在交叉段内继续传播。

### 4.3 程序数量会放大方向的竞争机会

如果每个程序独立归一化，某个方向产生越多 Refine 后代，就会拥有越多竞争条目，即使这些条目都没有带来新的信息。

修订后先按段分配总机会：

\[
G(S)=\max_{p\in S}V(p).
\]

段的机会只由段内最有竞争力的当前程序代表；段内程序再按价值竞争。这样连续开发不会因为记录数量本身取得额外总预算，而仍然可以通过更好的当前实现获得段内机会。

## 5. 修订后的机制

### 5.1 固定质量

初始化阶段得到的有效个体构成固定参考 cohort。有效程序按绝对成绩映射到 [0,1]；失败结果记为 0。质量不使用当前排名，也不使用“是否超过父代”作为收益。

### 5.2 开发段

开发段由现有字段推导：

- Init 是段根；
- Refine 延续父代段；
- Explore 和 Crossover 形成新的段根。

开发段是预算分配单元，不是算法思想分类器。

### 5.3 轨迹信用

每个程序维护一个由直接后续结果折扣汇聚得到的轨迹均值：

\[
T(p)=
\frac{\kappa_Tq(p)+\sum_tw_{p,t}q_t}
{\kappa_T+\sum_tw_{p,t}}.
\]

父代—算子组合的局部均值向轨迹均值收缩：

\[
M(p,o)=T(p)+
\frac{n_{p,o}}{\kappa_A+n_{p,o}}
(\bar q_{p,o}-T(p)).
\]

未观察到的组合继承父代轨迹判断；少量样本不能单独决定动作。

### 5.4 联合选择

先用父代价值计算段概率，再在段内选择父代，最后根据父代—算子组合选择算子：

\[
P(p,o)=P(S(p))P(p\mid S(p))P(o\mid p).
\]

三种算子的初始比例仍为 0.45、0.30、0.25，并通过小比例先验混合保留探索。交叉参考优先来自不同开发段的高质量程序。

## 6. 科学叙事

V19.2 的核心叙事不是“我们识别了算法思想”，因为现有程序记录无法可靠提供这个标签。

更准确的表述是：

> LLM-AAD 的预算分配可以看作对设计轨迹施加连续干预的信用分配问题。当前程序质量描述已有实现，轨迹信用描述该开发脉络在后续干预下的产出，父代—算子条件信用描述具体干预方式的适配性。

这个叙事有三个明确增量：

1. 把静态程序选择改写为开发轨迹上的资源分配；
2. 把轨迹传播限制在连续开发关系内，区分延续与转向；
3. 用开发段的部分汇聚缓解父代—算子组合过多造成的稀疏，而不引入语义聚类或额外规划器。

它不应被表述为完整的 Bayesian posterior，也不应把开发段称为算法思想簇。当前实现是固定质量尺度、轨迹信用、局部收缩和分段分配的简化选择机制。
