# DeltaEvolve：机制复现核对

我希望判断：没有作者实现时，论文是否足以支持我们复现其历史经验机制。

我的结论是：足以实现核心机制，但不足以唯一还原作者的完整系统与表中结果。主要缺口在采样、数据库维护和反馈渲染，而不是 delta 的内容格式。若将机制用于本项目六任务，应称为依据论文的机制复现与任务适配。

## 可直接实现的核心循环

1. 保存程序节点及其原父节点关系、评价、生成顺序、L1 摘要和 L2 修改计划。原父节点必须可追溯，才能确定这次修改相对谁发生。
2. 根据成绩偏置的随机策略选择待修改父程序。
3. 从历史中选择成绩最好的 k 个节点，以及 m 个多样性节点。默认 k=3、m=2。
4. 对选中历史节点按时间窗口展示 L1 或 L2。只对当前父程序展示完整代码 L3。
5. 模型在一次回复中生成 SEARCH/REPLACE 修改，以及 L1、L2 日志。
6. 将修改应用到父程序，重建子程序并评价。系统根据实际评价追加结果，再将可保留节点写入数据库。

依据：§4、Algorithm 1、Figures 5–6。第 6 步中失败节点如何保留、是否进入后续候选池，论文没有完整规则。

L1 使用 FROM/TO，分别描述原策略和新策略。L2 将修改拆成多个条目，每个条目包含 COMPONENT、OLD LOGIC、NEW LOGIC、HYPOTHESIS。提示要求 NEW LOGIC 提供具体参数、公式或启发式规则，而不是泛泛描述代码改动。

这里的 delta 是模型在生成修改时一并写出的说明。公式 Diff 并不对应论文已给出的独立差分提取算法。评价发生在生成之后，所以 HYPOTHESIS 是预期解释，不能当作评价后验证的原因。

三层表示存储在同一个节点上。L3 是重建后的完整程序；Figure 6 指定模型输出补丁，并非要求每次直接输出完整源码。Figure 5 要求日志置于回复末尾，落实输出顺序时应优先遵循具体模板。

## 采样与展示应如何理解

Algorithm 1 的逻辑可以直接翻译：

```text
parent = Sample(D, selection_policy)
elite = TopK(D, score, k)
diverse = MAPElitesSample(D, exclude=parent, m)
history = union(elite, diverse)
for node in history:
    render L2 if node.time > current_time - w else L1
append full parent code
```

我会以 Algorithm 1 作为展示层级的主要依据。§4.3 的正文一处说旧 elite 用 L1，另一处又说所有选中 elite/diverse 用 L2；Figure 4 和 Algorithm 1 更支持按新旧分层。这里的渐进披露是按节点时间选择已有表示，没有给出由模型临时请求展开详情的工具循环。

历史选择按节点绝对成绩，而不是按相对父节点的增益。选中节点的 delta 描述它相对原父节点的修改，不是描述它相对当前待修改父程序的修改。跨程序借鉴由生成模型完成。论文没有要求检索完整祖先链，也没有提供独立的组件迁移验证器。

## 完整系统仍缺少的决定

| 项目 | 论文明确内容 | 尚未明确或不一致的内容 | 对复现的影响 |
| --- | --- | --- | --- |
| 父程序选择 | 偏向高分但保留探索；表 4 为 weighted，比例为 elite 0.1、exploration 0.2、exploitation 0.7。 | 权重公式、各比例对应的候选池、负分与同分处理。 | 改变实际搜索分布。 |
| 多样性采样 | 文本 embedding、MAP-Elites、选择距父节点较远的单元。 | embedding 模型与输入、描述子、降维与分箱、距离和单元内选取规则。Figure 6 还提到 complexity/diversity，映射关系未交代。 | 无法唯一重建多样性节点。 |
| 新旧窗口 | Algorithm 1 指定 w 与时间比较。 | 表 4 没有 w；Time 是迭代、出生编号还是其他时间，未严格定义。 | 直接改变 L1/L2 比例、成本和信息量。 |
| 数据库维护 | population 40、archive 20、3 islands、每 10 轮迁移、迁移率 0.1。 | 容量作用范围、淘汰、归档、岛内或全局检索、迁移对象与目标。 | 完整系统不能只靠这些数值还原。 |
| 反馈渲染 | 式 (7) 说只用 Improved/Degraded；模板含 evaluator feedback。 | Figures 13–14 显示具体逐实例分数；是否属于实际生成输入、父程序反馈是否保留数值不明确。 | 不能将纯符号反馈断言为唯一忠实实现。 |
| 长度控制 | §4.2 称 L1 通常 20–40 tokens。 | Figure 13 显著更长，且含参数与分数；没有硬截断或重写规则。 | 不宜自行将 40 tokens 当作原文硬约束。 |
| 初始化与失败 | 描述五任务初始程序，提供补丁与日志格式。 | 种子节点没有 delta 时怎样渲染；补丁失败、缺失日志、无效程序和评价失败如何处理、重试是否用模型。 | 必须补充运行规则并计入成本。 |
| 改善标签 | 例子有 improved，正文提及 degraded。 | 等分、数值容差、评价失败标签及负向经验是否保留没有完整说明。 | 标签应由系统比较实际评价产生，不能让模型自行宣告。 |
| 去重与排序 | 伪代码用 elite/diverse 的并集，diverse 排除 parent。 | elite 是否排除 parent、跨组重复如何归类、具体输出顺序。 | 可用简单固定规则补足，但需标明。 |

OpenEvolve 是作者复现 AlphaEvolve 的基础，见 §5.1。但论文没有锁定其提交版本，也没有说明哪些默认参数被继承。不能把当前 OpenEvolve 的默认行为直接当成原系统事实。

## 哪些是机制，哪些是解释

Momentum 在这里对应重复利用历史语义修改，没有给出数值动量状态、衰减系数或梯度累加更新。实现核心机制不需要额外发明动量计算器。EM 主要组织采样与上下文更新的解释，也没有提供需要另行实现的 EM 求解步骤。

L2 的一个节点可能同时修改多个组件。评价分数验证整个子程序的表现，不验证每个组件各自的贡献，也不验证 HYPOTHESIS。该区分影响经验怎样被解释，但不妨碍按论文存储和提供这些经验。

论文主比较支持作者完整方案相对 full-code 基线的结果；§3.3 另比较精英选择与数值反馈。全文没有分别隔离 delta 格式、HYPOTHESIS、新旧分层与历史数量的完整消融。因此，不能据此确定收益主要来自哪一个部件，也不能由单条轨迹证明组件解释成立。

## 对我们最直接的实现判断

如果目标是测试这种经验表示，最小充分改动是：在同一个搜索骨架中保存两级 delta、按原选择策略取历史、按时间窗口渲染历史，保留父程序完整代码，并用实际评价绑定结果。SEARCH/REPLACE 与单次回复中的 delta 日志也应保持，避免另加事后反思模型而改变机制与成本。

父节点选择、MAP-Elites、岛模型等属于完整系统的重要条件，但不应与历史表示同时随意改变。没有作者代码时，可明确给出自己的固定规则；不能把“我们补齐的规则”写成“论文明确规定”。若只复现历史表示，可以保持同一搜索骨架与 full-code 对照，并清楚说明没有重建作者完整系统。

若下一步比较 full-code 与 delta，最好两组都要求生成同样的 delta 日志，仅改变后续历史展示。这样可以减少“多写了一段自我解释”与“历史表示改变”的混淆。新旧分层可在核心循环验证后单独比较，不必先扩展大量机制。

我们的六任务采用更小为好的 fitness，而论文统一按更大为好的 reward 描述。适配时应显式转换排序与改善方向。模型、任务接口、数据、生成预算和最终选择按本项目实际条件报告；沿用本项目条件是在测试机制迁移，不是在重现论文表 2。

## 2026-10-19 的待验证想法

以下是我阅读论文后的改动想法。它们不是论文机制，也不是当前忠实复现基线的决定。若实现，应作为独立变体与论文的文本协议对照。

1. **给 L1 增加一句主导假设。** 将 L1 从 `FROM ... TO ...` 扩展为 `FROM ... TO ... WHY ...`。按 Algorithm 1，久远历史只展示 L1，因而会丢掉 L2 中“为什么改”的机制与适用条件；只保留策略转向和成败标签，可能让后续生成只模仿目标策略，难以判断它是否适用于当前父程序。`WHY` 只概括主导机制，不重复 L2 的逐项假设。验证时应保持节点选择、历史数量、新旧渲染与预算口径不变，只比较原始 L1 与 `L1 + WHY`，并记录新增的输入与输出 token。一次修改包含多个组件时，总体 `WHY` 仍是模型在评价前写出的预期归因，不是评价验证的原因。
2. **改用无编号的 JSON Schema 结构化输出。** 用 Schema 直接约束语义计划与代码补丁的外层结构。当前优先考虑外层对象包含 `summary{from,to,why}`、`modifications[{component,old_logic,new_logic,hypothesis}]` 与一个完整的 `patch` 字符串；语义内容先于补丁生成，不要求 LLM 生成或维护 `modification_id`、edit 编号等工程字段，也不再把每处代码修改拆成一组 `search/replace` 字段。若端点的 JSON Schema 不稳定，可拆为语义计划与补丁两次调用。节点编号、迭代号、编辑位置、应用状态与成绩变化均由系统在解析、执行和评价后生成。论文目前用提示词交代字段、起止标记和输出顺序，再用轻量解析器提取字段，本质上是用提示词模拟 Schema。改用 JSON Schema 可以删去这部分格式指引和文本解析逻辑，使输出能直接校验、入库，并按需要渲染为 L1 或 L2。LLM 只需提供算法策略、逻辑变化、假设与代码补丁。只描述算法逻辑、定量写清新机制、逐组件说明假设等内容要求仍需简短保留。验证时应在相同模型、任务与预算口径下比较文本协议与 JSON Schema，并记录格式或补丁应用失败、总 token 和搜索结果。
3. **让语义计划先于代码编辑，并支持多处 edit。** 论文附录 C 要求模型先生成代码修改，再在回复末尾记录 L1 与 L2。可以改为先生成整体策略和每项修改的语义内容，再生成实现它们的代码编辑。一次变异可包含多个互不重叠的 edit，由执行器基于亲本快照统一应用；全部校验通过后只评价最终子程序一次，保存的 L1 与 L2 应对应实际成功应用的修改。进一步的 Agent 形式可由系统逐项呈现当前 modification，LLM 每轮只返回实现该项的 V4A 小块补丁；系统应用后反馈匹配或语法结果，再进入下一项或修复当前项。当前项指针、轮次与应用状态由系统维护，不要求 LLM 回显编号。验证时应分别比较论文文本协议、一次调用的语义先行批量多编辑与多轮 Agent，避免把输出顺序、JSON Schema 与额外修复调用的收益混为一谈；多轮形式还必须计入全部模型调用的 token。
4. **按继续改进的价值选择父代与历史。** DeltaEvolve 与其 AlphaEvolve 对照主要按当前分数偏置选择父代，再按程序绝对分数选高分历史，并按文本嵌入或 MAP-Elites 距离选多样性历史。这回答了“程序现在有多好”和“代码看起来有多不同”，但没有估计“下一步改它可能获得多少收益”，也没有判断某条历史 delta 是否适用于当前父代。后续可把谱系近期改善趋势、已获得的尝试机会、停滞程度、相对父代的实际增益、逻辑组件与当前父代的适配关系等因素纳入选择。验证时应固定历史表示、变异方式和总预算，只替换选择策略，并记录被选节点后续带来的改进与成本。
5. **区分少量明确的变异意图。** AlphaEvolve 与 DeltaEvolve 都主要使用一个通用 LLM 变异提示，由模型自行决定修改类型和幅度。可以由系统在每次变异前选择少量语义意图，例如局部精炼、核心策略探索、把某个历史逻辑组件迁移到当前父代等，再让 LLM 在该意图内完成算法设计。这样可能更可控地分配探索与利用，并能分别观察不同意图的后续收益。算子应保持少量且停留在算法语义层，不要求 LLM 维护编号等工程状态。验证时应固定父代与历史选择、历史表示和总调用预算，比较通用变异与意图条件变异，避免把提示变化误当成选择策略的收益。

### 当前推荐组合

基于 2026-10-19 的编辑格式验证，当前优先推荐“JSON 语义计划 + V4A 小块补丁 + 有界修复”，但尚未写入忠实复现基线。模型先输出 `summary{from,to,why}` 与逐组件 `modifications`，再输出完整的 V4A `patch`。每个 hunk 只改一处，包含少量上下文，不删除并重建整个文件。系统按子块应用补丁，做 AST 与任务入口签名检查；失败时反馈失败旧块和父程序中最接近的实际代码，最多修复两次。全部成功后只评价最终子程序一次，并把实际实现的语义计划保存为 L1、L2，与完整代码 L3 一起入库。整程序重写只作为短程序或补丁修复耗尽后的回退；simplified unified diff 可作为模型偏好或备用格式。

这一推荐来自 12 个真实改善父子案例在 Qwen3.8-27B-AWQ 与 DeepSeek-V4.1-Flash 上的配对指定改动实验。规则讲清并限制小 hunk 后，V4A 首轮 24/24 通过补丁应用与 AST，最终 23/24 可评价；simplified unified diff 首轮 20/24、修复后 23/24 通过 AST，最终 19/24 可评价。整程序重写在上一轮达到 24/24，但父程序最长只有 9,477 字符，不能直接外推到长程序。该实验验证的是给定语义改动后的代码落地能力，不是完整的开放式搜索；JSON 语义计划与 V4A 补丁组合本身还没有作为一个整体完成完整搜索 A/B。下一步应固定父代与历史选择、历史展示和总预算，只替换输出与编辑接口，与忠实基线比较。第 4、5 项选择与算子意图仍应随后单独验证，不与这次接口替换同时改变。

## 为什么暂时不能承诺重现原表结果

附录 D 给出任务描述、初始策略与部分评价公式，但未提供完整五任务运行材料。符号回归数据、各任务评价常数与聚合、卷积计时环境等仍不完整。D.1 描述两阶段评价，表 4 则写 Cascade evaluation=False，需要确认是否涉及同一种级联机制。

正文用三路随机种子 11、42、100 的最大 best score 和平均 token 数报告结果。复查表格时必须保留这种聚合口径，不能当作三路均值。§5.2 定义 token 为全部调用的消耗，正文部分位置又强调 input tokens；缺少调用日志时无法确定各表的细分统计。

附录 H 提供的是搜索发现的 BBOB 优化器，不是 DeltaEvolve 的搜索框架。它能辅助核对最终产物，不能补齐数据库和采样实现。本次没有运行该程序或五任务评价器。
