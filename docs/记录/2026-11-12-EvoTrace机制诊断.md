# EvoTrace V3：简化、预算分配与算子上下文的机制诊断

我优先怀疑简化时的保留判据。实际代码把结构锚点同时当作相似算法的代表，已经出现较差锚点排斥更好版本的情况。上下文对 Explore 的影响是第二个待验证解释。预算分配在 FSSP 上明显改变了搜索重心，其他三个任务没有同样的偏移。

这些判断来自冻结记录的重放。它们确定了机制发生偏离的位置，尚未测出各项偏离对最终成绩的贡献。

## 证据与比较条件

使用北京时间 2026-11-12 08:39 的[结果快照](../../experiments_result/analysis/evotrace_status_20261112_083922/)。EvoTrace 批次为 `20261111_235642_evotrace_v1_v3_co4`，Base 为 `20261109_base_boltzmann_co6`。每个任务各三个种子；共同评价预算分别为 TSP 540、CVRP 560、FSSP 640、OP 1000。初始化和后续轨迹不同，因此这些统计用于定位机制行为。

我重放了节点接入、保存的重构结果与父代选择概率，并核对实际源码差分。未调用模型或重新评价算法，也未改变正在运行的实验。脚本、逐步观察和案例见[诊断目录](../../experiments_result/analysis/evotrace_diagnosis_20261112_090235/)。

## 1. 简化：结构锚点排斥了更好的同类算法

`plan_consolidation` 先保留冠军、受保护方向及其结构闭包。随后计算候选与全部 `kept` 节点的最近 AST 距离，距离小于 0.08 就跳过。这里的 `kept` 包括仅为维持分叉和方向边界而留下的节点。

问题出在这个推论：**一个节点因结构需要留下，不代表它是这一类算法中值得继续搜索的最好版本。** 当前近邻排除规则没有检查这一点。

在共同预算内的229轮整理中，冠军全部保留。前10名节点共有537次删除事件，其中46次删除的节点优于所有保留的近邻；24次的近邻全部只是结构锚点。后者最直接暴露了结构维护和算法保留之间的冲突。

CVRP 种子0第三轮整理提供了完整过程证据：

- 节点 #92 的成绩为 8.896801，其子代 #93 为 8.719117，越小越好。
- #93 将距离的平方反比改为立方反比，并调整需求权重。AST 指纹忽略常数和变量名，两者距离为0。
- #92 因结构闭包进入保留集。此时仅保留11个节点；加入 #93 后闭包大小为12，仍远低于32的容量。
- #93 随即被近邻阈值排除，最终只留下较差的 #92。

这个例子直接定位到保留判据。路径重连和反思文本没有参与该次排除决定。逐次判定保存在 `pruning_block_trace.json`。

## 2. 预算：FSSP 对最优算法的开发明显减少

实际选择当时最优算法作为父代的比例为：

| 任务 | EvoTrace V3 | Base |
| --- | ---: | ---: |
| TSP | 12.4% | 2.3% |
| CVRP | 11.2% | 3.3% |
| FSSP | 9.0% | 60.1% |
| OP | 19.3% | 2.1% |

按非初始化生成尝试计数，包含并列最优。FSSP 中，父代距最优成绩0.1%以内的比例也从 Base 的97.2%降到36.9%。

当前质量项为 `sigmoid(10 × (中位数 − 成绩) / MAD)`，再乘 `1 / (1 + 累计子代数)`。较好节点的 sigmoid 容易同时接近1，质量差异随之变平。例如 FSSP 种子0第348次尝试，成绩3875.4375的冠军与3880.75的较差节点质量项都约为1；由于两者已有子代数分别为2和0，较差节点的采样概率是冠军的3倍。

这一现象使 FSSP 的质量偏好成为重点嫌疑。Base 的原始分数 Boltzmann 温度为1，在 FSSP 的分数尺度下高度集中于最优附近，在其他任务却比较平坦。对 EvoTrace 的同一批树状态改算 Base 概率，FSSP 冠军平均概率从8.2%变为66.4%。这是当前状态下的概率比较，尚无对应续跑成绩。

我修正了最初对累计子代数惩罚的怀疑：在同一批树状态上去掉这项惩罚，冠军平均概率在前三个任务反而下降。因此，不能把问题概括为“子代数惩罚普遍压低了冠军机会”。

## 3. 上下文：Explore 的改动收缩，但收益原因仍需配对检验

当前 Explore 读取至多8个方向的起点、最优保留设计、成绩，以及这些方向中保留节点和边上的完整经验。四任务 Explore 平均输入约4900—7400 tokens，Base 约1200—1800。对应的子代与父代平均 AST 距离为：

| 任务 | EvoTrace V3 | Base |
| --- | ---: | ---: |
| TSP | 0.319 | 0.423 |
| CVRP | 0.269 | 0.521 |
| FSSP | 0.277 | 0.474 |
| OP | 0.293 | 0.422 |

我最怀疑的解释是：大量已有方向及其成绩使 Explore 沿已知做法继续调整。实际代码提供了两个清楚案例：OP 种子0第508次尝试只将指数6改为5；CVRP 种子1第235次尝试将指数2改为4，并改了变量名。这些输出都会按 Explore 登记为新方向，进入后续方向统计与保护判定。

这说明算子标签与实际计算变化存在不一致。AST 距离也不能直接等同于计算语义：相同指纹可以包含不同的变量依赖和运算对象。严格保留变量名、只忽略数字常数的核查，仅发现 EvoTrace 两次纯常数变化的 Explore。因此我不把个例推广成“Explore 大量退化成调参”。

目前四任务的 Explore 改动都更接近父代，但其中三个任务刷新当前最优的频率仍高于 Base。改变幅度小本身不能解释成绩差距。判断上下文是否把探索带偏，需要固定同一父代和算子，只改变提供的材料，检查实际计算变化与评价结果。

## 下一步只验证一个问题

我建议先验证简化的保留冲突：固定同一整理前树状态、后续分配和提示，仅让“因结构需要保留的节点”不再凭相似性自动排除更好的候选。继续沿用已有 `selected_ids` 与 `kept_ids`，无需新增角色或模块。

先看这项改变是否保住案例中的优质版本，再做同起点的短程续跑，比较后续最优成绩和搜索去向。这个检验可以区分两种解释：当前简化确实丢掉了有用的开发起点，还是这些版本对后续搜索没有增量。确认后再决定是否改变分配或 Explore 上下文。
