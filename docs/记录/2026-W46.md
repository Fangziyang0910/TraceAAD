## 11月9日：机制三收缩为全局经验，删去核验负担

用户请我评估11月8日的机制三设计。我起初认为它对 V19.4 与 V20 的失败逐一给了对策，但没有说明相对机制二的增量：同起点比较和接续发展读的是机制二已经展示的事实，真正的增量是其他节点上的干预和滑出窗口的旧干预，而设计把它们排在材料装入的最后。用户把机制三的定位说得更清楚：机制二受上下文限制只能看到局部，机制三提供更全局的经验，承担长程记忆和优秀思想的迁移，类似 DeltaEvolve 的分层视图；核心是基于演化轨迹的反思比相关工作更有效，不是把篇幅花在核验上。用户还指出，反思和使用两端都不要给模型太多要求。

按这个定位，我重写了[机制三](../机制设计/机制3-轨迹反思与经验学习.md)。反思每10次有评价结果的尝试进行一次，只读这10次的机制二卡片（实际改动与结果）和当前笔记，原位改写最多6条笔记。旧设计中的"有新材料才反思"几乎总成立，已删除。指令只保留两条有依据的规则：原位修订，因为只追加会产生重复经验；实现输了不判定思想无效，而记录它怎样失败，因为11月2日的回放显示改变提问方式能减少否定判断，只改措辞几乎无效。三种轨迹关系的材料组装、每个算子各一句的指导、依据编号核验和生成时的引用要求都删去。Refine 与 Crossover 在上下文最前面读到全部笔记，由生成器自己决定是否采用；Explore 不读，保持机制二的隔离。首个实现接在 V21 上，对照只差笔记段和反思请求。

我的认识变化是：机制三与相关工作的区别在凝练对象，即程序算出的改动和评价器测出的结果，并在整条搜索上汇总修订；DeltaEvolve 的分层视图由变异模型自述组成，且按节点存放。关键未知量是笔记会落在计算思想还是常数取值上：Refine 占多数尝试，笔记可能主要记录调参。这需要读第一批运行的笔记判断。本次只修改设计文档，并同步了 WWH 与 method，没有实现或运行实验。

随后我审查了反思提示，发现四处问题：容量满时没有写明淘汰标准，模型会用近期材料挤掉旧笔记，长程记忆随之消失；没有允许"不改"，模型会凑满容量并反复改写；要求写"observed effect"，容易引出 V20 冒烟中那种强判断和只适用于原程序的常数；模板照搬了生成的"Implement the following function"。用户要求全量优化：必要规则简短说明，提示要充分激发模型总结好经验的能力，并想清楚与其他机制的配合。

我据此重写了提示。指令以读者为中心：笔记的读者是搜索中正在修改某个程序、看不到原始尝试的设计者，所以思想要按"计算什么"写，才能离开原程序被使用。好笔记写三项：计算什么、试时发生了什么、依赖什么或怎样失败。另加一句"计算思想比常数取值对读者更有用"，针对 Refine 小改占多数时笔记落入调参的风险。淘汰按用处而不按新旧，允许宁少勿弱和不改。输出前加 `analysis`，只问这批尝试说了什么笔记里还没有，因为请求关闭思考时它是唯一的思考空间。反思卡片沿用机制2格式，另加一行尝试开始前的搜索最好成绩，与机制1使用同一个成功标准。设计文档新增与 Base、机制1、机制2各算子的配合说明：笔记不进入预算分配，Explore 仍不读笔记，其新思想经反思后由 Refine 和 Crossover 继续发展。本次仍只改文档。

机制接通了，但笔记内容重现了 V19 的失败形态。最好程序在第7次尝试就出现（6.8202，最近邻加 $1/N$ 回程权重），之后10次尝试的偏离都更差。两版笔记于是写成"$1/N$ 系数优于其他衰减""复杂多项启发式会退步""一步前瞻不如动态回程贪心"，`analysis` 写"optimal""consistently underperform"。笔记出现后，生成说明直接引用："restore the proven simple two-term heuristic""remove the term noted to regress"。第16–35次的17个 Refine/Crossover 中有8个回到 6.8202。也有好的一条：最小距离项因对角线为零而恒为零。这与机制二文档中的实测一致，说明笔记能沉淀可迁移的实现教训。

我的解释是：指令中"初次实现不等于思想差"这一句没有起作用，原因在提问方式。我给 `analysis` 的问题是"这批尝试说明了什么"，正是11月2日回放中引出42%否定措辞的问法；改问"这个思想怎样能实现得更好"才降到27%。笔记定义中的"试时发生了什么"也让模型按结果比较排序。冒烟只有36次评价，不能判断机制效果，但它直接显示了提示的读法。用户随后问设计中是否已有对策。我核对后认为对策都停在措辞层面，而提示另有四处在要求评价思想优劣，其中读者目的"which ideas are worth using"本身就是排序要求；我加的每卡搜索最好成绩又把现任成绩放进每张卡片。根本原因是笔记的内容定义：只要回答"哪个更好"，多数偏离都输给现任的阶段性结果就会给出"现任最好"。改进方向是让笔记记录思想怎样实现、受什么限制、怎样实现得更好，不对思想排序。问题、证据、改进方案与检验见[独立记录](2026-11-09-V24冒烟-笔记向现任程序收敛.md)。

用户提出机制2已找到轨迹帮助Refine的方式，尚未找到帮助Crossover与Explore的方式，并建议Crossover改为提供“可迁移计算及其条件”的证据。我核对源码与数据后，保留“Crossover是机制2最大的负项”，不采纳新增证据形式。冠军父代上Crossover刷新冠军的比例，所有已有尝试次数合计为机制2 25/631（4.0%）、静态45/503（8.9%）；父代尚无子代时为9/68对14/51，三个任务同向。当前纯Boltzmann批次的V21.1与Base在冠军父代上仅有4/41对4/57个事件，尚无信息。冠军步长≥1%的频率相同（1.4对1.5／千次），差距全在<1%的小步（11.6对29.7）。新增的`cross_transplant.py`显示，机制2的Crossover子代中，相对父代新增的代码行有60%–68%（中位数）原样出现在参考代码里；静态上下文只给参考设计，该值为0，所以这一项只说明模型确实在移植，不说明移植有害。机制2内部按新增行出自参考的比例分三档，好于父代的比例为6.9／4.8／3.8%（14／7／12个事件），趋势与“移植降低产出”一致，强度不足以单独定论。另有37/704个Crossover子代相对父代没有新增行。我的判断是：Base的Crossover指令已经要求选互补计算并对齐表示与尺度，机制2的指令把这两条改弱了；要求“说明某项计算在来源中起什么作用”需要把单个成绩归因到某项计算，这类归因在V24.1经验里已出现错误。因此下一步先检验最简单的一项：Crossover改回参考设计与Base指令，其余机制2不变，任何新增轨迹证据都要超过这个臂。复制已有兄弟的Refine子代，其原件只有11%–13%曾好于父代，复制的是展示出来的程序，不是成功经验，所以“利用成功经验与复制成功代码的矛盾”不是Refine的真实矛盾。

## 11月10日：V21.2，把`analysis`改为轨迹引导的设计推理

用户指出V21.1的`analysis → code → design`没有给模型分析并利用轨迹的空间：`analysis`只问准备采用什么方案，关闭思考后它又是写代码前唯一的思考位置，轨迹读进来后模型直接给方案。我核对源码确认了这一点，Base原有的“the relevant evidence from the provided context”一句在V21.1中已删除。讨论后确定的原则是：不要求模型得出历史结论，而要求它利用相关历史作出当前设计决定；保留单次调用和三个字段，不加核对步骤。

[V21.2](../机制设计/V21.2.md)据此做了三项改变。公共模板只规定`analysis`为按[Instruction]进行的2–4句设计推理，具体问题由三个算子的指令给出，并都以一句修改决定结尾。Crossover不再给参考完整源码，改给设计描述和参考计算的形成记录：沿参考父代链取新增且仍被参考执行的代码行最多的4步，用户指出最近步骤和成绩变化最大的步骤不一定对应值得借用的计算，所以二者只作次要排序；完整源码作为`--reference-code`对照。Explore读本路此前的初始与Explore算法，给设计、产生时成绩、此后经Refine与Crossover的尝试数和其中最好成绩，不由系统标注“未充分检验”，因为开发次数少可能是它差，也可能是没有得到机会。子代卡片只保留修改决定（`analysis`最后一句）、实际改动与结果，完整推理不进入后续上下文。

用V21.1 TSP第1路的真实记录渲染时发现，按整棵子树统计开发次数会让初始算法覆盖几乎全部搜索（Algorithm 2为732次），后来另起的Explore方向也被算进去。改为只沿Refine与Crossover计数、遇到Explore即停之后，同一处为107次，Explore 26为124次，最近三条新Explore为0次；其中Explore 916与已开发124次的Explore 26是同一种贪心补全前瞻，这正是覆盖记录想让模型看到的情况。旧记录的`analysis`不以修改决定结尾，取最后一句时常得到理由句，新运行的记录才符合这一格式。全部438项测试通过。V21.2尚未运行，关键未知量是改写后的`analysis`是否真的改变修改对象，以及Crossover去掉完整源码后能否在不复制的同时保持实现正确。

V21.2精修。用真实TSP记录渲染完整提示后改了三处。Refine原先总是展示最好子代；这条路有至少两个有效子代的父代中，最好子代好于父代的只有111/214，近冠军处更少，而此前的复制主要复制这个固定展示的程序，所以改为最好子代只在好于父代时优先展示。初始算法的祖先卡片原先把初始方案说明的最后一句当作“修改决定”，改为给出其设计描述。各段段首说明记录按什么规则选出；三段指令改为更短的主动句，Refine改为“保留主要机制的其余部分”，Explore改为“较弱或发展很少的实现，仍留着这个思想的其他实现方式”。修改决定的切句不在“e.g.”“i.e.”处断开。机制2正文同步更新，439项测试通过。

V21.2按外部评审再改四处。融合参考的形成步骤按“新增且仍留在参考中的代码行”选取，但代码留存不说明它驱动了结果；原段首写成“参考仍在执行的计算”，说法过强，改为“新增行仍留在其代码中的步骤”，并直接告诉模型留存只说明代码来源。参考是随机选出的合格程序，不是每对都能合理融合，恢复V21.1的退出句：没有合适计算时在analysis中说明，再给出最合理的接入。Refine祖先卡片补上实际差分，使形成路径由实际变化组成；真实TSP记录上Refine上下文中位数6.7K字符、最长14K。V21.2原先改写了公共模板，初始化与修复也随之改变；现在新协议只用于三个演化算子，初始化与修复保持V21.1提示，使V21.1与V21.2的差别集中在演化生成。Explore覆盖记录保持不变，正文明确它是代表性的探索经历，不是完整的搜索空间。441项测试通过。

V21.2固定状态回放。我从V21.1四任务批次的TSP、OP、CVRP中，取第300次评价之后的49个真实状态：Refine 13个（父代排名前5，已有至少3个有效子代），Crossover 18个（参考至少有2个形成步骤），Explore 18个。每个状态用V21.1与V21.2的提示各生成3次，Crossover另加`--reference-code`，子代评价一次，不做程序修复，共348次。程序指标没有可分辨的差异：优于父代的子代数，Refine为7/39对6/39，Crossover为8/54对5/54（看代码组5/54），Explore为4/54对8/54（差异集中在TSP，3对7）；按状态配对，三个算子的胜/平/负分别为2/8/3、1/14/3、4/13/1。V21.2的Refine子代更接近父代（中位相似度0.71→0.85），与已有子代重复从10%降到5%。Crossover新增行原样来自参考的比例为0.56、0.45、0.49；我在前22条上看到的0.83只是早期小样本，看代码组也没有更高，形成记录没有造成更多照搬。

行为上的变化很清楚：analysis提到历史的比例，Refine从3%到59%，Crossover从11%到57%，Explore从4%到20%，引用的算法编号全部来自提示。人工阅读Refine的13个状态后，我看到两种使用方式。第一，有diff时模型能读出决定文字没有写的改动：CVRP状态358中，Algorithm 140的决定只说“偏好平滑转向”，模型从diff读出它把参考点从质心换成了仓库。第二，卡片只写“most of the code was replaced”时，模型用决定文字补全并出错：TSP状态419中，它称“此前尝试表明MST估计能改善成绩”，但MST那一步持平，改善来自计算被隐藏的Explore步骤，子代退步。主要失效是把退步解释成原因（“缺少随机性”“权重过猛”“未归一化”），再做失败想法的弱化版或调参；也有一例直接重做已展示的改善子代（TSP状态371重做Algorithm 224，成绩完全相同），违反“与已展示尝试实质不同”。Crossover的analysis大多点名参考中的具体计算（MST、regret、source factor）并给出接入方式，108次中没有一次说明无合适计算。

认识变化：显式设计推理确实让模型使用历史，但在这个规模下还没有转化为更好的修改。使用质量受两件事限制：一是历史卡片的实际改动表达不完整，大改写只报告规模，模型便用决定文字填补；二是模型倾向于从结果编造原因。前者与用户同日指出的diff问题一致：实际改动目前有四种表达（diff、改写规模、参考的残留行、失败时不给），应统一为一种并去掉兜底。V21.1四任务批次中，有效子代触发“大部分被替换”的比例为Refine 17%、Crossover 39%、Explore 89%。V21.1仍在运行的5路已于15:50停止，预算交给V21.2与回放。证据保存在`experiments_result/analysis/20261110_v21_2_replay/`。

V21.3：完整呈现每个演化步骤的实际改动。回放显示，模型能从真实diff读出修改决定没有写的改动，而读错的事实恰好出在被“most of the code was replaced”隐藏的卡片上。用户据此确定V21.3只解决一个问题：轨迹证据在传递中的信息损失。规则是三类材料各用一种表达：当前算法给完整代码；独立程序（探索记录、参考本身、初始祖先）给设计与成绩；有父代的演化步骤（祖先、有效与失败子代、参考形成步骤）给修改决定、规范化源码的完整unified diff（3行上下文，无相似度阈值）与结果，代码无法解析时比较原始文本并标明。参考改写步骤的“仍保留的新增行”格式删除。指令、展示条数、选择与输出协议不变；“从结果反推原因”留待之后单独处理。在49个回放状态上渲染，Refine上下文中位数从约7.0k字符增至14.2k（最大44.6k），Crossover从6.6k增至14.0k，Explore不变。上下文翻倍是完整呈现的真实成本；我没有加上限，若它带来问题，应在行为中直接看到。完整形成diff也意味着Crossover默认条件会看到参考的大部分代码，`--reference-code`的对照含义因此改为“按形成步骤组织的代码”对比“额外的平铺源码”。TSP状态419中，Algorithm 43原来只显示改写规模，现在可见它删除MST估计、改为前5个候选的最近邻补全，模型当时“MST带来改善”的说法可以直接被代码否定。

V21.3改为分层证据。审查兜底时发现三处由系统替模型决定的信息：卡片中的“Decision”是我从`analysis`按“最后一句”抽取的，把未经验证的意图当作事实标签传下去；失败摘要丢掉了抛出异常的代码行，只剩差分中无法对应的原始行号；Base在Crossover没有参考时静默改为Explore。第三处实际走不到：初始化留下至少5个有效程序，除非其中4个代码相同，中位数以内总有不同于父代的参考；现改为直接报错。用户随后确定借鉴DeltaEvolve的多层节点与渐进展示。我只借鉴组织方式，不让生成器另写修改摘要和假设：DeltaEvolve的L2是模型自述，回放已经显示自述会被下一次生成当作事实。三层都来自已有字段或系统测量：L1为`design`，L2为相对父代的完整diff，L3为完整代码。角色决定层级：当前与参考算法给L1＋L3，同起点有效与失败子代给L1＋L2（失败另给异常所在的候选源码行），最近3条祖先给L1＋L2，更早的祖先只给L1，探索记录不变。参考按用户意见只给个体本身，不给形成步骤；回放中另给完整源码的一组照搬比例与改善数都没有更差，这一简化有依据。`analysis`的任何部分都不再进入后续上下文。在49个回放状态上，Crossover上下文中位数为8.9k字符（V21.2为6.6k，上一版V21.3为14.0k），Refine为16.1k（V21.2为7.0k），其中各卡片的设计描述合计约3.9k；Refine变长主要来自每张卡片都带设计描述，以及子代差分的删除行重复当前代码。机制1中“没有合格参考时把C的权重并入E”与Base原有做法同类，尚未改动。

机制1中同类的兜底也已去掉：原先没有合格参考的父代不产生C动作，并把C的基础权重并入E。现在只要Crossover权重为正，分配前要求每个父代都有参考，没有则报错；`crossover_weight=0`的消融不受影响。受影响的测试原本用1–2个程序构造搜索，改为3个初始程序或显式关闭Crossover，原“缺参考转E”的测试改为检验报错。

## 11月10日：V21.3回放，完整差分没有减少错读，结果与算法编号的对应反而变差

在V21.2回放使用的同一批49个状态上，我用V21.3（`ad77fc2a`，快照`20261110b_traceaad_v21_3`）各生成3次，并与已有的V21.1、V21.2两组配对。程序指标没有分开。Refine改善数为V21.1 7/39、V21.2 6/39、V21.3 10/39，按状态配对V21.2→V21.3为6胜4平3负。Crossover三版都是5/54或8/54。Explore从V21.2的8/54降到2/54，但同一状态下两版Explore提示只差当前算法的一行Design，所以这个差距只能看作采样波动。它也说明了这次回放的分辨率：Refine的10对6与这一波动同一量级，不能当作改进。

分析文本给出了一个明确的反向信号。我把Refine分析里所有提到卡片编号的句子逐条与卡片上的结果标签核对。V21.2约25句，没有方向错误。V21.3约16句，其中5句的方向与标签相反，分布在4个状态。OP 354的一个样本说Explore子代196、345“显著改善”，卡片写的是−14.88→−12.56、regressed，模型据此引入贪心前瞻，子代退化到−13.86。OP 354的另一样本说32和220“比二次形式更好”，两者都标为regressed。OP 637说39“显著改善”，同一句又说它regressed。TSP 371说224“regressed”，实际为improved，而这个样本最终写出的程序恰好与224同分。CVRP 344把一次微小改善说成退化。5处中有3处在OP，3处对应的子代退化。从退化编造原因的写法没有减少：Refine中带regressed的断言里，V21.2有12/19附带原因词，V21.3为6/11。

对错读原因，我目前的判断是，结果标签与算法编号之间的距离变远了。V21.2的卡片是“编号—决定—改动摘要—结果”，5到20行。V21.3把结果放在设计描述和完整diff之后。被错读的卡片中，70为147行，196、345约65行，39为30行；V21.2中同样这几张卡片是5到6行。但32、220、224在V21.3中也只有18到26行，与读对的卡片同样长，所以长度只能解释一部分。另一部分可能来自卡片的语义摘要变了：V21.2的决定句描述的是这一步做了什么，V21.3的`design`描述的是整个程序。模型容易把程序层的设计与这一步的结果混在一起，再按自己的先验评价方法，例如认为“指数衰减更柔和，所以更好”。此外，Refine的子代列表中包含父代的Explore子代，它们相对父代的diff实际是整段重写，并不是对父代的修改。

认识变化：完整差分修复了信息丢失，但没有修复“读结果”的问题，还在一部分卡片上让结果更难对应到算法。下一步最直接的检验是把结果行移到卡片头部，紧跟编号、父代和算子，其他不变；只在13个Refine状态上重跑，用同一逐句核对比较方向错误。如果错误回到V21.2的水平，说明问题在材料顺序；如果不回到，说明`design`替代决定句才是主因。原始数据在server4快照`experiments_result/replay_v21_3/`（`replay.jsonl`为V21.3，`combined.jsonl`含三版），核对脚本为同目录的`claims.py`与`sentences.py`。

同日用V21.1全部运行统计了Crossover与Explore可利用的轨迹。Crossover共2508次，35%的接收方此前没有任何有效尝试，只有3%此前用过同一参考；有历史的1633次中，54%至少有一次修改新增了参考独有的代码行（逐行重叠，偏宽）。所以按相关性挑选接收方历史只能按计算内容，不能按参考身份，而且只影响约三分之一的Crossover。Explore的2973个有效Init/Explore起点中，83%没有任何有效后代，7%有后代但没超过起点，10%被超过；在被超过的起点中，起点到最优后代的路径中位长度为1。现在的探索记录已经能看出“未发展”，缺的是“发展后变好”的原因：后代最优分数既可能来自这个想法本身的修改，也可能来自Crossover带入的别的计算。拟议的补充是对变好的记录给出起点到最优后代的完整diff，不按分数挑“关键一步”。主要风险是Explore模仿展示的成功改动。

## 11月10日：V21.3的融合历史改为“以同一参考的此前融合”，结果移到卡片头部

用户确认，Crossover和Explore缺的是两种不同的过程信息。Crossover要知道某项计算以前怎样接入别的算法、暴露了什么问题；Explore要知道各方向怎样形成和发展。两者都不加反思模块，只改材料与设计问题的对应关系，并直接修改V21.3，不再叠加版本号。先改Crossover。原来的历史按算子类型选取，即“先取当前父代此前的融合，再取最近的其他子代”，不看当前参考，所以可能把与当前参考无关的接入记录放进提示。现在只取此前以同一参考进行的融合：先取当前父代的，再取其他接收方最近的；有效最多3条，失败最多2条；每条给结果、设计和相对其父代的差分。失败记录必须保留，因为“完整移植导致超时”这类问题正是接入经历的一部分。没有这样的记录时不展示历史。用户提出的第三类（当前父代以前对类似计算的融合）需要判断计算之间的关联，暂不做。在V21.1中，参考此前被其他接收方用过的融合占31%，同一对父代与参考占3%，所以约三分之二的融合不看历史。在18个回放状态上渲染，15个没有相关记录，Crossover上下文中位数从8.9k字符降到4.5k。

同时，卡片顺序改为“编号、父代、算子、结果、设计、差分”，针对的是上一节的结果错读。Explore的发展关系待Crossover之后再做。届时的方案是：对代表性探索记录，给出最好后代的设计，以及起点到最好后代的路径算子序列（例如Refine；Crossover with Algorithm 77；Refine），用来区分“方向自身发展”与“被融合替换”，不给差分。

有同参考历史的3个Crossover状态进一步暴露了“引用历史”和“利用历史”的区别。TSP 418的三个样本都将两次正常完成但质量退步的融合归因为计算成本，sample 1还编出先前超时；两个样本删除父代2-opt后退步，另一个加入对所有候选相同的常数，成绩持平。TSP 712的两个样本沿用参考中包含零对角线的行最小值，声称的连通性项实际恒零；第三个设计了路径相关惩罚，但超时。CVRP 844的三个样本都改善，能具体接入depot倍率等计算，却都没有明确分析先前记录815，不能归功于历史。我的判断是材料相关性已收窄，计算是否生效和因果解释是否有依据仍未解决；本轮不据此继续叠加提示或模块。条件、源码、原始数据和逐项核对见[独立记录](2026-11-10-V21.3结果前置与同参考融合回放.md)。

## 11月10日：恢复形成轨迹，压缩历史包装

用户随后修正简化边界：形成路径说明当前计算怎样被引入、替换与调整，同父代尝试说明从当前位置已经试过什么；两者不可替代。我此前把“同起点证据最直接”用于排除形成信息，使机制退化成局部试错记忆。现在保留两类信息，简化重复字段、历史完整代码、Design和analysis，不再把“暂未测出形成路径收益”当作删除它的充分理由。

## 11月10日：恢复三算子的不同轨迹用途

用户再次明确，机制二的主线一直包含三种互补用途：Refine借形成和修改经历决定改什么，Crossover借形成与迁移经历决定借什么、怎样接入，Explore借方向和后续发展决定探索什么。我上一轮仅恢复Refine、继续将另外两种算子设为静态输入，仍然把“简化实现规则”混同于“删除过程信息”。我据此恢复三算子轨迹框架，不再用眼下哪一部分有最直接正向证据来代替机制本身的研究问题。恢复材料不代表已有收益结论；模型利用经历提出设计决定，系统不要求它证明历史原因或组件贡献。

V21.3现在分别提供三类材料。Refine保留当前形成路径和同父代各类尝试；Crossover增加参考的真实形成diff和历史接入，接入材料同时包括当前父代过去的融合、以当前参考为来源的迁移，每条保留自身接收方与参考条件，不把不同接收方的同分代码合并；Explore恢复Init/Explore起点及后续发展，给出生Design和成绩、实际开发次数，若后来变好则给较好实现的Design与真实Refine/Crossover算子路径。后续Explore另起记录，Crossover路径保留参考编号，不把后代改善归因为起点思想。

选择规则同时做减法：形成路径用最近窗口，不再按成绩波动或留存行选取；尝试和接入按最近的有效、失败记录展示，不额外突出最好示范。Explore按出生或后续开发中的最近活动选择，最多6条不同源码的起点；相同源码只展示最近活动的实际分支，其统计不合并为思想层的结论。默认形成8步、有效3条、失败2条沿用现有窗口设置。三种算子继续单次`analysis → code → design`，不增加历史解释器、语义匹配或反思调用。`--reference-code`保留为额外的完整平铺参考源码；形成diff自身可能已经包含参考代码，所以该开关不表示有无任何参考源码。新协议为`operator_trajectory_context_v1`，历史运行仍归原冻结源码。
