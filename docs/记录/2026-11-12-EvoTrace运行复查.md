# EvoTrace运行复查：局部统计与复合机制

**用户指出应评估开发、淘汰、反思与后续设计的复合过程。我撤回仅依据冠军采样率就优先增强质量偏好的建议。** 下文保留局部统计作为过程证据；整体判断与修正见“复合机制复查”。

## 1. FSSP：质量项在较好节点之间缺少区分

实际父代选择中，EvoTrace选择当时冠军（含并列）的比例为8.7%，Base在对应评价前缀为83.3%。EvoTrace质量项使用中位数与MAD归一化后的sigmoid，较好节点容易同时接近1，接着由累计子代数折扣决定相对机会。

种子0第24次尝试给出一个具体例子：冠军#15适应度3937.0，已有2个子代；候选#13适应度3947.375，尚无子代。两者质量项分别为1.0和0.99574，但采样概率分别为4.63%和13.83%。较差算法因此得到约3倍机会。

为区分质量项和子代折扣，我在同一批229个实际树状态上重算概率，候选池保持一致：

| 概率规则 | 冠军平均概率 |
| --- | ---: |
| 当前规则 | 8.52% |
| 只去掉子代数折扣 | 8.11% |
| 质量改为 `exp(-适应度分差)`，保留原折扣 | 69.80% |

这定位了概率变化的来源：单独去掉子代数折扣并不能集中开发冠军。重算没有生成或评价后续算法，最终收益需同起点续跑检验。原始树状态、逐步概率和案例见[概率分析](../../experiments_result/analysis/evotrace_audit_20261112_1120/fssp_allocation.json)。

## 2. TSP：可执行性检查没有发现返回动作的语义错误

种子0的Explore候选#62使用子集动态规划（Dynamic Programming, DP），成绩从父代#49的6.38371退化到20.32366。它的 `dp[full_mask, i]` 表示从当前节点出发、遍历候选集合后以i结束的最短路径。最终循环却将这个末端节点i作为下一步节点返回，变量名还写为 `best_first_node`。

这段程序接口合法、返回值合法，执行也正常；错误在于内部DP状态与要求返回的第一步不一致。反思账本保留了“DP init with entry cost + no dest/density heuristic: score 20.3237”，没有指出这个状态含义问题。

同批#76同样使用子集DP，将DP初值改为0并在选点时加入入口代价，实测成绩为6.50062。因此，这次失败不能直接解释成DP方向没有价值。两份程序和差分分别见[候选62](../../experiments_result/analysis/evotrace_audit_20261112_1120/cases/tsp_seed0_62.py)、[候选76](../../experiments_result/analysis/evotrace_audit_20261112_1120/cases/tsp_seed0_76.py)、[实际差分](../../experiments_result/analysis/evotrace_audit_20261112_1120/cases/tsp_62_to_76.diff)。这是同批已发生的两个变体，不是本轮修复后重测。

## 3. 对上一轮判断的更新

- 410个可行Explore子代中，11个与此前可行程序的最近AST距离低于0.12，比例2.7%；没有规范化源码完全重复。大量结构近似改写当前不再是首要现象，生成程序的计算含义更值得具体检查。
- 28轮整理均能用冻结源码重放出实际保留集合。本次未找到“前10名候选优于全部近邻、近邻全部为结构补入节点、且仍有容量”的排斥实例。我不再将上一轮的案例直接当作本批首要问题。
- 540次区域反思没有调用或解析回退。反思约占当前总tokens的17.2%。格式层面的正常不代表经验已改善后续搜索。

## 复合机制复查

我现在优先关注的设计缺口是：程序版本被淘汰的理由、一个方向得到过多少开发、这条经历适用于什么计算背景，尚未在压缩后的经验中清楚区分。它们通过预算、淘汰和后续生成相互影响，不能分开用冠军采样率、单步改善率或格式正确率判断整体是否合理。

### 反思的定位合理，输出的证据条件仍需核对

路径经验保留形成过程、旁支经验保留已移除尝试，是合理的压缩分工。保留分支仍通过现存代码和路径呈现，因此旁支经验主要来自淘汰样本，本身不等于整个上下文只包含负面证据。

问题在于，旁支整理输入保留了真实父代差分，输出却主要要求“修改的计算：绝对成绩”。同一任务中的算法成绩可以比较，但局部改动的效果依赖它所在的原始算法。来自不同实际父代的尝试被挂到最近保留祖先后，这个条件尤其容易丢失。反思不需要编造历史原因，仍需要保留能够支撑下一次设计决定的比较条件。

同一份快照的392个旁支整理区中，115个包含实际父代不同于承接节点的尝试，93个包含多个实际父代；81个区包含相对自身父代改善的移除节点，合计101个。这些节点可能因相似性、更好的替代版本或容量竞争而被移除。“被淘汰”因此不能直接解释为“该计算尝试失败”。

### 预算规则可以作为简单启发式，冠军比例不能评价它的合理性

当前权重使用节点的当前成绩和累计子代数，分配的是当前版本的后续尝试机会。最终需要判断的是：有限预算内，哪个起点能在已有经验帮助下产生有用的后续改进。成绩和子代数是这个价值的代理，当前没有证据证明代理失效，也没有证据证明更集中开发冠军会更好。

预算规则与其余机制有两处需要一起考察的联系：同方向保留多个版本会累加该方向的父代概率，而新版本重新从较低子代数开始；反思改变生成上下文后，原节点的累计子代折扣继续保留。二者都影响后续开发机会，不能只由单个冠军的概率解释。经验即使不直接进入采样公式，也能通过生成的新代码与评价间接反馈预算，不能把没有直接使用经验分数当作循环中断。

### 当前最值得检验的是浅开发、淘汰与方向经验的联动

按现有Explore派生编号统计，410个可行起点中已有260个方向全部离开可选树，其中215个只经历一次实际评价，242个没有产生后续版本。有限预算下，浅尝后放弃可以是合理取舍。这些记录能说明某个实现的表现和当时的选择，不能说明整个计算方向已充分探索。

Explore指令要求参考方向版图与淘汰方向，避免已覆盖机制；版图又以派生编号和AST差异近似组织。需要检验的风险是：一次未充分开发的实现被移除后，摘要只保留计算和成绩，后续设计将这种有限经历理解为方向已经覆盖。这个风险源于多个机制的组合，现有快照尚未识别它对整体收益的因果影响。

540次反思输出中，392次是旁支经验、148次是路径经验。对至少存续10次后续尝试的348个旁支经验版本，111个直接进入过Refine或Crossover生成，其余多数只直接进入Explore；这些经验还可能经下一次反思继续合并，所以展示次数不能等同于使用价值。需要追踪的是信息是否在适当的起点、保有适用条件地影响下一轮设计。

## 调整后的优先事项

我将审查单位改为一轮完整的“开发—淘汰—反思—再开发”。先核对这轮中经验的对象、比较条件与尝试程度是否保持一致，以及保留的算法能否利用更新后的经验继续发展。候选验证应从同一树状态出发，至少跨越一次经验更新和后续开发；固定其余政策后比较经验的作用。更集中开发冠军暂不作为默认修正。

全局过程数据与可复查脚本见[复合循环记录](../../experiments_result/analysis/evotrace_audit_20261112_1120/global_loop.json)和[分析脚本](../../experiments_result/analysis/evotrace_audit_20261112_1120/global_loop.py)。这些数值是同一批轨迹内的事件计数，不作为独立重复的数量。

本轮只做只读查询与离线重放，没有修改方法代码、停止运行或启动新实验。机制改动仍需围绕上述问题讨论确定。
