# AAD 生成侧：从原始提示到轨迹接续开发

日期：2026-11-03（北京时间）。专项范围：生成表示、历史上下文和精炼／探索／融合提示。只做文献与作者源码核查；未运行算法搜索、模型调用或评价实验。未修改实现、method、WWH 或周报。

## 结论

我建议先采用一个简单方案：**当前父代提供完整代码、设计和成绩；祖先路径按形成顺序呈现修改；全部直接子代按同一父代列出尝试与反馈；经验作为待判断的启发；一次调用输出简短 `analysis`、完整 `design` 和完整 `code`。** 精炼、探索、融合共用这些材料，只改变本次修改要求。先选算子、再按预算机制选父代的约定保持不变。

这个建议有三层依据。EoH 的比较较直接地检验了“设计文字加代码”相对于只给代码的价值；ReEvo、RefineEvo 的实验说明反馈文字可能改善生成；MCTS-AHD 和 PathWise 确实把祖先材料或同起点生成反馈放进某些模型调用。然而，**这五个来源都没有单独证明“有序祖先修改＋全部直接子代＋累积经验”优于更简单上下文，也没有隔离历史全文、差分和摘要的效果。** 因而，下面的提示是可直接试用的候选方案，不是已证实最优的机制。

最重要的表示取舍是：**保留每条历史记录，不等于重复展示每份完整源码。** 当前父代必须完整，融合参考算法也应完整；历史优先保留具体改动及其结果，避免用大量相似旧代码挤掉本次设计空间。若历史摘要不能说明修改，补充对应源码片段或差分，明确其基准版本。这个选择是我的机制判断，现有消融尚不能裁定它。

## 1. EoH：设计文字与源码共同呈现，有较接近目标的表示消融

**作者机制。** 个体以自然语言思想（thought）与源码共同表示。当前源码 `_parent_block` 逐个插入 `algorithm`、`code`，未插入成绩、祖先或子代反馈。E1 要求产生不同形式；E2 先找共同骨架再设计和实现；M1 修改既有算法；M2 改参数；M3 分析并简化可能过拟合的组件。初始化、E1、M1、M2 通常要求一句设计文字与代码；E2 多一个显式的骨架辨认步骤。不能把它们统一称为已有独立 `analysis/design/code` 协议。

精确位置：[evolution.py:169](/home/fang/code/LLM4AD/reference_code/EoH/eoh/src/eoh/eoh/evolution.py:169)、[E2:192](/home/fang/code/LLM4AD/reference_code/EoH/eoh/src/eoh/eoh/evolution.py:192)、[M1–M3:203](/home/fang/code/LLM4AD/reference_code/EoH/eoh/src/eoh/eoh/evolution.py:203)。原论文附录也说明父代描述与实现共同入提示：[7-appendix.tex:113](/home/fang/code/LLM4AD/papers/Evolution_of_Heuristics_Towards_Efficient_Automatic_Algorithm_Design_Using_Large_Languag/7-appendix.tex:113)。当前代码经过后续维护，以上具体字符串只归于所列 HEAD。

**实验所见。** EoC 与 EoH-e1 都只用 E1，前者没有自然语言描述，后者有；实验使用同一初始种群，并匹配总评价个体数。它比“完整 EoH 对 EoC”的比较更接近隔离表示因素。完整方法与 EoH-e2 的差别则是一起加入三种修改算子，不能拆出每种修改的单独贡献。位置：[4-experiment.tex:176](/home/fang/code/LLM4AD/papers/Evolution_of_Heuristics_Towards_Efficient_Automatic_Algorithm_Design_Using_Large_Languag/4-experiment.tex:176)、[控制条件:205](/home/fang/code/LLM4AD/papers/Evolution_of_Heuristics_Towards_Efficient_Automatic_Algorithm_Design_Using_Large_Languag/4-experiment.tex:205)、[结果:218](/home/fang/code/LLM4AD/papers/Evolution_of_Heuristics_Towards_Efficient_Automatic_Algorithm_Design_Using_Large_Languag/4-experiment.tex:218)。

**作者解释。** 思想文字有益，多个提示策略有正向作用。

**我的判断。** 保留“设计＋代码”比只传代码有较直接的先例；但这不能区分输入描述、生成设计文字及额外推理各自的贡献，更不能证明输出分析应很长。E2 提取共同骨架适合借鉴，但融合不必寻找共同点：真正互补的算法可能恰好没有共同骨架。

## 2. ReEvo：比较反馈进入生成，常规比较不是同父代对照

**作者机制。** 常规选择从种群取两个成绩不同的个体；短期反思看两份完整源码及好坏次序，输出不足 20 个英文词的提示。交叉调用重新看两份代码和反思；变异调用看最好个体源码与累积长期反思。生成器要求只输出代码。短期提示不展示具体成绩数值，也不声明两个个体有共同起点。

精确位置：[选择与反思拼接:314](/home/fang/code/LLM4AD/reference_code/reevo/reevo.py:314)、[user_reflector_st.txt:1](/home/fang/code/LLM4AD/reference_code/reevo/prompts/common/user_reflector_st.txt:1)、[crossover.txt:1](/home/fang/code/LLM4AD/reference_code/reevo/prompts/common/crossover.txt:1)、[mutation.txt:1](/home/fang/code/LLM4AD/reference_code/reevo/prompts/common/mutation.txt:1)、[调用:408](/home/fang/code/LLM4AD/reference_code/reevo/reevo.py:408)。

**实验所见。** 一项更窄的比较是在 TSP50 的 ACO 启发式生成中，以当前及上一个程序作比较对象，种群设为 1、不做变异，切换短期反思有无；每组 3 次、每次 40 步随机游走。另有 TSP100 白盒／黑盒下移除短期反思、长期反思、交叉或变异的消融。位置：[06_ablation.tex:39](/home/fang/code/LLM4AD/papers/ReEvo/sections/06_ablation.tex:39)、[组件消融:62](/home/fang/code/LLM4AD/papers/ReEvo/sections/06_ablation.tex:62)。

**作者解释。** 反思类似语言梯度，改变可生成的邻域并使搜索地形更平滑。

**我的判断。** 短期反馈值得进入生成；但自适应随机游走两组会产生不同轨迹，并非固定同一目标父代的配对生成比较。常规好坏个体比较也不能确定哪些代码差别导致成绩差别。我们可借鉴短而具体的反馈，不应照搬“较优代码中的不同结构就是有效原因”。

## 3. RefineEvo：trajectory 是单次父子摘要，经验消融最接近归因问题

**作者机制。** `operate` 插入父代设计与完整源码，再插入成功／失败经验。实际 op1–op5 分别是异形式探索、骨架启发、修改、参数调整、简化；本地 README 对部分算子的概括与源码不一致，应以 `op_desc_dict` 与调用为准。生成输出为一句设计和完整代码，没有独立分析字段。

精确位置：[算子定义:208](/home/fang/code/LLM4AD/reference_code/RefineEvo/evo_interface.py:208)、[生成拼接:260](/home/fang/code/LLM4AD/reference_code/RefineEvo/evo_interface.py:260)、[生成格式:17](/home/fang/code/LLM4AD/reference_code/RefineEvo/prompts/common/system_generator.txt:17)、[经验措辞:12](/home/fang/code/LLM4AD/reference_code/RefineEvo/prompts/common/user_operate.txt:12)。父代成绩用于其他环节，但此处的父代文本循环只插入描述与源码，不能笼统称“生成器看到父代全部评价信息”。

`build_trajectory` 为一次演化打包父代、子代描述与目标值、算子目标和相对最好父代的增益。设计描述截到 400 字符；这个对象没有完整历史源码，也没有多步祖先序列或同父代全部尝试。它用于随后经验提取，不是原样作为下一次生成的完整局部历史。位置：[evo_interface.py:716](/home/fang/code/LLM4AD/reference_code/RefineEvo/evo_interface.py:716)。失败提取提示要求总结警告，并给出适用情形：[user_reflector_fail.txt:1](/home/fang/code/LLM4AD/reference_code/RefineEvo/prompts/common/user_reflector_fail.txt:1)。

**实验所见。** 论文 `w/o trajectory` 将父子追踪改成种群两两比较，报告的目标任务结果变差；`w/o situation` 是取消检索限制、注入全部经验，既改变相关性，也改变注入量。位置：[04_experiment.tex:273](/home/fang/code/LLM4AD/papers/RefineEvo_Planning-Guided_Heuristic_Evolution_with_Bidirectional_Experience/04_experiment.tex:273)、[解释:330](/home/fang/code/LLM4AD/papers/RefineEvo_Planning-Guided_Heuristic_Evolution_with_Bidirectional_Experience/04_experiment.tex:330)。

**作者解释。** 父子谱系形成更可操作的因果线索，情形匹配避免经验误用。

**我的判断。** 父子比较比任意两两比较更容易解释，是合理的经验来源；它仍不能单凭整段代码修改建立因果。此消融检验经验来源，不检验生成器读取多步轨迹，也不隔离更长历史的增益。最值得修正的是直接把失败经验写成禁令：生成提示应保留失败发生的起点与改法，允许改变实现或搭配后再试。

## 4. MCTS-AHD：真正的祖先源码先例，但顺序关系在提示前被重排

**作者机制。** s1 从当前节点沿父指针取到根之前的全部节点，包括当前节点；每份材料含设计、源码、目标值。随后 `population_management_s1` 按设计文字去重、按目标值从大到小排序。生成提示要求从这些算法提取有益思想，再描述和实现新算法。故“材料来自真实祖先路径”成立，“模型看到按演化顺序排列且带逐边修改的路径”不成立。

精确位置：[取路径:76](/home/fang/code/LLM4AD/reference_code/MCTS-AHD-master/source/mcts_ahd.py:76)、[去重排序:18](/home/fang/code/LLM4AD/reference_code/MCTS-AHD-master/source/pop_greedy.py:18)、[s1 提示:157](/home/fang/code/LLM4AD/reference_code/MCTS-AHD-master/source/evolution.py:157)。不能因为 `expand` 把 `children_info` 传入下层，就认为全部子代进入了提示；实际 `_get_alg` 按算子调用的生成函数，只读取选中的父代或 s1 集合：[evolution_interface.py:91](/home/fang/code/LLM4AD/reference_code/MCTS-AHD-master/source/evolution_interface.py:91)。

e2 还有一个可借鉴的非对称要求：保留当前父代形式，借鉴另一个算法。它比“混合两个算法”更接近在当前工程上融合一个部件：[evolution.py:101](/home/fang/code/LLM4AD/reference_code/MCTS-AHD-master/source/evolution.py:101)。

**实验所见。** 论文移除 s1 后至少一项任务变差；但该比较移除整个动作，并未以同量无谱系材料替代，不能拆出祖先身份、源码数量、成绩展示与提示要求的作用。正文写三次运行、表注写五次、原方法行标十次，不能把这项表格当精确等重复数的配对证据。位置：[icml2025.tex:417](/home/fang/code/LLM4AD/papers/MCTS-AHD/icml2025.tex:417)、[表格:428](/home/fang/code/LLM4AD/papers/MCTS-AHD/icml2025.tex:428)。

**作者解释。** s1 的效果体现树上有组织样本的价值。

**我的判断。** 可以说祖先材料确实用于生成，不能说路径因果关系已经经过验证。我们的有序修改记录相对它多保留了形成关系；这项信息是否值得占上下文，需要另测。

## 5. PathWise：同父代、同动作的实现比较确实存在，但没有完整同起点历史对照

**作者机制。** 世界模型生成调用插入所选父代的描述、源码与成绩、自然语言修改指令、此前代码生成反思，输出不足 30 个英文词的描述与代码。同一动作会生成多份 rollout；代码生成 critic 在该动作内过滤无效结果，取最好和最差的有效源码比较。只有至少两个有效且成绩不同时才形成该项反思。

精确位置：[父代与指令拼接:750](/home/fang/code/LLM4AD/reference_code/PathWise/pathwise.py:750)、[生成模板:1](/home/fang/code/LLM4AD/reference_code/PathWise/prompts/common/user_world_model.txt:1)、[同动作比较:1025](/home/fang/code/LLM4AD/reference_code/PathWise/pathwise.py:1025)。同一动作共享父代集合和基础指令，但部分 rollout 会另加探索短语，不能视为仅采样随机性不同，见同文件第 791–801 行。

**实验所见。** TSP 构造任务用 GPT-5-nano(low)、五次运行，移除 world model critic 后成绩变差；还有分别移除 policy critic 及提示扰动的比较。它没有把同起点比较换成等量随机个体比较，也未单测全部直接子代记录。位置：[example_paper.tex:832](/home/fang/code/LLM4AD/papers/PathWise/example_paper.tex:832)、[提示扰动消融:862](/home/fang/code/LLM4AD/papers/PathWise/example_paper.tex:862)。

**作者解释。** 两种 critic 分别改善行动规划与代码修改，形成互补反馈。

**我的判断。** 同起点比较是可以落实到模型调用的机制，而非只有图标签。它更接近区分“同一个修改指令的不同实现”，我们全部直接子代则还覆盖同父代的不同算子和不同思想。二者不等价。可以借鉴比较方式，但不要只留下最好／最差：无效实现、持平尝试和中间结果也可能解释下一步为何需要换实现。

## 跨来源判断：哪些因素真正被隔离

| 问题 | 最接近的原始对照 | 当前能作出的判断 |
| --- | --- | --- |
| 设计文字是否值得保留 | EoC 对 EoH-e1，同 E1、同初始种群、匹配评价数 | 有直接先例；未区分输入描述与输出设计各自的贡献 |
| 短期反馈文字是否改变生成 | ReEvo 有／无反思随机游走 | 有较窄对照；不是冻结同父代材料的逐项比较 |
| 经验应从父子关系还是任意对比提取 | RefineEvo `w/o trajectory` | 比较经验来源；不涉及多步生成历史 |
| 真实祖先材料是否被模型读取 | MCTS-AHD s1 的调用链 | 确实读取；移除 s1 不能隔离谱系关系 |
| 同起点反馈是否实际存在 | PathWise 同 action 的 rollout critic | 确实比较；critic 消融不隔离同起点身份的作用 |
| 全历史源码、差分或摘要哪个更好 | 五个来源中未找到直接替换对照 | 应作为待检验选择 |
| 分析→设计→代码是否优于设计→代码 | 五个来源中未找到同输入、同生成成本的直接对照 | 仅把简短分析作为可审查的设计依据，不能宣称已证实提升 |

## 生成上下文：最小可采用格式

下面是输入材料规范，不要求新建实现模块。每条真实记录保留身份；同一结果出现在路径和经验中时引用同一事件，不算新增证据。字段未知时写“未记录”，不要让模型补写历史。

```text
[任务]
目标与分数方向；接口；合法性与资源约束；评价条件及反馈含义。

[本次动作]
operator = 精炼 | 探索 | 融合
父代和算子已经选定。本次只生成一个候选。

[当前父代 p]
node_id；完整设计；完整代码；成绩；评价状态和评价条件。

[形成路径：最旧祖先 → ... → p]
每个节点：node_id、设计、成绩、评价状态。
每条边：event_id、source_id → target_id、算子、实际修改、前后成绩。
修改写具体计算或数据流；需要时附有基准版本的源码差分／片段。

[从 p 出发的全部直接尝试]
child_id；event_id；算子；设计；实际修改；成绩或无效原因；与 p 的差别。
失败、持平、成功均保留。明确 donor_id（若有）和评价条件差异。

[累积经验]
经验内容；发生时的算法结构／情形；来源事件（若已有）；观察与解释。
保留相反证据；注明是否与上面的局部记录来自同一次评价。

[融合参考算法：仅融合时]
已选参考算法的完整设计、完整代码、成绩与评价条件。

[本次算子要求与输出格式]
见下面提示。
```

“实际修改”优先来自源码核对；如果只有当时生成者的修改说明，明确标为“生成时说明，未核对”，不要把它改写为事实。历史片段不能取代当前父代完整源码。这里不要求再调一个模型生成历史摘要，也不假定来源事件已经全部可用。

| 候选 | 解决的问题与最小做法 | 潜在代价与取舍 |
| --- | --- | --- |
| 当前完整源码＋设计 | 保证模型能接续真实计算，而非接续一句模糊思想 | 有长度成本；作为当前固定输入保留 |
| 每个历史节点都给完整源码 | 历史设计文字可能漏掉实现变化 | 重复多、容易照抄；仅作为表示对照，不作为首选 |
| 有序边记录＋全部子代记录 | 保留形成关系和同起点尝试，不删失败历史 | 摘要可能遗漏交互；作为首选候选，关键处附片段或差分 |
| 全历史只给差分 | 更精确地表示编辑，减少重复源码 | 模型需重建中间状态；仅配合明确基准使用，不要求模型用长差分链重建父代 |
| 只给抽象经验 | 节省长度、便于跨算法借鉴 | 容易把解释固化为处方并丢失起点；不替代本地记录 |
| 单次短分析→设计→代码 | 让本次修改可追溯到具体观察，并检查设计是否落到计算 | 分析可能事后合理化；限定为简短设计依据，不加多代理与审核循环 |

## 可直接采用的提示草案

以下提示刻意不要求复述整段历史，不要求满足每条经验，也不要求每次都证明历史设计正确。输入材料若已过长，应先明确容量问题；不能把“全部直接子代”悄悄改为只展示成功者。

### 共用阅读与输出要求

```text
你将接续开发当前父代算法。任务、当前父代、形成路径、全部直接子代、
累积经验以及本次算子已提供。历史记录描述已经尝试过的候选方案，
不代表当前结构已最优，也不要求保留所有历史部件。

先检查当前代码实际执行的决策规则。沿祖先路径识别形成当前结构的修改；
比较从当前父代出发的尝试，关注改动、实现和评价条件有哪些相同与不同。
只展开会改变本次方案的观察。不要复述全部材料。

成绩变化首先属于记录中的那次实现与评价。一次失败不能排除整个思想；
一次成功也不能证明同时修改的每个部件都有益。共同起点便于比较，
但未消除实现差别、多部件交互或评价噪声。
同一评价在历史与经验中重复出现时，只当作一份证据。

经验是可以借鉴、调整或不采用的启发。指出与你的方案直接相关的经验，
以及它与当前结构的联系；没有相关经验时按当前代码和反馈提出方案。
允许采用更简单、足以实现本次目标的设计。

输出一个 JSON 对象，包含：
analysis：简短设计依据。指出最相关的历史观察、你对原因的判断、
         本次要解决的问题。区分记录事实与尚未检验的解释。
design：候选算法的完整设计。说明决策规则、关键计算及相对父代的改动；
        不依赖“同父代”“沿用之前”等指代才能理解。
code：符合任务接口的完整代码。代码必须实现 design 中提出的计算。
不要编造新候选的成绩，不要重复输出全部历史，不要只输出补丁。
```

### 精炼：在当前设计内改进

```text
本次算子：精炼（Refine）。
在当前设计的主要决策规则内，改善实现、参数、数值处理、计算效率或冗余结构。
选择当前代码或同起点反馈揭示的一个具体问题，给出足够解决它的修改。
允许删除无必要部件，允许重写实现，不要求逐行保留父代代码。
说明保留的主要决策规则与实际改动。不要仅为产生差异引入另一套算法思想。
如果重试此前未改善的改法，说明这次改变了哪项实现或组合。
```

对应问题是精炼退化为随机改常数，或不断叠加附加项。最小机制是明确主要决策规则与本次局部问题。代价是文字边界可能把有价值的结构变更排到探索；因此不把“改动行数少”当精炼标准。

### 探索：引入一个有计算含义的新思想

```text
本次算子：探索（Explore）。
针对当前设计或已有尝试显露的限制，引入一个新的算法思想。
在 design 中说明新的决策依据／状态表示／更新规则是什么，
它怎样改变实际计算，为什么值得在这个起点尝试。
不要把重命名、同一公式换写法或只改常数当作新思想。
允许替换当前主要机制并删去旧部件；以更简单且足以实现新思想的方案为宜。
历史较差的候选可以提供思想，历史高分结构也可以被替换。
若新思想曾经失败，指出旧实现与本次方案的具体区别；不用保证它立即优于父代。
```

对应问题是旧源码牵引使探索退回参数微调，以及失败记录过早封死方向。最小机制是说明新计算及与旧尝试的差别。代价是“必须新思想”可能诱导无必要复杂化，所以同时允许替换与简化，不要求增加模块或制造形式差异。

### 融合：借鉴另一算法，接入当前算法

```text
本次算子：融合（Fuse）。
参考算法已经给定。识别其中值得借鉴的一项思想，说明它与当前父代的互补点。
给出该思想在当前算法中的接入位置、使用的信息和产生的决策变化。
处理两种机制的尺度、状态、计算顺序或目标冲突。选择足够完成融合的简洁方案。
允许替换父代部件，不要求把两份完整实现并排保留，也不要求线性加权两个输出。
参考算法的总成绩不代表其中每个部件都优于父代；从具体计算解释借鉴理由。
说明最终算法实际采用了参考算法的哪项计算，避免只改描述却返回原父代。
```

对应问题是机械拼接、盲目照抄高分算法或名义融合。最小机制是明确借鉴部件、接入位置与冲突处理。代价是模型可能挑选最容易解释而非最有效的部件；完整参考源码与最终完整设计便于后续核对，但本报告不增加自动审核器。

## 尚未检验、最可能改变方案的关键点

1. **关系信息是否比相同历史材料本身更有用。** 固定父代、算子、经验和历史内容，比较有真实形成／共同起点标记的上下文，与保留同量内容但移除这些关系标记的上下文。若没有差异，就应收回“关系指导生成”的解释。祖先顺序与子代共同起点最好分别改变，避免只得到整体结论。
2. **历史精确度是否抵消源码牵引。** 固定全部事件，对比完整历史源码、边记录加关键片段、摘要加明确基准差分。首先看实际代码是否实现新思想、是否重复旧方案，再看评价；短上下文胜出也可能来自长度优势，不能直接归因于抽象更好。等输入长度与保留原长度回答的是不同问题，需分别解释。
3. **简短分析是否改善实际设计。** 同输入对比设计＋代码与简短分析＋设计＋代码，并记录生成成本。若分析只是复述或代码没有实现分析中的修改，保留它就只有记录价值，不能宣称提高生成质量。
4. **失败记录是否被读成永久禁令。** 对已有失败思想，核对提示是否允许改变实现后再试，以及生成是否真的提出不同计算。这个检查能区分“利用失败经验”与“删除整类方向”，无需先增加反思或预算机制。

以上是未来可区分解释的检验方向，本次均未执行。当前最值得保留的主张是：**把可核查的修改关系和同起点反馈交给生成器，让它据此接续开发；以设计和代码核对它究竟改了什么。** 是否因此找到更好的算法，仍需生成与评价证据。
