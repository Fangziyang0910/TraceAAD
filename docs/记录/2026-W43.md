# 2026-W43

## 10月20日：MCTS-AHD 的返回值截取与十二路重启

我在 server3 启动了 MCTS-AHD 十二路，批次为 `20261020_qwen_co6`。六任务各两路，种子 0、1，每路预算 1000，输出上限 8192，模型与采样设置同 EoH、ReEvo、FunSearch 的 Qwen 批次。超参数沿用论文设置：初始化 4，种群 10，选择 2，alpha 0.5，lambda_0 0.1。MCTS-AHD 每次只扩展一个节点，所以每路只有一个请求在途，两个端点各承接六路。

启动后约 15 次生成内，FSSP 两路没有一个有效程序。原因在代码截取。官方 `Evolution._get_alg` 贪婪截取到回复中最后一个 `return`，丢掉该行的返回表达式，再拼接一个固定变量名。变量名由函数名前缀决定：`select_next_node` 用 `next_node`，`heuristics` 用 `heuristics_matrix`，其他函数用 `result`。我们的任务 docstring 写明了自己的返回值，例如 FSSP 返回 `(perturbed_times, job_ids)`。模型照此写 `return perturbed, jobs`，截取后变成 `return result`，运行时报 `NameError`。这类错误在 FSSP 约占 95%，OP 约 90%，JSSP 约 70%，CVRP、TSP、图着色约 30–40%。官方代码遇到同样的回复也会失败，所以这是官方截取规则与我们任务接口的冲突，不是移植偏差。

用户决定保留模型自己的返回表达式。改动只有一处：仍贪婪截取到最后一个 `return`，但保留该行剩余内容，不再拼接固定变量名。提示词和其他官方逻辑不变。我用 FSSP 第一路的 33 条旧回复回放核对：旧规则 0 条可运行，新规则 32 条在随机输入上返回合法的二元组。原十二路停止后删除，用新快照 `TraceAAD_runs/20261020_qwen_co6_mcts_ahd` 重开。重开约 5 分钟后，十二路共 89 次评价，81 次有效，没有再出现截取导致的变量未定义。修改位于 `baselines/mcts_ahd/sampler.py`，新增检查 `test_mcts_keeps_the_models_return_expression`。启动脚本、源码包与校验值位于 `experiments_result/mcts_ahd/launch_logs/20261020_qwen_co6_*`。

## 10月20日：ReEvo JSSP 第二路放宽 CPU 上限后测试

ReEvo 批次 `20261019_qwen_co6` 的 JSSP 第二路完成 1000 次搜索。最终程序 699 在训练实例上通过；在 50 个测试实例上，平均函数 CPU 为 10.20 s，超过 10 s 上限，测试失败。该程序每个实例约用 9.8 s，越界幅度属于实例分布与计时的波动。用户决定放宽上限，让这一路通过。

我给测试入口加了 `--function-seconds`，以 11 s 上限重新测试同一程序，其他条件不变。结果有效，平均最大完工时间为 1823.48。这次平均函数 CPU 为 10.88 s，比第一次多 0.68 s，当时 server3 同时运行 MCTS 十二路。新结果记录 `function_seconds: 11.0`，原失败记录保存在该路 `logs/heldout_cpu10_failed.json`。

## 10月20日：生成提示只保留问题、接口与成绩

FSSP、图着色、JSSP 的任务说明原来附有“Evaluation uses 16 fixed generated train instances …”、按划分固定种子生成数据、数据生成不计时三句。协议规定实例数、数据划分、种子和评价记账不进入生成提示。我删除了这三句。随后核对相关方法：ReEvo、MCTS-AHD、PathWise 与 EoH 的官方任务提示都没有具体规模或实例数，EoH 的 FSSP 只写“n jobs and m machines”；我们的 TSP、CVRP、OP 也没有。生成提示不提时间预算，只给规模也无法据此估算计算量，程序在运行时可从输入读取规模。因此实例规模一并删除。用户把这条定为协议：实例数量与规模、数据划分与种子、评价记账一律不进入生成提示，新任务也适用。[实验条件](../../experiments/PROTOCOL.md)已写明，`test_generation_text_gives_no_instance_count_or_size` 检查六任务的说明与模板；旧说明下三项检查失败，新说明下通过。修改位于 `benchmarks/shared/fixed_evaluation.py` 和三个任务的 `dataset.py`。

随后我全面核对了生成提示的来源：六任务的说明与模板、各方法的提示代码，以及已有批次约 14 万条真实提示。主要问题是基线与 TraceAAD 看到的任务说明不同。TraceAAD 的提示构造器已去掉 CVRP 的时间限制句，并且不使用 FSSP、图着色、JSSP 末尾的评价器段落；基线却看到了这些内容。反过来，TSP 与 OP 的 `design_notes` 只进入 TraceAAD 的提示。经用户同意，我删除了以下内容：CVRP 的“Within the evaluation time limit …”；三个任务末尾的评价器段落，包括每实例重新执行、输入为副本、成绩不按参照归一化等；FSSP 的固定框架设置 `{'iterations': 200, 'local_passes': 3}`，EoH 官方 FSSP 提示也不写轮数；图着色与 JSSP 以“评价器不限制”为名列举的构造、修复、邻域、局部搜索、重启等方向；JSSP 的“reference schedule”句和重复的调用说明；TSP、OP 只给 TraceAAD 的 `design_notes`。三个任务的说明已写明最小化目标，所以不再另附成绩句。现在 TraceAAD 与基线使用同一份任务说明，TraceAAD 只保留自己的成绩行与提示结构。

各方法的官方原文保留，例如 Shinka、CALM 中的 “efficient”。CPU 超限的报错含实例数，但扫描确认它没有进入任何基线提示；TraceAAD 的超时修复只写实测 CPU 时间与上限，符合协议。协议新增上述禁止项，两项检查分别核对任务说明的内容和各方法任务说明的一致性；旧代码下 10 项检查失败，新代码下 147 项全部通过。

用户决定不重跑已完成和正在运行的批次，因为这些句子对生成影响很小。已完成的 DeltaEvolve、EoH、ReEvo、FunSearch，以及正在运行的 MCTS-AHD 十二路和本机 ReEvo、EoH，提示中都带有这些内容。之后启动的批次使用新的说明。
