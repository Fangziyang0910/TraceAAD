# ESS 与父代质量权重核对

日期：2026-10-30。状态：固定 ESS=8 已取消。本文保留当时改用排名质量乘开发效率的过程；该候选随后被[直接子代质量规则](2026-10-30-父代选择定案.md)替代，现行公式见 Base 第 6.3 节。

## 判断

我建议去掉 Base 固定 ESS=8 的温度校准，保留质量偏好与开发效率。直接原因是：8 没有针对当前机制的实验依据；这个 ESS 作用于不同成绩值，既不随程序库规模增加，也不约束最终父代概率。此前沿用旧设定是保持机制连续性的选择，不能作为有效性证据。

不能据此断言 ESS 无效。SMCEvolve 确实使用 ESS，并有局部正向消融；但它控制顺序蒙特卡洛的增量重加权，与我们对整个程序库固定有效成绩数的做法不同。

## 删除前的规则实际控制什么

Base 原第 8.3 节以 `exp(-beta*(fitness-best))*e_p` 选择父代；`e_p` 是平滑开发效率。`beta` 是选择的逆温度，不是大模型采样温度。ESS（effective sample size，有效样本量）为归一化概率的 `1/sum(p**2)`，衡量概率集中程度，不是允许选择的个体数。

[现有温度函数](../../traceaad/base/selection.py:33)先取不同成绩值；不超过8种时 `beta=0`，超过8种时解出这些成绩值的质量权重 ESS=8。同分个体的数量和开发效率都没有参与这一步，因此乘上效率、展开为个体以后，[实际 ESS](../../traceaad/base/selection.py:116)可以高于或低于8。这里仅核对共享的温度规则，不把旧实现的尝试计数当成新 Base 的调用成本定义。

一个数学算例：100个成绩等间距、开发效率相同的个体，设质量 ESS=8，前8名合计选择概率为 **86.608%**，前16名为 **98.207%**；其余92名仍占13.392%。可见集中度担忧有依据，但“只能选择前八个”不是准确描述。该算例不代表实际成绩分布。

我另读取 V15 的18路记录 `experiments_result/traceaad_v15/*/20261027_v15_co6_*/events.jsonl`，每个 program 保留最后一条记录，排除 repair，只取 `request.selection` 含 `ess` 的记录。共13176次选择，其中372次 `beta=0`；限定候选至少32个且 `beta>0` 后，11872次选择的候选数中位数为222，最终 ESS 中位数为 **18.084**，范围为5.024–110.686，成绩层级 ESS 中位数仍为8。V15 另有外层谱系分配，这不是新 Base 全程序库选择的性能实验，也没有证明改大 ESS 能提升成绩。

输入校验：按相对仓库路径排序，将每个文件的 `路径 + 空格 + SHA256` 用换行连接后再取 SHA256，结果为 `b607d290a364a7027db26e45d1e8afca276f272445066e0f8b2cd732eda94d8f`。

## 相关工作与证据边界

### SMCEvolve：确实采用 ESS，但用途不同

一手来源：[论文 v1](https://arxiv.org/html/2605.15308v1)，2026-05-14；[作者仓库](https://github.com/kongwanbianjinyu/SMCEvolve)。本轮依据论文第2.3节、表4与附录J表10核对，不声称逐项复核了其仓库实现。

论文用 ESS 决定退火步长，目标是增量重加权后保留 `kappa*N` 的有效粒子。默认每岛8个粒子、`kappa=0.9`，对应7.2；若剩余退火过程仍满足阈值，则直接到终点。它限制的是每一步权重退化程度，不是在不断扩大的档案中固定只有8种成绩有效。

表4在21个圆的圆堆积任务上固定模型调用预算，报告3个种子的最好成绩：默认自适应重采样0.9993，均匀重采样0.9514，贪心重采样0.9760。这个结果支持该系统的自适应重采样优于这两个极端；没有隔离 ESS 相对其他温度调度的收益，没有验证 TraceAAD 的固定8，也不是多任务平均效果。

### 其他常见选择方式

- **EoH** 按排名选择，`p_i ∝ 1/(N+r_i)`。[原论文](https://proceedings.mlr.press/v235/liu24bs.html)与[作者代码](https://github.com/FeiLiu36/EoH/blob/472545785c936dcfc863d2bc0d6109cf23c7ce62/eoh/src/eoh/eoh/evolution.py#L118-L123)一致；本地原论文 `3-method.tex:92–93` 也有明确公式。该规则不求解 ESS，且最好与最差个体的权重比小于2。
- **FunSearch** 对成绩簇使用随程序数循环变化的 softmax 温度；不是用 ESS 求温度。[作者代码](https://github.com/google-deepmind/funsearch/blob/cc53f274237d7ab05c19df939edbc1f9616a7c19/implementation/programs_database.py#L205-L215)。
- **ShinkaEvolve** 当前加权父代实现使用标准化成绩的 sigmoid 权重乘 `1/(1+children_count)`，不强制 ESS。[作者代码](https://github.com/SakanaAI/ShinkaEvolve/blob/8adc053a2ce4511ad2ac310e004c530a73fb974a/shinka/database/parents.py#L367-L407)。

这些来源证明存在不依赖 ESS 的质量选择方法，不证明它们在我们的整程序库机制中一定更好。

## 对 Base 的建议

取消固定有效成绩数8，继续用当前质量与直接开发经验共同决定选择。按质量排名赋权是一个简单替代方向，可以避免分数单位和温度求解；但 EoH 在筛选后的有限种群中使用较平缓的排名权重，不能把其参数直接当成不断扩大的程序库的最优设置。

下一步需确定质量偏好应有多强，再固定具体权重。实际收益需要保持生成与上下文不变的选择规则对照；本轮的源码核对、数学算例和历史分布统计均不能代替该对照。

## 当时确认的设计与后续修正

用户确认去掉该约束后，我在 [Base 选择权重](../TraceAAD-Base.md#63-选择权重)删除了指数质量项、温度求解和 ESS 目标，采用 EoH 的简单排名形式作为默认质量权重：`w_p=e_p/(N+r_p)`。`N` 为全部父代候选数，`r_p` 为成绩升序名次，从1开始，同分取平均名次；`e_p` 沿用平滑的单位调用成功产出率。

这一默认选择温和偏向高质量个体，不新增选择强度参数。它是待检验的 Base 设计，不是已验证优于原规则的结论。本次修改范围是机制文档，旧版本实现保留原状。

后续[核心机制审查](2026-10-30-Base核心机制审查.md)发现：EoH 的精英种群筛选没有随该公式一同迁移，整个程序库上的质量权重差距始终小于两倍，可能被仅奖励超过父代的局部成功率主导。[最终修正](2026-10-30-父代选择定案.md)采用倒数排名表示质量，以父代质量作初始估计，按调用成本汇总全部有效直接子代的质量；取消超过父代或参考的奖励条件。
