# 演化轨迹的信息增量与三个机制的作用位置

本轮讨论的问题是：相对当前代码、成绩和普通反馈，演化轨迹究竟增加了什么，以及这些信息应该在哪里改变决策。以下是我的分析与建议，尚未作为用户确认的设计写回WWH。本轮未运行新搜索或修改机制。

## 先区分比较对象

相对静态程序集合，任何父子修改与结果都是新增过程信息。但相对已有的反馈搜索、父子反思和路径提示，这些功能并非空白。ReEvo比较两个算法并积累短长期反思；RefineEvo明确比较父子修改，保存带适用条件的正负经验并检索；MCTS-AHD回传树上结果，并用路径上的程序进行生成。不能把“使用历史”“反思”“条件经验”整体都当作本方法额外创造的能力。

本轮重新核对了作者原文及本地源文件：

- [ReEvo §4](https://arxiv.org/html/2402.01145v3)：好差算法比较、短期反思和长期积累；本地`reference_code/reevo/reevo.py`核对输入。
- [RefineEvo §3.2–3.3](https://arxiv.org/html/2607.11358v1)：基于历史效用的算子调整、父子情境反思、条件化正负经验。
- [MCTS-AHD §3](https://arxiv.org/html/2501.08603v1)：树搜索和tree-path reasoning。

这只界定已有功能，不由论文的主张推断我们的机制一定有效，也不作独占性判断。

## 额外材料分别能回答什么

| 材料 | 相对上一层额外能够回答的问题 |
| --- | --- |
| 当前代码、描述、成绩；其他候选的代码和成绩 | 目前实现什么，当前谁较好，有哪些不同做法。 |
| 一次父子修改、结果、错误与成本 | 从这个起点做过一次什么变化，观察到什么结果。 |
| 同起点的多次修改 | 哪些方向已试，结果是否重复，哪些比较共享相同起点，尚缺哪些有效检验。 |
| 连续修改与修复路径 | 某项计算何时加入、丢失或重新生效；改善是否需要配套调整；后续收益经历多少成本。 |
| 不同分支上的相关修改及来源 | 同一计算关系在哪些实现条件下复现，哪些反例要求收窄或修订经验。 |

有序关系和共同起点不会自动产生因果结论。多项计算同时变化、评价条件变化或择优继续分支，仍可能混淆解释。轨迹的价值在于提供更可比较的材料，并指出还缺什么检验。

## 机制1：让已有开发响应影响下一份预算

最可能的作用位置是当前质量接近、而开发响应不同的父代—算子组合。价值属于程序、算子、生成上下文和剩余预算的共同状态，不能赋予节点一种独立于这些条件的固有潜力。

| 候选增量 | 所需轨迹信息 | 改变的决策 | 与已有能力的分界 |
| --- | --- | --- | --- |
| 估计同一父代在不同算子下的实际回报 | 同起点的真实尝试、失败、重复、成本及冠军变化 | 对同等质量的对象，优先尝试已有响应较好的动作 | 历史成功率和访问计数已有；进一步需要分清有效试了哪些改法，而非按次数机械降权。 |
| 判断历史反馈能否借给新候选 | 可比较的起点状态、修改类型、形成与接续过程 | 候选本身记录不足时，从相关开发经历借证据 | 单靠当前代码相似或质量匹配不需要轨迹；过程是否增加预测力要在这两者之上检验。 |
| 识别有实际兑现记录的延迟收益 | 结构变化—配套修改—结果的接续链及全部成本 | 比较多步发展路线与继续改进现有好程序的机会成本 | 保存退步节点、MCTS回传已有；某祖先出现冠军后代不等于祖先有独立因果贡献。当前冠军即时收益估计没有实现这项能力。 |
| 选择有依据的交叉参考 | 参考中某计算的引入、失效、恢复及接入条件 | 优先尝试有望解决接收方限制的参考计算 | 两段代码不同、嵌入距离大是静态多样性；形成经历差异不自动等于可迁移互补性。当前最远嵌入仅是候选规则。 |

我最看好第一项，并把第二项视为其扩展。第三项要有真实可比接续支持，第四项优先保留为具体配对问题。当前实现的形成路径特征只是出生算子、出生增益、符号动量和回撤；它没有自动理解改动内容与开发瓶颈。

一个重要限制：当前代码、提示、模型与采样分布均不变时，多尝试几次不会使代码本身必然“耗尽”。历史可以更新我们对回报的认识，冠军变化可以改变突破门槛，机制2更新提示也可以改变未来响应。不能把这些情况统称为尝试次数多所以没潜力。

## 机制2：围绕同起点证据改好下一步，首先服务Refine

Refine保留主要机制，局部修改最容易与已有尝试对应，因此是当前最有依据的主攻位置。

| 候选增量 | 轨迹使生成器多知道什么 | 具体作用 |
| --- | --- | --- |
| 避免重复无效修改 | 某个具体改法在相同起点上已经执行，结果及实际计算是什么 | 不再重复相同无效实现；实现或配套条件改变时仍允许重新检验思想。 |
| 选择下一项局部修改 | 同起点几个不同改法分别如何影响结果 | 继续有反馈的方向，换掉已被有效检验的不合适做法；不能将任意好差程序的差异当单项修改效果。 |
| 保留已有作用，定位回退 | 当前组件在哪一步引入、何时带来变化、哪次修改丢失它 | 在改其他部分时保留其作用，或有针对性恢复丢失的计算；代码本身能解释功能，历史补充已观察的作用。 |
| 区分思想失败与实现未完成 | 初始修改、报错或超时、修复实际改动及最终结果 | 重试尚未被正确实现的计算，避免把一次错误实现写成思想禁令。 |

当前固定提示消融支持同起点子代信息有用，未测出祖先段的一步增量。它支持优先聚焦局部尝试，不支持直接宣布所有祖先材料无用。证据见[上一轮效果分析](2026-11-10-Base与三个轨迹机制的效果和认识修正.md)。

Crossover的轨迹增量在接入条件：参考的一项计算在来源中依赖什么；接收方已试过哪些类似接入；哪些表示、尺度或调用位置导致失败。仅把参考源码写进提示、要求组合两个算法，是普通交叉能力。Explore中“换一种算法”“增大多样性”也不需要轨迹；轨迹可用于区分真正尝试过的方向与仅有失败实现的方向，但当前Explore不读历史，这个用途尚未实现，也没有直接收益证据。

不能把更好的通用指令、analysis/code/design顺序、源码规范化和更清楚的任务说明都记为轨迹贡献。这些是所有版本都可以获得的基础能力。

## 机制3：把多次修改形成的条件关系迁移到其他实现

它最有希望提供的额外收益，是当前节点的局部材料不足时，从其他分支或较早经历带来能够指导具体修改的认识。若笔记只复述当前父代的局部历史，就没有充分超出机制2。

| 候选增量 | 需要比较的材料 | 可形成的认识 |
| --- | --- | --- |
| 区分整体算法较好与某项修改有效 | 同起点的相关修改、实际差分与结果 | 在特定原实现上，某个计算变化与结果的关系；避免从最终冠军归因所有组件。 |
| 找到配套条件和修改顺序 | 引入新计算后的连续修复、调整、再评价 | 计算A初始失败是否因B未适配；B完成后A是否仍存在并发挥作用。缺少关键对照时保留为待验证关系。 |
| 学习适用范围 | 不同分支内部的变化及结果，再比较分支间关键条件 | 同一种改法为何在不同计算背景下呈现不同结果，哪些条件决定是否值得借用。 |
| 根据反例修订认识 | 旧经验的原始依据和新出现的相关事件 | 收窄、撤回或重构已有认识；同一来源重复出现不能当作多份支持。 |

维护笔记、语义检索、正负经验池和带条件的schema本身均不是轨迹独有能力。真正要验证的是：轨迹比较产生的认识，在另一个实现上能否指导正确修改并带来收益。

上一轮TSP案例需要进一步收窄归因：评分路径首节点与返回动作不一致，单看程序也能发现，所以这个代码规律不是轨迹独有发现。轨迹增加的是将6.032→7.760的退步定位到具体转换，以及用另一个内部2-opt有改善的案例反驳“内部2-opt普遍有害”。要进一步把分数损失归因于此不一致，还需修正后的受控评价。这里轨迹主要帮助找到应解释的变化与应排除的泛化。

高层经验应抽掉局部编号、变量名和偶然参数，同时保留决定作用的计算条件与关系。它不必抽成“简单模型更好”“不要复杂搜索”这样的宽泛原则。适用范围可以先是同任务不同分支，不必先追求跨任务泛化。

## 当前最值得围绕的三个问题

1. 机制1：在同等质量和相同生成条件下，哪一个父代—算子组合的已有开发记录说明下一次尝试更值得？
2. 机制2：在当前父代上，哪些改法确实被检验过，它们怎样改变这次Refine？
3. 机制3：某一修改关系在什么计算条件下成立，另一分支能否据此正确实施？

这三个问题分别要求证明分配变好、当前修改变好、跨实现借鉴变好。长历史、复杂表示与更抽象的文字都不是单独目标。本轮不再扩展机制，先明确每一项新增设计依赖哪条新增事实、改变哪项决策。
