## 3. 优先问题：整条旁支被删时，旧经验没有完整进入反思

`build_selection_prompt` 只读取被删子树入口节点的选择经验，并截取前240字符。它没有读取子树内部节点的选择经验，也没有读取该子树各条入边已有的变异经验。见 [reflection.py](../../evotrace_v1/reflection.py) 的 `build_selection_prompt`。

在257个旁支整理区域中，36个区域涉及这类遗漏：57条已有经验未完整进入新输入，其中29条只保留了前240字符，28条完全没有进入输入。按字段分，涉及41条选择经验和16条变异经验。

具体例子是OP种子0的第二轮重构：节点8被剪入节点4的选择经验。节点8入边已有一段变异经验，其中记录了中间改法的成绩 `-11.8538`。这段经历没有进入新的反思输入，输出中也没有保留该成绩。原来的“经历随结构压缩继续保留”在这里断了一次。核验见 [fact_loss_examples.json](../../experiments_result/analysis/evotrace_mechanism_audit_20261111_230808/fact_loss_examples.json)。

**最小修正方向：** 对每个即将移除的区域，把全部节点选择经验与全部入边变异经验收集后交给同一次反思合并。去重应作用于事实，不应先按入口位置或240字符截断证据。仍使用现有两种经验字段和一次区域反思。

## 4. 反思证据不完整，输出已出现事实错误

### 被删子树内部的失败没有展开

当一棵被删子树中存在可行节点时，当前输入只列入口与子树最优设计、成绩及部分差分。内部失败节点只贡献顶部的失败数量，没有具体错误记录。本批发现两处真实遗漏。

FSSP种子1的第一轮重构中，旁支 `6 → {10, 13}` 的节点13发生 `IndexError`。整理区域顶部写着 `1 infeasible`，正文却没有节点13的设计或错误。模型最终写出：

> No infeasible attempts or runtime errors were recorded in this consolidation.

这句话与真实评价相反。它已完整进入同一路第65次生成的提示词。原始错误、重建输入与输出见 [failure_context_audit.json](../../experiments_result/analysis/evotrace_mechanism_audit_20261111_230808/failure_context_audit.json)。

Refine也有同类信息缺口：本批4个请求展示了失败子代，但只给出算子和异常，未给出该子代尝试的改动。例如FSSP种子0的第39次尝试只能看到 `IndexError: index N is out of bounds...`，无法从这一条反馈判断前次具体试了什么计算。

**最小修正方向：** 在区域内列出实际存在的失败计算及其异常；Refine的失败卡片补上尝试设计或相关代码改动。按相同失败事实合并，而不是只保留失败数量。

### 差分按首尾截断，可能切掉核心运算

旁支整理的重点差分最多14行，超过后只保留首尾。349个反思输入中258个包含差分省略。变异反思另有完整端点代码可核对，旁支整理通常只有承接节点的代码，缺少被删算法的完整实现。

同一FSSP例子中，节点14执行 `perturbed_times += 0.8 * processing_times` 的掩码增量，相当于选中位置的原值变为1.8倍，再叠加噪声；这段关键计算被差分截断。凝练结果把该组计算概括成1.2至1.5倍，并使用了节点14的成绩。代码和经验中的参数范围不一致。

**最小修正方向：** 优先保留完整的实际修改，删除重复上下文；需要核对的核心计算不能只剩一段模型自述的Design。对于本来就受节点数限制的区域，先移除机械的首尾14行裁切，再根据真实输入长度决定是否还需要压缩。

## 5. 提示词中需要清理的内容

### 无错误套话大量进入经验

257条选择经验中有186条包含 `no infeasible`。这类句子通常没有提供算法计算或可复用的失败事实，却占据经验长度，并在后续合并中反复出现。提示词本身同时展示 `0 infeasible` 和“不要写 no infeasible attempts”的文字，持续把这句话放进输入。

**最小修正方向：** 输入只列实际存在的错误记录；输出要求聚焦计算、实测成绩和异常。删除关于“没有错误”的计数与套话要求，不再靠追加禁止词清单约束它。另有1条OP选择经验把局部退步解释成“软惩罚不如严格静态可行性屏蔽”，这属于超出记录的概括，也应从下游事实材料中去除。

### 初始化与修复的输出顺序和Schema不一致

EvoTrace使用 `analysis → code → design` 的Schema，但初始化与修复继承的Base模板要求 `analysis → design → code`。60次初始化和40次修复都存在这组相互冲突的顺序要求；真实回复全部按Schema输出 `analysis → code → design`。目前没有因此出现解析失败，但模板应统一。

### 候选代码注释的清洗不一致

演化生成和反思使用去注释后的代码。初始化和程序修复直接插入原始代码；本批60个上下文包含此前模型生成的注释，其中有 `Let's use...` 等过程自述。这些文字与独立的Design重复，也可能携带未验证的解释。应统一只展示算法实现；任务接口本身的参数与返回值说明继续保留。

没有发现机器目录、批次路径、调度器配置或论文叙事进入这些提示词。当前需要处理的主要是上述证据缺失、模型自述和经验套话。

## 6. 每个LLM环节的结论

| 环节 | 当前输入 | 审阅结论 |
| --- | --- | --- |
| 初始化 | 任务、接口、已有可行算法、最近失败 | 机制符合沿用Base的设计；统一输出顺序并清理候选代码注释。 |
| Refine | 当前代码、形成路径、经验、同节点尝试 | 主线明确；失败子代缺少“试了什么”的证据。 |
| Crossover | 当前代码、共同祖先、双分支、参考设计 | 上下文与设计一致；提示明确允许不适合融合时直接改进，因此算子标签不保证每个产物都融合了两套计算。 |
| Explore | 当前代码、最多8个方向、方向内经验 | 已完整读取展示方向的节点和边经验；抽查未发现旧的两条账本或260字符截断。 |
| 格式修复 | 原始回复、解析反馈、任务接口 | 本批未触发；静态模板有同一输出顺序冲突。 |
| 错误／超时修复 | 失败代码、设计、候选自身报错或超时说明 | 40次请求可完整复现；没有夹带框架路径，需统一顺序并清理候选注释。 |
| 路径变异反思 | 保留端点、路径改动、分数、旧经验 | 旧路径与中间节点经验会进入输入，基本符合设计。 |
| 旁支选择反思 | 入口／最优子代、部分差分、承接节点旧经验 | 优先修复：完整吸收被删区域的旧经验与失败记录，并补足代码证据。 |

对选择经验，我建议把指令收束为：

> 将以下已移除尝试与已有经验合并。按实际计算归类，每类记录改动及对应的评价值或异常。保留不同的计算方向和错误类型，合并同一公式的参数变化。输出将用于下一次算法修改。

这段指令需要建立在上述输入补全之后，不能仅靠改写指令弥补缺失的事实。本次完成的是审阅和复现；运行中的冻结代码尚未修改。
