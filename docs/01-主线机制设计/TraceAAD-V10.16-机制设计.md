# TraceAAD V10.16 机制设计

2026-10-03。V10.16 是在 V10.15-6 基础上的独立版本，代码位于 `traceaad/v10_16/`，运行入口为 `experiments/traceaad_v10_16/`。设计依据见[从专家设计过程看自动算法设计](../04-研究认识与构想/从专家设计过程看自动算法设计.md)。V10.15-6 中经检验有效的部分全部保留：每个算子的目标都是超过它看到的全部已评价版本；上下文只陈述事实；写代码前做简短的分析。

## 0. 一句话

**种群就是搜索积累的经验：它由程序和程序之间的生成事件组成。**选择出发点和构造生成上下文都读取这份经验，而不再只读取评价成功的个体。

## 1. 出发点

算法专家设计算法时依靠四样东西：先验知识、代价估算、实验，以及从实验中得到的经验。经验是关于改动的：哪一类改动效果多大、代价多少、在哪里出错、后来是否兑现。V10.15 只把评价成功的程序沉淀下来；超时、错误、写回已有代码的尝试都不进入搜索使用的数据结构。V10.15-6 的数据表明搜索没有从自己的实验中学习：

| 现象 | V10.15-6 中的证据 |
|---|---|
| 失败不随搜索减少 | TSP 超时率按每 250 次尝试分段，依次为 2%、8%、13%、16%；各任务的运行错误率没有下降 |
| 模型推理代价，但缺乏校准 | TSP 第 1 路父代耗时 ≥20 秒的 220 次 Refine，分析都讨论了时间，仍有 89 次超时 |
| 在同一处反复失败 | 单个程序最多被展开 45–90 次；每次都看不到之前从它出发的尝试 |
| 失败越多越难成功 | 下一次子代超过起点的比例：首次尝试约 18–21%，失败 1–4 次后约 9%，5–14 次后 3–6%，15 次以上约 1%；V10.15-5、-6 共十组运行的趋势一致，后一类尝试占预算的 10–15% |
| 没有经验的 Explore 只在前期有效 | 每千次 Explore 超过全局最好的次数，前 300 次与之后相比：TSP 25 对 6，CVRP 12 对 0，OP 16 对 0 |

V10.16 要回答的是：如果把这些经验交给搜索的两个决定，搜索是否会开始学习。

## 2. 核心概念：程序与生成事件

- **程序**：以规范化后的代码（去掉注释、docstring，统一格式）为身份。一份代码只对应一个程序，只评价一次。评价失败的程序也是程序，带有失败的测量结果；它们不能作为出发点，但会出现在经验中。
- **生成事件**：每次模型生成都是一个事件，计入预算。一个事件从某个程序出发（初始化时没有起点，Crossover 另有一个参考程序），产生一个程序：可能是新程序，可能是已知程序，也可能没有得到可用程序（交付失败）。修复也是事件，它的起点是失败的程序。
- **种群**：程序加上事件，也就是全部经验。下面几样东西都是种群的视图：
  - **出发点**：有效程序；
  - **形成路径**：通向当前程序的那几个事件，失败版本也包括在内；
  - **从当前程序出发的尝试**：以它为起点的事件；
  - **搜索的进展**：刷新全局最好分数的那些事件。

唯一被视为重复的是代码完全相同。重复的结果已知，所以不再评价，但它作为一个事件记录下来，指向已有的程序。训练分相同并不说明是同一个算法，V10.16 中没有任何机制按分数合并程序。父子关系只是记录程序从哪里改出来的数据结构。

## 3. 机制

### 3.1 数据结构

- 有效程序写入日志的 `node` 记录，字段与 V10.15 相同，另加 `valid`、`calls`、`function_seconds`。`attempt_id` 仍是最后一个字段，供监控建立索引。
- 失败程序由首次产生它的 `attempt` 记录表示：`program_id` 等于该尝试的 id，`new_program` 为真。恢复运行时由这些记录重建。
- 每条 `attempt` 记录都有 `program_id`，指向这次事件产生或写回的程序；交付失败时为空。
- 以下三种情况都链接到已有程序，不再评价：`duplicate`（写回了有效程序）、`copied_reference`（写回了本次的参考程序）、`known_failure`（写回了失败程序）。
- 修复事件的 `parent_id` 是失败程序。修复成功得到的程序挂在失败程序之后。修复得到的初始程序仍然算作根：判断标准是它的形成路径上没有有效的前驱。 运行错误与非法输出另记录程序中出错的那一行（traceback 中程序内最内层的栈帧），失败描述会附上这一行。

### 3.2 评价测量：超时是一次测量

评价时，候选函数被包装为计数版本。计数器放在共享内存里，评价进程被超时终止后，搜索进程仍能读到它，因此可以知道超时前完成了多少次调用。

- 每次评价记录两项：函数被调用的次数，以及函数内部花费的总时间。只计最外层调用，递归和通过目标名调用的辅助函数不会重复计数。
- 计数包装附加在程序文本上，所以像 OBP 这样每个实例都重新执行程序文本的评价器，同样会被计数。
- 对于有效程序，模型看到的是：`Score · Evaluation time · N calls to the function, about F s inside it`。以 TSP 为例，16 个实例共 768 次调用，模型可以据此自己估算每次调用的代价。ACO 任务的 N 是实例数，F 是启发式矩阵的计算时间，评价时间的其余部分属于蚁群。
- 对于超时，显示为 `stopped at the 30 s time limit after N calls (about F s inside it)`。
- 训练实例的规模仍然不写进上下文（V10.15 §4.1 的考虑）。调用次数与单次耗时都是对程序本身的测量，足以支持代价推理。

### 3.3 选择出发点：质量 × 经验

每个有效程序都是独立的候选，权重为

```
w_i = exp(β · (q_i − q_max)) × (k_i + s·r) / (n_i + s)
```

- `n_i`：从程序 i 出发的算子尝试次数（Refine、Explore、Crossover）。修复不单独计次，而是计入它所修复的那次尝试。
- `k_i`：其中产生了比 i 更好的新程序的次数。写回已有的更好程序不算。
- `r`：本次运行汇总的成功率，即 `(Σk + 1) / (Σn + 2)`；`s = 3` 是先验强度。在 V10.15-5/-6 的数据上，`s = 3` 能复现成功率随失败次数下降的曲线：连续失败约 3 次后降到一半，约 10 次后降到四分之一，与观测到的 1–4 次失败后约减半、15 次以上降到 1% 左右相符。
- **β 只是分数差的单位换算**：取让目前观测到的分数值在 ESS 意义上分布于 8 个有效档位的温度。它沿用了 V10.13 以来 ESS=8 的分配宽度；按排名统计，这个宽度与观测到的收益梯度吻合（第 1 名每千次约 25–36 次超过全局最好，第 21 名以后为 5–12 次）。之所以在观测到的分数值上拟合 β，而不是在程序上拟合，是因为程序上的 ESS 在最高分并列不少于 8 个时没有有限解：温度会趋于无穷，其余程序的权重全部变成 0。OBP 三路突破 Best Fit 的那一步，父代都比 Best Fit 差，所以这种退化是有害的。

这条规则对应专家的做法：一个设计还在不断出成果，就继续投入；在它身上试了很多次都没有进展，就转向别处。它不需要额外的“初生保护”或续投规则，计算余量也自动包含在内：接近时限的程序，子代大量超时，它的经验分就会下降。

**已知的代价**：最高分并列的程序很多时，每个并列程序都要被试过几次，权重才会降下来；V10.15-6 的 OBP 前期曾有 86–124 个并列程序。这是“不按分数合并程序”的代价，诊断中会单列观察（§6）。

### 3.4 生成上下文

| 区块 | 初始化 | Refine | Explore | Crossover | 修复 |
|---|---|---|---|---|---|
| Task、Evaluation、Target Function | ✓ | ✓ | ✓ | ✓ | ✓ |
| Current Algorithm（代码、分数、耗时、调用） | | ✓ | ✓ | ✓ | |
| 形成路径（≤8 步，含失败版本与修复） | | ✓ | | ≤4 步 | |
| **从当前程序出发的尝试**（最近 ≤8 次及其结果） | | ✓ | ✓ | ✓ | |
| Reference Algorithm 与它的形成路径（≤4 步） | | | | ✓ | |
| **搜索最好分数的进展**（最近 ≤8 次刷新） | | | ✓ | | |
| 已有根（第 5–8 个根） | ✓ | | | | |
| 失败程序、错误或超时测量 | | | | | ✓ |

**从当前程序出发的尝试**，每次尝试一行，包括算子、Design 和结果。结果有以下几种：
- 分数（与当前程序相比是改进、变差还是持平）和耗时；
- 失败及其测量；
- 与当前程序代码相同；
- 与这条路径上的早先版本，或搜索中已有的程序代码相同（附其分数）；
- 与已经失败的程序代码相同；
- 回复中没有可用程序。

修复的结果附在被修复的那次尝试后面。区块开头说明共有多少次尝试、其中几次得到了更好的新程序。

**搜索最好分数的进展**，列出每一次刷新全局最好的事件：它是什么算子、从多少分的程序出发、新分数和此前的最好分数、耗时，以及 Design。这是 Explore 的全局经验，取代 V10.15 的参考卡（`explore_cards`，已删除），也取代只给一个最好分数的做法。

**形成路径**中，第一版失败、随后被修复的一步合并显示为一步，例如 `Refine, then Repair · score 8.1 → score 7.9 (improved)`，并附一行 `First version failed: runtime error: IndexError: … at `<出错的那一行代码>``。diff 从有效的起点指向修复后的版本，即这一步实际保留的变化。失败版本的代码不作为一个版本展示：冒烟运行中，OP 的一次修复把出错的特征整段删掉，下一次 Refine 在路径上看到失败版本的完整 diff 后，把那行有错的代码原样抄了回来（§10）。每一步都附带新版本的评价耗时，所以计算量的变化趋势是可见的。

**目标句**沿用 V10.15-6，只把对象从“展示过的所有版本”扩展为“展示过的所有版本和尝试”：

- Refine：`Continue this line of development: write an algorithm that scores better than every version and attempt shown above.`
- Crossover：同样把对象扩展为两条开发线上展示的所有版本和尝试。
- Explore：不变，即超过全局最好，并改变当前算法的决策方式。

已经试过的尝试本身就是已知的结果，所以不需要“不要重复”这类规则。

**裁剪顺序**（总输入超过 24,320 token 时）：
- Refine：先裁最旧的历史步骤，保留最近一步；再裁最旧的尝试。
- Explore：先裁最旧的进展，再裁最旧的尝试。
- Crossover：先按 V10.15 的方式裁两侧历史，再裁尝试；仍然超出则退回 Refine。

### 3.5 修复

- 修复的起点是失败程序本身。提示内容与 V10.15 相同：失败程序、Design、错误信息，以及一句目标。
- 对超时，错误信息改为测量：`The evaluation stopped at the 30 s time limit after N calls to the function (about F s inside it). The algorithm it was developed from completes the evaluation with M calls in about T s, about F' s inside the function.`
- 运行错误的 traceback 中去掉了计数包装的栈帧。

### 3.6 交付

整段回复无法解析时，改用最后一个明确的 `Code:` 标签之后的内容再解析一次。V10.15-6 中有 6 个回复因前面夹带讨论或 diff 而被判失败，它们在最后一个 `Code:` 之后给出了完整实现，按这条规则都能通过。

交付失败仍然不进入修复：修复需要一个可以修改的程序，而交付失败时并没有程序。V10.15-6 中这类情况占 0.13%。

### 3.7 最终选择

- 训练分最高的 5 个程序进入选择，同分取较早者。
- 某个 finalist 在选择集上失败时，由训练排名中的下一个程序替补，替补总数不超过 5 次。
- 在 V10.15-6 OP 第 2 路，五个 finalist 共享同一个循环错误，整个运行最后没有交付任何程序。

## 4. 与 V10.15 的差异

| 方面 | V10.15（-6，截至 10-02 修正） | V10.16 |
|---|---|---|
| 种群 | 评价成功的程序 | 程序（含失败程序）与全部生成事件 |
| 重复、已知失败 | 只写入日志 | 作为事件链接到已有程序，进入上下文和经验 |
| 失败与修复 | 修复后的程序直接挂在原父代下，失败版本不可见 | 修复从失败程序出发；形成路径中失败与修复合并为一步，写明失败方式和出错的那一行 |
| 评价测量 | 墙钟时间 | 墙钟时间、调用次数、函数内时间；超时时记录完成了多少调用 |
| 选父 | 质量 Boltzmann（程序上的 ESS=8，并列不少于 8 个时在并列中均匀抽样） | 质量（β 在观测分数值上拟合）× 经验前景 `(k+s·r)/(n+s)` |
| Refine、Crossover 上下文 | 形成路径 | 形成路径（含失败与修复、每步耗时）＋从当前程序出发的尝试 |
| Explore 上下文 | 当前程序＋全局最好分数（参考卡默认关闭） | 当前程序＋从它出发的尝试＋搜索最好分数的进展；删除参考卡 |
| 超时修复提示 | “未在 30 秒内完成” | 测量：完成了多少调用，以及起点程序的调用数与耗时 |
| 交付 | 整段解析 | 整段解析失败时，改用最后一个 `Code:` 之后的内容 |
| finalist | 前 5 个程序 | 前 5 个程序，失败者由下一名替补，最多 5 次 |
| 诊断 | 各算子统计（修复单列） | 另有：投入在“已试 15 次以上仍无改进”的程序上的预算比例、按四分段的超时率与错误率、300 次之后 Explore 刷新前沿的次数 |

不变的部分：8 个根与 16 次初始化尝试的上限、算子比例 0.45/0.30/0.25、Crossover 参考选择（不低于中位数、代码差异较大的一半中均匀抽取）、写代码前的 Analysis 与 Design 格式、单一训练种子、各任务的训练与选择时限、模型与采样配置。

## 5. 刻意没有做的

- **没有反思层。** 经验以评价器测得的事实呈现，归纳由生成时的模型在上下文中完成；不让模型写下未经验证的“为什么”。
- **没有自适应算子比例。** 让 Explore 有了经验之后，先看它的后期收益能否恢复。“没有经验”这个原因还没有被排除之前，调整比例只是在改症状。
- **没有时间惩罚，也没有效率规则。** 代价通过测量事实和经验（超时会拉低经验分）进入决策。
- **不按分数合并任何程序。**
- **选择集不加入更大规模的实例。** held-out 包含 100 与 200 节点，选择集与训练分布相同，这仍是一个偏差。但它属于评测协议，与本版的搜索机制分开处理。
- **交付失败不修复**（理由见 §3.6）。

## 6. 可证伪的预测与诊断

如果核心判断正确（搜索开始从自己的实验中学习），与 V10.15-6 相比应当看到：

| 指标（`diagnostics.json`） | V10.15-6 | 预期 |
|---|---|---|
| `failure_rates_by_quarter` 的超时率 | TSP 2% → 16%，逐段上升 | 不再逐段上升 |
| `failure_rates_by_quarter` 的错误率 | 各任务持平 | 逐段下降 |
| `attempts_on_tried_out_programs` | 10–15% | 明显下降 |
| `explore_new_frontiers_after_300` | 每千次 Explore 约 0–6 次 | 明显大于 0 |
| 重复与已知失败的比例 | OBP 8.9% | 下降 |

**用来区分其他解释：**
- 如果失败与重复减少，前沿却没有提高，瓶颈在模型能力或任务上限，而不在经验。
- 如果经验加权使搜索过早离开仍有潜力的程序（例如 TSP 中需要多次精炼才能兑现的骨架），表现会是最好程序的形成路径明显变短、后期刷新减少。这时应检查 s 的取值。

## 7. 风险

- **上下文变长。** 尝试列表最多 8 行，进展最多 8 行，每行一两句话，预计增加 1,000–2,000 token，并且有裁剪顺序兜底。
- **趋同。** Explore 看到搜索进展后，可能都去模仿最近一次成功的改动。
- **失败经验可能让模型过度保守。** 有些超时只是实现问题，换个写法就能通过；看到失败后，模型可能直接回避整个方向。
- **最高分并列的代价**（§3.3）。
- **测量受负载影响。** 墙钟时间与调用次数中，前者会随主机负载变化；仍按“减少同时运行的路数”处理。

## 9. 待定问题

- 种群统一还可以走得更远：例如选择出发点时也使用其他程序上的经验，在相近的程序与改动之间汇总。本版只使用每个程序自己的经验，因为这是有直接证据支持的最小改动。
- 选择集是否应当覆盖 held-out 的规模。
- 训练实例的规模是否应当作为事实给出。目前只给调用次数与单次耗时。

## 10. 冒烟运行与修正（2026-10-03）

在 server3 上用真实的 Qwen 服务，TSP、OBP、OP 各跑一路，每路预算 30。机制按设计执行：
- 调用计数正确：TSP 768 次，OBP 12,000 次（每个实例重新执行程序也计入），OP 5 次；
- 重复链接到已有程序；失败程序与修复链进入数据结构；
- 尝试区块与进展区块进入提示，最长输入约 4.7k token。

发现的问题和处理如下：

1. **超时发生在一次调用内部时，耗时被漏算。** 一次调用的耗时要等它返回才累加，所以卡死的程序显示为“29 次调用，函数内 0.0 秒”。现在把当前调用的开始时间也放进共享内存，超时会写成“在第 30 次调用中到达时限，此前完成 29 次调用”。已用真实子进程验证：卡死的程序显示完成 9 次、卡在第 10 次；慢程序显示完成 157 次。
2. **失败版本的代码被重新抄回。** OP 的冒烟运行中，#23 在邻域密度那一行出现形状错误；修复（#24）没有修这一行，而是把密度特征整段删掉；从 #24 出发的 Refine（#28）在形成路径上看到 #23 的完整 diff，决定“加回密度因子”，并把那行有错的代码原样抄了回来。V10.15 的路径里看不到失败版本，这条通道是新机制打开的。修正方式：失败版本并入修复它的那一步，只写明失败方式和出错的那一行，diff 指向修复后的版本。
3. **OP 运行错误偏多不是计数包装造成的。** OP 冒烟中 7/30 次运行错误（-6 前 30 次为 4、2、0 次）。这 7 个程序用不带计数包装的 V10.15 评价器重新评价，错误完全相同，都是 OP 常见的形状错误与 NameError，其中 2 个出现在提示与 V10.15-6 完全相同的独立初始化阶段。
4. 函数内耗时不足 0.05 秒时，写作 “under 0.1 s”，不再写成 “0.0 s”。
