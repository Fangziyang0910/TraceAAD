# TraceAAD V10.16 机制设计

## 0. 版本身份

V10.16 是 [V10.15](TraceAAD-V10.15-机制设计.md) 的修订版，只改动 V10.15 首批正式实验（`batch_20260930`）暴露出的问题。未在本文列出的部分（预算与记账、初始化、动作配比、Crossover 参考、修复、上下文与提示词、参数）与 V10.15 逐字相同，提示词快照也未改动。

改动分两类，必须分开看待：

- **评测基础设施（§2）**：CPU 计时、OBP 实例隔离、VRPTW 接口说明。它们属于任务协议，对所有方法同样生效，不算 V10.16 的机制贡献。
- **搜索机制（§3）**：按分数类分配父代、按分数类取 finalist、放宽交付解析、补充诊断。

两类改动都会改变结果，所以比较 V10.16 与 V10.15 时，应先在新基础设施上重跑 V10.15 作为基线（§5）。

## 1. 触发改动的证据

以下数字来自 V10.15 首批 16 路已完成运行（CVRP 当时仍在运行），细节见 [2026-W40 周报](../06-总结与周报/2026-W40.md)。

| 现象 | 证据 | 判断 |
|---|---|---|
| TSP 超时大多是假的 | 30 个超时程序在空闲主机上重测，20 个在 20 秒内完成；当时成功的对照程序同样被拖慢约 2.5 倍 | 墙钟计时受并发负载影响：20 路搜索同时运行，CPU 密集进程多于核数，且 numpy 未限制 BLAS 线程 |
| OBP 分数依赖实例顺序 | rep3 选中的程序用全局变量累计物品统计；同一程序换 24 种实例顺序，箱数在 725.25–726.75 之间变化 | 评价器用同一次 exec 的函数依次评价所有实例，状态跨实例残留 |
| VRPTW 有 159 次无效输出 | 全部是"在 depot 时又返回 depot"；模板说明写的是"返回下一个节点，或返回 depot 开始新路线"，未说明在 depot 时不可返回 depot | 接口说明有歧义，模型只能在失败后从修复提示得知规则 |
| 父代抽样退化 | Refine、Crossover 分别有 26%、35% 的有效子代与父代同分，OBP 最高达 68%；每路 800–900 个节点只有 67–164 种分数；OP rep4 最高分并列 216 个 | 同分变体作为新节点进入档案，形成大并列簇；V10.15 在并列节点数 ≥ 目标 ESS 时退化为顶簇内均匀抽样，而目标 ESS 为档案规模的 10%，档案越大分配越分散 |
| finalist 失去比较对象 | OP rep1、rep4 和 OBP rep1 的 5 个 finalist 选择分完全相同 | finalist 只按代码 key 去重，同分变体可以占满 top-5 |
| 完整代码因缺少结尾围栏被拒 | 69 次 `delivery_failed`，模型以 `stop` 结束、代码完整，只缺结尾的 ``` | 交付规则过严 |
| 以"比父代好"衡量 Explore 失真 | 按父代比较，Explore 的改进率比 Refine 低约 7 倍；按刷新训练前沿，只低约 2.5 倍（4.8 对 12.1 次/千次），并贡献了 157 次刷新中的 24 次 | 父代按质量挑选，Explore 的子代离开父代骨架，天然难以超过父代 |

## 2. 评测基础设施（对所有方法生效）

### 2.1 CPU 计时

- 评价超时改为限制**整个评价进程组的 CPU 时间**（用户态 + 内核态，含已回收的子进程），预算为 `timeout_seconds × cpu_parallelism`：
  - TSP、VRPTW、OBP 单进程评价，`cpu_parallelism = 1`；
  - CVRP、OP 用 4 个 ACO worker，`cpu_parallelism = 4`。这比"空闲主机上 4 worker 的墙钟时限"略宽，因为 worker 的并行效率不到 100%。
- 保留**墙钟安全上限** `4 × CPU 预算`，防止阻塞或等待的程序无限挂起。
- 实验入口在导入 numpy 之前把 BLAS/OpenMP 线程数设为 1（`experiments/__init__.py`），评价子进程及其派生的 ACO worker 继承这一设置。否则多线程会让 CPU 时间高于实际工作量，也会加剧主机超额占用。
- 每次评价记录实际消耗的 `cpu_seconds`。
- 训练、选择和 held-out 评价都使用 CPU 计时（`experiments.infra.base.use_cpu_timeout`）。提示中的时限说法不变："在空闲主机上 X 秒内完成"正是 CPU 预算的含义。
- **验证：** 用 V10.15 的 30 个超时程序和 12 个对照程序重测，CPU 时间与空闲时的墙钟时间一致（差值约 0），有 7 个程序仍然超时，与 60 秒墙钟重测的结果吻合。高负载下判定是否稳定，待 CVRP 运行结束后单独做压力测试确认。
- **局限：** CPU 时间也不是完全不受负载影响（缓存、内存带宽、超线程、降频），但波动远小于墙钟时间下的约 2.5 倍。

### 2.2 OBP 实例隔离

评价每个实例前重新执行一次候选程序，模块级状态不能跨实例保留，分数也就不再依赖实例顺序。不使用全局状态的程序，分数与之前完全一致。

### 2.3 VRPTW 接口说明

模板和任务描述写明：调用时 `unvisited_nodes` 从不为空；只有车辆不在 depot 时才能返回 depot 结束当前路线，在 depot 时必须返回一个客户。评价器的判定规则本身不变。

**可比性：** 模板文本改变后，VRPTW 结果不能与旧模板下的历史结果直接比较，报告时需注明模板版本。

## 3. 搜索机制改动

### 3.1 分数类

在单一训练种子、确定性评价下，训练分完全相同的程序几乎总是行为等价。V10.16 把训练分相同的节点归为一个**分数类**。这是行为等价的近似：OP 这类离散目标上，行为不同的程序也可能恰好同分，这时会被错误合并。

节点仍然全部保留在档案中（它们的形成路径和代码仍会进入提示）；分数类只影响父代分配和 finalist 选择。

### 3.2 父代选择

令 K 为分数类数，`q_k` 为第 k 类的训练质量：

```
p_β(k) = exp(β · (q_k − q_max)) / Σ_j exp(β · (q_j − q_max))
目标 T = min(K, 8)
```

- `β ≥ 0` 的求解方法与 V10.15 相同，使 `ESS(β) = T`。K ≤ 8 时取均匀分布。
- 抽中一个类后，在类内均匀抽取一个成员作为父代。
- **与 V10.15 的区别：**
  - 一个同分簇无论有多少种写法，都只占一个类的份额；
  - 最高分并列时不再只在顶簇内抽样，次优类仍保有各自的份额；
  - 目标 ESS 固定为 8（V10.13 的质量 ESS），不再随档案规模增长。

### 3.3 最终程序选择

搜索结束后，按训练质量取前 5 个**不同的分数类**，每类取最早的节点作为 finalist。选择集、选优规则和测试隔离与 V10.15 相同。

### 3.4 交付解析

在 V10.15 规则之外，额外接受一种情况：回复以 `stop` 结束，只有一个开头的代码围栏且没有闭合，围栏后的内容能解析，并且恰好定义一次目标函数。Idea 的提取也以未闭合的围栏为终点。其余情况仍记为 `delivery_failed`；因长度截断结束的回复依旧不接受。

### 3.5 记录与诊断

- 有效尝试记录 `same_as_parent`（子代与父代同分）。
- 评价记录增加 `cpu_seconds`。
- `diagnostics.json` 增加以下内容：
  - `new_frontiers_by_action`：各动作刷新训练前沿的次数；
  - `score_classes`、`top_class_size`、`largest_class_size`；
  - `valid_cpu_seconds`：有效评价 CPU 时间的中位数、p95 和最大值。

## 4. 可证伪的预期

| 预期 | 若不成立，说明 |
|---|---|
| 新基础设施下，同一任务各 rep 的超时率明显下降，且彼此接近 | 超时主要来自程序本身，而非负载 |
| 选择阶段不再出现 top-5 全部并列 | 分数类的划分方式有误 |
| 父代分配的 ESS 稳定在约 8，OBP 等任务不再出现大规模顶簇抽样 | 实现未按设计执行 |
| 与新基础设施上的 V10.15 相比，held-out 不劣 | 分数类分配削弱了对有效变体的利用 |

第四条是真正的机制检验，前三条只是检查设计是否按预期执行。4 路重复只能检出较大的差异。

## 5. 实验协议

1. **基础设施验证（小规模）：** TSP、OBP 各 2 路，先后在当前负载和人为加压下运行，确认超时率与 rep 间差异下降。
2. **基线：** 在新基础设施上重跑 V10.15（5 任务 × 4 路），作为 V10.16 的直接对照。
3. **V10.16：** 5 任务 × 4 路，种子为 `repeat − 1`，其余设置与 V10.15 相同。
4. **模型服务：** 两批实验使用相同的服务配置。local（llama.cpp，GGUF UD-Q4_K_XL，KV q8_0，MTP 投机解码）与远程（vLLM 0.28.0，AWQ INT4）的排查结果如下：
   - 聊天模板渲染和分词完全相同，上下文均为 32768；
   - 客户端此前只发送 temperature、top_p、top_k，其余采样参数由两种服务各自取默认值，现已全部显式发送；
   - 同一个 TSP 提示各采样 40 次，local 有 11 次代码块未闭合，server3 为 0 次。关闭 MTP 后 local 仍有 4/18，而且真实 logprob 显示，模型在最后一行代码后直接给结束符 0.06–0.99 的概率，远程同一位置约为 0.0003。因此差异来自量化后的模型数值（GGUF 权重，可能还有 KV 量化），而不是投机解码。§3.4 的放宽规则消除了它对交付的主要影响，但两种服务的输出分布并不相同；正式实验应只使用同一种权重和服务。
5. **采样参数：** 搜索均关闭 thinking，但此前所有运行使用的是官方 thinking 模式的采样参数（temperature 1.0、top_p 0.95、无 presence penalty）。自 V10.16 起，默认改为官方非 thinking 模式配置：temperature 0.7、top_p 0.8、top_k 20、min_p 0、presence_penalty 1.5、repetition_penalty 1.0。这是对所有方法生效的协议变化，与历史结果比较时需要注明；在新协议上重跑的 V10.15 基线也使用这组参数。presence_penalty 会惩罚已出现过的 token，而代码天然会重复标识符，因此步骤 1 的小规模验证要同时检查有效率和交付失败率是否下降。
6. **判读：** 以 held-out 为主，过程指标用于解释结果是怎样产生的。
