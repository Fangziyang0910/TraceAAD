# TraceAAD：从设计轨迹中学习可复用的算法变换

Oct 25, 2026 · @matt pocock

LLM 自动算法设计让模型在每一次生成中从零构思修改：它不知道当前算法走过哪些路、踩过哪些坑，也无法复用其他路线上已被证明有效的修改方法。我们提出 TraceAAD：让每个算法携带自己的设计轨迹，并从全体轨迹中归纳可复用的算法变换。生成下一代时，系统依据父代自己的来时路，从变换库中选择适用、尚未用过、也未在本谱系失败过的变换加以实施，同时保留开放生成以发现新的变换。搜索由此积累的不只是更好的程序，还有可迁移的算法改进能力。

## 1 引言

算法设计是一个迭代过程。好的算法很少一次写成，而是在初始版本上反复修改、评价、再修改得到的。在这个过程中，有经验的设计者会积累两类知识。一类关于眼前这个算法：它经历过哪些修改才成为现在的样子，哪些尝试带来了改进，哪些尝试踩了坑。另一类是可以带到别的算法上的改进手法，例如“先用便宜的规则筛选候选，再对少量候选做昂贵的评价”。前者让他不重复犯错，后者让他不必每次都从头想办法。

基于 LLM 的自动算法设计把这一过程交给了进化搜索：每一轮选出父代，由 LLM 生成子代，再由评价决定去留。然而在每一次生成中，LLM 看到的通常只是父代的代码，加上少量示例或全局经验，上述两类知识都缺席了。父代自己的发展历史没有交给 LLM，于是已经失败过的修改会被反复尝试，已经确立的改进可能被无意撤销。某条路线上发现的有效修改，也不会成为其他路线可以直接使用的手法：它只能随整个程序被选择或交叉传播，其余路线每次都要让 LLM 重新构思、重新实现。

已有工作从两个方向改善了这一状况。表示方向为个体提供更易操作的视角：EoH 用自然语言思想与代码共同表示算法，BehaveSim 从求解行为比较算法，LHS 把程序映射到可以按梯度移动的潜空间。这些工作的价值不只在于更完整地描述算法，更在于让新的搜索操作成为可能。经验方向把搜索历史转化为指导：ReEvo 用短期与长期反思，DeltaEvolve 用语义化的修改差分，RefineEvo 用带适用条件的正负经验池。这些方法让历史发挥了作用，但它们产出的是供 LLM 阅读的建议，而不是可以直接执行的操作；经验也大多在种群层面组织，并不附着于正在被修改的那个算法。

我们注意到，搜索轨迹包含一种其他来源都没有的材料：算法是如何被改变的，以及改变带来了什么结果。每一次被评价的修改，都是一个“起点、修改、结果”的三元组。对单个算法而言，这些三元组串起来就是它的来时路，记录了它试过什么、在哪里失败过。对整个搜索而言，它们是关于算法设计操作的样本，可以从中归纳出能够作用于其他算法的修改方法。

基于这一观察，我们提出 TraceAAD。它让每个算法个体携带自己的设计轨迹，并从全体轨迹中归纳可复用的算法变换，每个变换包含适用结构、修改操作和必须保留的依赖。生成下一代时，系统依据父代自己的轨迹，从变换库中选出适用于它、尚未用过、也未在本谱系中失败过的变换加以实施，同时保留开放生成，让新的修改方法不断出现。每次评价的结果同时写回父代的轨迹和变换库。这与医生诊治病人相似：开方时既读这位病人的病历，看哪些治疗有效、哪些药物引起过不良反应；也参照由大量病例总结出、并不断被新病例修正的诊疗方案。

本文的贡献如下：

1. **视角**：把搜索轨迹看作“算法如何被改变”的记录，提出在个体层面（来时路与试错）和跨个体层面（可复用的算法变换）两级利用它。
2. **方法**：提出 TraceAAD，包括基于共享谱系图的轨迹记录、从轨迹中归纳带适用条件与依赖关系的算法变换、在新父代上受约束地实施变换并依据使用结果修正，以及以父代自身轨迹引导生成、让变换在不同算法路线之间传播。
3. **实验**：除常规的同预算对比与消融外，设计两类检验迁移能力的实验：把变换作用于未参与归纳的父代，以及重置程序种群、只保留变换库重新搜索。

## 2 问题设定

**自动算法设计。** 给定问题实例分布 𝒟，程序 p 的性能记为 f(p)，即它在 𝒟 上的期望得分，越大越好。LLM 驱动的进化搜索维护一个程序种群：每一轮选出父代 p，由 LLM 生成子代 c，评价 f(c)，再更新种群。

**谱系图。** 记 𝒢 为搜索中所有被评价过的程序构成的有向图，包括未被种群采纳的子代。每条边 p → c 记录三项信息：这次修改的内容 δ（一句自然语言摘要，以及实际的代码差异）；修改的来源，即调用了哪个变换，或者是自由生成；修改的结果 Δ = f(c) − f(p)，以及状态（改进、无改进、无效）。交叉产生的子代有两个父代。

**设计轨迹。** 种群中个体 p 的祖先路径记为 (p₀, p₁, …, p\_k = p)。它的轨迹由两部分组成：

```latex
T(p) = \Big(\underbrace{\{(\delta_i, \Delta_i)\}_{i=1}^{k}}_{\text{成长路径}},\;\; \underbrace{\mathcal{S}(p)}_{\text{旁支尝试}}\Big)
```

成长路径记录 p 是怎样一步步变成现在的样子的。旁支尝试 𝒮(p) 是从路径上任一节点出发、但不在这条路径上的所有子代，其中也包括从 p 本身生成过的子代。旁支尝试中无改进或无效的部分，就是这个谱系踩过的坑；有改进但走向别处的部分，是兄弟路线探索过的其他可行方向。

**算法变换。** 一个变换描述“在什么样的程序上，做什么样的修改”：

```latex
\tau = \big(\, C_\tau,\; O_\tau,\; D_\tau,\; \Theta_\tau,\; R_\tau \,\big)
```

- 适用结构 C\_τ：变换适用的程序结构，例如“先生成候选，再对每个候选调用昂贵的评价”。
- 修改操作 O\_τ：插入或替换什么计算，附若干修改前后的参考代码。
- 依赖关系 D\_τ：必须一起保留或一起加入的计算，例如筛选后仍须通过原有的可行性检查。
- 可适配参数 Θ\_τ：随目标程序调整的部分，例如筛选规模。
- 使用记录 R\_τ：它在哪些程序、哪些谱系上被实施过，结果如何。

把 τ 实施到程序 p 上，记为 τ(p; θ)：在 p 中找到满足 C\_τ 的位置，绑定变量与函数，按参数 θ 执行 O\_τ，并满足 D\_τ。

**变换库与候选邻域。** 第 t 轮的变换库记为 ℒ\_t。对父代 p，可以考虑的变换集合为：

```latex
\mathcal{N}_t(p) = \{\, \tau \in \mathcal{L}_t \;:\; C_\tau \text{ 与 } p \text{ 匹配},\; \tau \text{ 不在 } p \text{ 的成长路径上},\; \tau \text{ 不是 } p \text{ 谱系中的已知失败} \,\}
```

它是由已学变换在 p 上实际可以构造的搜索邻域，随变换库与 p 的轨迹一起变化。除此之外，系统始终保留不受变换库约束的自由生成。

**目标。** 在给定的评价与 LLM 调用预算内找到更好的算法；同时，搜索中积累的变换库应当具有迁移性，能够帮助从新的程序出发的搜索。

## 3 方法

### 3.1 概览

TraceAAD 在一个能维护多条算法路线的基础搜索器之上，加入两个相互供给的对象：每个个体的**设计轨迹**，以及由全体轨迹归纳出的**变换库**。轨迹是变换库的数据来源，变换库是生成新修改的工具，而每次修改的结果又同时写回两者。

&#91;embedded content: TraceAAD 总览 · 谱系轨迹与变换库的闭环\]

左侧是个体层面的来时路，右侧是跨个体的变换库。生成子代时同时使用两者，评价结果又同时写回两者。

一轮搜索按以下顺序进行：

1. **记录**：每个被评价的子代都挂到谱系图上，成为父代轨迹的一部分，无论它是否被种群采纳（3.2）。
2. **归纳**：带来改进的自由修改，以及在不同路线上重复出现的相似修改，被提炼为可复用的变换，加入变换库（3.3）。
3. **实施**：为父代选择一个适用的变换，在其代码上受约束地实施；或者进行开放生成（3.4、3.6）。
4. **修正**：变换在新程序上的使用结果，用来修正它的适用条件和依赖关系（3.5）。
5. **传播**：一条路线发现的变换可被其他路线调用，各路线保留自己的主要设计（3.7）。

这一循环与人工智能中基于案例的推理一致：检索与当前问题相似的案例，复用其解法，按结果修订，再保留为新的案例。TraceAAD 中的“案例”是一次次对算法的修改，“解法”是从中归纳出的变换。不同之处在于，这里的检索同时受到个体自身历史的约束：父代的轨迹决定了哪些变换已经用过、哪些在这个谱系上失败过。

### 3.2 设计轨迹：记录来时路与踩过的坑

**修改的记录。** 每个子代评价完成后，系统为它与父代之间的边生成一条修改记录。记录包含实际代码差异、一句由 LLM 根据差异和生成时陈述的意图写出的修改摘要、修改来源，以及结果与状态。状态分三种：改进、无改进、无效（运行错误或超时）。所有子代都被记录，被种群淘汰的子代同样保留，因为它们恰恰是踩过的坑。

**轨迹是共享谱系图上的视图。** 轨迹不随个体复制。每个个体只保存自己在谱系图中的位置，它的轨迹在需要时由“根到该节点的路径，加上路径各节点的旁支尝试”即时构成。这样做有一个直接的好处：后来在某个祖先上发现的失败，会立刻出现在它所有后代的轨迹里；一个父代被再次选中时，它此前生成过的失败子代也自然成为它的轨迹的一部分。交叉产生的个体同时拥有两条祖先路径，共同祖先只出现一次。

**轨迹的压缩。** 轨迹随搜索增长，交给 LLM 时需要压缩，分三部分：

- **近期细节**：最近若干步的修改摘要与结果，以及这些节点上的旁支尝试，逐条列出。
- **谱系摘要**：更早的历史压缩成一段说明，讲清这个算法是怎样演变到近期起点的。摘要在每个新节点创建时生成一次：新节点的摘要由父代摘要与新的一步合并而成，此后被所有后代复用。
- **试错清单**：从整条路径上收集失败的旁支尝试，合并语义重复的条目，并保留次数，例如“加入前瞻：在本谱系尝试 3 次，均变差”。清单在读取时即时汇总，因此总能包含最新发现的失败。

例如，一个装箱启发式经过“引入后悔值评分”“加入 2-opt 修复”“调整阈值”三步成为当前父代；途中“加入前瞻”被试过两次，都使结果变差。它的压缩轨迹会把前两步写进谱系摘要，把最后一步列为近期细节，并把“加入前瞻”列入试错清单。

### 3.3 变换归纳：从轨迹中提炼可复用的修改方法

**何时归纳。** 两种情况触发归纳：一次自由生成的修改带来了改进；或者语义相似的修改在两条以上的路线上出现，无论结果好坏。前者提供有效修改的首个样本，后者提供跨背景的多个样本。

**输入。** 修改前后的代码、实际差异、修改摘要与结果；如果库中或谱系图中已有相似修改，一并提供这些样本。

**输出。** LLM 把具体修改抽象为第 2 节定义的变换：

- **适用结构**用程序的计算模式来描述，例如“对候选集合逐个调用某个代价高的评价函数”，而不是具体的变量名或行号。
- **修改操作**说明要插入或替换的计算，并保留来源样本中修改前后的代码片段作为参考。
- **依赖关系**从差异中识别：同一次修改中哪些改动是彼此配合的，例如加入筛选的同时保留回退规则。有多个样本时，始终同时出现的改动被视为依赖。
- **可适配参数**来自样本之间的差异：多个样本共有的部分构成操作本身，彼此不同的部分成为参数。

这一步与程序合成中的库学习思路相近：从多个具体解中提取共同结构，把差异参数化。区别在于，这里被抽象的对象不是求解实例的代码组件，而是对算法程序本身的修改。

**去重。** 新归纳出的变换先与库中已有变换比对。如果它只是某个已有变换的又一次实例，就作为新的使用记录并入，而不是另立一条。

**失败修改的去向。** 无改进或无效的修改不会产生新变换。如果它与库中某个变换对应，就作为该变换的一条反例写入使用记录，供 3.5 修正适用条件；同时它留在所属谱系的试错清单里。

### 3.4 变换实施：在新父代上匹配、绑定与修改

变换的价值在于能被直接实施，而不是再次交给 LLM 自由发挥。实施分为四步。

**检索。** 对父代 p，先从库中找出适用结构可能与 p 匹配的变换，再用 p 的轨迹过滤：已经在成长路径上实施过的去掉；在本谱系中失败过、且相关部分此后没有变化的去掉。剩下的就是候选邻域 𝒩\_t(p)。

**选择。** 在候选邻域中，依据已观察到的使用记录选择一个变换：在相似程序上的成功次数与尝试次数之比越高，被选中的机会越大；尚未在相似程序上试过的变换保留基本的机会。这里只使用已经发生的结果，不估计任何程序的未来价值。

**匹配与绑定。** LLM 阅读 p 的代码和变换规格，指出 p 中满足适用结构的具体位置，并说明绑定关系：p 中哪个函数、变量或数据结构对应变换中的哪个角色。若找不到满足条件的位置，本次实施记为“不适用”。

**受约束的修改。** LLM 只在匹配到的位置及依赖关系涉及的位置上做修改，以局部编辑块的形式输出，并在可适配参数的范围内选择取值；程序的其他部分保持不变。生成后，系统重新摘要实际差异，核对它是否实现了修改操作、是否满足依赖关系。若不符合，记为“实施失败”，与“变换无效”区分开。

这样，同一个变换在不同父代上的实施，是一系列可比较的受控尝试：改的是同一种东西，只是被适配到了不同的程序上。

### 3.5 变换修正：用使用结果更新适用条件

刚归纳出的变换只是候选工具；它的适用范围由后续的实际使用逐步界定。每次实施都落入四种结果之一，并分别更新变换库和父代的轨迹：

| 实施结果 | 对变换库的更新 | 对父代轨迹的更新 |
| --- | --- | --- |
| 不适用：找不到匹配位置 | 记录一条“结构不符”的样本，用于收紧适用结构的描述 | 不记为失败 |
| 实施失败：实际修改不符合规格 | 不计入变换的成败；若在某类程序上反复发生，说明规格不够清楚，需要补充参考样本 | 不记为失败 |
| 实施成功但无改进 | 写入一条反例，附上该程序的结构特征 | 记入试错清单 |
| 实施成功且改进 | 写入一条正例 | 成为成长路径的一步 |

**适用条件的细化。** 当一个变换积累了一定数量的正例和反例后，LLM 对比两组程序的结构，改写适用条件：缩小它的范围，或把它拆成适用于不同结构的两个变换。失败因此不只是“不要这样做”，而是变成关于“在哪里不该这样做”的具体知识。

**依赖的发现。** 如果一个变换只在已经实施过另一个变换的程序上有效，就把后者记为它的前提，必要时把两者合并为一个组合变换，作为整体实施。

**降级而不删除。** 使用记录持续为负的变换降低被选中的机会，但保留在库中，并在相关程序的提示中作为提醒出现，避免它被以别的形式重新提出。

### 3.6 轨迹条件化的生成：本谱系的历史如何决定下一步

每个子代由三种方式之一产生。三种方式的提示中都包含父代的压缩轨迹，所以无论用哪种方式，LLM 都知道这个算法的来时路。

**变换模式。** 按 3.4 从候选邻域中选择并实施一个变换。父代的轨迹在这里起过滤作用：已用过的和在本谱系失败过的变换不会被选中。

**开放模式。** LLM 先回顾轨迹，写出三点简短判断：这个算法近来在哪些方向上取得了进展；试错清单说明哪些方向走不通；兄弟路线上有哪些成功的修改值得参考。然后提出一个新的修改，并给出一句意图说明。约束有两条：不重复试错清单中的修改，除非说明此后程序发生了什么变化使它值得重试；不重复变换库中已有的修改，这类修改交给变换模式完成。开放模式是新变换的来源。

**轨迹感知的交叉。** 从两个父代的轨迹中找出共同祖先，共同的历史只展示一次，再分别列出两条分支各自取得的改进和各自的试错清单。LLM 被要求把两条分支的改进结合起来，同时避开两者踩过的坑。子代在谱系图上拥有两个父代，它的轨迹是两条路径的合并。

**方式的比例。** 三种方式的比例依据各自近期观察到的改进率调整，开放模式保有最低比例。变换库再丰富，系统也始终在提出库中没有的新修改。

### 3.7 跨路线传播与多样性

**路线的维护。** 种群按算法思路划分为若干路线，可以沿用已有的小生境方法，例如按 EoH 式思想描述或按求解行为聚类。每条路线保有一份最低生成预算，其余预算按各路线近期观察到的改进分配；路线内部按实际成绩竞争。

**传播的单位是变换，而不是整个程序。** 一条路线上归纳出的变换进入共享的变换库，其他路线的父代只要结构匹配，就可以在变换模式中调用它，同时保留自己的主要设计。不同思路之间的交融因此不必通过“用一个高分程序替换另一个”来实现，而是让一条路线学到的修改方法作用于另一条路线。

**多样性的两重作用。** 不同路线首先是需要被持续开发的对象。同时，它们为同一个变换提供了不同的背景：一个变换若在多条路线上都有效，说明它是通用的改进方法；若只在来源路线上有效，则更像针对那份代码的局部修补。没有多样的路线，系统无法做出这种区分，变换库也会退化为某一个程序的修改历史。

**知识可以来自任何程序。** 变换的来源不限于高分程序。一个整体成绩不强的程序，也可能包含一次有效的修改；是否值得复用，由它在接收程序上的实际效果决定。这里评价的是“这个变换能否帮助另一个程序”，而不是“这个程序将来是否会变好”。

### 3.8 完整流程

**初始化。** 由 LLM 生成初始程序并评价，建立谱系图的根节点和初始路线；变换库为空。

**每一轮：**

1. 按路线的预算份额选出一条路线，再在路线内选出父代 p。
2. 读取 p 的压缩轨迹：谱系摘要、近期细节与试错清单。
3. 按各方式的比例，选择变换模式、开放模式或轨迹感知的交叉。
4. 变换模式：检索候选邻域、选择变换、匹配绑定、受约束修改、核对实施。开放模式：回顾轨迹后提出新修改。交叉模式：合并两条轨迹后结合两条分支的改进。
5. 评价子代，把它作为一条带修改记录的边挂到谱系图上。
6. 更新变换库：变换模式下按四种结果修正该变换；开放模式下，若子代改进，或相似修改已在其他路线出现，则触发归纳。
7. 按基础搜索器的规则更新种群与路线划分。

**输出。** 最终最好的程序，以及一个附带使用记录的变换库。

**额外成本。** 不增加评价次数。额外的 LLM 调用包括：每个新节点一次修改摘要与谱系摘要，变换模式中的匹配与核对，以及按需触发的归纳与适用条件细化；这些调用都可以使用较小的模型。

## 4 与相关工作的关系

TraceAAD 与经验类方法共享“利用搜索历史”的出发点，区别在于两点：历史附着于具体个体的谱系，并包含旁支上的失败；经验被提炼为可以在其他程序上直接实施、并依据使用结果修正的变换，而不只是供 LLM 阅读的建议。

| 工作 | 历史如何组织与使用 | TraceAAD 的区别 |
| --- | --- | --- |
| [DeltaEvolve](https://arxiv.org/html/2602.02919v1) | 把程序与父代之间的语义变化写成摘要与逐组件计划；上下文中的变化来自数据库中的精英与多样个体，用于启发新的方向而非直接复用 | 历史取自父代自己的谱系，包含旁支失败；变化被归纳为可在其他父代上实施的变换 |
| [RefineEvo](https://arxiv.org/html/2607.11358) | 从父子比较中提取带修改摘要、建议与适用条件的正负经验，按语义相似度检索后注入提示，并改写算子提示 | 经验具有匹配、绑定和受约束修改的实施过程；适用条件由实施结果修正；失败同时记入所属谱系 |
| ReEvo | 短期反思比较候选，长期反思累积全局文字经验 | 经验按谱系组织，并形成可执行的变换 |
| MCTS-AHD、PathWise | 以树或推导图组织候选，在生成中利用推导路径 | 把旁支尝试作为试错清单纳入轨迹，并从全体轨迹归纳跨路线的变换 |
| [CCTS](https://arxiv.org/html/2602.03132v1) | 从程序中抽取概念，按好坏程序对比估计概念效用，用于选父代和注入概念 | 学习对象是对程序的修改操作，而不是程序具有的特征 |
| EoH、BehaveSim、LHS | 以思想、行为、潜空间表示个体 | 表示的对象从“算法是什么”扩展到“算法怎样被改变” |

在技术来源上，从修改示例中学习代码变换，在软件工程中已有按示例变换的研究；“检索、复用、修订、保留”的循环来自基于案例的推理。TraceAAD 的增量在于：以算法性能反馈驱动变换的归纳与修正，以个体轨迹约束变换的选择，并让变换成为不同算法路线之间传播知识的单位。

## 5 实验设计

实验回答三个问题：TraceAAD 能否在同等预算下找到更好的算法；个体轨迹和变换库各自贡献了什么；搜索积累的变换能否迁移到新的程序和新的搜索。

### 5.1 设置

**任务**：在线装箱、TSP 构造式启发式、CVRP、FSSP 等 LLM4AD 常用任务，以及 CO-Bench 的一个子集；一律报告留出测试实例上的结果。

**基线**：EoH、ReEvo、DeltaEvolve、RefineEvo、MCTS-AHD。

**预算**：评价次数相同；LLM 调用次数与 token 用量全部计入并报告，包括摘要、匹配、核对与归纳的调用。

### 5.2 主实验

在相同预算下比较最终程序在测试实例上的性能，以及最好成绩随预算增长的曲线。

### 5.3 受控实验：轨迹对单次修改的作用

固定一批父代程序，只改变交给 LLM 的历史信息：无历史；种群级的反思经验；只有成长路径；成长路径加试错清单。比较子代的改进比例、改进幅度的分布，以及重复已知失败修改的比例。这个实验把轨迹的作用与选择、预算分配等因素分开。

### 5.4 迁移实验一：变换作用于未参与归纳的父代

用一组运行的轨迹归纳变换库，再作用于另一组运行中的父代。在使用同一批历史证据的前提下比较三种方式：让 LLM 直接阅读历史修改；阅读结构化的文字经验；调用归纳出的变换。核心问题是：变换能否跨不同实现使用，是否比阅读经验后自由修改更有效。

### 5.5 迁移实验二：重置种群，保留变换库

各组从相同的初始程序重新开始搜索：一组不保留任何经验，一组保留文字经验，一组保留变换库。若保留变换库的一组改进更快，就说明系统从上一段搜索中获得了可迁移的算法改进能力，而不只是保存了更好的程序。进一步可以检验跨任务迁移，例如把 TSP 上积累的变换用于 CVRP。

### 5.6 消融

| 变体 | 检验的问题 |
| --- | --- |
| 去掉试错清单，只保留成长路径 | 失败轨迹的作用 |
| 去掉个体轨迹，只保留变换库 | 来时路对变换选择与开放生成的作用 |
| 去掉变换库，只保留个体轨迹 | 可复用变换的作用 |
| 变换只作为提示中的建议，不做匹配、绑定和受约束修改 | 可执行性是否必要 |
| 去掉变换修正 | 用使用结果界定适用范围是否必要 |
| 变换只在来源路线内使用 | 跨路线传播的作用 |
| 去掉开放模式的最低比例 | 持续发现新修改的作用 |

### 5.7 分析

- **重复踩坑率**：子代重复本谱系试错清单中某条修改、并再次失败的比例。
- **变换库的演化**：变换数量、被复用的次数、跨路线生效的比例。
- **通用与局部**：哪些变换在多条路线上有效，哪些只在来源路线上有效。
- **案例**：追踪一个变换的完整生命周期，包括它从哪次修改归纳而来、被哪些路线采用、适用条件怎样被细化。
