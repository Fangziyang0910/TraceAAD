# TraceAAD V11.0 机制与实验分析

## 核心判断

V11.0 没有形成跨五个任务的稳定独立优势。它在 CVRP-ACO 上取得了可重复的 held-out 改善，但 TSP、OP-ACO 和 VRPTW 退化，OBP 基本不变。当前证据最支持的解释是：**V11 的预算分配先把搜索变成了精英锁定的贪心开发；参考上下文的组织又没有为所有任务提供可执行的机制证据；两者耦合后形成了“父代选择很窄、参考信息很宽”的搜索结构。**

这不是对 V11 研究目标的否定。V11 的初始目标正是把 V10.11 对照中观察到的任务/算子—上下文匹配联合起来，以提高各算子的有效性并让五类任务更稳定。当前失败说明联合设计的两个支点没有配平：预算选择没有给不同上下文模式足够的开发机会，Pivot/Fuse 的参考形式也没有完整承载 V10.11 中已经观察到的可执行经验。后续设计应修复这套联合机制，而不是退回一个不包含上下文匹配的单因素版本。

提示词措辞和解析不是首要原因。现有结果没有提供同一调度下的提示孤立对照，因此不能把退化归因于某句话；但格式遵守和解析失败没有出现足以解释跨任务退化的变化。

## V11 实际改变了什么

V11 相对 V10.11 generic 有两项主要机制变化：

1. 父代从 V10.11 的 ESS 校准质量 Softmax 抽样，改为按唯一 AST code 计算质量百分位与探索加分，并直接选择最高分 code。
2. Pivot/Fuse 从 V10.11 的形成轨迹和 Fuse donor 代码，改为共享最多 8 个 Idea+fitness 参考节点；参考按 reciprocal-rank 无放回抽样。

Refine/Tune 的短形成轨迹、四算子各 25%、单亲树、任务契约、一次有界修复、真实评价预算和持久化规则保持不变。

实现位置：父代打分与选择在 [`traceaad.py`](../../llm4ad/method/traceaad_v11_0/traceaad.py:203)，Pivot/Fuse 参考组装在 [`trajectory.py`](../../llm4ad/method/traceaad_v11_0/trajectory.py:140)。

## 结果事实

V11 正式批次为五任务、五重复、每路 1000 次真实评价。固定 24 路和补齐 CVRP rep3 的结果显示：

| 任务 | V11 相对 V10.11 generic 的 held-out 信号 | 结论强度 |
|---|---|---|
| TSP | 50/100/200 规模约退化 3.5%–4.3% | 中高 |
| CVRP-ACO | 五重复补齐后 50/100/200 规模改善约 3.70%/4.46%/3.75% | 高，限于 CVRP |
| OP-ACO | 50/100/200 规模约退化 0.37%/1.70%/3.58% | 中 |
| OBP | 多数规模变化小于 0.3% | 中高，接近不变 |
| VRPTW | 50/100 规模约退化 4.92%/2.34%，200 规模有一项缺失 | 中 |

完整训练和 held-out 口径见 [`V11.0-实验结果.md`](各版本实验记录/V11.0-实验结果.md)。这些结果区分了训练 best 与 held-out，不能用 CVRP 的收益代表 V11 全局有效。

## 首要问题：预算分配的实现退化

V11 的选择规则是：

\[
S_t(x)=q_t(x)+0.1\sqrt{\frac{\ln(1+T)}{1+n_t(x)}}
\]

然后每轮只选择 `S_t(x)` 最大的 code。这里的问题不只是探索系数 `0.1` 偏小，而是选择结构本身：

- `q_t(x)` 是不同 code 的 fitness 百分位，范围为 0 到 1，直接取最大值会形成确定性头部选择；
- `n_t(x)` 统计的是完全相同 AST code 被直接开发的次数，不是任务机制、搜索路线或分支覆盖；
- 新候选大多是新 AST code，exact-code 的尝试次数很少复用；
- 当前实现没有向低分但未充分检验的候选提供独立预算配额；
- 四个算子共用同一个最高分父代选择器，Pivot 没有 V10.11 中的 50% 均匀混合。

现有 V11 运行摘要中，`num_codes` 通常接近 `num_nodes`。这说明代码去重统计没有形成有意义的“开发臂”，而是把大量候选当成互不重复的单点。于是所谓 exploration bonus 只是在极少数分数接近时改变排序，不能抵消最高百分位选择。

行为证据与此一致：正常开发中约 99.7%–100% 的请求落在 `q ≥ 0.95` 的 code，`q < 0.75` 的 code 几乎没有开发机会；best 节点形成深度约 50–72，高于 V10.11 的约 9–34；Pivot 的 parent 改进率从 V10.11 的约 9%–16% 降至 V11 的约 1.5%–3.2%。

这表示 V11 的预算策略没有测量“某类经验是否值得继续开发”，而是在重复开发当前已经高分的程序。CVRP 的结构较适合精英机制传播，因此这种偏置可能有效；在 TSP、OP 和 VRPTW 中，它更容易把早期偶然路径放大成长期锁定。

## 第二个问题：参考上下文与任务收益形成结构不匹配

V10.11 的对照表明：

- TSP 和 VRPTW 更依赖短形成轨迹，连续的局部修改、阶段协调和约束关系需要保留形成顺序；
- CVRP 的精英档案参考更有效，距离、容量、节约和 depot 相关机制可以跨路径传播；
- OBP 的有效证据是参考思想真正改变了 `argmax` 排序，而不是 Idea 本身出现；
- OP 对上下文具有规模和阶段依赖，全代码上下文在后期出现收益，但没有稳定的全程优势。

V11 把 Pivot/Fuse 的参考压缩成 Idea+fitness，并用 reciprocal-rank 抽样扩大长尾参考比例。约 40%–43% 的参考来自前 32 名之外，而 V10.11 的 rank-softmax 参考约为 2%。这些条目没有代码、算子、形成顺序或实际行为变化，模型可以知道“某个想法分数是多少”，却无法可靠判断它改变了哪项计算、适用于什么父代、是否能与当前实现兼容。

因此：

- CVRP 可以从高质量 Idea 中提取稳定的几何和容量机制，V11 得到收益；
- TSP/VRPTW 需要连续形成关系，Idea-only 参考不能替代短轨迹；
- OBP 需要可验证的排序变化，Idea-only 参考缺少关键证据；
- OP 需要根据规模判断参数或组合机制，全局统一参考形态不足。

## 耦合问题

单独看，V11 的精英父代选择可能适合 CVRP，V11 的 Idea 参考也可能帮助 Pivot/Fuse 获得跨路径材料。问题在于两者同时变化后形成了不对称结构：

1. 父代侧极度集中，只有极少数高分程序得到连续预算；
2. 参考侧却扩大到大量长尾 Idea，且缺少代码和行为证据；
3. Pivot/Fuse 没有足够的独立探索预算来验证替代方向，也没有足够的可执行材料把参考转成可靠代码；
4. Refine/Tune 继续沿着被集中选择的父代开发，导致代码膨胀或局部陷阱被延续。

这解释了为什么单看某个局部指标会产生误判：C 类对照中 Pivot 的 parent 改进率可以升高，但 frontier 改进率接近零；V11 某些任务能够持续产生局部更好候选，却没有形成更好的最终前沿。

## 算子与提示层的证据边界

算子语义本身没有被证明失效。四算子概率仍为 25%，解析协议和一次修复也沿用稳定实现。当前证据只支持以下判断：

- Refine/Tune 的短形成轨迹有任务相关价值；
- Pivot/Fuse 的参考形式需要与任务收益结构匹配；
- 算子标签不能代替代码行为核验；
- “parent 改进”不能代替“frontier 改进”。

没有同一预算、同一父代调度下只替换 prompt wording 的对照，因此提示措辞不是当前首因。应把提示层保持稳定，先修复预算选择，再单独测试参考上下文。

## 结论与研究边界

V11 的失败不是“模型不会生成算法”，也不是一个算子单独失效。更准确的机制表述是：

> V11 把预算分配从随机质量开发变成了按最高百分位 code 的确定性开发；同时把 Pivot/Fuse 的经验压缩成带长尾噪声的 Idea 卡片。窄父代选择与宽而弱的参考上下文没有互补，导致 CVRP 受益而其他任务无法稳定获得可开发的新方向。

V11 证明了不同 task 上的经验收益存在差异，不证明应把 task 名称写成上下文选择规则。V10.11 的结果只能作为判断算子所需信息类型的间接证据，尚未充分识别“每个算子各自最优的上下文”。BC 批次已停止，且为部分运行；它可以作为运行成本和方差的辅助证据，不能作为新的最终质量排名或因果结论。
