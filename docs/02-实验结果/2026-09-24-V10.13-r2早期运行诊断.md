# V10.13-r2 早期运行诊断：输出损耗与决策停滞

V10.13-r2 没有发现运行中断或评价记账异常，但目前也没有表现出预期的稳定质量提升。相同 E50 下，TSP、CVRP、VRPTW 的四重复训练 best 均值略差于上一批 r1，OP 较好，OBP 的收益集中在少数重复。更确定的问题是输出协议与实际模型响应不匹配，以及部分搜索在不同代码和 Idea 下重复相同决策。此前“机制执行成功”只证明协议链路发生，不能升级为优化有效。

## 3. 输出协议确实在损耗搜索

固定快照含 2,471 个候选结算事件：1,726 成功、638 `invalid_output`、107 `eval_failed`。评价前拒收占 **25.82%**；107 次实际评价失败则占 1,833 次结算评价的 **5.84%**。这两个分母不可混用。

离线检查 638 次被拒响应，在不改写代码、不修补转义、不调用评价器的条件下：

- **322 次**内部存在唯一可识别的 JSON 提案，单独取出后能通过现有 parser 的语法、接口和 edit 检查；外层说明、围栏等使原响应被拒。不是说这些候选一定有高 fitness，也没有把它们回填正式结果。
- **72 次**包含可识别的 JSON 上下文请求，并处于允许读取的阶段，所请求的 trial/reference 合法；由于外围文字或 `<tool_call>` 包装，分支没有识别请求，反而进入代码失败及修复路径。其中 71 次修复已结算，61 成功、7 评价失败、3 再次拒收；另一次修复尚在固定边界外。
- 13 次取出 JSON 后仍未通过代码或 edit 检查；4 次含多个不同 payload，不能简单选一份。其余 227 次包括坏 JSON、已有合法 JSON 但代码/字段不合法、没有完整提案等，不作统一归因。
- 637/638 次 `finish_reason=stop`，仅 1 次为 length。当前不能将主要问题解释为输出 token 上限不足。

因此，日志中的大量 `syntax_error` 不全是 Python 能力问题：未被识别的 JSON/请求会落入 Python 解析支路。更严重的是，合法的“先读参考再改进”意图被转成“修复坏代码”，实际设计过程改变了。这是可定位的接口缺陷。

在全 20 路相同 E50（合计 E1000）下：

| 成本/过程 | r1 | r2 |
| --- | ---: | ---: |
| LLM 调用 | 1,115 | 1,662（+49.1%） |
| 评价前拒收 | 115 | 364 |
| 实际评价失败 | 53 | 64 |
| 修复提案占用的评价 | 134 / 1,000 | 356 / 1,000 |
| 输入 tokens | 2,311,499 | 3,127,077（+35.3%） |
| 输出 tokens | 1,691,190 | 1,365,197（-19.3%） |
| 报告的总 tokens | 4,002,689 | 4,492,274（+12.2%） |

解析拒收不消耗真实评价槽，不能用其数量直接解释同 E 的质量差距。它确定增加模型调用，且修复候选在评价中的比例从 13.4% 升到 35.6%，改变了实际提案来源。各路达到 E50 的耗时总和反而从 53,485 秒降至 48,479 秒，任务间也不一致；不能声称 r2 全面更慢，服务吞吐也不是方法变量。

## 4. 上下文读到了什么，没读到什么

**空读是确定损耗。** 544 次局部 trial 读取中，217 次为空（39.9%）。实现无论是否已有可读子代，都展示读取入口；返回“没有记录”仍需要下一次完整生成调用。系统本来知道是否有数据，没必要让 LLM 花一次调用发现空集。

**参考卡不等于借鉴实现。** 840 次正常 Pivot/Fuse 提案中，92 次读取完整参考，748 次未读（89.0%）；Fuse 为 66/426（15.5%），Pivot 为 26/414（6.3%）。这里统计的是显式读取，不是断言没读代码就不能创造好算法。思想卡可能足够启发 Pivot，但不能据此证明 Fuse 已完成精确组件整合；前述请求误解析还压低了实际读取机会。r1 自带参考代码，不应用 r2 的显式读取字段衡量 r1 是否看到代码。

**精确父代记忆未解决行为等价的试验分散。** OBP rep2 在 E189 的最后一次选父时，182 个有效节点中最高分并列数为 173，`parent_ess_target=173`、实际 ESS≈175。ESS-8 在并列条件下提高目标是代码明确的数学处理，不是数值失灵。若大量不同节点实现相同决策，节点级机会就分散到重复行为上；这些节点的子代试验又被分别记录，同一个父代的局部记忆不能自然合并它们。

这是“高节点覆盖不保证高算法多样性”的具体风险，不能把同分一概等同于同行为，也不能据此立刻引入按 fitness 合并或复杂语义分类器。

## 5. OBP：思想描述与实际决策脱节的实码证据

固定快照中，rep1 E157、rep2 E189 的 best 都仍是首次评价的 -744.5。rep1 的 155 个有效候选里 128 个为该分数；rep2 的 183 个有效候选里 174 个为该分数。rep2 初始化的 8 个 root 已全部同分。

具体看 **rep2 candidate232 / node182 / E189 / Fuse**，fitness=-744.5。节点 Idea 声称增加 concave fragment shaping，避免中等碎片；实际关键代码是：

```python
remaining = bins - item
base = -remaining
t = np.clip(remaining / max(item, 1.0), 0.0, 1.0)
frag_bonus = 0.5 * t * (1.0 - t)
tie = 0.0001 * (-remaining / max(np.max(remaining), 1.0))
result = base + frag_bonus + tie
```

任务输入为整数 item/capacity，评价器用 `argmax` 选 feasible bin。不同 slack 的基项至少相差 1；fragment bonus 始终在 [0, 0.125]，tie 项进一步偏好更小 slack，同 slack 时附加项也相同。因此在这份任务的合法整数输入上，这段新增机制不会改变 best-fit 的选择。Idea 中“actively avoids medium-sized gaps”的说法没有代码行为支持。

它展示的三个参考 node46/124/168 也都围绕 best-fit 加 fragment shaping，前两张还直接承诺“不改变原有 tight-fit ordering”。不同 AST、质量/均匀/低曝光的来源和三张卡，没有自动带来互补思想。node182 的形成路径经历多次 Fuse，分数仍全部 -744.5。这比仅看同分更强地支持“叙述和实现变化尚未到达实际决策”。

不能据此否定 edit 或全部搜索。**rep3 node133** 通过 Refine/edit 将 -728.75 改至 -728.0；其形成路径为：

`-744.5 → -739.25 → -731.5 → -734.25 → -729.0 → -728.75 → -728.0`

路径中 Fuse 引入的模块化余量收益随后得到开发；Pivot 的暂时退步节点也被继续选择。node50/75/84 在固定边界内分别被继续开发 5/14/12 次，node133 被继续开发 2 次。最终代码含 modular reuse bonus 和 dead-space penalty，在一些合法状态下能够真正翻转 best-fit 的选择。这说明“生成新结构—评价选择—继续开发”的正向链条在个别重复中发生了，但还不稳定，未提供 held-out 证据。

结构化 Idea 目前只是更易检索的**作者假设**。字段存在不保证准确；精确代码与真实评价仍是检验依据。默认继续使用短 Idea+fitness 合理，但“这些信息绝对不会误导”并不成立。

## 6. 判断与后续选择

**第一优先：修复输出和读取接口，保留创造过程。** 下一冻结修订应对同一原响应只提取明确、唯一的 JSON 提案/请求；多个冲突对象不擅自猜选，内部坏代码仍按失败处理。context 与 full/edit 共用一致的封装识别。精确版本绑定由宿主维护，避免让模型抄写 64 位 hash；继续保留唯一 search 匹配等 edit 安全校验。此次离线取出 payload 只是诊断，不是已经验证的生产 parser 策略。

**第二优先：让读取有可用信息，且信息对得上动作。** 无 trial 时隐藏读取入口或直接显示无记录；Fuse 若明确选中要整合的 donor，再展开一份相关实现。Pivot 可以保留轻量思想启发，不要求所有操作都强制读代码。先恢复模型已经表达的有效读取意图，不增加原始 diff 或更多卡片。

**第三优先：提示聚焦真实的算法变化，避免给叙述加字段。** 以本次反例改进算子语言：改进排序器时思考什么状态下应改变选择；组合信号时考虑尺度和交互是否足以到达输出。Tune 可以保持主原则，但不应把“永不改变排序”当作成功校准。上述是促使内部推理关注实际算法的方向，不要求模型提交繁重证明或行为表格。Idea 不准确时不要把它继续传播成已验证知识。

**暂不归罪于单一预算公式，也不废弃 edit。** E50 有效开发候选（不含 root，包含修复）的超父数 r1/r2 为 204/787 与 186/776，前沿改进数 54 与 48，尚不能定位为纯调度失败。r2 的 edit 有效开发候选 188 个，其中 50 个超父、15 个超前沿；选择偏差使这些比例不能证明 edit 比 full 更优，但已有成功代码路径，没理由因 JSON 外壳失败把 edit 一并撤掉。

保持本批冻结至既定 E1000，不因早期训练差距单独停批；出现明确记账不一致、进程退出或长时间无进展才进入基础设施处置。后续在所有重复达到相同预算时更新一次前缀比较；完赛用既有 `experiments/infra/evaluate.py` 和原 held-out 口径评测。接口修订的最低检验是重放这些真实失败响应及现有恢复测试，不调用真实 evaluator；若进一步正式运行，单独冻结新批、保持任务/种子/预算不变，并记录模型成本。当前没有启动额外实验。

后续授权更新：用户在看到诊断后要求从简修正并重启。上述保持本批运行的建议已由该决定替代；r2 将作为 stopped/partial 保留，新机制定义见 [r3 机制设计](../01-主线版本/TraceAAD-V10.13-r3-机制设计.md)。
