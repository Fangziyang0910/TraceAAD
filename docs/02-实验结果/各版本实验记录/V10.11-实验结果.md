### 完赛状态与上下文溢出发现

VRPTW rep1 与 TSP rep2 两路曾以相同方式中断：`ValueError: complete prompt exceeds the model context budget`（`trajectory.py check_capacity`）。history_code 模式把形成历史中每步算法的**完整代码**编入提示，随搜索推进提示持续增长，两路分别于 883/1000 与 627/1000 预算处撞上上下文上限，launcher 各重试 3 次均于同一状态复现同样错误。溢出的恰是代码最长、最易膨胀的 TSP 与 VRPTW 两任务，属机制固有代价而非偶发故障。

2026-09-17 修订：生成上下文组装加入**轨迹逐级截断**——完整历史超限时按「去掉最早一步」逐级缩短重试（8→7→…→0，保留最近步骤）直到放得下，零历史仍超限才终止（已入主线代码并有单测覆盖）。修订后两路从断点续跑至完赛：VRPTW rep1 于 09-17 13:20 完赛（续跑段触发 2 次截断），TSP rep2 于 09-17 17:45 完赛（续跑段触发 22 次截断，best 由中断时的 6.0456 改善至 5.9005）。因此本批为「13 路未触发截断 + 2 路溢出后截断续跑」的混合口径，与纯原机制的批次有一处受控差异。

### idea_code 批说明

- **VRPTW 结论按三路修正**：两路时（18.9338/31.9421/52.0453）曾好于主批与全部基线，但溢出续跑完赛的 rep1 是**均匀弱的一路**（训练 best 20.398、held-out 21.52/35.14/58.76），三路均值 19.7965/33.0082/54.2849 与 generic（19.1492/32.9027/54.3395）回到同一档（50/100 略差、200 略好），rep 间方差大（±1.5~±3.9）。此前「全代码轨迹 VRPTW 大幅最优」的判断系两路样本偏乐观，现修正为：**全代码轨迹在 VRPTW 上与短轨迹相当，强 rep（18.83/31.77/52.32）依旧强，但批内一致性变差**。
- **TSP 方向相反且代价最大**：全代码轨迹三规模（6.0658/8.5882/12.3634）差于短轨迹与无轨迹，TSP200 跌破多数基线（EoH 12.3553、CALM 12.0738），且 rep 间方差四方最大（±0.82）。续跑完赛的 rep2 单路其实很强（5.9338/8.3305/11.5247），拖垮均值的是 rep1（13.17）。VRPTW 与 TSP 同为长代码任务，一个两强一弱、一个一强两弱，全代码历史的作用方向按任务强烈分化且一致性变差。
- **OP/CVRP 小幅受益、OBP 与短轨迹大致持平**：OP test_50/100（15.1838/30.5083）与 CVRP test_50/100（9.2460/15.7709）为三方最优；OBP 与 generic 互有胜负（1k_100 差 2.2 箱、5k/10k_100 略好），仍整体不如 no_traj。
- **本批 best 算子分布（15 路）**：Refine 6 / Fuse 6 / Tune 3 / Pivot 0；VRPTW 两强路 best 均为 Refine、TSP 未中断两路均为 Fuse（续跑 rep2 的 best 为 Refine）。
- **机制代价与修复**：上下文溢出曾致两路中断；轨迹逐级截断修订后两路均续跑完赛，说明「超限时牺牲最早历史保住搜索」的降级策略可行。完赛路的搜索后半程也在逼近预算上限的提示里进行。全代码轨迹是一种「高方差」上下文策略——上限与下限都被拉宽，且稳定性受上下文硬约束威胁。

### rand_ctx 批说明

- **OBP 是 rand_ctx 的最强任务**：六规模与 no_traj 同档（1k/10k_100 略差、5k_100 略好），显著好于 generic 与 idea_code；5k_500（401.867）与 10k_500（803.200）双双好于主表最佳的 V10.10R（401.933/803.400）。OBP 上「无轨迹」与「随机档案卡」都优于结构化形成路径，且唯一一次 Pivot best 也出现在此——去掉轨迹约束后搜索路线更发散。
- **TSP/VRPTW 上随机档案卡替代不了形成路径**：TSP（6.1738/8.4888/11.8459）与 VRPTW（20.4262/34.2216/57.2534）均落在 no_traj 同档或更差，全面差于 generic。结合 idea_code 批：VRPTW 需要的是**当前血统的结构性历史**（短/全代码轨迹均可），TSP 对任何加重上下文的改法（全代码、随机卡）都变差。
- **OP 是 rand_ctx 最弱任务**：三规模（14.9246/29.6195/52.2820）为四方对照最低，rep3 全线崩（训练 best 14.566、test_200 仅 47.18），方差四方最大（±4.48）。随机参考卡在 OP 上既没带来 few-shot 收益也没保住下限。
- **CVRP 是 rand_ctx 的另一强点且是家族最强**：三规模（8.9799/15.2913/27.7452）全面好于 generic/no_traj/idea_code，三路高度一致（±0.06/0.20/0.47）；test_50 的 8.9799 与 test_100 的 15.2913 好于主表全部行（含 MCTS-AHD 的 9.0986/15.4513），test_200 与 MCTS-AHD（27.7063）相当。CVRP 上「随机档案卡」明显优于任何形成路径方案。
- **程序重量出现病态样本**：rep1 的 OP best（#734，136 行）实测复杂度约 O(n³)——单实例 test_50 21.4s、test_100 150.5s、test_200 约 20 分钟，其 test_200 单 unit 评测耗时 14,986 秒（4.16 小时；其余两路 52~64 秒）。程序质量不差（test_100 实例值 32.23），但运行时代价随规模爆炸——「档案卡只带 idea 不带代码」并未约束生成程序的重量，与 idea_code 批的上下文膨胀构成同向提醒：上下文策略的两个副作用（提示超限、程序超重）都已在实验中实际出现。
