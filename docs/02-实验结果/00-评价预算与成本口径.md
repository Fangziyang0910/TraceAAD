# TraceAAD 评价预算与成本规范

**TraceAAD 以候选程序的实际评价次数计搜索预算：成功与候选自身导致的失败均计一次；未送评的解析失败不计；确认由基础设施故障导致的异常调用不扣搜索预算，但必须留存调用与故障记录。** 来源不明或缺回执时，保留预算预约并阻断，查明后结算。

本页是 M1 的权威规范，作为 TraceAAD 后续方法设计和实验比较的基础约定，2026-09-24 经逐项讨论确认。具体版本的修复次数、阻断阈值和恢复实现由对应版本定义。

实现见 [traceaad.py](../../traceaad/v10_13/traceaad.py)，验证见 [test_traceaad_v1013.py](../../tests/method/test_traceaad_v1013.py)。

## 1. 标准术语

| 术语 | 定义 |
| --- | --- |
| 实际评价调用次数 | 实际调用评测器的次数，包含候选失败、重复送评、修复重评和基础设施故障调用 |
| 搜索评价次数 | 已结算且计入搜索预算的候选评价次数，排除确认的基础设施故障调用 |
| 评价预算 | 每路允许的搜索评价次数上限，由批次 manifest 冻结 |
| 预算预约 | 送评前暂占的预算；未结算时不得视作空闲预算再次使用 |
| 有效程序数 | 经评价获得合法分数并按该方法规则接收的候选数，与评价次数分开统计 |
| 解析失败 | 模型响应无法转成可送评的程序，未调用评测器 |
| 候选评价失败 | 候选自身造成的代码错误、运行时错误、超时、非法返回或非有限分数 |
| 基础设施故障 | 已确认由评测器、执行环境或服务故障导致，无法可靠评价该候选的事件 |
| 模型成本 | 实际模型调用及输入、输出 token 消耗，包含解析失败和修复请求 |
| held-out | 冻结测试集上的泛化评测，单独记录成本，不进入搜索反馈 |

## 2. 预算结算与故障处理

| 情况 | 扣搜索预算 | 处理 |
| --- | --- | --- |
| 正常返回合法分数 | 1 次 | 记录结果 |
| 候选自身报错、超时或返回无效结果 | 1 次 | 记录失败；是否修复遵循版本机制 |
| 重复代码再次实际送评 | 每次 1 次 | 重复不免除已发生的评价成本 |
| 修复后的代码实际送评 | 每次 1 次 | 与首次评价分别计数 |
| 解析失败，未调用评测器 | 0 次 | 记录模型成本 |
| 确认的基础设施故障 | 0 次 | 阻断、修复基础设施；保留原调用、故障证据和预算调整记录 |
| 来源未明的异常或有预约无回执 | 暂不结算，保留预约 | 阻断自动恢复；查明后决定计入或解除预约 |

异常从评测器直接抛出，不足以证明是基础设施故障，也可能是候选异常未被捕获。核定应保留异常栈、执行日志、故障原因和处理记录。基础设施故障不能通过让模型修改候选来掩盖。

调用记录不可因不扣预算而删除。确认故障后若需要重评，应在基础设施恢复后，以新的唯一评价号建立记录并关联原故障调用；评价号不因释放预算而复用。

例如：解析失败后修复并成功送评，计 1 次；候选运行失败后修复并成功送评，计 2 次；一次确认的基础设施故障后重新成功送评，实际调用 2 次，搜索评价计 1 次。

## 3. 成本报告与版本适用

版本间、方法间比较须并列报告：

1. **搜索评价次数、实际评价调用次数**，以及确认的基础设施故障数、未决预约数；
2. **有效程序数**；
3. **模型调用数与输入、输出 token 消耗**，包括解析拒收和修复成本。

在每次调用均已结算且无其他排除项时，搜索评价次数 = 实际评价调用次数 − 确认的基础设施故障调用次数。未决预约单列，不当作零成本；服务端已执行但消耗记录缺失的模型调用标明缺失。

比较算法质量时对齐搜索评价预算，同时保留实际成本；相同评价次数不代表相同 token 或墙钟时间。解析率、修复率和有效程序数用于解释搜索行为，不替代重复实验与 held-out 质量证据。

历史口径依据见 [V10.9](../01-主线版本/生成协议与上下文演进.md)、[V10.10](../01-主线版本/TraceAAD-V10.10-机制设计.md)；原有成本报告示例见 [r2 诊断](../01-主线版本/V10.13设计演进.md)。新实现中 `search_evaluations` 是已结算搜索评价次数，`budget_reserved` 是未决预约，`budget_used` 是两者之和，用于限制继续送评。`evaluation_attempts` 是单调增加的预约总数，也用于分配唯一评价号；`evaluation_calls_with_receipts` 是已取得回执的实际调用数。缺回执时，预约不能证明调用已经发生，因此不把预约总数直接当作确定的实际调用次数。`infrastructure_failures` 单列已确认的故障调用。

本规范对应预算策略 `candidate_evaluations_exclude_confirmed_infrastructure_v1` 和持久化协议 `staged_candidate_receipt_v3`。旧批次按其 manifest 中的原口径解释，并使用对应版本恢复；跨口径比较依据原始回执核对差异。

### 故障识别与人工核定入口

- `prepare_error` 来自 `SecureEvaluator` 的准备或执行环境管理层，按基础设施故障结算；评测适配器显式返回的 `infrastructure_error` 同样处理。
- 候选的 `exec_error`、`runtime_error`、`timeout`、`invalid_result`、`nonfinite_fitness` 均扣一次预算。
- 直接抛出的未分类异常记为 `evaluation_error`，保留预约并阻断；不能仅凭异常类型自动免责。

诊断确认某次失败实际源于基础设施后，可在同配置的 V10.13 实例上调用：

```python
method.confirm_infrastructure_failure(
    evaluation_id,
    evidence="已核实的故障原因及诊断日志路径",
)
```

该入口只处理最新已提交的失败候选，要求已有评价回执和非空诊断证据。结论追加到 `evaluation_resolutions.jsonl`，保留原始回执、事件和调用；同一结论可幂等重放，预算由持久化证据重新计算。成功评价不能通过此入口免责。核定只结算预算，仍保持阻断，不自动修复环境、重评或继续搜索。缺回执时须先核对并恢复证据，不通过此入口猜测结果。


## 4. 基线方法口径对照

各基线（本地实现）的预算单位不同，"每路 1000 次"含义互不相同；跨方法比较必须按第 3 节报告成本后再对齐：

| 方法 | 预算单位 | 解析失败 | 评价执行但结果无效 | 代码依据 |
| --- | --- | --- | --- | --- |
| EoH | 拿到合法分数的样本 | 不计 | 不计 | [eoh.py:275-288](../../baselines/eoh/eoh.py#L275-L288)，无效分数在计数前返回 |
| ReEvo | 候选尝试（模型请求异常另行处理） | 计 | 计 | [reevo.py:217-227](../../baselines/reevo/reevo.py#L217-L227) |
| ShinkaEvolve | 执行了的评价 | 不计（补丁失败免费） | 计 | [shinka_evo.py:395-399](../../baselines/shinka_evo/shinka_evo.py#L395-L399) |
| MCTS-AHD | 评价过的函数 | 不计 | 计（文档明言不论有效与否） | [mcts_ahd.py:77](../../baselines/mcts_ahd/mcts_ahd.py#L77) |
| TraceAAD | 真实调用 evaluator 的评价 | 不计 | 计 | [traceaad.py:296-297](../../traceaad/v10_13/traceaad.py#L296-L297) |

在候选送评并返回结果的路径上，TraceAAD 与 ShinkaEvolve、MCTS-AHD 的口径相近。ShinkaEvolve 在评测调用直接抛异常时不增加计数（[实现](../../baselines/shinka_evo/shinka_evo.py#L381-L395)），不能把异常路径也称为完全一致。以上是本地实现事实，本次未核查各方法官方版本；本规范是 TraceAAD 的项目约定，不据此声称全领域已有统一标准。
