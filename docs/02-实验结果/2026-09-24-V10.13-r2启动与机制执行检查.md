## 从上下文到代码的实际案例

### 参考读取和 edit 确实串联

`20260924_v1013r2_vrptw_v1013_rep1`，candidate 10，Fuse，host node 6，reference node 2，生成 node 8：

1. 首轮模型返回 `{"mode":"context","reference_id":2}`。
2. 第二轮提示实际包含 node 2 的完整实现，模型返回 edit，并声明 donor_id=2。
3. 补丁将 host 的 min-max 归一化多目标评分改为原尺度加性评分；donor 的距离、紧迫度和需求利用率组合进入返回节点选择所依赖的 score，代码重建与节点一致。
4. 训练 fitness 从 host 的 −31.7624 提高到 −27.1356，略高于 donor 的 −27.2144，但未超过当时该路前沿。

这支持“读取—代码迁移—评价”链路已经执行，不能归因为参考读取必然有效。补丁也改变了其他表达式，不能把整体改善全算到单一迁移组件上。

### Edit 可以形成数值调整，也可能附带其他改动

`20260924_v1013r2_obp_v1013_rep4`，candidate 10，Tune，将 remainder penalty 系数从 0.1 改为 0.35；同时改了零尺寸输入分支。有效训练 fitness 为 −744.25，parent 为 −744.5。不能称为严格单参数效果；它证明精确文本编辑成功落地，不能证明 Tune 标签保证纯参数修改。

### 局部试验读取不保证提升

同一 OBP 路 candidate 22，Tune，parent node 9。一次读取返回其子代 node 13 的 Idea 和整体 fitness −744.25 → −744.5。模型随后用 edit 改变归一化与余数权重，成功评价却退步到 −763.25。提示确实读到了该父代的新试验，但“读到”不是“正确利用”的充分证据。

### 有效候选确实得到继续开发

00:30:43 抽查 `20260924_v1013r2_tsp_v1013_rep1`：candidate 14 改善后，其节点被 candidate 18 再次 Refine，fitness 从 −7.17897 到 −7.15422。OP rep1 的 candidate 17 → 18 也发生了继续开发和再次提升。只说明调度未把所有成果留在 archive 中闲置，不能据此估计继续开发的平均收益。

## 发现的代价与尚未回答的问题

1. **JSON 接口仍有明显生成成本。** 85/423（约 20.1%）事件未通过输出解析，包括 JSON 转义、缺失代码围栏结束、混合 Python/JSON、多段代码、真正的 Python 语法错误，以及一次抄错 parent hash。不能全部归因于 JSON；但当前提示式结构化输出并不保证格式正确。已有修复多数成功，仍消耗额外调用。
2. **空局部读取较多。** 54 次读取中有 36 次未得到可用子代试验，早期父代缺少子代是直接原因。这是可量化的无新增材料调用，不应把读取率本身当成机制成功。未来若改，应优先研究是否在首轮明确材料是否存在，或根本不提供空读取入口；本批次保持冻结。
3. **轻量 Idea 仍可能错误解释代码。** 摘要存在不等于语义正确；纯代码节点被接受是预期行为，但这些节点用于思想卡时材料较少。没有额外摘要模型为其补写，也没有将作者自述当作验证过的组件机制。
4. **代码变化不等于行为或质量变化。** 部分 OBP 候选改变了公式却保持相同 fitness。按需试验也出现退步。单路前沿改善与超过双亲只用于执行诊断，不能提前排名或推断泛化。

这批结果应继续运行，不因早期峰值或格式统计中途调整规则。下一步在相同 E1000 与既有 held-out 下判断整体收益，同时报告模型成本；若协议损耗持续较高，下一冻结修订优先处理有证据的格式负担和空读取，而不是增加更多提示规则。
