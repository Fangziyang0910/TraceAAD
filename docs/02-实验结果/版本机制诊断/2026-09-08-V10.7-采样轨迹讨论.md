# TraceAAD V10.7 机制设计

当前实现以第 4 节的采样设计为新版方案，默认 `sampled_trajectory_v1`，另保留 `ancestor_history` 与 `uniform_trajectory_v1` 用于三组比较。第 1–3 节记录原始单次调用基线，其中“保持不变”仅适用于该基线模式。

实现细化：每种完全相同的归档代码随机选择一条完整真实记录；以可容纳候选的线性插值 1/3、2/3 分位数分层，等于边界归较低层，同分不拆层。单参考容量预筛后，每个参考位置最多无放回尝试 32 次。最多三份程序包含底座；Init 仍从头生成。新模式完整展示原始 Code 与 Idea，以实际 Prompt 精确计数，不使用祖先历史的 8192-token 分区。配置、日志与验证入口见运行说明。

**V10.7 仅取消 V10.6 的第二次独立校准调用，生成流程为单次「简短 Idea → 完整 Code」。其余机制沿用 V10.6 完整机制设计。**

## 1. 调整依据

V10.6 配对核查的 30 组样本中，12 组存在局部纠错，但尚未统计出明确的整体净改善。第二次调用仍会漏判行为等价、无效改动、偏好方向和算法退化，也会新增错误的父代变化描述。

第二次调用不修改当前代码，其收益只能通过更准确的历史描述间接影响后续生成。目前尚无证据证明这条收益链能以合理成本改善搜索，而额外调用已增加成本与等待时间。因此，面向有限预算下达到 SOTA 的目标，取消这层尚未证明净价值的复杂度。该决定取代核查文档中当时“保留两阶段流程”的工作建议，不代表证明独立校准完全无效。

## 2. 唯一机制变更

Init、Refine、Pivot、Fuse 统一在一次生成调用中输出：

1. **Idea**：简短说明算法思路和预期产生的决策变化，指导代码生成。
2. **完整 Code**：输出完整实现，作为正式评价对象。

第一次调用的 Idea 直接写入节点 `idea` 字段，后续历史以 `Idea` 展示。取消第二阶段及其专用 Prompt、响应、重试、恢复、状态和耗时字段；生成、检查与正式评价流程继续沿用原规则。

Idea 仍是生成前提出的设计说明，不能视为经过最终代码校准的实现事实；历史同时保留完整代码作为当前个体的主要依据。

## 3. 保持不变

搜索树与入档规则、8 个有效根初始化、正式评价预算、父代分配、算子比例与指令、Fuse donor 选择及回退、公共任务描述与模板、评价器和实验配置均沿用 V10.6。

历史仍使用最近最多 8 条形成边，历史区上限 8192 tokens。上下文窗口、输出额度、裁剪顺序与代码完整性要求不变。

实现入口见运行说明。本轮未启动实验；后续用实际调用成本与完整搜索结果检验该调整，不以局部纠错作为保留额外调用的充分依据。

## 4. 全档案采样算法轨迹：完整设计建议

以下完整保留方案原文，作为采样模式的设计依据；上文记录单次调用基线。原文中的提交号、代码状态与“建议”等措辞属于提出方案时的记录，当前实现状态以本页开头和运行说明为准。

**我建议以 V10.7 为底座，把“取最近八代祖先”替换为“从整个已评价档案中采样少量程序，组成算法轨迹”。采样范围覆盖不同分数，不要求登顶、不要求血缘，也不为新节点额外保留评价预算。**

这里最重要的变化不是换一个“轨迹”的名字，而是：**下一次生成所依据的材料，从一条固定的形成路径，变成一次主动组织的算法对照。** 每份材料仍然只有已有的 Idea、Code，以及真实评价分数，不增加第二次模型调用，不增加行为探针。

我读取的是 `exp` 分支提交 **`9c85876e`**。当前 V10.7 已经取消第二次调用，但祖先历史、选父规则、算子比例和 donor 规则尚未改变；仓库也把新的上下文采样方案单独列为构想，没有将其混作已实现内容。下面是基于这个版本的具体修改建议，而不是已经实施的功能。

## 一、先明确这次机制的出发点

你举的例子成立。假设越小越好，已有程序的分数依次为：

> 10、9、8、6、7。

**7 没有刷新纪录，不等于它没有参考价值。** 它可能包含另一种结构、不同组合方式，或者一个尚未充分实现的想法。甚至分数 9 的程序中，也可能有适合迁移到分数 6 程序中的局部机制。

但需要区分两个判断：

**“它有资格作为材料”可以直接由采样规则保证；“它的某个部分确实有用”不能仅凭分数断言。**

因此，这次不需要先识别哪些较差程序“真正有潜力”。我们要做的是让不同质量层的有效程序有机会进入上下文，再由生成模型比较、取舍，最后评价新代码。

对于你强调的“大跳变”，也采用同样的态度：**不能因为跳变后退步就排除，也不因为跳变很大就自动加分。** 大幅分数变化和大幅代码变化都不等于发现了新算法方向。首发机制不增加一个“跳变价值评分”，而是通过较广的材料来源，让这类候选不被“只看 best”的筛选消掉。

所以，这次的核心不是：

> 找出谁最有希望，然后连续投资。

而是：

> **保留较好的设计底座，同时让不同质量的已有实现参与下一次设计。**

## 二、V10.7 当前具体限制在哪里？

我核对了 `prompts.py` 和 `_schedule()`，有三个直接相关的事实。

首先，当前 `build()` 仍然调用 `formation_events(current, ancestors, ...)`，材料来源被限定在当前节点的真实祖先链。其次，历史区展示的是每条边的 Idea 和分数，**并不展示祖先程序的代码**；完整代码主要来自当前程序和 Fuse donor。最后，非根节点的 Idea 通常依赖历史区展示，不能简单删掉历史区而不补回当前程序的 Idea。

这意味着新方案必须同时改变两件事：

**材料从哪里来：** 从祖先链改为全档案采样。

**材料是什么：** 从多条“Idea＋父子分数”改为少量“完整 Idea＋Code＋该程序分数”。

因此，这不是只修改 `history_ids`，也不是把 `Development History` 改成 `Algorithm Trajectory` 就完成了。需要新增采样器，并重写上下文构造。

## 三、建议的完整机制：一个底座，加少量跨质量材料

我建议先保留 V10.7 的选父与算子概率，把主要改动集中在材料采样和使用方式上。这样既能落地，也能判断收益来自哪里。

### 1. 不变的部分

保留单次 `Idea → Code`、八个有效根初始化、原 evaluator、真实评价预算、完整档案与当前最佳程序输出。每次只生成一个候选、评价一次，然后重新决策；有效的退步、持平和重复程序继续按现行规则留档。V10.7 当前就是这一单次生成协议。

父代仍按现有质量与次数基座选择，请求算子比例先保持 **Refine / Pivot / Fuse = 50% / 15% / 35%**。不同时引入节点保活、成功率调度或停滞触发规则。

这里保留“父代”只是为了明确 Refine 的修改底座，以及兼容当前实现。**它不再决定其它上下文材料必须来自哪里。**

### 2. 每次最多三个程序，而不是“八代历史再加参考”

推荐首发配置是：

> **一份选中的程序＋至多两份采样程序，总计最多三份完整 Idea＋Code。**

三份是一个待验证的工程起点，不是理论最优值。上下文放不下时减少为两份，不能为了凑数量截断代码；材料不足时也不重复填充。

重要的是，**新算法轨迹直接替代旧历史区，不与八代祖先叠加。** 当前程序只展示一次，它的 Idea 也直接随代码展示，不再通过历史区间接获得。

### 3. 从全档案抽取参考，取消登顶和血缘条件

参考候选池包含当前时刻之前已经完成评价、fitness 有效，并且能够装入本次上下文的程序。

不要求它：

- 曾经刷新全局 best；
- 改善过父代；
- 来自 Pivot 或 Fuse；
- 属于另一条分支。

祖先、后代、兄弟节点都可以成为参考。**来源关系既不决定资格，也不进入提示。**

同一个上下文内，排除完全相同的代码重复出现，避免三个位置放了同一份实现。但不能因为两个程序分数相同，就把它们当成重复；同分数的不同代码必须保留选择机会。

首版只用现有归档代码的精确身份做上下文去重，不引入语义聚类或复杂相似性模型。

### 4. 用质量分层采样，而不是只偏向高分或完全均匀抽样

这是此次采样器最核心的一条规则。

把可用参考程序按当前任务的 fitness 排序，形成**较低、中间、较高三个质量层**。层的作用只是控制采样覆盖，不表示算法簇。

抽取第一份参考时，先从非空质量层中随机选一层，再从这一层中随机选程序。抽第二份参考时，优先从尚未选过的其它质量层中抽；不足时再从剩余候选中补充。

这里有两个必要细节。

**第一，同分数不应因节点 ID 顺序被人为解释成不同质量。** 分层使用真实分数的分位边界；如果大量并列导致某一层为空，就使用实际非空层，不强行凑三层。

**第二，分层应在上下文内去重后的候选上进行，避免大量重复代码挤占材料概率。** 同代码有多条记录时，本次只抽一条真实记录，不拼接不同记录的 Idea 与 fitness。

为什么用这个规则？

完全质量偏置可能继续反复拿到相近的高质量材料；完全均匀抽样则容易被数量最多的质量区域支配。**先抽质量层，再抽程序，是一种简单的覆盖安排：每个质量区域都有机会提供材料，但不声称每份材料同样有用。**

这也保证了你所说的 7 分程序能够被选中，而不是因为从未登顶就永久不可见。

### 5. 不必强制每次都包含一个很差的程序

三个质量层不是三个必填槽位。

选中的底座已经占一个位置，其余两份参考从质量层中抽取；可以抽到较高＋中间，也可以抽到中间＋较低。**不为了多样性而强制每次塞入最差程序，也不要求采样覆盖整个分数范围。**

例如，在已有 `10、9、8、6、7` 的情况下，一次可能使用：

> 8、7、6。

另一次可能使用：

> 10、7、6。

也可能主父代本身就是 7，再参考 8 和 6。7 在这里既可能作为普通竞争选出的底座，也可能作为设计材料。

这就是“各类分数都有一定价值”应当落到机制里的方式：**保留被采样和被利用的机会，而不是赋予固定的价值奖励。**

## 四、怎样把样本组织成“算法轨迹”？

### 推荐：按质量从弱到强排列，但不伪造修改过程

采样完成后，统一按照当前任务的评价方向，从较弱到较强排序。

对于越小越好的原始目标，`8、7、6` 按这个顺序展示。仓库内部已经采用 higher-is-better fitness，实际实现应继续用内部方向化分数排序，不能另写一套按任务名称判断最大化或最小化的逻辑。

每个位置只包含：

```text
Algorithm 1
Fitness: ...
Idea: ...
Code: ...

Algorithm 2
Fitness: ...
Idea: ...
Code: ...
```

**不显示分支、祖先、创建算子、节点 ID，也不解释这些程序来自哪里。**

同时删除旧提示中的：

- `Previous version fitness`；
- `Resulting version fitness`；
- “这些历史描述当前算法是如何被构造出来的”。

因为新上下文不再承担还原实际形成过程的职责。当前这些措辞确实还存在于 V10.7 的历史渲染逻辑中。

这里不需要额外给模型一段“它们不是父子”的说明。只要将它们呈现为供参考的算法序列，而不是写成虚构的改动事件，就够了。

**排序也不意味着下一次生成必须继续单调提高。** 我们是在给模型组织质量对照，不是在承诺这是一条确定可行的改进路线。

按分数组织采样程序有现成先例：FunSearch 就从程序库抽取多个程序，再按分数排列构造提示；其方法不要求这些程序构成真实父子链。这个先例支持采用简单方案，但不能预先保证它对 TraceAAD 的增益。

### 不要求轨迹最后一个程序一定是本次父代

这是一个容易写错的细节。

如果本次按原规则选中 7 分程序作为 Refine 底座，而参考中存在 6 分程序，排序之后最后一份会是 6。

**不能因此偷偷把 Refine 底座改成 6。** 否则我们同时改变了父代选择机制，也抹掉了让 7 继续竞争的机会。

正确做法是保留统一排序，再在设计指令中明确：

> 本次以 Algorithm 2 为基础继续设计。

这只是角色标记，不是血缘说明。相同材料可以因目标程序不同而形成不同的设计任务。

## 五、三类算子怎样使用这条轨迹？

我不建议给三类算子凭空增加“机制优势”“失败原因”等字段。**它们看到的原始材料都是 Idea、Code 和分数；区别在于本次任务是否绑定修改底座，以及如何利用其它材料。**

首发可以共用质量分层采样器，不必为了形式上显得不同，先设计三套复杂采样概率。

| 算子 | 材料组织 | 模型需要完成的任务 |
|---|---|---|
| Refine | 指定一个底座，另外至多两份程序作比较材料 | 沿底座的主要思路继续改进，可借鉴其它实现 |
| Pivot | 所有程序均作为已知尝试，不提供祖先链 | 借助已有材料提出替代性的主要决策思路 |
| Fuse | 指定主程序和一份融合参考，其余程序为辅助对照 | 选择并适配有用部分，形成一个连贯实现 |

### Refine：保留精炼任务，但不再只允许从祖先学习

建议指令含义为：

> 以指定算法为基础，继续发展它的主要思路。比较参考程序中的计算和实现方式，选择有助于改进该算法的部分，形成一个连贯的新版本。

不要求保持所有结构，不要求参考程序全部被使用，也不要求输出必须高于所有参考。精炼方向由指定底座约束，不靠祖先链约束。

这时，分数较差的参考也有用途：模型可以看到不同的计算、参数或组合方式，并自行决定是否吸收。我们不替模型声明其中哪一部分是正确答案。

### Pivot：解除“继续这份程序”的默认绑定

建议指令含义为：

> 参考这些算法及其评价结果，为同一任务设计一种替代性的主要决策方法。选择可利用的部分，形成完整、可执行的新算法。

Pivot 不再展示“当前算法八代以来怎样发展”的叙述，也不要求逐行改写某个指定程序。采样所得的原父代仍可作为材料之一，但没有必须继承它的提示约束。

这样，探索条件发生了实质变化：**由一份程序和其发展史，变成少量不同质量实现的比较材料。**

它仍不保证生成真正不同的算法簇，但不需要另设新颖性判官才能运行。

### Fuse：参考程序不再限定于 top-5 和跨血缘候选

我建议让 Fuse 的 donor 从本次已经采样的参考程序中确定，而不是继续运行旧的 top-5、排除祖先后代规则。

首发可以采用一个简单安排：

**在采样参考中，选当前质量较好的一份作为主要 donor；其它样本仍留作辅助材料。**

注意，这是“从已经广泛采样的材料中确定主参考”，不是“从整个档案永远只取最高分”。低分和中分样本仍可能被采入，并被模型利用。

指令含义为：

> 以指定程序和主要参考为材料，选择兼容的计算方法或实现部分，形成一个连贯算法。根据最终设计需要保留、替换或重组各部分。

不要求双亲必须各自贡献多少，不要求超双亲才入档。没有第二份可用、不同代码的参考时，继续沿用 Fuse 回退为 Refine 的逻辑。

**这里删除血缘过滤是必要修改。** 否则我们虽然扩大了“轨迹”来源，Fuse 仍然会因祖先、后代关系排除本来有价值的材料，和新认识不一致。

## 六、预算分配这轮怎么处理？

**这轮改变的是“生成基于哪些材料”，不是额外购买哪些连续开发机会。**

具体而言：

父代的质量与次数竞争先保留；Refine 子代不因新出生获得优待。Pivot、Fuse 子代也不自动保活。所有有效候选都进入档案，之后既可能被选为修改底座，也可能被选作参考。

这提供了一条此前被低估的通道：

> **某个程序暂时没有竞争到后续修改预算，也可以通过进入其它生成的上下文参与搜索。**

但不能把它称为免费收益。参考材料会增加输入 token、注意力负担和推理耗时，这些必须计入比较。

另一个关键点是**计数职责不混淆**。某节点只是作为参考出现，不增加它“被作为父代修改”的次数。可以另记参考曝光次数用于分析，但首版不把曝光次数再塞进采样权重，避免一次引入过多控制变量。

算子比例本轮先保持原值，也不因为短期几次未突破立即改变。理由不是固定比例最优，而是当前正要改变算子的输入条件；应先看这组条件下的完整搜索表现，再考虑调度。

| `traceaad_v10_7/sampling.py`，新增 | 全档案候选过滤、上下文内代码去重、质量分层、随机抽样、质量排序 |
| `traceaad_v10_7/prompts.py` | 新增程序序列渲染；每个样本展示 Idea＋完整 Code＋fitness；不再依赖 `formation_events()` |
| `traceaad_v10_7/traceaad.py::_schedule()` | 选父和算子后调用采样器；Fuse donor 从已选材料确定；记录完整上下文样本 |
| `experiments/traceaad_v10_7/run.py` | 增加明确的上下文采样模式与最大程序数；祖先参数只用于旧模式 |
| 测试和方法文档 | 固定抽样、排序、上下文容量、回退、恢复及证据口径 |

当前 `_schedule()` 是选父、选算子、选 donor，再提取 ancestors 并调用 builder；因此切入点很明确，不需要重写 `_advance()` 的生成、评价与入档主循环。

当前 runner 的 `--traj-gens=8` 和 `--history-tokens=8192` 面向祖先历史。新模式下不能悄悄把它们解释成“三个全代码程序”的限制；应新增清楚的配置，如 `--context-policy` 和 `--max-context-programs=3`。

### 上下文容量：以完整程序为单位取舍

沿用当前总上下文和输出预留：32768 总窗口、16384 输出预留、256 余量，即输入最多 16128 tokens。新方案不再另外叠加 8192-token 祖先历史区。

构造时先保证任务、必要指令和指定底座能够完整放入，再尝试加入参考。候选不适合剩余空间时，在相应采样层中尝试其它候选；尝试次数设上限，不能为了凑三份程序无限重抽。

最终放不下就少放一份。**不截断代码，不调用模型再摘要，不将过长程序直接从完整档案删除。** 同时记录实际程序数，不能在结果里把“名义三份、实际经常一份”当成同样的机制。

Idea 继续用单次生成中的短说明。完整代码始终是实现依据，不把 Idea 当成经过独立校准的事实；这与当前 V10.7 文档的定位一致。

### 日志：保留来源，但不把来源喂给模型

新增或明确记录：

`context_node_ids`、展示顺序、指定底座、主要 donor、采样质量层、每个程序及整个提示的 token 数、裁剪或回退原因、采样协议标识。

这些是复现信息，不是提示内容。原来的 `parent_id` 可以为兼容继续保存，但不能再把它当作新程序全部信息来源；完整的上下文依赖由 `context_node_ids` 表达。

尤其不要复用 `history_ids` 却继续在分析脚本中把它理解为祖先。当前这个字段正是由形成事件提取出来的，需要明确区分新旧含义。

采样结果和随机数状态要在请求前一起持久化。中断恢复时复用已选材料和原 prompt，不能因为重启就重新采样另一条轨迹。

### 复杂度

这套方案不运行额外算法探针，也不比较求解轨迹。主要开销来自排序、抽样、代码身份检查和 token 计数。

可以缓存节点代码哈希与文本视图；质量排序随档案更新，不必反复计算全量两两距离。整体不需要 BehaveSim 那种随算法对数增长的距离矩阵。

但三份完整代码可能比原先的一份代码加短 Idea 更长，因此**低观测复杂度不等于零推理成本**。需要实际报告输入 token 和耗时，不能只报告 evaluator 次数不变。

## 八、怎样验证这一版，才能直接服务于搜索性能？

我建议主比较围绕**原始 V10.7 与新采样版的完整搜索**开展，不再设置 Refine 潜力预测或单步超父门槛。

不过，至少需要一个简单的控制版本：

| 版本 | 用途 |
|---|---|
| 原始 V10.7 | 当前单次调用＋祖先历史基线 |
| 全档案随机材料 | 相同数量、格式、排序与算子提示，但参考直接均匀抽样 |
| 全档案质量分层材料 | 本文建议的采样规则 |

后两个版本之间只改变“如何抽参考”，这样可以区分：

**收益来自展示多份完整程序，还是质量分层采样确实带来了额外作用。**

若只比较原版与新方案，仍然可以评价整体改进，但不能把所有收益都归因于采样分层，因为材料数量、代码展示和提示组织也一起变化了。

在正式运行前，测试至少应覆盖几个关键情形：

**7 分但从未登顶的程序能被抽到；同分不同代码能同时成为候选；祖先后代没有被错误过滤；相同代码不在同一提示重复占位；所有分数并列时仍能正常采样；上下文不足时完整退化；恢复后不重新抽样。**

现有 V10.7 测试已经覆盖单次调用、Idea 入档以及保留旧历史形状。这些测试需要保留旧模式断言，同时为新采样模式增加独立测试，不能把原断言直接改掉而失去基线检查。

最终仍然看固定评价预算下的训练 best、独立重复、冻结后的 held-out，以及总调用与 token 成本。采样覆盖了多少质量层、参考是否多样，只是机制运行检查，不是成功标准。

如果有收益，再研究二份和三份程序、排序和不排序、不同算子的材料数。**不在第一轮同时加入跳变加分、动态算子调度、保活与相似度模型。**

## 最终建议

我会把这次改造收束为下面这条流程：

> **按现有规则确定本次设计任务 → 从全档案不同质量层抽取少量已有程序 → 组成有序的 Idea＋Code 算法轨迹 → 按 Refine、Pivot 或 Fuse 的要求生成一份新算法 → 评价并完整留存 → 重新采样。**

这里，分数 6、7、8 乃至更弱的程序都有参与设计的机会；它们不需要先被判断为潜力节点，也不需要拥有真实父子关系。模型只看到值得比较的程序材料，不看到冗余的来源叙述。

**这次最值得验证的主张是：合理组织不同质量的已有实现，比机械复述当前程序的八代历史，更有助于有限预算下持续产生强算法。**

它仍然属于你的轨迹引导搜索，只是“轨迹”从被动截取一段历史，变成了**为下一次算法设计主动采样的一条程序序列**。
